Part A — Database Foundations

1 What Is a Database and a DBMS?

Picture: A school office. Loose papers in drawers (plain files) get lost, copied wrongly, and two clerks can scribble on the same page. A well-run register with rules, an index, a lock on the cupboard and a backup copy is a database; the office staff who manage it are the DBMS.
Problem with plain filesHow a DBMS solves it
Same data copied in many files (redundancy) and copies disagree (inconsistency)One shared, normalised store with constraints
Hard to ask new questionsA query language (SQL)
Two people editing at once corrupt dataConcurrency control (locks, MVCC)
A crash halfway through leaves a messTransactions and recovery (all or nothing)
Anyone can read everythingUsers, roles and permissions
Slow searching in big filesIndexes and a query optimizer
Program breaks when the file layout changesData independence (programs see a logical schema)

Good to know

  • Database = the organised data. DBMS = the software that stores, queries and protects it (PostgreSQL, MySQL, SQLite, Oracle, SQL Server, MongoDB...).
  • Related guides: System Design (scaling databases), Operating Systems (files, fsync, locks), Python, Java (JDBC, JPA), RAG (vector databases).
Honest note: every SQL example on this page was really run in SQLite 3.50.4 through Python 3.14 (18 Nov 2026), and the internals (B+ tree, join algorithms, serializability test, 2PL, MVCC, recovery) are Python implementations that ran. PostgreSQL, MongoDB, Redis and ORM code are templates (no such servers on this machine). SQL dialects differ slightly between systems.

7 Relational Algebra

Picture: A small set of Lego moves for tables: pick rows (select), pick columns (project), glue tables (join), combine (union), subtract (difference). Every SQL query is built from these moves.
Relational algebra operators on Python sets (run for real)
# Relational algebra with Python sets: each operator returns a new relation (a set of tuples).
Student = {(101, "Asha", "CSE"), (102, "Ravi", "CSE"), (103, "Meena", "ECE"), (104, "John", "ECE")}
Enroll = {(101, "DBMS"), (101, "OS"), (102, "DBMS"), (103, "OS"), (104, "CN")}
select = lambda R, p: {t for t in R if p(t)}                               # sigma
project = lambda R, idx: {tuple(t[i] for i in idx) for t in R}           # pi (removes duplicates!)
join = lambda R, S, i, j: {r + s for r in R for s in S if r[i] == s[j]}   # theta/natural join on one column
print("sigma dept='CSE' (Student)          :", sorted(select(Student, lambda t: t[2] == "CSE")))
print("pi dept (Student)                   :", sorted(project(Student, [2])), "<- 2 rows, not 4")
SE = join(Student, Enroll, 0, 0)
print("Student join Enroll (on roll)       :", len(SE), "rows")
dbms = project(select(SE, lambda t: t[4] == "DBMS"), [1]); os_ = project(select(SE, lambda t: t[4] == "OS"), [1])
print("names taking DBMS                   :", sorted(dbms))
print("DBMS UNION OS                       :", sorted(dbms | os_))
print("DBMS INTERSECT OS                   :", sorted(dbms & os_))
print("DBMS MINUS OS                       :", sorted(dbms - os_))
courses = project(select(Enroll, lambda t: t[1] in ("DBMS", "OS")), [1])
div = {r for (r,) in project(Enroll, [0]) if all((r, c) in Enroll for (c,) in courses)}
print("DIVISION: rolls enrolled in ALL of {DBMS, OS}:", div)
print("SQL equivalent of the first line: SELECT * FROM student WHERE dept = 'CSE'")

# ----- Output (real run) -----
# sigma dept='CSE' (Student)          : [(101, 'Asha', 'CSE'), (102, 'Ravi', 'CSE')]
# pi dept (Student)                   : [('CSE',), ('ECE',)] <- 2 rows, not 4
# Student join Enroll (on roll)       : 5 rows
# names taking DBMS                   : [('Asha',), ('Ravi',)]

# DBMS INTERSECT OS                   : [('Asha',)]

  • Relational calculus (tuple and domain) says what you want declaratively; algebra says how step by step. SQL is based on both; the optimizer turns SQL into an algebra plan.

# Functional dependencies: attribute closure, candidate keys, and a BCNF check/decomposition.
from itertools import combinations
def closure(attrs, fds):
    res = set(attrs); changed = True
    while changed:
        changed = False
        for lhs, rhs in fds:
            if set(lhs) <= res and not set(rhs) <= res: res |= set(rhs); changed = True
    return res
def keys(R, fds):
    found = []
    for k in range(1, len(R) + 1):
        for c in combinations(sorted(R), k):
            if closure(c, fds) == set(R) and not any(set(f) <= set(c) for f in found): found.append(c)
    return found

    return decompose(X, fds) + decompose(R - (X - set(l)), fds)

Building a small B+ tree (max 3 keys per node) and searching it (run for real)
# A B+ tree (max 3 keys per node): inserts cause splits; leaves are linked for fast range scans.
class Node:
    def __init__(s, leaf): s.leaf, s.keys, s.kids, s.next = leaf, [], [], None
ORDER = 3
root = Node(True)
def insert(key):
    global root
    split = _ins(root, key)
    if split:
        k, right = split; r = Node(False); r.keys = [k]; r.kids = [root, right]; root = r
def _ins(n, key):
    if n.leaf:
        n.keys.append(key); n.keys.sort()
        if len(n.keys) <= ORDER: return None
        mid = len(n.keys) // 2; right = Node(True); right.keys = n.keys[mid:]; n.keys = n.keys[:mid]
        right.next, n.next = n.next, right; return right.keys[0], right            # copy the first right key UP
    i = sum(key >= k for k in n.keys); split = _ins(n.kids[i], key)
    if not split: return None
    k, child = split; n.keys.insert(i, k); n.kids.insert(i + 1, child)
    if len(n.keys) <= ORDER: return None
    mid = len(n.keys) // 2; right = Node(False)
    up = n.keys[mid]; right.keys = n.keys[mid + 1:]; right.kids = n.kids[mid + 1:]; n.keys = n.keys[:mid]; n.kids = n.kids[:mid + 1]
    return up, right                                                               # internal split MOVES the middle key up
def levels():
    out, cur = [], [root]
    while cur:
        out.append("  ".join(str(n.keys) for n in cur)); cur = [k for n in cur for k in n.kids]
    return out
for k in [10, 20, 5, 6, 12, 30, 7, 17, 3, 25, 27, 1]:
    insert(k)
print("after inserting 10 20 5 6 12 30 7 17 3 25 27 1:")
for i, l in enumerate(levels()): print("  level %d: %s" % (i, l))
def search(key):
    n, path = root, []
    while not n.leaf: path.append(n.keys); n = n.kids[sum(key >= k for k in n.keys)]
    return key in n.keys, path + [n.keys]

n = root
while not n.leaf: n = n.kids[0]
rng = []

    rng += [k for k in n.keys if 6 <= k <= 25]; n = n.next

print("height stays tiny: with ~200 keys per node, 3 levels hold %s keys" % format(200 ** 3, ","))

Good to know

  • All data pointers live in the leaves; internal nodes only guide the search. Leaves are linked for range scans.
  • Insert: put the key in its leaf; if the leaf overflows, split it and push a separator key up (splits can reach the root, which is how the tree grows taller). Delete: borrow from or merge with a sibling.
  • B-tree vs B+ tree: B-trees also keep data in internal nodes; B+ trees are preferred for databases because internal nodes hold more keys and range scans are easy.
  • LSM trees (RocksDB, Cassandra) are the main alternative for write-heavy workloads: buffer writes in memory, flush sorted files, compact in the background.

def nested_loop(R, S, limit=2000):                      # only the first 2,000 R rows: the full join would take too long
    return [(r, s) for r in R[:limit] for s in S if r[0] == s[0]]
def hash_join(R, S):
    h = {}
    for s in S: h.setdefault(s[0], []).append(s)       # build on one side
    return [(r, s) for r in R for s in h.get(r[0], [])] # probe with the other
def sort_merge(R, S):
    R, S = sorted(R), sorted(S); i = j = 0; out = []
    while i < len(R) and j < len(S):
        if R[i][0] < S[j][0]: i += 1
        elif R[i][0] > S[j][0]: j += 1
        else:
            k = R[i][0]; i2 = i; j2 = j
            while i2 < len(R) and R[i2][0] == k: i2 += 1
            while j2 < len(S) and S[j2][0] == k: j2 += 1
            out += [(r, s) for r in R[i:i2] for s in S[j:j2]]; i, j = i2, j2
    return out

29 Schedules and Serializability

Picture: Two cooks sharing a kitchen. If the final dishes are the same as when one cook finished completely before the other started, their interleaving was safe ('serializable').
Precedence-graph test for conflict serializability (run for real)
# Is a schedule conflict-serializable? Build the precedence graph and look for a cycle.
def precedence(schedule):
    edges = set()
    for i, (t1, op1, x1) in enumerate(schedule):
        for t2, op2, x2 in schedule[i + 1:]:
            if t1 != t2 and x1 == x2 and "W" in (op1, op2): edges.add((t1, t2))   # conflicting pair: same item, different txns, at least one write
    return edges
def has_cycle(edges):
    nodes = {a for e in edges for a in e}
    def reach(a, b, seen=()):
        return any(y == b or (y not in seen and reach(y, b, seen + (y,))) for x, y in edges if x == a)
    return any(reach(n, n) for n in nodes)
def topo(edges, txns):
    order, e = [], set(edges)
    while txns:
        t = next(t for t in sorted(txns) if not any(y == t for x, y in e)); order.append(t); txns.remove(t); e = {(x, y) for x, y in e if x != t}
    return order
S1 = [("T1", "R", "A"), ("T1", "W", "A"), ("T2", "R", "A"), ("T2", "W", "A"), ("T1", "R", "B"), ("T1", "W", "B"), ("T2", "R", "B"), ("T2", "W", "B")]
S2 = [("T1", "R", "A"), ("T2", "R", "A"), ("T1", "W", "A"), ("T2", "W", "A")]
for name, s in (("S1", S1), ("S2", S2)):
    e = precedence(s)
    print("%s: %s" % (name, " ".join("%s(%s)%s" % (op, x, t[1]) for t, op, x in s)))
    print("    edges %s -> %s" % (sorted(e), "NOT serializable (cycle)" if has_cycle(e) else "serializable, equivalent to " + " -> ".join(topo(e, {t for t, _, _ in s}))))
print("S2 is the lost-update pattern: both read A, both write A.")

# ----- Output (real run) -----

#     edges [('T1', 'T2')] -> serializable, equivalent to T1 -> T2
# S2: R(A)1 R(A)2 W(A)1 W(A)2
#     edges [('T1', 'T2'), ('T2', 'T1')] -> NOT serializable (cycle)

S1 interleaves operations but every conflict goes T1 → T2, so it equals running T1 then T2. S2 (both read A, then both write A) has edges both ways: a cycle, so it is not serializable: it is exactly the lost-update pattern.

Good to know

  • Conflicting operations: same item, different transactions, at least one write (R-W, W-R, W-W).
  • Conflict-serializable ⇒ view-serializable (not the reverse). Recoverable schedules: a transaction commits only after those it read from commit; cascadeless: read only committed data.

31 Locking and Two-Phase Locking

Picture: Library rules: many people may read the same book together (shared lock), but someone writing notes in it needs it alone (exclusive lock). And once you start returning books you may not borrow new ones (two-phase rule).
Shared/exclusive locks and a deadlock found with a wait-for graph (simulation) (run for real)
# Two-phase locking with shared (S) and exclusive (X) locks, and deadlock detection with a wait-for graph (simulation).
locks, waits, log = {}, {}, []                                   # item -> (mode, set of holders); txn -> item it waits for
def request(t, mode, item):
    held = locks.get(item)
    if held is None: locks[item] = (mode, {t}); log.append("%s gets %s(%s)" % (t, mode, item)); return True
    m, holders = held
    if holders == {t}: locks[item] = ("X" if "X" in (m, mode) else "S", holders); log.append("%s upgrades/keeps lock on %s" % (t, item)); return True
    if m == "S" and mode == "S": holders.add(t); log.append("%s shares S(%s)" % (t, item)); return True
    waits[t] = item; log.append("%s WAITS for %s(%s) held by %s" % (t, mode, item, sorted(holders))); return False
def deadlock():
    g = {t: next(iter(locks[i][1] - {t}), None) for t, i in waits.items()}
    for start in g:
        seen, cur = [], start
        while cur in g and cur not in seen: seen.append(cur); cur = g[cur]
        if cur == start: return seen
    return None
request("T1", "S", "A"); request("T2", "S", "A")                  # readers share
request("T1", "X", "B"); request("T2", "X", "B")                  # T2 waits for T1
request("T1", "X", "A")                                           # T1 wants to write A, but T2 also holds S(A): T1 waits for T2
print("\n".join(log))
cyc = deadlock()
print("wait-for cycle:", " -> ".join(cyc + [cyc[0]]) if cyc else None, "-> DEADLOCK: abort the younger transaction (T2) and restart it")
print("Rules of 2PL: growing phase (only acquire), then shrinking phase (only release). Strict 2PL holds X locks until commit (no cascading aborts).")

# ----- Output (real run) -----
# T1 gets S(A)
# T2 shares S(A)
# T1 gets X(B)
# T2 WAITS for X(B) held by ['T1']
# T1 WAITS for X(A) held by ['T1', 'T2']
# wait-for cycle: T2 -> T1 -> T2 -> DEADLOCK: abort the younger transaction (T2) and restart it
# Rules of 2PL: growing phase (only acquire), then shrinking phase (only release). Strict 2PL holds X locks until commit (no cascading aborts).

Both transactions share A for reading; T1 takes B exclusively, so T2 waits; then T1 wants to write A but T2 still reads it, so T1 waits for T2 while T2 waits for T1: deadlock. The system aborts one transaction (the victim) and restarts it.

32 Timestamps, MVCC and Snapshot Isolation

Picture: Instead of making readers wait, the library keeps old editions of each book. Readers get the edition that was current when they arrived; writers publish a new edition.
Versions for readers, and the write-skew anomaly (simulation) (run for real)
# MVCC and snapshot isolation (simulation): readers see a snapshot; writers create new versions. And the 'write skew' anomaly.
versions = {"x": [(0, 10)], "doctor_A_on_call": [(0, True)], "doctor_B_on_call": [(0, True)]}   # key -> list of (commit_ts, value)
ts = 0
def read(key, snap): return max((v for v in versions[key] if v[0] <= snap), key=lambda v: v[0])[1]
def commit(writes):
    global ts; ts += 1
    for k, v in writes.items(): versions[k].append((ts, v))
    return ts
snap_reader = ts
commit({"x": 20})
print("long report started at snapshot %d reads x = %d; a new reader sees x = %d" % (snap_reader, read("x", snap_reader), read("x", ts)))
print("versions of x kept for old snapshots:", versions["x"], " (garbage collection / VACUUM removes old ones later)")
s1 = s2 = ts                                                   # two doctors start 'go off call' at the same time
ok1 = read("doctor_B_on_call", s1); ok2 = read("doctor_A_on_call", s2)   # each checks that the OTHER is still on call
if ok1: commit({"doctor_A_on_call": False})
if ok2: commit({"doctor_B_on_call": False})
print("write skew: A on call =", read("doctor_A_on_call", ts), ", B on call =", read("doctor_B_on_call", ts), " <- nobody on call, though each check passed")

# versions of x kept for old snapshots: [(0, 10), (1, 20)]  (garbage collection / VACUUM removes old ones later)
# write skew: A on call = False , B on call = False  <- nobody on call, though each check passed

The long report keeps reading x = 10 from its snapshot while new readers see 20. Two doctors each checked that the other was still on call and then went off call: under snapshot isolation both succeed (they wrote different rows) and nobody is on call. That is write skew.

Good to know

  • Timestamp ordering: each transaction gets a timestamp; operations that would violate timestamp order abort (Thomas write rule ignores obsolete writes).
  • MVCC is used by PostgreSQL, Oracle, MySQL InnoDB, SQL Server (snapshot), SQLite WAL readers. Old versions need cleanup (VACUUM, purge).
  • PostgreSQL's SERIALIZABLE uses Serializable Snapshot Isolation (SSI) to detect write skew and abort one transaction.

33 Crash Recovery: Logs, Checkpoints, ARIES

Picture: A shopkeeper writes every sale in a notebook before moving money. After a power cut, the notebook tells exactly which sales finished (redo them) and which were half-done (undo them).
REDO then UNDO from a write-ahead log (simplified ARIES) (run for real)
# Crash recovery with a write-ahead log (WAL), simplified ARIES-style REDO then UNDO (simulation).
disk = {"A": 100, "B": 200, "C": 300}
log = [("T1", "BEGIN"), ("T1", "UPDATE", "A", 100, 50), ("T2", "BEGIN"), ("T2", "UPDATE", "B", 200, 250), ("T1", "COMMIT"),
       ("T2", "UPDATE", "C", 300, 0), ("CHECKPOINT",), ("T3", "BEGIN"), ("T3", "UPDATE", "A", 50, 75)]
# CRASH here: some pages reached disk, some did not (steal / no-force buffer policy)
disk.update({"A": 75, "B": 200, "C": 0})                       # A has T3's uncommitted value; B lost T2's change; C has T2's change
print("disk after crash:", disk)
committed = {r[0] for r in log if len(r) > 1 and r[1] == "COMMIT"}
for r in log:                                                  # REDO: repeat history (every logged update, in order)
    if len(r) == 5: disk[r[2]] = r[4]
print("after REDO (repeat history):", disk)
for r in reversed(log):                                        # UNDO: roll back losers (no COMMIT record), newest first
    if len(r) == 5 and r[0] not in committed: disk[r[2]] = r[3]; print("   undo %s: %s back to %s" % (r[0], r[2], r[3]))
print("after UNDO:", disk, " committed:", sorted(committed), " losers:", sorted({r[0] for r in log if len(r) > 1 and r[0] not in committed}))
print("Rule (WAL): a change's log record must reach stable storage BEFORE the changed page does, and COMMIT is durable once its log record is flushed.")

# ----- Output (real run) -----
# disk after crash: {'A': 75, 'B': 200, 'C': 0}
# after REDO (repeat history): {'A': 75, 'B': 250, 'C': 0}
#    undo T3: A back to 50
#    undo T2: C back to 300
#    undo T2: B back to 200
# after UNDO: {'A': 50, 'B': 200, 'C': 300}  committed: ['T1']  losers: ['T2', 'T3']
# Rule (WAL): a change's log record must reach stable storage BEFORE the changed page does, and COMMIT is durable once its log record is flushed.

After the crash the disk held a mix: T3's uncommitted change to A, but not T2's change to B. Redo repeated all logged updates; undo then rolled back the losers T2 and T3 newest-first. Only T1 (committed) survives: A ends at 50, B and C at their original values.

Hash-mod vs consistent hashing when adding a server (run for real)
# Hash vs range partitioning (sharding) and what happens when you add a server.
import hashlib
keys = ["user%d" % i for i in range(10000)]
h = lambda k: int(hashlib.md5(k.encode()).hexdigest(), 16)
def mod_assign(n): return {k: h(k) % n for k in keys}
a4, a5 = mod_assign(4), mod_assign(5)
print("hash(key) mod N: going from 4 to 5 servers moves %.0f%% of keys" % (100 * sum(a4[k] != a5[k] for k in keys) / len(keys)))
import bisect
def ring(servers, vnodes=100):
    pts = sorted((h("%s#%d" % (s, v)), s) for s in servers for v in range(vnodes)); return [p for p, _ in pts], [s for _, s in pts]
def assign(r, k):
    pts, owners = r; i = bisect.bisect(pts, h(k)) % len(pts); return owners[i]
r4, r5 = ring(["s0", "s1", "s2", "s3"]), ring(["s0", "s1", "s2", "s3", "s4"])
moved = sum(assign(r4, k) != assign(r5, k) for k in keys)
print("consistent hashing (100 virtual nodes each): adding a 5th server moves %.0f%% of keys (ideal 20%%)" % (100 * moved / len(keys)))
print("range partitioning (A-F, G-M, ...) keeps ranges together for range scans but can create hot spots.")

39 Interview Questions (With Answers)

Picture: Grouped by theme, easiest first. Click to reveal.

A. Basics

Q1: DBMS vs file system?

DBMS adds a query language, integrity constraints, concurrency control, recovery, security and data independence.

Q2: Primary key vs unique key vs foreign key?

Primary: unique + not null, one per table. Unique: no duplicates, may allow NULL. Foreign: must match a key in another table.

Q3: Super key vs candidate key?

Super key identifies rows; candidate key is a minimal super key.

Q4: DDL vs DML vs DCL vs TCL?

Define structure; manipulate data; control permissions; control transactions.

Q5: DELETE vs TRUNCATE vs DROP?

DELETE removes chosen rows (logged, can use WHERE); TRUNCATE removes all rows quickly; DROP removes the table itself.

B. SQL

Q6: INNER vs LEFT vs FULL OUTER join?

Matches only; all left rows plus matches; all rows from both sides.

Q7: WHERE vs HAVING?

WHERE filters rows before grouping; HAVING filters groups after aggregation.

Q8: Find the second-highest salary.

SELECT max(salary) FROM emp WHERE salary < (SELECT max(salary) FROM emp) or DENSE_RANK() = 2.

Q9: RANK vs DENSE_RANK vs ROW_NUMBER?

1,2,2,4 / 1,2,2,3 / 1,2,3,4.

Q10: Why does NOT IN sometimes return no rows?

If the subquery returns a NULL, every NOT IN comparison is UNKNOWN.

Q11: What is a correlated subquery?

A subquery that refers to the outer query's row and is (logically) evaluated per row.

Q12: View vs materialized view?

Saved query vs saved result that must be refreshed.

Q13: How do you prevent SQL injection?

Parameterised queries, least privilege, validation; never concatenate input into SQL.

C. Design

Q14: What is normalization and why?

Organising tables to remove redundancy and update/insert/delete anomalies by following FDs.

Q15: 2NF vs 3NF vs BCNF?

2NF: no partial dependency on a composite key. 3NF: no transitive dependency of non-prime attributes. BCNF: every determinant is a super key.

Q16: When would you denormalize?

For read performance in reporting or hot paths, accepting duplication and the work to keep it consistent.

Q17: Map an M:N relationship to tables.

A junction table with both foreign keys as a composite primary key, plus relationship attributes.

D. Storage and indexing

Q18: Why B+ trees for indexes?

Shallow, balanced, high fan-out (few page reads), sorted leaves linked for range scans.

Q19: Clustered vs non-clustered index?

Clustered stores rows in key order (one per table); non-clustered is a separate structure pointing to rows.

Q20: When is an index not used?

Functions on the column, leading wildcard LIKE '%x', non-leftmost composite columns, low selectivity, type mismatches, outdated statistics.

Q21: Hash join vs sort-merge vs nested loop?

Hash: large equality joins; sort-merge: sorted inputs or inequality; nested loop: small inputs or with an inner index.

E. Transactions

Q22: Explain ACID.

Atomicity, Consistency, Isolation, Durability (see the transfer demo).

Q23: What are dirty read, non-repeatable read and phantom read?

Reading uncommitted data; a re-read row has changed; a re-run query returns new rows.

Q24: What is 2PL and strict 2PL?

Acquire locks then release (no acquiring after the first release) → serializable; strict holds X locks until commit → no cascading aborts.

Q25: How are deadlocks handled in databases?

Wait-for graph detection and victim abort, or prevention by wait-die/wound-wait, or timeouts.

Q26: What is MVCC?

Keeping multiple versions so readers see a snapshot without blocking writers.

Q27: What is write skew?

Two transactions read overlapping data and write different rows, breaking an invariant under snapshot isolation.

Q28: How does WAL-based recovery work?

Log before data; after a crash redo logged changes, then undo uncommitted transactions; checkpoints limit work.

F. Distributed

Q29: State the CAP theorem.

Under a network partition a system must choose consistency or availability.

Q30: Sharding vs replication?

Sharding splits data across nodes for scale; replication copies it for availability and read scale.

Q31: SQL vs NoSQL?

Relational with schemas, joins, strong transactions vs specialised models (document, key-value, wide-column, graph) chosen for scale or flexibility; choose by access patterns.

41 FAQ

Picture: Click a question to reveal the answer.
Q: Which database should a beginner learn?

SQLite to start (no server, used on this page), then PostgreSQL.

Q: Are the SQL outputs real?

Yes: every SQL example ran in SQLite 3.50.4 through Python 3.14 and the output is shown. PostgreSQL/MongoDB/Redis/ORM code is a template.

Q: Will this SQL work in MySQL/PostgreSQL?

Mostly yes; small differences exist (PRAGMA is SQLite-only, LIMIT vs TOP, some functions).

Q: Should I always normalise to BCNF?

Aim for 3NF/BCNF for transactional data; denormalise deliberately for read-heavy reporting.

Q: Which books are classic?

Silberschatz, Korth and Sudarshan 'Database System Concepts'; Elmasri and Navathe; Ramakrishnan and Gehrke; Kleppmann 'Designing Data-Intensive Applications' for distributed data.

42 Common Mistakes and Checklist

Picture: Traps students and engineers fall into.

🕳️ = NULL

Use IS NULL.

🚫 NOT IN with NULLs

Use NOT EXISTS.

💥 UPDATE without WHERE

Run the SELECT first; use transactions.

🧵 Read-modify-write in the app

Lost updates; use SET x = x - n or versions.

🐌 Function on an indexed column

Index not used.

📇 Index everything

Writes slow down; index what queries need.

💉 String-built SQL

Use parameters.

💰 FLOAT for money

Use DECIMAL/NUMERIC or integer paise.

⏳ Long transactions

Hold locks/versions; keep them short.

🔁 N+1 queries in ORMs

Join or eager-load.
