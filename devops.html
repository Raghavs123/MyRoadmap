Part A — Foundations

1 What is DevOps? (the 10-second answer)

DevOps is a way of working where the people who build software (Developers) and the people who run it (Operations) work as one team, using automation and constant feedback so that good changes reach users quickly, safely and repeatedly.
Think of a restaurant. In the old way, the chefs invent dishes and shove them through a hatch, and the waiters (who never saw the recipe) have to serve them and deal with angry customers. In the DevOps way, chefs and waiters work in one kitchen: they test dishes together, agree on how to serve them, and when a customer complains they fix the recipe the same day — with checklists (automation) so nothing gets forgotten.

DevOps is not a single tool, and it's not just a job title. It's three things together:

PartWhat it meansEveryday example
🤝 CultureShared ownership, no blame, learning from mistakes"We built it, we run it, we fix it — together"
🔁 PracticesSmall changes, version control, automated tests, frequent releases, monitoringShipping ten tiny updates a week instead of one giant yearly release
🛠️ ToolsGit, CI/CD pipelines, containers, Kubernetes, infrastructure as code, monitoringA robot that tests and deploys every change automatically
If you remember one sentence: DevOps = make the road from "an idea in a developer's head" to "working in front of users" short, safe and boring.

The habits that matter most

📦 Small batches

Small changes are easier to review, test, and undo. A bug in a 20-line change is found in minutes; in a 20,000-line change, in days.

🧯 Blameless postmortems

After an incident, ask "what in our system let this happen?" not "who messed up?" People hide mistakes when punished; systems get fixed when mistakes are shared.

🔁 Fast feedback

Know in minutes if a change broke something — from tests before release and monitoring after.

🤖 Automate the boring

If a human does it the same way every time, a script should. Humans are for judgement.

A common mistake: renaming the "sysadmin team" to "DevOps team" and buying tools. Without shared ownership you've just built a new wall with a trendier label.

8 Measuring Success — The DORA Five

How do you know if DevOps is working? The DORA research programme (years of studies of thousands of teams) found five delivery measures that predict how a team and its organisation do. The 2025 report grouped them as throughput (how fast) and instability (how bumpy):

Fig 3 — DORA's five delivery metrics. Top teams are good at both columns: speed and stability are not a trade-off.
MetricPlain meaningExample
Change lead timeTime from a change being committed until it is live for usersMerged Monday 10:00, live 10:25 → 25 min
Deployment frequencyHow often you deploy to production12 deploys this week
Failed-deployment recovery timeHow long to recover after a release goes wrongRolled back in 8 minutes
Change fail rateShare of deployments that need a rollback or hotfix2 of 40 deploys → 5%
Deployment rework rateShare of deployments that were unplanned fixes for production problems3 of 40 → 7.5%
DORA's own advice: measure per service, don't use the numbers as targets to compete on (Goodhart's law: "when a measure becomes a target, it stops being a good measure"), and use them as a way to find the next thing to improve. The old "elite/high/medium/low" labels were replaced in 2025 by team profiles.
It's like checking a delivery service: how fast does the parcel arrive (lead time), how often do trucks leave (frequency), how often is a parcel damaged (fail rate), and how fast do you send a replacement (recovery time)?

AI's effect (DORA 2025): from a survey of nearly 5,000 professionals, using AI assistants was linked with higher throughput but also with more instability — faster shipping without matching safety nets (tests, reviews, small batches) makes things bumpier. More in Section 40.

10 Code Review & Pull Requests

Before a change joins main, a teammate looks at it — a second pair of eyes catches bugs, shares knowledge and keeps style consistent.

Good habitWhy
Keep PRs small (a few hundred lines at most)Small PRs get faster, better reviews
Write what and why in the descriptionReviewers shouldn't have to guess
Let automation do the boring checksLinters, formatters and tests run on every PR so humans focus on design and logic

AI-written code needs more careful review, not less: it can look confident and be wrong, or add insecure patterns. Treat it like code from a fast new teammate (Section 40).

13 Continuous Integration (CI)

Continuous Integration means every developer merges small changes into the shared code many times a day, and every merge automatically triggers a build and tests — so integration problems appear in minutes, not months.
Fig 6 — A CI pipeline: every change flows through checkout, checks, build, test and publish; any failure stops the line and notifies the author.
CI ruleMeaning
Keep the build greenIf main is red, fixing it is everyone's top priority
Fast feedbackAim for a pipeline of minutes (≈10 or less) so people actually wait for it
Same pipeline for everyoneThe server's checks are the ones that count, not "it passed on my laptop"
Fail loudly, earlyCheap checks (lint, unit) first; slow ones later
Pipeline as codeThe pipeline definition (YAML) lives in the repo and is reviewed like any code (Level 2)
A bouncer who checks every guest at the door as they arrive, not one who waits until the party is over and then finds out half the guests were trouble.

16 Feature Flags — Deploy Is Not Release

A feature flag is an on/off switch in the code: if flag("new-checkout"): …. You can deploy the code to production switched off, then release it (turn it on) later — for 1% of users, then 10%, then everyone — without a new deployment.

UseExample
Hide unfinished work (keeps branches short — trunk-based)Merge half-built search every day, invisible until ready
Gradual rollout1% → 10% → 50% → 100% of users
Kill switchTurn a misbehaving feature off in seconds, no rollback
Targeting / experimentsShow the new design to one country; A/B test two versions
Permissions & plansPremium features on for paying customers
A light switch you install in every room before the party: wiring (deployment) happens quietly beforehand; flipping the switch (release) happens at exactly the moment you choose.
Flags are debt: remove them once a feature is fully launched, or the code fills with old branches nobody dares delete. Name an owner and an expiry for each flag.

17 GitOps — Git as the Single Source of Truth

GitOps means: you describe what you want running (the "desired state") in files in Git, and a tool inside the cluster continuously compares reality to Git and fixes any difference. Four principles (from the OpenGitOps project): the system is declarative, versioned and immutable in Git, changes are pulled automatically, and the system is continuously reconciled.

Fig 8 — Push-based deployment vs GitOps: instead of the pipeline pushing into the cluster, an agent in the cluster pulls from Git and keeps reality equal to it.
BenefitWhy
Audit trailEvery change is a reviewed commit: who, what, when, why
Easy rollbackRevert the commit; the tool restores the old state
Drift correctionHand-made changes are detected and reversed (or flagged)
Safer credentialsThe cluster reaches out to Git; CI doesn't need keys to production
Disaster recoveryRebuild a cluster by pointing a new one at the same repo

The two best-known GitOps tools, Argo CD and Flux, are both CNCF graduated projects. In the CNCF/SlashData Q1 2026 technology radar, Argo CD sits in the "Adopt" ring for workflow automation.

A thermostat: you set the temperature you want (Git); the thermostat keeps checking the room and turns the heating on or off to match, without you walking over each time.

Part E — Containers & Kubernetes

19 Containers — A Lunchbox for Software

A container packs an application together with everything it needs to run (libraries, settings) into one portable unit that behaves the same on your laptop, a test server or the cloud — ending "works on my machine".

Fig 9 — A virtual machine carries a whole guest operating system; containers share the host's kernel, so they're far smaller and start in seconds.
Virtual machineContainer
IncludesFull operating systemJust the app and its libraries
SizeGigabytesMegabytes to a few hundred MB
Start timeMinutesSeconds or less
IsolationStrong (separate kernels)Good, but a shared kernel — security needs care
Best forDifferent operating systems; strong isolationPackaging and scaling application services
Shipping goods in standard steel shipping containers: the crane, ship and lorry don't care what's inside; they handle every box the same way. A software container is the standard box for programs.
  • Image vs container: an image is the frozen recipe/package; a container is a running copy made from it (like a class vs an object, or a cake recipe vs a baked cake).
  • OCI (Open Container Initiative) standardises image and runtime formats so Docker, Podman, containerd and Kubernetes all understand each other.
  • Under the hood, Linux features (namespaces for isolation, cgroups for resource limits) make containers possible.

21 Kubernetes — The Big Picture

One container is easy. Hundreds across many machines — restarting crashed ones, spreading load, rolling out updates — is not. Kubernetes ("K8s") is the system that does this: you tell it what you want ("run 3 copies of this image"), and it keeps making reality match.

Fig 10 — Kubernetes architecture: the control plane stores the desired state and decides; worker nodes (via the kubelet) actually run the Pods.
An airport: the control tower (control plane) knows the plan — which plane lands where. The runways and gates (nodes) do the physical work. If a plane (Pod) breaks down, the tower reroutes another to keep the schedule.

The core idea: declarative + reconciliation

  • Declarative: you write what you want in YAML, not how to get there.
  • Reconciliation loop: controllers constantly compare "desired" with "actual" and act — a crashed Pod is replaced without anyone being paged.
  • Everything goes through the API server, so access control (RBAC), auditing and GitOps all plug into one place.

27 Infrastructure as Code (IaC)

32 SLIs, SLOs & Error Budgets — How Reliable Is Reliable Enough?

100% reliability is impossible and absurdly expensive. SRE replaces "never fail" with an agreed target:

TermStands forMeaningExample
SLIService Level IndicatorA measurement of how well it's working% of requests that succeed in under 300 ms
SLOService Level ObjectiveThe internal target for the SLI99.9% of requests good over 30 days

Fig 11 — The error budget turns "speed vs stability" into a shared, measurable rule: spend the budget on change while you have some; protect it when it's nearly gone.
A monthly data plan: you're allowed a certain amount of "badness" (like gigabytes). Use it freely while you have plenty; when it's nearly gone, stop streaming and wait for next month.

Burn rate — how fast are we spending?

A burn rate of 1× means you'd use exactly your whole budget by the end of the period. 10× means you'd empty it in a tenth of the time. Teams alert on fast burns (page), and slower burns (ticket). A commonly used example from Google's SRE Workbook: a 14.4× burn sustained for 1 hour uses about 2% of a 30-day budget — worth a page. The numbers in Level 5 show how it works.

Pick SLOs from what users care about (fast, correct, available), start with one or two per service, and revisit them. "Reliability" is a feature with a price: each extra "nine" costs far more than the last.

37 The Software Supply Chain — Trust What You Ship

Modern software is mostly other people's code (libraries, base images, build tools, CI actions). The supply chain is every link between a developer's keyboard and a running service. Attackers go after the weakest link, because one poisoned package can reach thousands of companies.

What's been happening (as reported by security researchers, 2026)

Reports from vendors and researchers describe a series of attacks that abused CI/CD pipelines — for example, compromised build workflows used to steal publishing tokens and push trojanised packages to npm and PyPI, and at least one case where a malicious package carried valid build-provenance because the trust rule was too broad (covering a whole repository instead of one protected workflow). 47 Level 5 — Error-Budget & Burn-Rate Math

slo.py — plain Python (run for real) 
# slo.py -- how much "badness" are we allowed? (error budget math)
SLO = 0.999                      # promise: 99.9% of requests succeed this month
DAYS = 30
minutes_in_month = DAYS * 24 * 60

allowed_bad_fraction = 1 - SLO                       # 0.1% may fail
budget_minutes = minutes_in_month * allowed_bad_fraction
print(f"SLO {SLO:.3%} over {DAYS} days -> {budget_minutes:.1f} minutes of full outage allowed")

# Request-based view: how much of the budget is left?
total_requests = 10_000_000
failed_requests = 6_500
budget_requests = total_requests * allowed_bad_fraction   # 10,000 failures allowed
used = failed_requests / budget_requests
print(f"Failures so far: {failed_requests} of {budget_requests:.0f} allowed -> {used:.0%} of budget used")

# Burn rate: how fast are we eating the budget compared with 'exactly on pace'?
def burn_rate(error_rate_now, slo=SLO):
    return error_rate_now / (1 - slo)

for rate in (0.0005, 0.001, 0.01, 0.0144):
    br = burn_rate(rate)
    hours_to_empty = (DAYS * 24) / br
    print(f"error rate {rate:.2%} -> burn rate {br:5.1f}x -> budget gone in {hours_to_empty:7.1f} hours")

# Output from a real run:
#   SLO 99.900% over 30 days -> 43.2 minutes of full outage allowed
#   Failures so far: 6500 of 10000 allowed -> 65% of budget used
#   error rate 0.05% -> burn rate   0.5x -> budget gone in  1440.0 hours
#   error rate 0.10% -> burn rate   1.0x -> budget gone in   720.0 hours
#   error rate 1.00% -> burn rate  10.0x -> budget gone in    72.0 hours
#   error rate 1.44% -> burn rate  14.4x -> budget gone in    50.0 hours

Read the table: at 1× you'd spend the whole month's budget in exactly a month (720 hours) — fine. At 10× it's gone in 3 days — worth a ticket. Much faster burns (like 14.4× held for an hour) are worth a page. The matching alert rule for Prometheus (YAML syntax-checked, not run):

48 Level 6 — Deploy, Check Health, Roll Back Automatically

The heart of safe delivery in 25 lines: ship, look, and undo yourself if it looks bad (what Argo Rollouts, Flagger and similar tools do at scale).

deploy.py — plain Python simulation (run for real) 
# deploy.py -- deploy, check health, roll back automatically if it looks bad
import random

def deploy(version):
    print(f"  deploying {version} ...")

def healthy(version, samples=20):
    """Pretend health check: v2 is secretly buggy and fails ~40% of requests."""
    fail_rate = 0.4 if version == "v2" else 0.01
    failures = sum(random.random() < fail_rate for _ in range(samples))
    print(f"  health check for {version}: {failures}/{samples} requests failed")
    return failures / samples <= 0.05          # allow up to 5% errors

def release(new, old):
    deploy(new)
    if healthy(new):
        print(f"  OK: {new} is live")
        return new
    print(f"  BAD: rolling back to {old}")
    deploy(old)
    return old

random.seed(1)
print("release 1:"); live = release("v1", "v0")
print("release 2:"); live = release("v2", live)
print("live version is now:", live)

# Output from a real run:
# release 1:
#   deploying v1 ...
#   health check for v1: 1/20 requests failed
#   OK: v1 is live
# release 2:
#   deploying v2 ...
#   health check for v2: 11/20 requests failed
#   BAD: rolling back to v1
#   deploying v1 ...
# live version is now: v1

Release 2 was secretly broken; the automatic check noticed 11 of 20 requests failing and put v1 back — no human paged, and users only saw a short bump. Real systems use real metrics (error rate, latency) instead of random numbers, and shift traffic gradually (a canary, Section 15).

50 FAQ

Q: Is DevOps a job, a team, or a culture?

Primarily a culture and set of practices. Companies do hire "DevOps engineers", but if development and operations stay in separate silos with a new job title in between, you haven't adopted DevOps — you've renamed the wall.

Q: Do we need Kubernetes?

Not necessarily. It's excellent for many services, portability and complex needs, but it's heavy to operate. Many teams do well on container platforms (Cloud Run, ECS/Fargate, Azure Container Apps) or PaaS until they genuinely need what Kubernetes uniquely offers.

Q: What's the difference between CI and CD?

CI automatically builds and tests every change merged to the shared code. CD takes the tested artifact and delivers it — to a "ready to release" state (delivery) or all the way to production automatically (deployment).

Q: Terraform or OpenTofu?

They share the same language and workflow. Terraform is under the Business Source License (HashiCorp is owned by IBM); OpenTofu is an open-source fork under the Linux Foundation. Many 2026 guides suggest OpenTofu for new projects that value open governance, while Terraform remains the most widely used. Check current licenses, features and provider support before deciding; keeping code modular makes switching easier.

Q: How often should we deploy?

As often as you can do it safely. DORA finds speed and stability go together: teams with small, frequent, automated releases tend to have fewer failures and faster recovery. Start by shrinking batch size and automating tests and rollback.

Q: What's the difference between monitoring and observability?

Monitoring watches known signals and alerts on known problems. Observability means your telemetry (metrics, logs, traces) is rich enough to investigate unknown problems and ask new questions without shipping new code.

Q: Will AI replace DevOps engineers?

It's changing the work rather than removing the need: AI speeds up writing code, configs and incident investigation, while humans are still needed for design, safety, judgement and accountability. DORA 2025 found AI tends to raise both throughput and instability, which makes strong pipelines, tests and guardrails more important, not less.

Q: What's the first security step for a small team?

Turn on MFA/hardware keys, stop committing secrets (add secret scanning), keep dependencies locked and updated, give CI tokens read-only permissions by default, pin third-party actions, and use short-lived cloud credentials. Those cover a large share of real-world incidents.

Q: How do I get hands-on experience without a company cluster?

Use a local cluster (kind, minikube, k3d), free tiers of cloud providers (watch the billing alerts!), and a personal GitHub repo with Actions. Build the loop end-to-end: app → container → pipeline → deploy → dashboard → alert.

51 Interview Questions (With Answers) — The Complete Set

Grouped by category, easy → hard.

51.1 — Fundamentals

Q: What is DevOps?

A culture and set of practices that unify development and operations through shared ownership, automation, small frequent changes and fast feedback, so software is delivered quickly, safely and reliably.

Q: Describe the DevOps lifecycle.

A continuous loop: plan, code, build, test, release, deploy, operate, monitor — with monitoring and incident learnings feeding back into planning.

Q: DevOps vs Agile vs SRE?

Agile is about iterative development with customer feedback; DevOps extends that speed and collaboration through release and operation; SRE is a specific engineering approach to reliability using SLOs, error budgets and automation — often described as one concrete way of implementing DevOps.

Q: What does CALMS stand for?

Culture, Automation, Lean, Measurement, Sharing.

Q: What are the DORA metrics?

Five: change lead time, deployment frequency, failed-deployment recovery time (throughput), and change fail rate and deployment rework rate (instability). They're used per service as improvement signals, not targets.

Q: What is platform engineering and why did it emerge?

A team builds an internal developer platform of self-service golden paths so product teams don't each have to master pipelines, Kubernetes, security and cloud — reducing cognitive load and inconsistency.

51.2 — Git, CI & Testing

Q: Trunk-based development vs GitFlow?

Trunk-based: short-lived branches merged to main at least daily, with feature flags hiding unfinished work — fast feedback, fewer conflicts. GitFlow: long-lived develop/release branches — more ceremony and later integration. Research associates short-lived branches with better delivery performance.

Q: git merge vs rebase vs revert?

Merge joins histories with a merge commit; rebase replays your commits on top of another base for a linear history (rewrites your branch — avoid on shared branches); revert adds a new commit that undoes a previous one, safe for published history.

Q: What makes a good CI pipeline?

Fast (minutes), reliable (no flaky tests), runs on every change, cheap checks first, defined as code, produces a versioned artifact once, and keeps the main branch green with quick fixes when it breaks.

Q: Explain the testing pyramid.

Many fast, focused unit tests; fewer integration tests; very few slow end-to-end tests. It balances speed, cost and confidence; inverting it (mostly E2E) gives slow, flaky pipelines.

Q: How do you handle flaky tests?

Detect them (track pass/fail history), quarantine so they don't block everyone, find the root cause (timing, shared state, external dependencies), fix or delete, and never normalise re-running until green.

Q: What does "build once, deploy many" mean?

Create one immutable artifact and promote that same artifact through environments, injecting environment-specific configuration at deploy time — so what you tested is exactly what you run.

51.3 — Delivery & Release

Q: Continuous delivery vs continuous deployment?

Delivery keeps every change releasable with a human approval for production; deployment releases every passing change automatically. Deployment needs stronger tests, monitoring and rollback.

Q: Compare rolling, blue-green and canary deployments.

Rolling replaces instances gradually (no extra capacity, mixed versions during rollout). Blue-green runs two full environments and switches traffic (instant rollback, double capacity). Canary routes a small percentage of traffic to the new version and expands as metrics stay healthy (smallest blast radius, needs good observability).

Q: Why use feature flags?

They decouple deploy from release: hide unfinished work, roll out gradually, run experiments and flip a kill switch instantly. Manage their lifecycle — remove stale flags.

Q: What is GitOps and how does it differ from push-based CD?

Desired state is declared in Git and an in-cluster controller (Argo CD, Flux) continuously pulls and reconciles. Versus a pipeline pushing with cluster credentials, GitOps gives an audit trail, easy rollback by revert, drift correction and no production credentials in CI.

Q: How do you do database changes safely with continuous deployment?

Use backward-compatible migrations (expand/contract): add new columns/tables first, deploy code that works with both, backfill, then remove old structures later. Version migrations in code, test them, and avoid destructive changes in the same release as the code that needs them.

Q: A deployment is causing errors in production. What do you do first?

Mitigate before diagnosing: roll back or disable the feature flag, confirm recovery with the same metrics that alerted, then investigate with the preserved evidence and write a blameless postmortem.

51.4 — Containers & Kubernetes

Q: Container vs virtual machine?

A VM virtualises hardware and carries a whole guest OS; a container shares the host kernel and isolates processes, so it's lighter and starts faster, with weaker isolation than a VM.

Q: How do you make a Docker image small and safe?

Small trusted base (slim/distroless), multi-stage builds, only needed files via .dockerignore, non-root user, pinned versions/digests, no secrets in layers, order layers for caching, scan images and generate an SBOM.

Q: Explain Kubernetes architecture.

A control plane (API server, etcd, scheduler, controller manager) stores desired state and decides; worker nodes run the kubelet, a container runtime and kube-proxy to execute Pods. Controllers run reconciliation loops to make actual state match desired state.

Q: Pod vs Deployment vs StatefulSet vs DaemonSet?

Pod: smallest unit. Deployment: manages replicas and rolling updates of stateless Pods. StatefulSet: stable identity and storage for stateful apps. DaemonSet: one Pod per node (agents).

Q: How does a Service differ from an Ingress/Gateway?

A Service gives a stable virtual address and load balancing to a set of Pods inside the cluster. Ingress/Gateway API define how external HTTP(S) traffic is routed to Services (hostnames, paths, TLS). Note ingress-nginx was retired in March 2026; Gateway API is the recommended direction.

Q: What are readiness and liveness probes?

Readiness decides whether a Pod receives traffic; liveness decides whether it should be restarted. Misconfigured liveness probes can cause restart loops, so keep them cheap and tolerant.

Q: How would you upgrade a Kubernetes cluster safely?

Read release notes and removed APIs; upgrade one minor version at a time; control plane first, then nodes; rehearse in staging; use PodDisruptionBudgets and readiness probes for availability; update add-ons; have a rollback/backup plan. Check support status, since each minor gets about a year of patches (e.g., 1.34 reached end of life on 27 Oct 2026).

Q: Are Kubernetes Secrets secure?

By default they are only base64-encoded and stored in etcd. Enable encryption at rest, restrict access with RBAC, avoid committing them to Git unencrypted (use sealed secrets/SOPS/External Secrets or a manager like Vault), and prefer short-lived credentials.

51.5 — Infrastructure as Code & Cloud

Q: Why Infrastructure as Code?

Repeatability, review via pull requests, version history, consistent environments, fast disaster recovery and the ability to apply policy checks automatically.

Q: Declarative vs imperative?

Declarative describes the desired end state and lets the tool compute the steps (idempotent, safe to re-run). Imperative scripts specify steps and may behave differently on re-run.

Q: What is Terraform state and how do you manage it?

The mapping between your code and real resources. Store it in a remote, encrypted backend with locking, restrict access (it may hold sensitive values), split state per environment/component, and never edit by hand.

Q: What is configuration drift and how do you handle it?

Reality diverging from code due to manual changes. Detect via plan/drift detection or GitOps reconciliation, restrict console write access, and either revert the change or codify it.

Q: Terraform vs OpenTofu vs Pulumi?

Terraform and OpenTofu use HCL with the same workflow; Terraform is BSL-licensed (IBM-owned), OpenTofu is the Linux Foundation open-source fork. Pulumi uses general-purpose languages (loops, tests, libraries). Choice depends on licensing comfort, team skills and ecosystem.

Q: What does "shared responsibility" mean in cloud?

The provider secures the underlying infrastructure; the customer secures configuration, identities, data and applications. Most breaches stem from customer-side misconfiguration.

51.6 — Observability, SRE & Incidents

Q: Metrics vs logs vs traces?

Metrics are numeric time series (trends and alerting); logs are detailed event records (what happened); traces follow a request across services (where time went). Together, correlated by IDs, they enable investigation.

Q: What are the four golden signals?

Latency, traffic, errors and saturation.

Q: Explain SLI, SLO, SLA and error budget.

SLI: measured indicator; SLO: internal target; SLA: contractual promise with penalties; error budget: 1 − SLO, the permitted unreliability that can be spent on change. When budget is exhausted, prioritise reliability over features.

Q: What does a 99.9% SLO allow over 30 days?

0.1% failure — about 43.2 minutes of complete downtime (or the equivalent in failed requests).

Q: What is a burn rate and how is it used in alerting?

How quickly the budget is consumed relative to an even spend (1× = exactly on pace). Multi-window alerts page on fast burns (e.g., ~14.4× over an hour ≈ 2% of a 30-day budget) and ticket on slower ones, aligning alerts with user impact.

Q: How do you reduce alert fatigue?

Alert on user-visible symptoms and SLO burn, make every page actionable with a runbook, tune or delete noisy alerts, use severities and routing, and review alert quality after incidents.

Q: Walk through incident response.

Detect, triage (severity, impact), assign roles (commander, responders, comms, scribe), mitigate first (rollback/flag/failover), resolve and verify, then run a blameless postmortem with owned follow-up actions.

Q: RPO vs RTO?

RPO is the maximum tolerable data loss (drives backup/replication frequency); RTO is the maximum tolerable downtime (drives recovery design). Test restores regularly.

51.7 — Security

Q: What is DevSecOps / "shift left"?

Embedding security checks (secret scanning, SAST, SCA, IaC and image scanning, DAST) in the pipeline from the start so issues are found early and cheaply, with security as a shared responsibility.

Q: How do you secure a CI/CD pipeline?

Least-privilege read-only tokens by default; OIDC instead of stored cloud keys; pin third-party actions to commit SHAs; avoid script injection and risky triggers like pull_request_target with untrusted code; protect branches and workflow files with CODEOWNERS; ephemeral runners; scoped trusted publishing; audit workflows with scanners.

Q: What is an SBOM and why do you want one?

A machine-readable inventory of components in an artifact (CycloneDX/SPDX). When a vulnerability is disclosed you can instantly find affected builds; it also supports licence and compliance checks.

Q: What is SLSA, and why isn't provenance enough?

SLSA is a framework for build integrity levels. Provenance says how an artifact was built, but if the build workflow itself is compromised or the trust policy is too broad, malicious artifacts can still carry valid provenance — so scope trust tightly and harden the build.

Q: A secret was pushed to a public repo. What do you do?

Revoke/rotate immediately (removing the commit isn't enough), review audit logs for misuse, purge history if appropriate, and add prevention: pre-commit/server-side secret scanning, short-lived credentials, and a secrets manager.

Q: Principle of least privilege in practice?

Separate identities per service/person, minimal scoped permissions, time-bound access, regular reviews, and logged access — so a compromise exposes as little as possible.

51.8 — Platform, AI & Scenarios

Q: How would you design a golden path for new services?

Offer a template that creates repo, CI pipeline with tests and scans, container build, Kubernetes/GitOps config, dashboards, alerts, SLO scaffolding and ownership metadata in one step; measure adoption and developer satisfaction; keep it optional but easier than the alternative.

Q: How would you safely introduce AI agents into DevOps workflows?

Start read-only (triage and summarising), connect via least-privilege identities (e.g., through MCP servers with scoped tools), require human approval for destructive or production actions, run changes through the same pipeline and policy checks, sandbox first, log all agent actions, and treat tickets/logs as untrusted input to avoid prompt injection.

Q: What did DORA 2025 conclude about AI?

AI adoption was associated with higher delivery throughput but also with higher instability — so teams need strong foundations (small batches, tests, review, observability) to benefit safely. DORA also moved to five metrics and replaced the old performance tiers with team profiles.

Q: Your pipeline takes 45 minutes and developers avoid it. How do you fix it?

Profile stages; parallelise; cache dependencies and build layers; run cheap checks first and slow ones later or on merge; shard tests and remove or quarantine flaky ones; use larger/ephemeral runners; only run what changed (path filters); aim for ≈10 minutes for PR feedback.

Q: Your cloud bill doubled this month. How do you investigate?

Break costs down by tag/team/service; look for new or forgotten resources, retry storms, data egress, log volume, over-provisioned instances or autoscaler misconfiguration; correlate with deploys; add budgets/alerts and policy guardrails; and track unit cost per request/customer.

Q: How would you migrate from ingress-nginx?

Inventory Ingress resources and annotations; choose a maintained controller or Gateway API implementation; use ingress2gateway (or equivalent) to translate what maps cleanly and hand-port the rest; run both in parallel with traffic shifting; test; then decommission ingress-nginx. The upstream project stopped releases and security fixes after March 2026.

52 Common Problems & Production Checklist

🧱 A new wall with a new name

Creating a separate "DevOps team" that everyone throws work at. Aim for shared ownership.

🐘 Big-bang releases

Batching months of changes. Ship small and often with fast rollback.

🔴 Ignored red builds

Flaky tests and slow pipelines teach people to ignore failures. Keep CI fast and trustworthy.

🖱️ Click-ops in production

Manual console changes cause drift and mystery outages. Change via code and reviews.

🔑 Secrets in the wrong places

Keys in Git, images, logs or long-lived CI variables. Use a manager and short-lived credentials.

📣 Alert fatigue

Hundreds of noisy alerts. Alert on user pain and error-budget burn; delete the rest.

🧰 Tool-first thinking

Adopting Kubernetes or a platform because it's trendy. Start from the problem and the team's needs.

⏳ Falling behind on versions

Running unsupported Kubernetes, dependencies or controllers (like retired ingress-nginx). Track end-of-life dates.

Production-readiness checklist for a service:
  • ☐ Code, pipeline and infrastructure all in Git; main branch protected; reviews required
  • ☐ CI runs lint, tests and security scans in minutes; builds one versioned artifact
  • ☐ Safe rollout (rolling/canary), health checks, and a tested, one-command rollback
  • ☐ Infrastructure as code with remote locked state; policy checks in PRs
  • ☐ Dashboards for golden signals; at least one SLO; alerts tied to user impact with runbooks
  • ☐ Centralised structured logs and traces with request IDs and version info
  • ☐ Secrets in a manager; least-privilege identities; CI actions pinned; read-only tokens by default
  • ☐ Backups with tested restores; RPO/RTO defined; on-call and incident process documented
  • ☐ Cost tags and budgets; dependency/image scanning and SBOMs; end-of-life dates tracked

53 Quick Quiz 🎯

Click each question to reveal the answer.

Q1: In one sentence, what is DevOps?

Developers and operations sharing ownership, using automation and fast feedback to deliver software quickly, safely and repeatedly.

Q2: What are the two groups of DORA metrics?

Throughput (change lead time, deployment frequency, failed-deployment recovery time) and instability (change fail rate, deployment rework rate).

Q3: Which strategy sends a small slice of users to the new version first?

A canary release.

Q4: What does GitOps change about deployment?

Git holds the desired state and an agent in the cluster pulls and reconciles — deploy by merging, roll back by reverting, and drift is corrected automatically.

Q5: A 99.9% SLO over 30 days allows roughly how much downtime?

About 43 minutes.

Q6: Why pin GitHub Actions to a commit SHA?

Tags can be moved to malicious code; a full commit SHA is immutable, so you run exactly what you reviewed.

Q7: Which Kubernetes object keeps N identical Pods running and handles rolling updates?

A Deployment.

Q8: What is the safest first role for an AI agent in operations?

Read-only investigation and summarising, with human approval and least-privilege access before any write or destructive actions.
