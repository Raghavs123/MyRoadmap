1 What is System Design (HLD)?

High-Level Design (HLD) = deciding the big pieces of a software system (servers, databases, caches, queues, networks), how they talk to each other, and how the whole thing keeps working when millions of people use it and when parts break.
Daily-life picture: Planning a city, not building one house. You decide where the roads, the water supply, the hospitals and the fire stations go, and how many people each can serve — before any builder lays a brick. A house plan (low-level design) shows where each wall and socket goes; a city plan (high-level design) shows how everything fits together and what happens when a road is closed.

Question"What are the parts and how do they connect and scale?""How is each part written inside?"

What makes a system "big"?

👥 Many users

Millions of people at the same time. One computer can't serve them all.

📦 Lots of data

More data than one disk holds, and too much to scan quickly.

🌍 Spread out

Users all over the world; the speed of light matters (Section 11).

💥 Things break

With thousands of machines, something is always failing. The design must expect it.

🔄 Always changing

New features every week, traffic spikes on sale days, software upgrades without downtime.

💰 Limited money

Every extra server costs money; good designs are efficient, not just big.

The core skill: every design decision trades one good thing for another — speed vs consistency, cost vs reliability, simplicity vs flexibility. A strong designer says why they chose something and what they gave up. That's what interviews (and real architecture reviews) test. For the code-level side, see the LLD guide when it is available; for the building blocks' foundations see DevOps, Linux and Python.

4 Back-of-the-Envelope Estimation

Picture: Before cooking for a wedding, you estimate: "500 guests × 2 plates × 150 g rice ≈ 150 kg". You don't need exactness — you need to know whether to buy 15 kg or 150 kg. System design estimates do the same: are we building for 100 requests per second or 1,000,000?

The recipe

  1. Users → daily active users (DAU).
  2. Actions per user per day → total requests per day.
  3. Divide by 86,400 seconds → average requests per second (QPS). Multiply by 2–5× for peak.
  4. Multiply by size per item → data per day → ×365×years → total storage (×3 if you keep three copies).
  5. Requests × size → bandwidth.
  6. Round aggressively. Use powers of 10. State your assumptions out loud.
A Twitter-like service: QPS, storage and bandwidth (run for real) 

# Back-of-the-envelope estimate for a Twitter-like service (ALL numbers are assumptions you can change)
dau = 200_000_000                 # daily active users
posts_per_user_per_day = 0.5      # average posts a user writes
reads_per_user_per_day = 100      # timeline views/tweets read per user
avg_post_bytes = 300              # text + metadata
media_share = 0.2                 # share of posts with a photo/video
avg_media_bytes = 500_000         # 0.5 MB average attachment
peak_factor = 3                   # peak traffic vs average
SECONDS = 86_400

writes_per_day = dau * posts_per_user_per_day
reads_per_day = dau * reads_per_user_per_day
write_qps = writes_per_day / SECONDS
read_qps = reads_per_day / SECONDS
print("writes/day: %s  -> avg %.0f writes/s, peak %.0f/s" % (format(int(writes_per_day), ","), write_qps, write_qps * peak_factor))
print("reads/day : %s -> avg %.0f reads/s,  peak %.0f/s" % (format(int(reads_per_day), ","), read_qps, read_qps * peak_factor))
print("read:write ratio = %d : 1  (a read-heavy system -> caching matters)" % round(read_qps / write_qps))

text_per_day = writes_per_day * avg_post_bytes
media_per_day = writes_per_day * media_share * avg_media_bytes
tb = 1e12
print("\nnew text per day : %.2f TB" % (text_per_day / tb))
print("new media per day: %.1f TB" % (media_per_day / tb))
print("5-year storage   : %.0f TB (text) + %.1f PB (media)" % (text_per_day * 365 * 5 / tb, media_per_day * 365 * 5 / 1e15))

egress = read_qps * 20 * avg_post_bytes * 8 / 1e9    # 20 posts per read, text only, bits/s
print("\ntext egress at average load: about %.1f Gbit/s (media goes through a CDN, which is why we need one)" % egress)

# reads/day : 20,000,000,000 -> avg 231481 reads/s,  peak 694444/s
# read:write ratio = 200 : 1  (a read-heavy system -> caching matters)

Reading it: 100 million posts a day sounds huge but is only about 1,157 writes per second on average. Reads are 200 times more frequent (231,481 per second) — so this is a read-heavy system and caching will matter more than write speed. Text is tiny (0.03 TB a day) but media is 10 TB a day, which adds up to about 18 petabytes in 5 years — media must live in cheap object storage behind a CDN, not in the main database. Notice how a few lines of arithmetic already decided three architecture choices.

The key trick: make servers stateless

Picture: A restaurant where every waiter remembers your order in their head: if "your" waiter is on break, nobody can serve you. If orders are written on a shared ticket system instead, any waiter can pick up. A stateless server keeps no user data in its own memory; state lives in a shared database or cache, so any server can handle any request and you can add or kill servers freely.
Where state can liveNotes
Browser (cookies, tokens)Signed tokens (JWT, Section 45) let servers stay stateless
Shared cache (Redis/Valkey)Sessions and hot data; fast
DatabaseThe source of truth

Typical bottlenecks, in the order you meet them

  1. One web server's CPU → add more (stateless) servers behind a load balancer.
  2. The database's reads → add caching and read replicas.
  3. The database's writes → shard (split) the data.
  4. Slow or spiky work → move it to queues and background workers.
  5. Users far away → CDN and multiple regions.
  6. Operational pain → monitoring, automation, better deployment.

Why the average lies: percentiles

Most requests are quick and a few are very slow. The average hides the slow ones. So we report percentiles: p50 (median) = half of requests are faster; p99 = 99% are faster, 1% are slower.

100,000 simulated requests, and the fan-out surprise (run for real) 

import random, statistics
random.seed(7)

# Most requests are fast, a few are slow (a "long tail"): model with a log-normal distribution
lat = sorted(random.lognormvariate(3.0, 0.7) for _ in range(100_000))     # milliseconds
pct = lambda p: lat[int(len(lat) * p / 100) - 1]
print("requests: 100,000")
print("mean = %.1f ms | p50 = %.1f | p90 = %.1f | p95 = %.1f | p99 = %.1f | p99.9 = %.1f | max = %.0f" % (
    statistics.mean(lat), pct(50), pct(90), pct(95), pct(99), pct(99.9), lat[-1]))
print("-> the AVERAGE hides the slow tail; users who hit it are unhappy. Always look at p95/p99.")

print("\nTail latency at scale: a page that calls N backends in parallel is as slow as its SLOWEST call")
p99 = pct(99)
for n in (1, 10, 50, 100):
    prob_slow = 1 - 0.99 ** n
    print("  fan-out %3d: chance the page sees at least one 'p99-slow' call = %5.1f%%" % (n, prob_slow * 100))
trials = 20_000
for n in (1, 10, 100):
    worst = sorted(max(random.choice(lat) for _ in range(n)) for _ in range(trials // n * 5))
    print("  simulated page latency (max of %3d calls): median %.0f ms, p95 %.0f ms" % (n, worst[len(worst)//2], worst[int(len(worst)*0.95)]))

# ----- Output (real run) -----
# requests: 100,000
# mean = 25.7 ms | p50 = 20.1 | p90 = 49.4 | p95 = 64.0 | p99 = 102.5 | p99.9 = 176.1 | max = 396

#
# Tail latency at scale: a page that calls N backends in parallel is as slow as its SLOWEST call
#   fan-out   1: chance the page sees at least one 'p99-slow' call =   1.0%

The average is 25.7 ms, the median 20.1 ms — but 1 in 100 requests takes 102 ms or more, and the worst took almost 400 ms. Tail latency at scale: a web page that calls 100 backend services in parallel is only as fast as the slowest one. If each call is "slow" 1% of the time, then with 100 calls the chance that at least one is slow is 63%! The simulation confirms it: the median page time rises from 20 ms (1 call) to 114 ms (max of 100 calls). That is why big systems fight hard for p99, not the average (hedged requests, timeouts, fewer fan-outs).

print("%-10s %-14s %-16s %-14s" % ("availability", "downtime/year", "downtime/month", "downtime/day"))
for nines in ("99", "99.9", "99.95", "99.99", "99.999"):

#   3 services at 99.9% each in series  -> 99.700%  (worse than any single one)
# Components in PARALLEL (any one is enough): failure probabilities multiply
#   1 redundant copies of a 99% service -> 99.0000%
#   2 redundant copies of a 99% service -> 99.9900%
#   3 redundant copies of a 99% service -> 99.9999%

"Three nines" (99.9%) still allows 8.8 hours of downtime a year; "five nines" allows only 5.3 minutes. In a chain (every part must work) availabilities multiply, so three 99.9% services give only 99.7% — the chain is weaker than any link. In parallel (any one copy is enough) the failure chances multiply: two 99%-available copies give 99.99%, three give 99.9999%. This is why we add redundancy — and why every extra required dependency lowers availability.

Little's Law — a one-line tool

How many requests are "in flight"? (run for real) 

# Little's law:  L = lambda x W   (items in the system = arrival rate x time each item spends there)
def concurrency(rate_per_s, latency_s):
    return rate_per_s * latency_s

print("A service gets 2,000 requests/s and each takes 150 ms:")
print("  requests being handled at any moment L = 2000 x 0.150 = %.0f" % concurrency(2000, 0.150))
print("  with 50 worker threads we could only handle %.0f req/s (50 / 0.150)" % (50 / 0.150))
print("  threads needed (no queueing) = %.0f" % concurrency(2000, 0.150))

print("\nIf latency doubles to 300 ms (a slow dependency), the same traffic needs twice the concurrency:")
print("  L = 2000 x 0.300 = %.0f   <- this is how slow dependencies exhaust thread pools" % concurrency(2000, 0.300))

print("\nDatabase connection pool sizing example: 500 queries/s x 20 ms = %.0f connections busy on average" % concurrency(500, 0.020))

# ----- Output (real run) -----
# A service gets 2,000 requests/s and each takes 150 ms:
#   requests being handled at any moment L = 2000 x 0.150 = 300
#   with 50 worker threads we could only handle 333 req/s (50 / 0.150)
#   threads needed (no queueing) = 300
#
# If latency doubles to 300 ms (a slow dependency), the same traffic needs twice the concurrency:
#   L = 2000 x 0.300 = 600   <- this is how slow dependencies exhaust thread pools
#
# Database connection pool sizing example: 500 queries/s x 20 ms = 10 connections busy on average

L = λ × W: the number of items in a system equals the arrival rate times the time each spends there. At 2,000 requests/s and 150 ms each, 300 requests are being handled at any moment — so you need at least 300 workers/connections. If a slow dependency makes each request take 300 ms, the same traffic needs twice the concurrency — this is how a slow downstream service exhausts your thread pool and takes you down too.

7 Why Busy Servers Get Slow (Queueing)

Picture: A single checkout counter at a shop. When customers arrive randomly, even if the cashier is only 50% busy, sometimes two arrive together and one waits. As the cashier gets busier (90%… 95%…), queues grow dramatically, and a little extra traffic creates a huge wait. Servers behave exactly like that.
One server, random arrivals: latency vs utilisation (run for real) 

import random
random.seed(3)

# One server, random (Poisson) arrivals, random (exponential) service times: the M/M/1 queue.
def simulate(rho, n=200_000, service_ms=10.0):
    arrival_rate = rho / service_ms
    t = 0.0; free_at = 0.0; waits = []
    for _ in range(n):
        t += random.expovariate(arrival_rate)
        start = max(t, free_at)
        s = random.expovariate(1 / service_ms)
        free_at = start + s
        waits.append(free_at - t)                # total time in system = wait + service
    waits.sort()
    return sum(waits) / n, waits[int(n * 0.99)]

print("service time averages 10 ms. How does response time grow as the server gets busier?")
print("%-12s %-16s %-16s %-18s" % ("utilisation", "mean latency", "p99 latency", "theory mean 10/(1-rho)"))
for rho in (0.3, 0.5, 0.7, 0.8, 0.9, 0.95, 0.98):
    mean, p99 = simulate(rho)
    print("%-12s %-16s %-16s %-18s" % ("%d%%" % (rho * 100), "%.0f ms" % mean, "%.0f ms" % p99, "%.0f ms" % (10 / (1 - rho))))
print("Latency does not grow in a straight line: past ~80% utilisation it shoots up. Keep headroom (aim for 50-70%).")

# ----- Output (real run) -----

The average service time is 10 ms. At 50% utilisation, a request takes about 20 ms in total; at 80%, 51 ms; at 90%, 96 ms; at 98%, 453 ms — and the slowest 1% (p99) take over 2 seconds. The simulated averages match the textbook formula service time ÷ (1 − utilisation). The lesson: latency is not linear — beyond about 70–80% utilisation it explodes. That is why you provision servers to run at 50–70% on average, not 95%, and why you must shed load before collapse (Section 35).

Algorithms — and what they really do

Five strategies on 1,000 requests, including slow requests (run for real) 

import random, itertools, hashlib
random.seed(1)

servers = ["A", "B", "C"]
weights = {"A": 5, "B": 3, "C": 2}                 # A is twice as big as C...
requests = 1000

def show(name, counts):
    print("%-26s %s" % (name, "  ".join("%s=%4d" % (s, counts[s]) for s in servers)))

# 1) Round robin
rr = itertools.cycle(servers); c = {s: 0 for s in servers}
for _ in range(requests): c[next(rr)] += 1
show("round robin", c)

# 2) Weighted round robin
pool = [s for s in servers for _ in range(weights[s])]; wr = itertools.cycle(pool); c = {s: 0 for s in servers}
for _ in range(requests): c[next(wr)] += 1
show("weighted round robin 5:3:2", c)

# 3) Random
c = {s: 0 for s in servers}
for _ in range(requests): c[random.choice(servers)] += 1
show("random", c)

# 4) IP hash (sticky: the same client always lands on the same server)
c = {s: 0 for s in servers}
def ip_hash(ip): return servers[int(hashlib.md5(ip.encode()).hexdigest(), 16) % len(servers)]
clients = ["10.0.%d.%d" % (i // 250, i % 250) for i in range(requests)]
for ip in clients: c[ip_hash(ip)] += 1
show("ip hash", c)
print("   same client again goes to the same server:", ip_hash("10.0.0.7") == ip_hash("10.0.0.7"))

# 5) Least connections when requests take DIFFERENT amounts of time (some are slow)
def run(strategy):
    active = {s: 0 for s in servers}; done_at = []; served = {s: 0 for s in servers}; busy_peak = 0
    rr = itertools.cycle(servers)
    for t in range(requests):
        # finish requests whose time has come
        for item in list(done_at):
            if item[0] <= t: active[item[1]] -= 1; done_at.remove(item)
        s = next(rr) if strategy == "rr" else min(servers, key=lambda x: active[x])
        dur = random.choice([1, 1, 1, 2, 40])      # most are quick, a few are very slow
        active[s] += 1; served[s] += 1; done_at.append((t + dur, s))
        busy_peak = max(busy_peak, max(active.values()))
    return served, busy_peak
for strat, name in (("rr", "round robin (slow reqs)"), ("lc", "least connections (slow)")):
    served, peak = run(strat)
    print("%-26s peak concurrent on one server: %2d   served %s" % (name, peak, served))

Round robin deals requests out in turn (334/333/333). Weighted round robin gives a bigger server a bigger share (A gets 500 because it is twice the size of C). Random is almost even. IP hash sends the same client to the same server (useful for sticky sessions or cache locality) but can be uneven. A toy LSM-tree: memtable, SSTables and compaction (run for real) 

import bisect, random
random.seed(31)

class ToyLSM:
    """Writes go to a sorted in-memory table (memtable); full memtables are flushed as immutable sorted files (SSTables); reads check newest first."""
    def __init__(self, memtable_limit=4):
        self.mem = {}; self.limit = memtable_limit; self.sstables = []; self.wal = []; self.flushes = 0
    def put(self, k, v):
        self.wal.append((k, v))                               # 1) append to the write-ahead log (sequential, durable)
        self.mem[k] = v                                       # 2) update memory
        if len(self.mem) >= self.limit:
            self.sstables.insert(0, sorted(self.mem.items())); self.mem = {}; self.wal = []; self.flushes += 1
    def get(self, k):
        if k in self.mem: return self.mem[k], "memtable"
        for i, t in enumerate(self.sstables):                 # newest SSTable first
            j = bisect.bisect_left(t, (k,))
            if j < len(t) and t[j][0] == k: return t[j][1], "sstable #%d" % i
        return None, "not found"
    def compact(self):
        merged = {}
        for t in reversed(self.sstables): merged.update(dict(t))     # older first, newer overwrite
        self.sstables = [sorted(merged.items())]

An LSM-tree (log-structured merge tree) makes writes cheap: each write is appended to a log (for durability) and put in a sorted in-memory table (the memtable). When it is full it is flushed to disk as an immutable sorted file (an SSTable) — only sequential writes. Reads check the memtable and then SSTables from newest to oldest (get('a') found the newer value 10 in the newest table). Compaction merges files in the background and discards overwritten values. Cassandra, RocksDB, LevelDB and HBase work this way (with Bloom filters to skip files, Section 38).

20 Schema Design & Denormalization

Normalization stores each fact once (users in a users table, orders refer to user_id) — no duplicates, easy updates, but reading often needs JOINs. Denormalization copies data to avoid JOINs (store the user's name inside every order) — faster reads, but updates must change many places.

Design from the queries, not just the entities

  • List the access patterns first ("get the 20 newest posts of user X", "get all orders for a customer"). In NoSQL, design the keys and tables around those queries.
  • Pick the partition key so that load is even (not a few hot values) and your common query hits one partition (Section 22).
  • Prefer immutable events and soft deletes/timestamps for data you may need to audit; plan retention (TTL) for data that must expire.
  • Avoid unbounded growth in a single row (e.g. one list that keeps growing forever); split it.
  • Store money as integers (paise/cents) or exact decimals, times as UTC timestamps, and IDs as stable surrogate keys (Section 37).
  • Plan schema migrations that don't lock tables: add columns first, backfill, switch code, then remove old columns (expand/contract).

Delay it: first use indexes, caching, read replicas and bigger machines. When you must shard, choose a key with high cardinality, even distribution, and that appears in your main queries. Many managed databases (DynamoDB, Cassandra, CockroachDB, Vitess for MySQL, Citus for PostgreSQL) automate parts of it.

23 Consistent Hashing

With hash(key) mod N, adding or removing a server changes N, so almost every key moves to a different server — a disaster for caches and databases. Consistent hashing fixes this: servers and keys are placed on the same circle (a "ring"); each key belongs to the first server clockwise from it. When a server joins, it only takes keys from its neighbour.

Fig 12 — A consistent-hash ring (schematic).
20,000 keys, 4 → 5 servers: mod-N vs consistent hashing (run for real) 

import hashlib, bisect, statistics

def h(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16)

class Ring:
    def __init__(self, nodes, vnodes=100):
        self.vnodes = vnodes; self.ring = []; self.owner = {}
        for n in nodes: self.add(n)
    def add(self, node):
        for i in range(self.vnodes):
            k = h("%s#%d" % (node, i)); self.owner[k] = node; bisect.insort(self.ring, k)
    def get(self, key):
        i = bisect.bisect(self.ring, h(key)) % len(self.ring)      # first node clockwise from the key
        return self.owner[self.ring[i]]

keys = ["user:%d" % i for i in range(20_000)]
nodes = ["n1", "n2", "n3", "n4"]

# Naive approach: node = hash(key) % number_of_nodes
mod_before = {k: nodes[h(k) % 4] for k in keys}
mod_after = {k: (nodes + ["n5"])[h(k) % 5] for k in keys}
moved_mod = sum(mod_before[k] != mod_after[k] for k in keys)

ring4 = Ring(nodes); before = {k: ring4.get(k) for k in keys}
ring5 = Ring(nodes + ["n5"]); after = {k: ring5.get(k) for k in keys}
moved_ring = sum(before[k] != after[k] for k in keys)

print("20,000 keys, going from 4 to 5 nodes:")
print("  hash %% N          : %5d keys move (%.0f%%)  <- almost everything is reshuffled" % (moved_mod, 100 * moved_mod / len(keys)))
print("  consistent hashing: %5d keys move (%.0f%%)  <- about 1/5 = the new node's fair share" % (moved_ring, 100 * moved_ring / len(keys)))

for v in (1, 10, 100, 500):

    for k in keys: load[r.get(k)] += 1
    vals = list(load.values())

Quorums: tuning consistency with numbers

With N replicas, a write waits for W acknowledgements and a read asks R replicas. If R + W > N, every read overlaps with at least one replica that has the latest write.

N = 5 replicas, different R and W (run for real, 20,000 trials each) 

import random, itertools
random.seed(4)

class Replica:
    def __init__(self, name): self.name = name; self.value = None; self.version = 0; self.up = True

def write(replicas, value, version, w):
    acks = 0
    for r in random.sample(replicas, len(replicas)):            # the write reaches replicas in some order
        if r.up:
            r.value, r.version = value, version; acks += 1
            if acks == w: break                                   # stop once W replicas acknowledged (the rest are lagging)
    return acks >= w

def read(replicas, r_count):
    live = [r for r in replicas if r.up]
    if len(live) < r_count: return None
    chosen = random.sample(live, r_count)
    return max(chosen, key=lambda x: x.version).value             # return the newest value among the R answers

def stale_rate(n, r, w, trials=20000):
    stale = 0
    for t in range(trials):
        reps = [Replica("r%d" % i) for i in range(n)]
        for rep in reps: rep.value, rep.version = "old", 1
        write(reps, "new", 2, w)
        if read(reps, r) != "new": stale += 1
    return stale / trials

Ordering events without a clock: logical and vector clocks

Which happened first? Lamport and vector clocks (run for real) 

# Without a shared clock, how do we know which event happened first? Logical clocks.
class Node:
    def __init__(self, name, n, idx): self.name, self.idx = name, idx; self.lamport = 0; self.vc = [0] * n
    def local(self): self.lamport += 1; self.vc[self.idx] += 1
    def send(self):
        self.local(); return self.lamport, list(self.vc)
    def receive(self, msg):
        l, vc = msg; self.lamport = max(self.lamport, l) + 1
        self.vc = [max(a, b) for a, b in zip(self.vc, vc)]; self.vc[self.idx] += 1

def compare(a, b):
    if a == b: return "same"
    if all(x <= y for x, y in zip(a, b)): return "happened-before"
    if all(x >= y for x, y in zip(a, b)): return "happened-after"
    return "CONCURRENT"

A, B, C = Node("A", 3, 0), Node("B", 3, 1), Node("C", 3, 2)
A.local()                      # A: event a1
m1 = A.send()                  # A sends to B
B.receive(m1)                  # B learns about A's events
B.local()                      # B: event b3
C.local()                      # C: independent event (never talked to A or B)
print("A =", A.vc, " B =", B.vc, " C =", C.vc, "(vector clocks)")
print("A's send vs B's later state :", compare(A.vc, B.vc))
print("B's state vs C's event      :", compare(B.vc, C.vc), " <- neither knew about the other: concurrent (a conflict to resolve)")

Machine clocks are never perfectly in sync, so distributed systems track causality instead. A vector clock keeps one counter per node. A's message to B made A's earlier events "happen-before" B's later state. Plain Lamport clocks give an order but can't tell "ordered" from "concurrent". Dynamo-style stores return all conflicting versions ("siblings") to be merged.

Merging without conflicts: CRDTs

A grow-only counter that always converges (run for real) 

# A G-Counter CRDT: replicas count independently (even while disconnected) and always merge to the same answer.
class GCounter:
    def __init__(self, replica_id): self.id = replica_id; self.counts = {}
    def increment(self, n=1): self.counts[self.id] = self.counts.get(self.id, 0) + n
    def value(self): return sum(self.counts.values())
    def merge(self, other):
        for k, v in other.counts.items(): self.counts[k] = max(self.counts.get(k, 0), v)      # take the max per replica: safe to repeat

mumbai, london, tokyo = GCounter("mumbai"), GCounter("london"), GCounter("tokyo")
for _ in range(5): mumbai.increment()          # 5 likes in Mumbai while the network is partitioned
for _ in range(3): london.increment()
for _ in range(2): tokyo.increment()
print("before syncing:", {r.id: r.value() for r in (mumbai, london, tokyo)})

Cache-aside, the stampede problem and its fix, write strategies, TTL jitter (run for real) 

import threading, time, random
db_calls = 0; db_lock = threading.Lock()
DB = {"price:42": 999}

def slow_db_read(key):
    global db_calls
    with db_lock: db_calls += 1
    time.sleep(0.05)                                   # a slow query
    return DB[key]

# ---- Cache-aside (lazy loading): the app checks the cache first
cache = {}
def get_cache_aside(key):
    if key in cache: return cache[key], "HIT"
    v = slow_db_read(key); cache[key] = v; return v, "MISS"
print("cache-aside:", get_cache_aside("price:42"), get_cache_aside("price:42"))

# ---- Cache stampede: a hot key expires and 50 requests all hit the database at once
def stampede(protect):
    global db_calls
    db_calls = 0; cache.clear(); locks = {}; guard = threading.Lock()
    def worker():
        if "price:42" in cache: return
        if not protect:
            cache["price:42"] = slow_db_read("price:42"); return
        with guard: lock = locks.setdefault("price:42", threading.Lock())
        with lock:                                         # "single flight": only the first request reloads
            if "price:42" not in cache: cache["price:42"] = slow_db_read("price:42")
    threads = [threading.Thread(target=worker) for _ in range(50)]
    [t.start() for t in threads]; [t.join() for t in threads]
    return db_calls
print("hot key expires, 50 simultaneous requests:")
print("  no protection : %2d database queries" % stampede(False))
print("  single-flight : %2d database query"  % stampede(True))

# ---- Write strategies
store = {}; cache = {}
def write_through(k, v): store[k] = v; cache[k] = v            # both updated together: consistent, slower writes
def write_back(k, v, dirty): cache[k] = v; dirty.add(k)       # cache first, database later: fast, risk of loss
def write_around(k, v): store[k] = v; cache.pop(k, None)      # skip the cache; next read loads it
dirty = set()

An LRU cache from scratch, and how big it needs to be (run for real) 

import random
from collections import OrderedDict

class LRU:
    def __init__(self, capacity): self.cap = capacity; self.d = OrderedDict(); self.hits = self.misses = 0
    def get(self, k):
        if k in self.d:
            self.d.move_to_end(k); self.hits += 1; return self.d[k]       # recently used goes to the back
        self.misses += 1; return None
    def put(self, k, v):
        self.d[k] = v; self.d.move_to_end(k)
        if len(self.d) > self.cap: self.d.popitem(last=False)             # evict the least recently used (front)

c = LRU(2)
c.put("a", 1); c.put("b", 2); c.get("a"); c.put("c", 3)                    # "b" is the least recently used -> evicted
print("after put a, put b, get a, put c (capacity 2): keys =", list(c.d))

# How big must a cache be? Real traffic is skewed (a few hot items get most requests): Zipf-like
random.seed(9)
N = 100_000                                          # number of distinct items
weights = [1 / (i ** 1.0) for i in range(1, N + 1)]
requests = random.choices(range(N), weights=weights, k=200_000)
print("\n200,000 requests over 100,000 items (skewed). Cache hit rate by cache size:")
for pct in (0.1, 0.5, 1, 5, 10, 20):
    cache = LRU(int(N * pct / 100))

    rate = cache.hits / (cache.hits + cache.misses)
    print("  cache holds %4.1f%% of items (%6d) -> hit rate %5.1f%%" % (pct, cache.cap, rate * 100))
print("A small cache absorbs most traffic because popularity is skewed; the gain per extra GB shrinks fast.")

def send_email(job):
    attempts[job["id"]] += 1
    if random.random() < 0.55: raise RuntimeError("SMTP timeout")      # a very flaky dependency
    processed_effects[job["id"]] += 1

def worker():
    while True:
        job = jobs.get()
        if job is None: break
        if job["id"] in done:                                           # idempotency: skip work already completed
            jobs.task_done(); continue
        try:
            send_email(job); done[job["id"]] = True

            job["tries"] += 1
            if job["tries"] >= 4: dead.append(job["id"])                # dead-letter queue after too many failures
            else: jobs.put(job)                                         # retry later
        jobs.task_done()

ts = [threading.Thread(target=worker) for _ in range(3)]

32 Streams, Pub/Sub & Kafka

A queue hands each message to one worker and then forgets it. A log/stream (Kafka-style) keeps messages for a while, in order, so many different readers can each read the whole history at their own pace; pub/sub delivers each message to every subscriber.

A tiny Kafka-like partitioned log with consumer groups (run for real) 

import hashlib

class Topic:
    """A tiny Kafka-like log: messages are appended to partitions; consumers remember an OFFSET per partition."""
    def __init__(self, partitions): self.parts = [[] for _ in range(partitions)]
    def publish(self, key, value):
        p = int(hashlib.md5(key.encode()).hexdigest(), 16) % len(self.parts)     # same key -> same partition -> ordered
        self.parts[p].append((key, value)); return p

class ConsumerGroup:
    def __init__(self, topic, members):
        self.topic = topic; self.offsets = [0] * len(topic.parts)
        self.assignment = {m: [p for p in range(len(topic.parts)) if p % len(members) == i] for i, m in enumerate(members)}
    def poll(self, member):
        out = []
        for p in self.assignment[member]:
            while self.offsets[p] < len(self.topic.parts[p]):
                out.append((p, self.topic.parts[p][self.offsets[p]])); self.offsets[p] += 1
        return out

t = Topic(partitions=4)
users = ["asha", "ben", "chitra", "dev", "esha", "farid", "gita", "hari"]
for i in range(3):
    for u in users: t.publish(u, "%s-event-%d" % (u, i))
for i, p in enumerate(t.parts):
    print("partition %d holds %2d messages; keys inside: %s" % (i, len(p), sorted({k for k, _ in p})))
asha_p = [i for i, p in enumerate(t.parts) if any(k == "asha" for k, _ in p)]
print("all of asha's events are in partition %s, in order: %s" % (asha_p, [v for k, v in t.parts[asha_p[0]] if k == "asha"]))

g = ConsumerGroup(t, ["worker-1", "worker-2"])
print("\nconsumer group with 2 workers shares the 4 partitions:", g.assignment)
for m in g.assignment: print("  %s read %d messages" % (m, len(g.poll(m))))
print("  polling again returns nothing new (offsets remember progress):", [len(g.poll(m)) for m in g.assignment])

Messages are published with a key (the user name). The key is hashed to choose a partition, so all of "asha"'s events land in the same partition (3) in order, while different users spread over four partitions (3, 9, 6 and 6 messages). A consumer group with two workers splits the partitions between them (worker-1 takes 0 and 2, worker-2 takes 1 and 3) and each remembers an offset per partition, so polling again returns nothing new. A second, separate group would start at offset 0 and see everything — that is pub/sub. Rule: within a group, at most one consumer per partition, so the partition count caps parallelism. Ordering is guaranteed only within a partition.

33 Rate Limiting

Picture: A bouncer at a club: at most 100 people per hour, so the dance floor doesn't get crushed. A rate limiter caps how many requests a user, IP or API key may make in a time window — protecting servers from abuse, bugs, scrapers and traffic floods, and sharing capacity fairly.
Fixed window, sliding log and token bucket on a boundary burst (run for real) 

import time, collections

class FakeClock:
    def __init__(self): self.t = 0.0
    def now(self): return self.t
clock = FakeClock()

class FixedWindow:
    def __init__(self, limit, window): self.limit, self.window, self.counts = limit, window, collections.Counter()
    def allow(self):
        w = int(clock.now() // self.window); self.counts[w] += 1
        return self.counts[w] <= self.limit

class SlidingLog:
    def __init__(self, limit, window): self.limit, self.window, self.log = limit, window, collections.deque()
    def allow(self):
        now = clock.now()
        while self.log and self.log[0] <= now - self.window: self.log.popleft()
        if len(self.log) < self.limit: self.log.append(now); return True
        return False

class TokenBucket:
    def __init__(self, rate, capacity): self.rate, self.cap, self.tokens, self.last = rate, capacity, capacity, 0.0
    def allow(self):
        now = clock.now(); self.tokens = min(self.cap, self.tokens + (now - self.last) * self.rate); self.last = now
        if self.tokens >= 1: self.tokens -= 1; return True
        return False

class CircuitBreaker:
    def __init__(self, fail_max=3, reset_after=5): self.fail_max, self.reset_after = fail_max, reset_after; self.state = "CLOSED"; self.fails = 0; self.opened_at = 0
    def call(self, fn, now):
        if self.state == "OPEN":
            if now - self.opened_at >= self.reset_after: self.state = "HALF-OPEN"
            else: return "rejected fast (circuit OPEN)"
        try:
            r = fn(); self.state = "CLOSED"; self.fails = 0; return r
        except ConnectionError:
            self.fails += 1
            if self.state == "HALF-OPEN" or self.fails >= self.fail_max: self.state = "OPEN"; self.opened_at = now
            return "failed"

Picture: A water pipe feeding a tank that drains slowly. If you keep pouring faster than it drains, it overflows. Good plumbing pushes back ("slow down!") or sends the overflow elsewhere. Unbounded vs bounded queues when overloaded by 20% (run for real) 

import collections

def run(queue_limit, arrivals_per_tick=12, capacity_per_tick=10, ticks=60):
    queue = collections.deque(); served = rejected = 0; latencies = []; arrival_tick = {}
    next_id = 0
    for t in range(ticks):
        for _ in range(arrivals_per_tick):
            if queue_limit is not None and len(queue) >= queue_limit: rejected += 1
            else: queue.append(next_id); arrival_tick[next_id] = t; next_id += 1
        for _ in range(capacity_per_tick):
            if queue: i = queue.popleft(); served += 1; latencies.append(t - arrival_tick[i])
    return served, rejected, len(queue), (sum(latencies) / len(latencies) if latencies else 0)

import uuid

import time, threading

EPOCH = 1_700_000_000_000          # custom epoch in ms (so the 41-bit timestamp lasts ~69 years)

class Snowflake:
    """64-bit id = 41 bits time | 10 bits machine | 12 bits sequence (4096 ids per ms per machine)"""
    def __init__(self, machine_id):
        assert 0 <= machine_id < 1024
        self.machine = machine_id; self.last_ms = -1; self.seq = 0; self.lock = threading.Lock()
    def next(self):
        with self.lock:
            ms = int(time.time() * 1000) - EPOCH
            if ms == self.last_ms:
                self.seq = (self.seq + 1) & 0xFFF
                if self.seq == 0:                       # sequence exhausted in this millisecond: wait for the next one
                    while ms <= self.last_ms: ms = int(time.time() * 1000) - EPOCH
            else: self.seq = 0
            self.last_ms = ms
            return (ms << 22) | (self.machine << 12) | self.seq

38 Bloom Filters

Picture: A club bouncer with a smudged guest list. If your name is definitely not on it, you're refused instantly. If it looks present, he says "probably" and a second check confirms. A Bloom filter answers "is X in the set?" with definitely not or probably yes, using tiny memory.
100,000 items in about 117 KB (run for real) 

import hashlib, math, random
random.seed(8)

class Bloom:
    def __init__(self, n_items, fp_rate):
        self.m = int(-n_items * math.log(fp_rate) / (math.log(2) ** 2))          # bits
        self.k = max(1, round(self.m / n_items * math.log(2)))                    # hash functions
        self.bits = bytearray(self.m // 8 + 1)
    def _positions(self, item):
        d = hashlib.sha256(item.encode()).digest()
        a = int.from_bytes(d[:8], "big"); b = int.from_bytes(d[8:16], "big") | 1
        return [(a + i * b) % self.m for i in range(self.k)]
    def add(self, item):
        for p in self._positions(item): self.bits[p // 8] |= 1 << (p % 8)
    def __contains__(self, item):
        return all(self.bits[p // 8] & (1 << (p % 8)) for p in self._positions(item))

39 Counting at Scale: HyperLogLog & Count-Min Sketch

Exact counting of billions of distinct things needs gigabytes. Probabilistic data structures give approximate answers in kilobytes.

How many distinct visitors? — HyperLogLog

Estimating unique counts with 4,096 tiny registers (run for real) 

import hashlib, math, random, sys
random.seed(15)

class HLL:
    """HyperLogLog: estimate the number of DISTINCT items using a few KB of memory."""
    def __init__(self, p=12): self.p = p; self.m = 1 << p; self.reg = [0] * self.m
    def add(self, item):
        x = int(hashlib.sha1(str(item).encode()).hexdigest(), 16) & ((1 << 64) - 1)
        idx = x >> (64 - self.p); rest = x & ((1 << (64 - self.p)) - 1)
        rank = (64 - self.p) - rest.bit_length() + 1                  # position of the first 1-bit
        self.reg[idx] = max(self.reg[idx], rank)
    def count(self):
        alpha = 0.7213 / (1 + 1.079 / self.m)
        est = alpha * self.m * self.m / sum(2.0 ** -r for r in self.reg)
        zeros = self.reg.count(0)
        if est <= 2.5 * self.m and zeros: est = self.m * math.log(self.m / zeros)           # small-range correction
        return int(est)

print("%-12s %-12s %-10s" % ("true count", "HLL estimate", "error"))
for n in (1_000, 10_000, 100_000, 500_000):
    h = HLL(); [h.add("visitor-%d" % i) for i in range(n)]
    est = h.count(); print("%-12s %-12s %5.1f%%" % (format(n, ","), format(est, ","), 100 * (est - n) / n))
print("memory: HLL uses %d registers (~%d KB with 1 byte each, ~3 KB if packed to 6 bits); an exact set of 500,000 strings needs tens of MB" % (4096, 4))
print("(one estimate can be off by a few percent; the typical error is about 1.04/sqrt(m) = %.1f%% -> good enough for 'unique visitors' dashboards; Redis offers it as PFADD/PFCOUNT." % (100 * 1.04 / math.sqrt(4096)))

What is trending? — Count-Min Sketch

Counting hashtag frequencies in a fixed-size table (run for real) 

import hashlib, random, collections
random.seed(21)

class CountMin:
    def __init__(self, width, depth=5): self.w, self.d = width, depth; self.t = [[0] * width for _ in range(depth)]
    def _idx(self, item, row): return int(hashlib.md5(("%d:%s" % (row, item)).encode()).hexdigest(), 16) % self.w
    def add(self, item):
        for r in range(self.d): self.t[r][self._idx(item, r)] += 1
    def estimate(self, item): return min(self.t[r][self._idx(item, r)] for r in range(self.d))        # never underestimates

40 Consensus & Leader Election

Several machines must agree on one fact — "who is the leader?", "what is the next log entry?" — even when messages are delayed and machines crash. This is the consensus problem; Paxos and Raft are the famous solutions. They need a majority (quorum) of nodes alive.

Picture: A class electing a monitor. Each student gets one vote per round; someone needs more than half the votes. If the monitor is absent, the class holds a new election with a new round number ("term"). If fewer than half the class is present, nobody may be elected — better no monitor than two rival monitors.
A simplified leader election and the majority rule (run for real) 

import random
random.seed(5)

class Node:
    def __init__(self, i): self.id = i; self.alive = True; self.term = 0; self.voted_for = None; self.role = "follower"

def election(nodes, who_times_out_first):
    cand = nodes[who_times_out_first]
    cand.term += 1; cand.role = "candidate"; cand.voted_for = cand.id
    votes = 1
    for n in nodes:
        if n is cand or not n.alive: continue
        if n.term < cand.term:                         # grant at most one vote per term
            n.term = cand.term; n.voted_for = cand.id; votes += 1
    alive = sum(n.alive for n in nodes); majority = len(nodes) // 2 + 1
    if votes >= majority:
        cand.role = "LEADER"
        return True, votes, majority
    cand.role = "follower"
    return False, votes, majority

41 Distributed Transactions: 2PC, Saga & Outbox

One database can do an ACID transaction. But when an order touches three services with three databases (orders, payments, stock), how do you get all-or-nothing?

Two-phase commit (2PC)

2PC: vote, then decide — and what happens when the coordinator dies (run for real) 

import random
random.seed(2)

class Participant:
    def __init__(self, name, will_vote_yes=True): self.name = name; self.vote_yes = will_vote_yes; self.state = "INIT"; self.data_committed = False
    def prepare(self):
        self.state = "PREPARED" if self.vote_yes else "ABORTED"; return self.vote_yes       # after YES it must wait for the coordinator
    def commit(self): self.state = "COMMITTED"; self.data_committed = True
    def abort(self): self.state = "ABORTED"

def two_phase_commit(parts, coordinator_crashes_after_prepare=False):
    print("  phase 1 (prepare): asking everyone...")
    votes = [p.prepare() for p in parts]
    for p, v in zip(parts, votes): print("     %-9s votes %s" % (p.name, "YES" if v else "NO"))
    if coordinator_crashes_after_prepare:
        print("  !! coordinator crashed after collecting the votes")
        print("     participants stuck in:", {p.name: p.state for p in parts}, "<- locks are held, nobody knows the decision")
        return
    if all(votes):
        print("  phase 2: COMMIT"); [p.commit() for p in parts]
    else:
        print("  phase 2: ABORT"); [p.abort() for p in parts]
    print("     final:", {p.name: p.state for p in parts})

print("1) all vote yes")
two_phase_commit([Participant("orders"), Participant("payments"), Participant("stock")])
print("2) one participant votes no")
two_phase_commit([Participant("orders"), Participant("payments", False), Participant("stock")])
print("3) the coordinator dies between the phases (the blocking problem)")

Saga: a chain of local transactions with undo steps

An order saga with compensating actions (run for real) 

class StepFailed(Exception): pass

def run_saga(steps, fail_at=None):
    done = []
    for i, (name, action, compensate) in enumerate(steps):
        try:
            if fail_at == name: raise StepFailed(name)
            print("   do      :", action); done.append((name, compensate))
        except StepFailed:
            print("   FAILED  :", name)
            for n, comp in reversed(done):
                print("   undo    :", comp)                       # compensating actions, in reverse order
            return "ROLLED BACK"
    return "COMPLETED"

    ("create_order", "create order #1001 (PENDING)", "cancel order #1001"),
    ("reserve_stock", "reserve 1 x laptop in inventory", "release the reserved laptop"),
    ("charge_card", "charge Rs 60,000 to the card", "refund Rs 60,000"),
    ("ship", "ask warehouse to ship", "cancel shipment"),
]
print("Saga 1: everything works")

print("   result:", run_saga(order_steps, fail_at="charge_card"))

Outbox pattern: don't lose the event

Saving the order and publishing the event atomically (run for real) 

import sqlite3, json

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, item TEXT)")
db.execute("CREATE TABLE outbox (id INTEGER PRIMARY KEY AUTOINCREMENT, topic TEXT, payload TEXT, sent INTEGER DEFAULT 0)")
broker = []                                          # pretend message broker

def place_order_bad(item, broker_up):
    db.execute("INSERT INTO orders (item) VALUES (?)", (item,)); db.commit()       # 1) save to DB
    if not broker_up: raise ConnectionError("broker down")                          # 2) crash before publishing -> lost event!
    broker.append(("order.created", item))

def place_order_outbox(item):
    with db:                                           # ONE transaction: order row + event row commit together (or neither)
        cur = db.execute("INSERT INTO orders (item) VALUES (?)", (item,))
        db.execute("INSERT INTO outbox (topic, payload) VALUES (?, ?)", ("order.created", json.dumps({"id": cur.lastrowid, "item": item})))

def relay(broker_up):                                  # a background process publishes unsent outbox rows (at-least-once)
    if not broker_up: return 0
    rows = db.execute("SELECT id, topic, payload FROM outbox WHERE sent = 0").fetchall()
    for i, topic, payload in rows:
        broker.append((topic, payload)); db.execute("UPDATE outbox SET sent = 1 WHERE id = ?", (i,))
    db.commit(); return len(rows)

try: place_order_bad("book", broker_up=False)
except ConnectionError: pass
print("naive: orders in DB = %d, events published = %d  <- the order exists but nobody was told" % (db.execute("SELECT COUNT(*) FROM orders").fetchone()[0], len(broker)))

place_order_outbox("laptop"); place_order_outbox("phone")

print("relay while broker down publishes:", relay(False))
print("broker recovers, relay publishes:", relay(True), "->", [b[1] for b in broker])
print("Consumers must be idempotent (the relay may publish twice after a crash). This is how services keep DB and events consistent without 2PC.")

Event sourcing: store the events, derive the state (run for real) 

# Event sourcing: store what HAPPENED (immutable events), derive the current state by replaying them.
events = []
def record(kind, amount=0): events.append({"seq": len(events) + 1, "type": kind, "amount": amount})

def replay(upto=None):
    balance = 0; state = "open"
    for e in events[:upto]:
        if e["type"] == "deposited": balance += e["amount"]
        elif e["type"] == "withdrawn": balance -= e["amount"]
        elif e["type"] == "frozen": state = "frozen"
    return {"balance": balance, "state": state}

# CQRS idea: the WRITE side appends events; the READ side builds query-friendly views (tables, search indexes) from the same events.
# Great for: audit trails, finance, undo, rebuilding views. Costs: more complexity, eventual consistency, event schema evolution.

Instead of storing "balance = 250", we store what happened (deposited 500, deposited 250, withdrawn 100, withdrawn 400, frozen) and compute the state by replaying the events: balance 250, state frozen. Replaying only the first three events gives the state at that earlier time — a free audit trail and time travel. Snapshots avoid replaying a long history. CQRS (command-query responsibility segregation) separates the write model (append events) from read models built from them (tables, search indexes, caches) — each optimised for its job. Costs: more moving parts, eventual consistency between write and read sides, and event schemas that must evolve carefully.

43 Gossip & Failure Detection

Picture: Rumours in a school. One student tells one friend; next break both tell new friends… soon everyone knows, with no announcer. In gossip protocols, each node periodically shares its news (who is alive, what data changed) with a few random peers.
How fast does news spread? (run for real) 

import random, math
random.seed(12)

def rounds_to_spread(n, fanout=1, trials=200):
    results = []
    for _ in range(trials):
        informed = {0}; rounds = 0
        while len(informed) < n:
            new = set()
            for node in informed:
                for _ in range(fanout): new.add(random.randrange(n))        # each informed node tells `fanout` random peers
            informed |= new; rounds += 1
        results.append(rounds)
    return sum(results) / trials

print("gossip: each round, every node that knows the news tells 1 random peer. Rounds until EVERYONE knows:")
print("%-10s %-14s %-12s" % ("nodes", "avg rounds", "log2(n)"))
for n in (10, 100, 1000, 10000):
    print("%-10s %-14.1f %-12.1f" % (format(n, ","), rounds_to_spread(n, trials=100 if n <= 1000 else 30), math.log2(n)))
print("spreading time grows like log(n): 10,000 nodes need only a few more rounds than 1,000 -> great for membership and failure detection (Cassandra, Consul).")

Tokens: how a login can be verified without a database lookup

Create, verify and attack a signed token (run for real) 

import base64, hashlib, hmac, json, time

SECRET = b"server-side-secret-never-sent-to-clients"
b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b"=").decode()
unb64 = lambda s: base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

def sign(payload, ttl=3600):
    header = b64(json.dumps({"alg": "HS256", "typ": "JWT"}).encode())
    body = b64(json.dumps({**payload, "exp": int(time.time()) + ttl}).encode())
    sig = b64(hmac.new(SECRET, ("%s.%s" % (header, body)).encode(), hashlib.sha256).digest())
    return "%s.%s.%s" % (header, body, sig)

def verify(token):
    try:
        header, body, sig = token.split(".")
        good = b64(hmac.new(SECRET, ("%s.%s" % (header, body)).encode(), hashlib.sha256).digest())
        if not hmac.compare_digest(sig, good): return "REJECTED: signature does not match (token was tampered with)"
        payload = json.loads(unb64(body))
        if payload["exp"] < time.time(): return "REJECTED: expired"
        return "OK: " + json.dumps({k: v for k, v in payload.items() if k != "exp"})
    except Exception as e:
        return "REJECTED: malformed (%s)" % type(e).__name__

t = sign({"sub": "asha", "role": "user"})
print("token (3 parts: header . payload . signature):\n ", t[:50] + "..." + t[-12:])
print("payload anyone can read (it is only encoded, NOT encrypted):", json.loads(unb64(t.split(".")[1])))
print("verify genuine token ->", verify(t))
h, b, s = t.split(".")
forged = "%s.%s.%s" % (h, b64(json.dumps({"sub": "asha", "role": "admin", "exp": 9999999999}).encode()), s)
print("verify forged 'admin' token ->", verify(forged))
print("verify expired token ->", verify(sign({"sub": "asha"}, ttl=-10)))
print("Stateless auth scales (no session store lookup) but tokens can't be revoked early -> keep them short-lived + refresh tokens.")

A JWT has three dot-separated parts: header, payload and signature, signed with a secret only the server knows. The payload (sub, role, expiry) is merely encoded, not encrypted — anyone can read it, so never put secrets in it. The genuine token verifies. When an attacker edits the payload to say role: admin but keeps the old signature, verification rejects it because the signature no longer matches. An expired token is rejected too. Benefits: servers stay stateless and need no session lookup. Costs: a token cannot be revoked before it expires (so keep access tokens short — minutes — and use refresh tokens, or maintain a small deny-list), and the signing key must be protected and rotated.

Passwords: make guessing expensive

pw = b"correct horse battery staple"

def timed(fn, reps=1):

    for _ in range(reps): r = fn()
    return r, (time.perf_counter() - t) * 1000 / reps

A single SHA-256 takes under a thousandth of a millisecond, so an attacker with a stolen database can try astronomical numbers of guesses. scrypt (tuned here to about 50 ms) and PBKDF2 (about 250 ms) are deliberately slow — making each guess tens of thousands of times more expensive — and scrypt also needs lots of memory, which blunts GPUs. A random salt per user makes identical passwords produce different hashes (defeating precomputed tables), and hmac.compare_digest compares in constant time. Use Argon2id, scrypt or bcrypt, store the algorithm, parameters, salt and hash, and add multi-factor authentication for important accounts.

Defence in depth: assume any single layer fails. Put authentication at the gateway and authorization in each service; encrypt in transit and at rest; limit blast radius with network segmentation and per-service credentials; and keep dependencies patched (supply-chain attacks target libraries and build pipelines — see the DevOps guide).

Capacity planning answers: "How many servers (and how much database, cache, bandwidth) do we need now, at peak, and next year?" Combine the estimates of Section 4 with measured data.

50 Design a URL Shortener (like bit.ly)

Picture: A cloakroom ticket: you hand in a big, heavy coat (a very long URL) and get a tiny numbered ticket (the short code). Show the ticket later and you get the coat back.

1. Requirements

FunctionalNon-functional
  • Create a short link for a long URL
  • Opening the short link redirects to the long URL
  • Optional: custom alias, expiry date, click analytics
  • Redirects must be very fast (< 100 ms) and highly available (99.99%)

  • A 7-character base62 code gives 627 ≈ 3.5 trillion combinations — plenty (Section 37)

5. Architecture

Fig 20 — URL shortener architecture (redirect path and analytics path).
  • Write: generate a unique code (counter → base62, or hash + check), store (code → URL), return the short link.
  • Read: check cache (hit ≈ 90%+, popular links) → on miss read the store → cache it → reply 302 with Location.
  • Analytics: don't count clicks in the request path: publish an event to a queue; workers aggregate later.

6. Deep dives

Generating codes

Options: (a) counter + base62: unique, short, but sequential (guessable) and needs a distributed counter — give each app server a block of numbers; (b) hash of the URL, take the first 7 characters: collisions happen (shown below), so use a unique constraint and retry with a salt; (c) random 7 characters with a uniqueness check; (d) a Snowflake-style id converted to base62.

302 vs 301

301 (permanent) lets browsers and CDNs cache the redirect — less load but you stop seeing clicks. 302 (temporary) means every visit reaches you, so analytics and link changes work. Most shorteners use 302 (or 301 with analytics at the edge).

Scaling

Reads dominate: cache hot codes, put a CDN in front, add read replicas or shard by code with consistent hashing. Writes are tiny (40/s) — the main need is availability, not write throughput.

A working shortener: HTTP server, SQLite store, cache, 302 redirects and click counting (run for real) 

import sqlite3, threading, http.server, urllib.request, urllib.error, json, time

ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
def b62(n):
    s = ""
    while n: n, r = divmod(n, 62); s = ALPHABET[r] + s
    return s or "0"

db = sqlite3.connect(":memory:", check_same_thread=False)
db.execute("CREATE TABLE urls (id INTEGER PRIMARY KEY AUTOINCREMENT, code TEXT UNIQUE, long_url TEXT NOT NULL, clicks INTEGER DEFAULT 0)")
lock = threading.Lock(); cache = {}
BASE = 100_000_000                              # start the counter high so codes are at least 5 characters

class Handler(http.server.BaseHTTPRequestHandler):
    def log_message(self, *a): pass
    def _send(self, code, body="", headers=None):
        self.send_response(code)
        for k, v in (headers or {}).items(): self.send_header(k, v)
        self.end_headers(); self.wfile.write(body.encode())
    def do_POST(self):                          # POST /shorten  {"url": "..."}
        n = int(self.headers.get("Content-Length", 0)); data = json.loads(self.rfile.read(n))
        if not data.get("url", "").startswith(("http://", "https://")): return self._send(400, "invalid url")
        with lock:
            cur = db.execute("INSERT INTO urls (code, long_url) VALUES ('', ?)", (data["url"],))
            code = b62(BASE + cur.lastrowid); db.execute("UPDATE urls SET code = ? WHERE id = ?", (code, cur.lastrowid)); db.commit()
        self._send(201, json.dumps({"short": "http://localhost:%d/%s" % (self.server.server_port, code), "code": code}))
    def do_GET(self):                           # GET /<code> -> 302 redirect
        code = self.path.strip("/")
        if code in cache: url, src = cache[code], "cache"
        else:
            with lock: row = db.execute("SELECT long_url FROM urls WHERE code = ?", (code,)).fetchone()
            if not row: return self._send(404, "not found")
            url, src = row[0], "db"; cache[code] = url
        with lock: db.execute("UPDATE urls SET clicks = clicks + 1 WHERE code = ?", (code,)); db.commit()
        self._send(302, "", {"Location": url, "X-Served-From": src})

server = http.server.ThreadingHTTPServer(("127.0.0.1", 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
port = server.server_port

class NoRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, *a, **k): return None
opener = urllib.request.build_opener(NoRedirect)

def post(url):
    req = urllib.request.Request("http://127.0.0.1:%d/shorten" % port, data=json.dumps({"url": url}).encode(), headers={"Content-Type": "application/json"})
    return json.loads(urllib.request.urlopen(req).read())

7. Trade-offs & bottlenecks

  • Sequential codes are guessable → use random/hashed codes for private links, and rate-limit lookups to deter scanning.
  • Custom aliases need a uniqueness check and reserved-word protection.
  • Expiry: store expires_at, check on read, and clean up with a background job (return 410 Gone).
  • Abuse (phishing links): scan URLs against safe-browsing lists, allow reporting, rate-limit creation per user.

  • Return 429 with Retry-After when exceeded

6. Deep dives

Which algorithm?

Token bucket is the usual choice: tiny state, allows bursts, smooth average rate. Use a sliding-window counter when you need stricter fairness. Fixed windows can allow 2× bursts at the boundary (see Section 33's demo).

Atomicity across servers

Local + global limits

To avoid a network call on every request, each gateway can keep a small local allowance and sync with the shared store periodically (approximate but cheap). Strict limits (billing, security) use the shared store on every call.

Failure behaviour

If the limiter store is down: fail-open (allow everything — keep the site up, risk overload) or fail-closed (block — protect the backend). Choose per endpoint: login attempts → closed; product browsing → open.

import time, collections

class FakeClock:
    def __init__(self): self.t = 0.0
    def now(self): return self.t
clock = FakeClock()

class FixedWindow:
    def __init__(self, limit, window): self.limit, self.window, self.counts = limit, window, collections.Counter()
    def allow(self):
        w = int(clock.now() // self.window); self.counts[w] += 1
        return self.counts[w] <= self.limit

class SlidingLog:
    def __init__(self, limit, window): self.limit, self.window, self.log = limit, window, collections.deque()
    def allow(self):
        now = clock.now()
        while self.log and self.log[0] <= now - self.window: self.log.popleft()
        if len(self.log) < self.limit: self.log.append(now); return True
        return False

class TokenBucket:
    def __init__(self, rate, capacity): self.rate, self.cap, self.tokens, self.last = rate, capacity, capacity, 0.0
    def allow(self):
        now = clock.now(); self.tokens = min(self.cap, self.tokens + (now - self.last) * self.rate); self.last = now
        if self.tokens >= 1: self.tokens -= 1; return True
        return False

        clock.t = t; allowed += limiter.allow()
    return allowed

52 Design a Distributed Key-Value Store (Dynamo-style)

Picture: A huge wall of lockers spread over several buildings. A rule tells you which building holds each locker (consistent hashing), three buildings keep a copy of each locker's contents (replication), and a locker counts as changed once two of the three confirm (quorum).

1. Requirements

FunctionalNon-functional
  • put(key, value) and get(key)
  • Scales to many machines; survives machine failures
  • Tunable consistency (read and write quorums)
  • Highly available for reads and writes
  • Low latency (single-digit ms)
  • Eventual consistency by default, stronger with quorums

2. Estimates (assumptions)

  • 1 billion keys × 1 KB = 1 TB; ×3 replicas = 3 TB → ~30 nodes with 100 GB each (headroom)
  • 1 million operations/s across 30 nodes ≈ 33,000/s per node — comfortable for an in-memory/LSM engine

3. API

put(key, value, W=2)  →  ok | error
get(key, R=2)           →  value (newest by version) | not_found
delete(key)             →  writes a tombstone (so deletion replicates too)

4. Data model

PieceDetails
PartitioningConsistent-hash ring with virtual nodes; each key belongs to N consecutive distinct nodes (the preference list)
Per-node storageLSM-tree engine (write-ahead log + memtable + SSTables, Section 19)
VersionsVector clocks or timestamps per value for conflict detection

5. Architecture

Fig 22 — A Dynamo-style store: any node coordinates; N replicas; quorum acknowledgement.
  • Write: the coordinator finds the key's N replicas on the ring, sends the write to all, and replies ok after W acknowledge.
  • Read: ask R replicas, return the newest version; if replicas disagree, fix the stale ones (read repair).
  • Failure: if a replica is down, another node stores a hint and hands the data over when it returns (hinted handoff); background anti-entropy (Merkle trees) repairs differences.

6. Deep dives

Partitioning and rebalancing

Consistent hashing with virtual nodes (Section 23): adding a node moves only its share of keys, and a failed node's load spreads over all the others.

Quorums and consistency

With N=3: W=2, R=2 gives R+W > N so reads see the latest write and one node can be down. W=1/R=1 is fastest but may return stale data. W=3 maximises durability but fails if any replica is down (Section 25).

Conflicts

Two clients write the same key concurrently during a partition → versions diverge. Detect with vector clocks and either keep both (siblings) for the application to merge, or use last-write-wins (simple, can silently drop an update), or use CRDTs.

Failure detection and membership

Nodes gossip membership and use a failure detector with suspicion levels (Section 43). No single master → no single point of failure.

A miniature version: consistent hashing + 3 replicas + quorum reads/writes + node failures (run for real) 

import hashlib, bisect, random
random.seed(10)

def h(s): return int(hashlib.md5(s.encode()).hexdigest(), 16)

class Node:
    def __init__(self, name): self.name = name; self.store = {}; self.up = True

class Cluster:
    """Consistent-hash ring + N replicas per key + quorum reads/writes (R + W > N)."""
    def __init__(self, names, n=3, r=2, w=2, vnodes=64):
        self.nodes = {x: Node(x) for x in names}; self.N, self.R, self.W = n, r, w; self.ring = []; self.owner = {}
        for x in names:
            for i in range(vnodes): k = h("%s#%d" % (x, i)); self.owner[k] = x; bisect.insort(self.ring, k)
        self.clock = 0
    def replicas(self, key):
        i = bisect.bisect(self.ring, h(key)); out = []
        while len(out) < self.N:
            node = self.owner[self.ring[i % len(self.ring)]]
            if node not in out: out.append(node)
            i += 1
        return out
    def put(self, key, value):
        self.clock += 1; acks = 0
        for name in self.replicas(key):
            if self.nodes[name].up: self.nodes[name].store[key] = (self.clock, value); acks += 1
        return acks >= self.W
    def get(self, key):
        answers = [self.nodes[n].store.get(key) for n in self.replicas(key) if self.nodes[n].up]
        if len(answers) < self.R: return "UNAVAILABLE (fewer than R replicas up)"
        answers = [a for a in answers if a]
        return max(answers)[1] if answers else None

ok = sum(c.get(k) == "v1" for k in keys)

w_ok = sum(c.put(k, "v2") for k in keys)
print("writes accepted with B down: %d/1000" % w_ok)

c.nodes["B"].up = True

fresh_reads = sum(c.get(k) == "v2" for k in keys)

7. Trade-offs & bottlenecks

  • Availability vs consistency is a per-request knob (R, W) — document the defaults and let callers choose.
  • Hot keys overload their replicas: add caching in front or split the key.
  • Large values hurt: store big blobs in object storage and keep pointers here.
  • Operational cost: repairs, compaction, rebalancing and monitoring are real work — managed services (DynamoDB, Cassandra-as-a-service) remove much of it.
  • Secondary indexes and range queries are limited — design keys around your queries.

Freshness and trending

A nightly rebuild is stale for breaking news. Add a small real-time layer (stream processing with a Count-Min sketch, Section 39) for trending queries and merge it with the static results.

class Trie:
    def __init__(self): self.children = {}; self.count = 0; self.top = []          # top = cached best completions at this prefix
class Autocomplete:
    def __init__(self, k=3): self.root = Trie(); self.k = k
    def add(self, word, count):
        node = self.root
        for ch in word:
            node = node.children.setdefault(ch, Trie())
            node.top.append((count, word)); node.top = heapq.nlargest(self.k, set(node.top))   # keep only top-k per prefix
    def suggest(self, prefix):
        node = self.root
        for ch in prefix:
            if ch not in node.children: return []
            node = node.children[ch]
        return [w for c, w in sorted(node.top, reverse=True)]

import math
BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"

def geohash_encode(lat, lon, precision=6):
    lat_r, lon_r = [-90.0, 90.0], [-180.0, 180.0]; bits = []; even = True
    while len(bits) < precision * 5:
        rng, val = (lon_r, lon) if even else (lat_r, lat)
        mid = (rng[0] + rng[1]) / 2
        if val >= mid: bits.append(1); rng[0] = mid
        else: bits.append(0); rng[1] = mid
        even = not even
    return "".join(BASE32[int("".join(map(str, bits[i:i + 5])), 2)] for i in range(0, len(bits), 5))

def haversine_km(a, b):
    R = 6371; la1, lo1, la2, lo2 = map(math.radians, (*a, *b))
    d = math.sin((la2 - la1) / 2) ** 2 + math.cos(la1) * math.cos(la2) * math.sin((lo2 - lo1) / 2) ** 2
    return 2 * R * math.asin(math.sqrt(d))

Avoiding double booking

Never 'check, then update' (a race — see the demo). Use one atomic statement UPDATE seats SET status='HELD' WHERE seat_id=? AND status='AVAILABLE' and check the affected row count; or row locks (SELECT … FOR UPDATE), optimistic locking with a version column, or a unique constraint on (event, seat).

Holds and expiry

Store hold_expires_at; treat expired holds as available when reading and clean up in the background (or use a TTL key in Redis). Extend or cancel on payment events.

Payment safety

Idempotency keys (Section 36), a clear state machine (HELD → PAYING → BOOKED/FAILED), and reconciliation jobs for payments whose callbacks were lost (Section 62).

Handling the spike

Waiting room + rate limits + autoscaling + CDN for the static seat map + a cached read model for availability; only the final seat claim goes to the strongly consistent store. Bot defence: CAPTCHAs, purchase limits per account/payment method.

The double-booking race and the atomic fix (real threads, SQLite) (run for real) 

import sqlite3, threading, time

def setup():
    db = sqlite3.connect(":memory:", check_same_thread=False, isolation_level=None)
    db.execute("CREATE TABLE seats (id INTEGER PRIMARY KEY, holder TEXT)")
    db.execute("INSERT INTO seats VALUES (1, NULL)")
    return db

# WRONG: check, then write (a race: two users both see the seat as free)
db = setup(); lock = threading.Lock(); winners = []
def naive(user):
    row = db.execute("SELECT holder FROM seats WHERE id = 1").fetchone()
    if row[0] is None:
        time.sleep(0.01)                                   # the gap between check and update
        with lock: db.execute("UPDATE seats SET holder = ? WHERE id = 1", (user,))
        winners.append(user)
ts = [threading.Thread(target=naive, args=("user%d" % i,)) for i in range(5)]
[t.start() for t in ts]; [t.join() for t in ts]
print("check-then-update  : %d users were told 'booked!'  <- DOUBLE BOOKING %s" % (len(winners), winners))

# RIGHT: one atomic conditional update decides the winner inside the database
db = setup(); winners = []
def atomic(user):
    cur = db.execute("UPDATE seats SET holder = ? WHERE id = 1 AND holder IS NULL", (user,))
    if cur.rowcount == 1: winners.append(user)
ts = [threading.Thread(target=atomic, args=("user%d" % i,)) for i in range(5)]
[t.start() for t in ts]; [t.join() for t in ts]
print("atomic UPDATE ... WHERE holder IS NULL: %d user booked it: %s" % (len(winners), winners))
print("final owner in DB:", db.execute("SELECT holder FROM seats").fetchone()[0])
print("other tools: SELECT ... FOR UPDATE (row lock), optimistic locking with a version column, unique constraints, a short-lived 'hold' with expiry.")

# ----- Output (real run) -----
# check-then-update  : 5 users were told 'booked!'  <- DOUBLE BOOKING ['user0', 'user2', 'user1', 'user4', 'user3']
# atomic UPDATE ... WHERE holder IS NULL: 1 user booked it: ['user0']
# final owner in DB: user0

Five users tried to book the single seat at the same time. With check-then-update, all five were told "booked!" — a classic race (each saw the seat free before anyone wrote). With one atomic UPDATE … WHERE holder IS NULL the database decided: exactly one user won (user0), and the final owner in the database matches.

7. Trade-offs & bottlenecks

  • Strong consistency on seats limits write scaling — shard by event, accept that one hot event concentrates load on one shard.
  • Hold duration trade-off: long holds frustrate others, short holds frustrate payers.
  • Overbooking (airlines) is a deliberate business policy; seats usually shouldn't be.
  • Fairness: waiting-room order vs bots; may randomise admission instead of first-come.

6. Deep dives

Exactly-once effect

Networks time out, so you will retry. Combine the idempotency key (Section 36), a unique constraint, and a state machine that rejects impossible transitions. The demo below shows the double charge without a key and the safe replay with one.

Handling uncertainty

If the provider call times out you don't know whether the charge happened. Mark it unknown/pending, then query the provider by your reference or wait for the webhook — never blindly retry a non-idempotent charge.

The ledger

Double-entry bookkeeping: money never appears or vanishes; every movement is two equal opposite entries. Entries are immutable; corrections are new entries. Balances are derived (or maintained as cached aggregates that can be rebuilt).

Distributed consistency

Use the outbox pattern (Section 41) to publish payment events reliably; sagas for multi-step flows (reserve stock → charge → ship) with compensation (refund).

Security

Never store raw card numbers yourself — use the provider's tokenisation/hosted fields to stay out of PCI scope; encrypt sensitive fields; protect webhooks with signatures; add risk scoring and 3-D Secure/UPI authentication; log and alert on anomalies.

A retried payment with and without an idempotency key (the demo from Section 36) (run for real) 

import uuid

class PaymentService:
    def __init__(self): self.balance = {"asha": 1000}; self.processed = {}; self.charges = 0
    def charge(self, user, amount, idempotency_key=None):
        if idempotency_key and idempotency_key in self.processed:
            return self.processed[idempotency_key] + " (replayed, NOT charged again)"
        self.balance[user] -= amount; self.charges += 1
        result = "charged %d" % amount
        if idempotency_key: self.processed[idempotency_key] = result
        return result

print("  ", svc.charge("asha", 300, key)); print("  ", svc.charge("asha", 300, key)); print("  ", svc.charge("asha", 300, key))
print("   balance =", svc.balance["asha"], "| real charges made:", svc.charges)
print("Rule: any operation that can be retried (networks fail!) must be safe to repeat: idempotency keys, unique constraints, upserts.")

63 Design a Metrics & Monitoring System (Prometheus/Datadog-like)

1. Requirements

FunctionalNon-functional
  • Collect metrics (name, labels, value, timestamp) from many services
  • Query and graph them (rates, percentiles, aggregations)
  • Evaluate alert rules and notify on-call
  • High write throughput (millions of points/s)
  • Fast dashboards over recent data; cheap storage for old data
  • Alerting must stay up even when the system it watches is failing

2. Estimates (assumptions)

  • 10,000 servers × 200 metrics each, every 10 s = 200,000 points/s ≈ 17 billion points/day

3. API

Push:  POST /write {metric: "http_requests_total", labels: {service: "checkout", code: "200"}, value: 1234, ts}

Query: GET /query?expr=rate(http_requests_total[5m]) by (service)

4. Data model

PieceDesign
SeriesIdentified by metric name + label set; each series is an append-only list of (timestamp, value) compressed in blocks

5. Architecture

Fig 33 — Collect → buffer → store → query/downsample/alert.
  • Agents or exporters expose or push metrics; collectors (sharded by target so each target is scraped once) batch them into a buffer.
  • The time-series database appends points to per-series blocks, compresses them, and replicates shards.
  • The query engine serves dashboards; downsampling jobs create coarser long-term data; an alert evaluator runs rules every minute and sends notifications.

6. Deep dives

Time-series storage tricks

Timestamps are nearly regular → store deltas (delta-of-delta); values change slowly → XOR with the previous value. Together these give ~10× compression. Write to an in-memory head block and a write-ahead log, flush to immutable blocks.

Cardinality: the silent killer

Every distinct label combination is a new series. A label like user_id or request_id can create millions of series and crash the database. Keep labels low-cardinality (service, status code, region); put high-cardinality data in logs/traces instead.

Percentiles at scale

You can't average p99s across servers. Use histograms (fixed buckets) or sketches (t-digest/HDR) that can be merged across machines, then compute the percentile from the merged data.

Alerting reliability

The alerting path must not depend on the thing it monitors: run it redundantly in separate failure domains, add a 'dead man's switch' alert that fires if the alerting pipeline itself stops, and route to multiple notification channels (Section 55).

7. Trade-offs & bottlenecks

  • Push vs pull: pull (scraping) makes health detection and control easy; push suits short-lived jobs and firewalled hosts.
  • Resolution vs cost: keep seconds-level data for days, minutes-level for months, hours-level for years.
  • Sampling traces/logs controls cost but can hide rare problems — keep all errors and slow requests.
  • Multi-tenant fairness: per-team quotas on series and query cost.

64 Design a Search Engine (document search)

Picture: The index at the back of a giant book: for every word, a list of the pages where it appears. To answer 'caching latency' you look up both words and find pages that contain them — then rank pages that match better higher.

1. Requirements

FunctionalNon-functional
  • Index documents; search by keywords/phrases
  • Ranked results with snippets, filters (facets), pagination
  • Near-real-time: new documents become searchable within seconds
  • Query latency under ~100 ms at p99
  • Scales to billions of documents and thousands of queries/s
  • Highly available; relevance quality matters

2. Estimates (assumptions)

  • 1 billion documents × 5 KB = 5 TB of text; the inverted index is typically similar in size (compressed)
  • 10,000 queries/s; each query touches many shards in parallel (scatter-gather)

3. API

PUT  /index/docs/{id}   {title, body, tags, ts}      → indexed (searchable after the next refresh)
GET  /search?q=caching+latency&filter=tag:db&limit=10&cursor=…  → {hits: [{id, score, snippet}], facets}

4. Data model

StructureMeaning
Inverted indexterm → postings list: sorted document ids (+ term frequency, positions) — compressed

5. Architecture

Fig 34 — Scatter-gather search over sharded inverted indexes.
  • Indexing: an analyzer lowercases, tokenises, removes stop words and stems words; documents are routed to a shard (by hash of id) and added to its index segments.
  • Query: the coordinator sends the query to every shard (or one replica per shard); each shard scores its documents and returns its top-K; the coordinator merges them into the global top-K.
  • Ranking: TF-IDF/BM25 text relevance plus signals (freshness, popularity), optionally re-ranked by an ML model or embeddings (see RAG for semantic/vector search).

6. Deep dives

Inverted index and scoring

A query for several words intersects or unions their postings lists. A word that appears in few documents is more informative than a common one — that is the IDF part of TF-IDF (the demo below shows it). Modern engines use BM25, a refinement.

Sharding and replication

Shard the index so each shard is small enough to be fast (10–50 GB is a common guideline), replicate each shard for availability and read throughput. Every query fans out to all shards, so tail latency depends on the slowest shard (Section 6) — hedged requests and replicas help.

Near-real-time

New documents go into a small in-memory buffer that is 'refreshed' into a searchable segment every second or so; durability comes from a write-ahead log (translog). Background merges keep the number of segments low.

Relevance and quality

Analyzers (stemming, synonyms, language-specific rules), typo tolerance (fuzzy search), phrase and proximity queries, boosting, and learning-to-rank. Measure with click-through, NDCG and human judgements.

Keeping the index in sync

The search index is a derived copy of the source of truth: feed it from change-data-capture or events (outbox, Section 41) and design for rebuilding it from scratch.

67 Common Design Mistakes

🏃 Jumping straight to boxes

Drawing before asking what to build. Fix: clarify and estimate first (Sections 3–4).

🧩 Over-engineering

Kafka, sharding and 12 microservices for 100 users. Start simple and add complexity when numbers demand it.

🎯 Single point of failure

One database, one load balancer, one region with no plan. Ask of every box: "what if this dies?"

🔥 Ignoring hot spots

Even sharding fails when one key (a celebrity, a hot event) gets most traffic. Plan for skew.

📏 No numbers

"It should scale" is not a design. Say requests/s, GB and latency targets, even if rough (Sections 4, 69).

🤝 Assuming the network is reliable

Timeouts, retries, duplicates and partitions are normal. Use timeouts, backoff, idempotency (Sections 34, 36).

🗄️ Cache with no invalidation story

Say what happens when data changes, and how stale is acceptable (Section 29).

🔗 Distributed transaction by default

Two-phase commit across services is slow and fragile; prefer sagas, outbox and idempotent steps (Section 41).

🔭 No observability

A system you cannot see you cannot fix: metrics, logs, traces, alerts (Section 44).

🔐 Security as an afterthought

Authentication, authorisation, encryption, rate limits and secrets belong in the first diagram (Section 45).

💸 Forgetting cost

The design that works but bankrupts the company is not a good design (Section 48).

🗣️ Not stating trade-offs

Every choice has a downside. Saying it shows maturity.

R + W > N means reads overlap the latest write. N=3, R=2, W=2 is the common balance.

Availability

99.9% ≈ 8.8 h downtime a year; 99.99% ≈ 53 min; 99.999% ≈ 5 min. In a chain, availabilities multiply; in redundancy, failures multiply.

Watch p95/p99, not the average. Fan-out makes the tail worse. Set timeouts on everything.

71 FAQ

Q: Is System Design only for interviews?

No. Interviews use it as a test, but the same thinking decides real outcomes: how a product handles ten times more users, survives a data-centre failure, or keeps the cloud bill sane.

Q: What is the difference between HLD and LLD?

High-level design (this page) is the big picture: services, databases, queues, how they talk and scale. Low-level design is inside one component: classes, methods, patterns, data structures.

Q: Do I need to know every technology (Kafka, Redis, Cassandra…)?

Know the ideas (queue, cache, wide-column store) and one or two real tools for each. Interviewers care that you pick appropriately and explain trade-offs, not that you recite configuration.

Q: SQL or NoSQL — which should I choose?

Start with a relational database (PostgreSQL, MySQL) unless you have a specific reason: it handles far more than people think. Move to NoSQL for massive scale with simple access patterns, flexible schemas, or special models (graph, time series). See Sections 17–18.

Q: When should I use microservices?

When many teams need to deploy and scale independently. For a small team, a well-structured monolith is simpler, faster and cheaper. Many companies have moved back toward fewer, larger services (Section 42).

Q: How precise must my estimates be?

Within a factor of 2–3 is fine. The goal is to know whether you need 1 server or 100, 1 GB or 1 PB, so you pick the right architecture.

Q: How do I practise?

Pick a design from Part F, close the page, design it on paper in 45 minutes, then compare. Run the code samples, break them, and read real engineering blogs (Resources). Explain your design out loud to someone.

Q: Does AI/LLM change system design?

It adds new components (model gateways, vector stores, caching of expensive calls, evaluation, guardrails) and new trade-offs (cost per request, latency, non-determinism), but the fundamentals here (queues, caching, scaling, failure handling) still apply. See the RAG, LLM and AI Agents guides.

Q: Are the numbers on this page exact?

No. Latency numbers are rough orders of magnitude; the per-design estimates are labelled assumptions; the code outputs are from real runs of small simulations on one laptop, so treat them as demonstrations of behaviour, not benchmarks.

Q: What should I learn alongside this?

Networking basics and Linux (Linux guide), a database in depth, Docker and CI/CD (DevOps), and one cloud provider's core services.

A. Fundamentals

Q1: What is horizontal vs vertical scaling, and which would you pick first?

Vertical = a bigger machine; horizontal = more machines. Start vertical (simple, no distributed complexity) until cost or limits bite; go horizontal for fault tolerance and beyond-one-machine scale. Horizontal needs stateless services and a way to split data.

Q2: Latency vs throughput?

Latency is time per request; throughput is requests per unit time. A system can have high throughput and high latency (a big batch job) or the reverse. Optimise the one your users feel.

Q3: Why do we use percentiles (p99) instead of averages?

Averages hide the slow tail. If 1% of requests take 5 seconds, the average looks fine but one in a hundred users suffers, and a page that makes many calls hits the slow ones often. Track p95/p99 (Section 6).

Q4: What does "99.99% available" mean in practice?

About 53 minutes of downtime per year. Each extra nine is roughly ten times harder and costlier; also, dependencies in a chain multiply (two 99.9% parts in series give about 99.8%).

Q5: What is a stateless service and why does it matter?

It stores no per-user data in memory between requests, so any instance can serve any request. That makes load balancing, autoscaling and replacing failed instances trivial. State goes to databases, caches or tokens.

Q6: Explain a load balancer and two algorithms.

It distributes traffic and removes unhealthy servers. Round robin cycles through servers; least connections sends to the least busy; consistent/IP hashing keeps a client on the same server (Section 12).

B. Networking & APIs

Q7: What happens when you type a URL and press Enter?

DNS lookup → TCP connection (and TLS handshake) → HTTP request, perhaps via CDN/load balancer → server processes (cache, database) → response → browser renders and fetches more resources (Sections 9–11).

Q8: REST vs GraphQL vs gRPC?

REST: simple, cacheable, resource-oriented. GraphQL: client chooses fields, fewer round trips, harder caching and cost control. gRPC: fast binary, strong contracts, great between services (Section 14).

Q9: Polling, long polling, SSE, WebSocket?

Polling asks repeatedly (simple, wasteful). Long polling holds the request until news. SSE streams server→client over HTTP. WebSocket is a two-way persistent channel for chat, games, collaboration (Section 15).

Q10: How do you design a good API for pagination?

Use cursor (keyset) pagination for large or changing data: it stays fast and consistent, whereas offset pagination gets slower the deeper you go and can skip or repeat items (Section 16 demo).

Q11: What is a CDN and what can't it cache well?

Edge servers close to users caching static (and some dynamic) content. It is poor for highly personalised or rapidly changing responses unless you cache carefully with short TTLs or edge logic (Section 11).

C. Data & Storage

Q12: How do database indexes work and what is the cost?

An index (often a B-tree) lets the database find rows without scanning the table, turning lookups from linear to logarithmic. Cost: extra storage and slower writes, since each index must be updated (Section 19: ~185× faster reads, slower writes in our demo).

Q13: Explain ACID.

Atomic: all or nothing. Consistent: rules (constraints) always hold. Isolated: concurrent transactions don't see each other's half-done work. Durable: committed data survives crashes (Section 18).

Q14: Replication: leader-follower vs multi-leader vs leaderless?

Leader-follower: one writer, many readers (simple; lag, failover). Multi-leader: writers in several regions (conflicts to resolve). Leaderless (Dynamo-style): any replica accepts writes with quorums (high availability, tunable consistency) (Section 21).

Q15: How do you shard data, and what can go wrong?

Choose a shard key and map by hash (even load, no range scans) or range (ordered scans, hot spots). Problems: hot shards, cross-shard queries and transactions, resharding pain; consistent hashing reduces data movement (Sections 22–23: 79% vs 22% of keys moved).

Q16: Explain CAP and PACELC.

During a network partition you can keep consistency or availability, not both. PACELC adds that even without a partition you trade latency for consistency (Section 24).

Q17: What is a quorum, and what do R and W mean?

N replicas; a write succeeds after W acknowledgements, a read asks R replicas. If R + W > N, a read overlaps the newest write. In our demo, stale reads dropped to 0% once R + W > N (Section 25).

Q18: Where would you store images, logs, time-series and a social graph?

Images: object storage + CDN. Logs: log pipeline (Kafka) to object storage/search. Time-series: a TSDB. Graph: graph database or adjacency tables. Match the store to the access pattern (Section 26–27).

D. Caching, Queues & Reliability

Q19: Cache-aside vs write-through vs write-back?

Cache-aside: the app checks the cache, loads from DB on miss (most common). Write-through: writes go to cache and DB together (consistent, slower writes). Write-back: write to cache first, DB later (fast, risk of loss) (Section 29).

Q20: How do you prevent a cache stampede?

Per-key locking or request coalescing so only one request rebuilds the value, randomised TTLs, serving stale while refreshing, and pre-warming (demo: 50 DB queries became 1).

Q21: Why a message queue?

To decouple producers and consumers, absorb spikes, retry failures and scale workers independently. Delivery is usually at-least-once, so consumers must be idempotent (Sections 31, 36).

Q22: Kafka vs RabbitMQ/SQS?

Kafka is a partitioned, replayable log suited to high-throughput streaming and many independent consumers. Classic queues (RabbitMQ, SQS) deliver each message to one worker and delete it, which suits task distribution (Sections 31–32).

Q23: Explain retries, backoff and jitter.

Retry transient failures with exponentially growing waits plus randomness so thousands of clients don't retry in sync and create waves of load (our simulation showed jitter spreads the waves; the gain was modest) (Section 34).

Q24: What is a circuit breaker?

After many failures it "opens" and fails fast instead of calling the broken dependency; after a pause it lets a few trial requests through ("half-open") and closes if they succeed (Section 34).

Q25: Compare token bucket, fixed window and sliding window rate limiting.

Token bucket allows bursts at a steady average rate; fixed window is simple but permits double bursts at boundaries; sliding window is accurate but costlier (Section 33; our demo: 10 vs 5 allowed).

Q26: What is idempotency and how do you implement it?

Repeating an operation has the same effect as doing it once. Implement with client-generated idempotency keys stored with the result, unique constraints, or natural idempotent updates (PUT, upserts) (Section 36: charged twice vs once).

Q27: What is backpressure?

A signal that makes producers slow down or stop when consumers are overloaded; bounded queues with rejection beat unbounded queues that hide the problem until memory runs out (Section 35: 120 waiting, average wait 5.0 vs 3.2 vs 0.0).

E. Distributed Systems

Q28: Why can't we use exactly-once delivery?

Over an unreliable network you can't distinguish a lost message from a lost acknowledgement, so you choose at-least-once (duplicates) or at-most-once (loss). "Exactly-once effect" is achieved with at-least-once plus idempotent processing or transactional systems.

Q29: How do you generate unique ids in a distributed system?

UUIDs (no coordination, large, unordered), database auto-increment/ticket servers (simple, a bottleneck), or Snowflake-style ids (timestamp + machine + sequence: sortable and decentralised) (Section 37).

Q30: How does leader election work?

Nodes vote; a candidate needs a majority; terms prevent stale leaders; heartbeats detect failure (Raft). Use ZooKeeper/etcd/Consul rather than inventing it. A tie or lost majority means no leader until retry (Section 40 demo).

Q31: Two-phase commit vs saga?

2PC makes all participants commit or none, but it blocks if the coordinator fails and doesn't scale across services. A saga runs local transactions in sequence and undoes earlier ones with compensating actions if a later step fails (Section 41).

Q32: What is the outbox pattern?

Save the business change and the event in the same database transaction (an "outbox" table), then a relay publishes the event. This avoids "database updated but event lost" (Section 41).

Q33: How do you handle clock differences between machines?

Don't trust wall clocks for ordering. Use logical clocks (Lamport, vector clocks), sequence numbers, or databases with bounded-uncertainty time (Section 25).

Q34: How would you count unique visitors at huge scale?

HyperLogLog gives approximate distinct counts in kilobytes with ~1–2% error (our run: errors within about ±5%), and sketches can be merged across servers (Section 39).

Q35: How do nodes in a cluster learn about each other?

Gossip: each node periodically shares what it knows with a few random peers; information reaches N nodes in roughly log N rounds (Section 43 demo: ~24 rounds for 10,000 nodes in our setting).

F. Design Scenarios

Q36: Design a URL shortener — key decisions?

Read-heavy (100:1). Generate 7-char base62 codes (counter blocks or hash + collision check), store code→URL in a key-value store, cache hot codes, return 302 so clicks can be counted via a queue (Section 50).

Q37: Design a news feed for celebrities and normal users.

Hybrid fan-out: push post ids to followers' timelines for normal authors, pull celebrities' posts at read time and merge; cache timelines; paginate with cursors (Section 53).

Q38: Design a chat system.

WebSocket gateways, a connection registry, a message service that persists then routes to the recipient's gateway, offline queues + push notifications, ordering by per-chat ids, idempotency by client message id (Section 54).

Q39: How do you prevent double booking of the last seat?

One atomic conditional update (or a row lock/unique constraint), never check-then-update; add holds with expiry and a waiting room for spikes (Section 61: 5 buyers vs 1 winner).

Q40: Design nearby-driver search.

Index live locations by geohash/S2/H3 cell in memory; query the user's cell and neighbours, compute exact distances for candidates, rank by ETA; partition by city; assign rides with a strongly consistent state machine (Section 58).

Q41: Design a rate limiter for an API gateway.

Token bucket per key in a shared Redis-like store with an atomic script, rules cached locally, fail-open or fail-closed per endpoint, clear 429 + Retry-After responses (Section 51).

G. Advanced & Operations

Q42: How would you make a system survive a whole region failing?

Multi-region deployment with replicated data (decide sync vs async and the RPO), health-checked traffic failover (DNS/global load balancer), stateless services, regular failover drills, and defined RTO/RPO (Section 47).

Q43: How do you roll out a risky change safely?

Feature flags, canary releases to a small percentage with automated metric checks, blue-green for instant rollback, backwards-compatible database migrations in expand/contract steps (Section 46).

Q44: Latency suddenly spiked. What do you check?

Recent deploys and config changes; the four golden signals (latency, traffic, errors, saturation); dependency health (database, cache hit rate, queue depth); traces to find the slow hop; resource limits (CPU, memory, connections); then mitigate (roll back, scale, shed load) before the deep root cause (Section 44).

Q45: How do you decide how many servers you need?

Estimate peak requests/s, measure requests/s per server at a safe utilisation (queueing theory: latency explodes past ~70–80% busy, as in the Section 7 demo), add headroom for failure (N+1 or N+2), and load-test (Section 49).

73 Pitfalls & Checklist

🎰 Premature optimisation

Measure first. Most systems never need what interviews describe.

🧱 Everything in one database

One database for OLTP, analytics, search and caching hurts all four at scale. Split by access pattern when needed.

⏱️ No timeouts

A call without a timeout can hang a thread forever and cascade into an outage.

♻️ Retries without limits

Unbounded retries turn a small blip into a retry storm. Cap them and add jitter.

🌊 Unbounded queues

They hide overload until memory is gone. Bound queues; reject or shed load.

🔑 Hot keys

One viral item can melt one shard or cache node. Detect, replicate, or split hot keys.

🔄 Cache and database drift

Decide an invalidation strategy and an acceptable staleness before shipping.

📦 Dual writes

Writing to the database and a queue separately can lose one. Use the outbox pattern.

🕳️ Untested backups

A backup you have never restored is a hope, not a backup (Section 47).

🔐 Secrets in code

Use a secrets manager; rotate keys; least privilege (Section 45).

Design review checklist:
  • ☐ Requirements (functional and non-functional) and out-of-scope items are written down
  • ☐ Back-of-envelope numbers for traffic, storage, bandwidth exist; peak vs average considered
  • ☐ API and data model defined; access patterns match the chosen stores
  • ☐ No single point of failure; each dependency has a timeout, retry limit and fallback
  • ☐ Consistency requirements stated per data type; idempotency for retried operations
  • ☐ Scaling path identified for the first bottleneck (and the second)
  • ☐ Hot keys, skew and thundering-herd cases considered
  • ☐ Metrics, logs, traces and alerts planned, with SLOs
  • ☐ Security: authentication, authorisation, encryption, rate limits, secrets, auditing
  • ☐ Deployment, rollback and migration plan; disaster-recovery RTO/RPO and tested restore
  • ☐ Cost estimated; trade-offs and alternatives written down

74 Quick Quiz 🎯

Click each question to reveal the answer.

Q1: A site gets 100 million requests a day. About how many per second on average?

100,000,000 ÷ 86,400 ≈ 1,157 per second. Plan for a peak of 2–5× that.

Q2: Why is "check seat is free, then mark it booked" unsafe?

Two requests can both see it free before either writes (a race). Use one atomic conditional update, so the database lets only one succeed.

Q3: With N=3 replicas, which R and W guarantee reading the latest write?

Any with R + W > 3, e.g. R=2, W=2 (or W=3, R=1).

Q4: Why use consistent hashing instead of hash % N?

With modulo, changing N remaps most keys (79% moved in our demo). Consistent hashing moves only about 1/N of keys (22%).

Q5: What does a CDN reduce?

Latency for users (nearby copies), and load and bandwidth on your origin servers.

Q6: Name two ways to stop retries from causing duplicate payments.

Idempotency keys stored with the first result, and a unique constraint on the payment/order reference.

Q7: Why does utilisation above ~80% hurt latency so much?

Queues grow non-linearly as servers approach full: in the Section 7 simulation mean latency went from 14 ms at 30% busy to 96 ms at 90% and 453 ms at 98%.

Q8: When do you choose push fan-out vs pull fan-out in a feed?

Push for authors with few/moderate followers (fast reads); pull for celebrity authors (avoids millions of writes); real systems mix both.

Q9: What is the purpose of a dead-letter queue?

To hold messages that keep failing, so they don't block the queue and can be inspected or replayed later.

Q10: What is the first thing to do in any design question?

Clarify requirements and scope (and then estimate scale) before drawing anything.
