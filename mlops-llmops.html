Part A — MLOps Foundations

1 What Is MLOps? Why Models Fail After Launch

Picture: You teach a child to recognise fruit using photos of apples and oranges. At the exam the child is shown a mango and a photo taken at night. The child was not stupid; the world was different from the lesson. A model in a notebook is a child that passed the practice test. MLOps is everything that keeps the child useful in the real world: teaching it carefully, checking it, sending it to work, watching it, and re-teaching it when the world changes.
Notebook worldReal world
Data is a tidy file that never changesData arrives every second, in new shapes, with holes and mistakes
One person runs cells in any orderA team needs the same result every time, by machine
Accuracy on a test set is the goalSpeed, cost, fairness, safety and business results matter too
The model is a file on a laptopThe model is a service that must be up, fast, versioned and rollbackable
Done when the score is goodNever done: data and behaviour drift, so the model slowly gets worse
In one line: MLOps = DevOps ideas (automation, testing, versioning, monitoring) applied to the extra things that make machine learning special: data and models that learn.

Good to know

  • A well-known paper from Google (Sculley and others, 'Hidden Technical Debt in Machine Learning Systems') pointed out that the model code is a small box inside a large system of data collection, checking, serving and monitoring. Most of the work, and most of the trouble, is outside the model.
  • LLMOps (Part D) is MLOps for large language model applications: prompts, evaluation sets, tokens, cost, guardrails and tracing take the place of classic training pipelines.
  • Related guides: Machine Learning, Deep Learning, LLMs, RAG, AI Agents, Docker & Kubernetes, CI/CD, AI Security.
Honest note on this page: all scikit-learn, NumPy, SciPy, pandas and PyTorch demos were really run (Python 3.14.2, 17 Nov 2026). Every 'LLM' in a demo is a clearly labelled scripted stand-in. Commands that need servers, GPUs, cloud accounts or API keys are templates, not run.

2 The ML Lifecycle: A Loop, Not a Line

Good to know

  • Each box can be automated; the goal of MLOps is to make every arrow in this picture a button (or no button).
  • Two clocks run: the code clock (a developer changes the program) and the data clock (the world changes). Either one can break the model. A good system reacts to both.

7 Versioning Data (Not Just Code)

Picture: A photo album with dates. If a model was trained on the 'March album' you must be able to open exactly that album again, even if new photos were added later.

Git is bad at big files. Data-versioning tools (DVC, lakeFS, Delta Lake / Iceberg time travel, Pachyderm, warehouse snapshots) store data by the hash of its content; Git keeps only a tiny pointer file. The simulation shows the idea: unchanged rows are stored once, and two versions can be compared.

Content-addressed data versions (the core idea behind DVC / lakeFS) (run for real)
# Data versioning idea (what DVC and lakeFS do): store files by the hash of their content; a "version" is a small list of hashes.
import hashlib, json
store = {}                                           # the content-addressed store: hash -> bytes
def add(rows):
    ids = []
    for r in rows:
        b = json.dumps(r, sort_keys=True).encode(); h = hashlib.sha256(b).hexdigest()[:8]
        store.setdefault(h, b); ids.append(h)
    return ids
v1 = add([{"id": i, "age": 20 + i, "label": i % 2} for i in range(1000)])
v2_rows = [{"id": i, "age": 20 + i, "label": i % 2} for i in range(1000)]
v2_rows[10]["label"] = 1 - v2_rows[10]["label"]      # one label corrected
v2_rows += [{"id": 1000 + i, "age": 30, "label": 1} for i in range(50)]   # 50 new rows
v2 = add(v2_rows)
print("v1: %d rows, v2: %d rows" % (len(v1), len(v2)))
print("objects in the store:", len(store), "(not %d: unchanged rows are stored once)" % (len(v1) + len(v2)))
print("dataset v1 fingerprint:", hashlib.sha256("".join(v1).encode()).hexdigest()[:12])
print("dataset v2 fingerprint:", hashlib.sha256("".join(v2).encode()).hexdigest()[:12])
a, b = set(v1), set(v2)
print("diff v1 -> v2: removed %d row version(s), added %d row version(s)" % (len(a - b), len(b - a)))

# ----- Output (real run) -----
# v1: 1000 rows, v2: 1050 rows
# objects in the store: 1051 (not 2050: unchanged rows are stored once)
# dataset v1 fingerprint: f8614869e1ac
# dataset v2 fingerprint: 2e836f16a3bb
# diff v1 -> v2: removed 1 row version(s), added 51 row version(s)

git checkout v1.0 && dvc checkout                      # go back to the exact data + code of an old version

Good to know

  • A model version = code commit + data version + parameters + environment. Lose one of the four and you cannot rebuild it.
  • Also record where data came from (lineage), who may use it, and when it must be deleted (privacy law). See the governance section.
  • Labels are data too: version label sets and keep the labelling guidelines.

8 Data Validation: Stop Bad Data Early

Picture: A security guard at the kitchen door checking every delivery: wrong box, rotten fruit, missing label. Better to refuse the delivery than to cook with it.

Check schema (columns and types), ranges, missing values, allowed categories, duplicates, freshness and distribution (is it close to what we trained on?). Tools: Great Expectations, pandera, TensorFlow Data Validation, Soda, dbt tests, Deequ. The program below shows the idea with plain pandas.

Six checks on a table with planted mistakes (run for real)
# Data validation: cheap checks that stop bad data BEFORE it trains or feeds a model (the idea behind Great Expectations / pandera).
import numpy as np, pandas as pd
rng = np.random.default_rng(1)
df = pd.DataFrame({"age": rng.integers(18, 80, 500).astype(float), "income": rng.normal(50000, 12000, 500).round(0), "country": rng.choice(["IN", "US", "DE"], 500)})
df.loc[3, "age"] = -5; df.loc[7, "age"] = np.nan; df.loc[11:14, "income"] = np.nan; df.loc[20, "country"] = "XX"; df.loc[30, "income"] = 9_900_000
checks = [
    ("age is between 0 and 120",        lambda d: ((d.age < 0) | (d.age > 120)).sum()),
    ("age has no missing values",       lambda d: d.age.isna().sum()),
    ("income missing at most 1%",       lambda d: max(0, d.income.isna().sum() - 0.01 * len(d))),
    ("income below 1,000,000",          lambda d: (d.income > 1_000_000).sum()),
    ("country is one of IN/US/DE",      lambda d: (~d.country.isin(["IN", "US", "DE"])).sum()),
    ("no duplicate rows",               lambda d: d.duplicated().sum()),
]
failed = 0
for name, fn in checks:
    bad = fn(df); ok = bad == 0; failed += (not ok)
    print("%-6s %-32s violations: %g" % ("PASS" if ok else "FAIL", name, bad))
print("\n%d of %d checks failed -> a pipeline should STOP here instead of training on this data" % (failed, len(checks)))

# ----- Output (real run) -----
# FAIL   age is between 0 and 120         violations: 1
# FAIL   age has no missing values        violations: 1
# PASS   income missing at most 1%        violations: 0
# FAIL   income below 1,000,000           violations: 1
# FAIL   country is one of IN/US/DE       violations: 1
# PASS   no duplicate rows                violations: 0
#
# 4 of 6 checks failed -> a pipeline should STOP here instead of training on this data

Four of six checks fail: a negative age, a missing age, an income of 9.9 million, and an unknown country 'XX'. A pipeline should stop and alert instead of silently training on this.

Good to know

  • Put validation at two places: when data enters the pipeline, and again just before training or serving.
  • Decide the reaction: block, quarantine the bad rows, or alert and continue. Silent continuation is the worst choice.

9 Data Leakage: When Results Look Too Good

Picture: A student who sees the exam answers while studying gets 100%, then fails real life. Leakage means the model saw something at training time that it will not have at prediction time.

Three classic leaks: a feature computed from the answer (target leakage), mixing the same row into training and test (duplicates), and information from the future (time leakage). The run builds a hard problem and then adds a leaking column.

Accuracy jumps from 0.67 to 1.00 with a leaking column (run for real)
# Data leakage: the model sees something at training time that it will NOT have in real life. Results look wonderful and are false.
import numpy as np
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier
rng = np.random.default_rng(0)
n = 2000
X = rng.normal(size=(n, 5)); y = (X[:, 0] + 0.5 * X[:, 1] + rng.normal(scale=1.5, size=n) > 0).astype(int)    # a genuinely hard problem
leak = y + rng.normal(scale=0.05, size=n)                    # a column computed FROM the answer (e.g. 'refund_issued' for a churn model)
for name, feats in [("honest features", X), ("plus a leaking column", np.column_stack([X, leak]))]:
    Xtr, Xte, ytr, yte = train_test_split(feats, y, test_size=0.3, random_state=0)
    m = RandomForestClassifier(n_estimators=100, random_state=0).fit(Xtr, ytr)
    print("%-24s test accuracy %.3f" % (name, m.score(Xte, yte)))
# Duplicates across the split are another quiet leak
base = rng.normal(size=(300, 5)); yb = (base[:, 0] + rng.normal(scale=1.5, size=300) > 0).astype(int)
Xd = np.vstack([base, base]); yd = np.concatenate([yb, yb])    # every row appears twice
Xtr, Xte, ytr, yte = train_test_split(Xd, yd, test_size=0.3, random_state=0)
m = RandomForestClassifier(n_estimators=100, random_state=0).fit(Xtr, ytr)
print("duplicated rows split randomly: test accuracy %.3f (the model has seen most test rows already)" % m.score(Xte, yte))
Xtr, Xte, ytr, yte = train_test_split(base, yb, test_size=0.3, random_state=0)
m = RandomForestClassifier(n_estimators=100, random_state=0).fit(Xtr, ytr)
print("same data split BEFORE duplicating: test accuracy %.3f" % m.score(Xte, yte))

# ----- Output (real run) -----
# honest features          test accuracy 0.673
# plus a leaking column    test accuracy 1.000
# duplicated rows split randomly: test accuracy 0.844 (the model has seen most test rows already)
# same data split BEFORE duplicating: test accuracy 0.644

If a result is much better than the domain makes plausible, suspect leakage first. The duplicated-rows case also looks better (0.84) than the honest number (0.64).

Good to know

  • Prevention checklist: split before any fitting step (scaling, imputing, encoding); split by time or by group (customer) when rows are related; remove features that exist only after the outcome; check for duplicates across the split.
  • Put preprocessing inside a scikit-learn Pipeline so each cross-validation fold fits it only on its own training part.

10 Features and Feature Stores (Point-in-Time Correct)

Picture: A recipe says 'one cup of flour'. A feature is a ready-measured cup of information about a customer ('visits in the last 30 days'). A feature store is the pantry where every team finds the same measured cups, fresh for serving and correctly dated for training.

Two jobs: offline (build training sets with history) and online (look up the latest values in milliseconds). The hard part is point-in-time correctness: a training row for 10 January may only use what was known on 10 January. The naive join below uses the latest value and leaks the future.

Naive join vs point-in-time join (pandas merge_asof) (run for real)
# Point-in-time correctness: a training row must only use feature values that were KNOWN at that moment.
import pandas as pd
events = pd.DataFrame({"user": ["a", "a", "a"], "event_time": pd.to_datetime(["2026-01-10", "2026-02-10", "2026-03-10"]), "bought": [0, 0, 1]})
features = pd.DataFrame({"user": ["a", "a", "a", "a"], "feature_time": pd.to_datetime(["2026-01-01", "2026-02-01", "2026-03-01", "2026-04-01"]),
                         "visits_last_30d": [2, 4, 9, 30]})        # the 30 only became known on 1 April
naive = events.merge(features.sort_values("feature_time").groupby("user").tail(1), on="user")       # "latest value": LEAKS the future
correct = pd.merge_asof(events.sort_values("event_time"), features.sort_values("feature_time"), left_on="event_time", right_on="feature_time", by="user")
print("naive join (latest feature value):"); print(naive[["event_time", "visits_last_30d", "bought"]].to_string(index=False))
print("\npoint-in-time join (as-of the event):"); print(correct[["event_time", "visits_last_30d", "bought"]].to_string(index=False))

# ----- Output (real run) -----
# naive join (latest feature value):
# event_time  visits_last_30d  bought
# 2026-01-10               30       0
# 2026-02-10               30       0
# 2026-03-10               30       1
#
# point-in-time join (as-of the event):
# event_time  visits_last_30d  bought
# 2026-01-10                2       0
# 2026-02-10                4       0
# 2026-03-10                9       1

The naive join gives every row the value 30 that became known only on 1 April. The as-of join gives 2, 4 and 9, which is what a real system would have known.

11 Training/Serving Skew

Picture: A baker tests a recipe with a metric oven at home and the restaurant uses a different-scale oven. Same recipe, different result. Skew means features are computed differently in training and in production.

Typical causes: two code paths (SQL for training, Python for serving), different missing-value handling, different time zones or units, stale lookups. Here the same model is served two ways.

Same model, different missing-value fill at serving (run for real)
# Training/serving skew: the feature is computed differently in training and in production.
import numpy as np
from sklearn.linear_model import LogisticRegression
rng = np.random.default_rng(3)
n = 4000
age = rng.normal(40, 10, n); income = rng.normal(60, 15, n)
y = ((age - 40) / 10 + (income - 60) / 15 + rng.normal(scale=0.8, size=n) > 0).astype(int)
miss = rng.random(n) < 0.2; income_obs = np.where(miss, np.nan, income)        # 20% of incomes are missing
Xtr_i = np.where(np.isnan(income_obs), np.nanmean(income_obs), income_obs)      # training: fill with the MEAN (about 60)
m = LogisticRegression().fit(np.column_stack([age, Xtr_i]), y)
print("trained with mean-imputation (fill = %.1f)" % np.nanmean(income_obs))
for label, fill in [("serving fills with the same mean", np.nanmean(income_obs)), ("serving fills with 0 (a different code path)", 0.0)]:
    Xs = np.column_stack([age, np.where(np.isnan(income_obs), fill, income_obs)])
    print("%-46s accuracy %.3f" % (label, m.score(Xs, y)))
print("Fix: ONE shared function (or a feature store / sklearn Pipeline saved with the model) used by both training and serving.")

# ----- Output (real run) -----
# trained with mean-imputation (fill = 59.9)
# serving fills with the same mean               accuracy 0.817
# serving fills with 0 (a different code path)   accuracy 0.767
# Fix: ONE shared function (or a feature store / sklearn Pipeline saved with the model) used by both training and serving.

The accuracy falls from 0.817 to 0.767 only because serving fills missing incomes with 0 instead of the training mean. On other data the damage can be far larger, and it is silent: no error message appears.

Good to know

  • Cure: one shared feature function, saved with the model (scikit-learn Pipeline, a feature store, or a packaged library used by both sides).
  • Detect: log the features seen at serving time and compare their distribution with the training set (drift section) and with the offline recomputation of the same rows.

12 Experiment Tracking (MLflow, Weights & Biases and Friends)

Picture: A lab notebook that fills itself: every try, with its settings and its score, so you can say 'run 17 was the best, and here is how to repeat it'.

A tracker stores per run: parameters, metrics (also over time), artifacts (model, plots), the code version and the environment. Tools: MLflow (open source), Weights & Biases, Neptune, Comet, ClearML, DVC experiments, cloud trackers. The mini tracker below writes real run records and queries them.

A 30-line experiment tracker and a query for the best run (run for real)
# A tiny experiment tracker (what MLflow / Weights & Biases do): every run stores params + metrics + a time, so results can be compared.
import json, os, tempfile, time
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler
from sklearn.pipeline import make_pipeline
log = os.path.join(tempfile.mkdtemp(), "runs.jsonl")
def track(params, metrics):
    with open(log, "a") as f: f.write(json.dumps({"params": params, "metrics": metrics}) + "\n")
X, y = load_breast_cancer(return_X_y=True)
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.25, random_state=0, stratify=y)
for C in [0.001, 0.01, 0.1, 1, 10, 100]:
    m = make_pipeline(StandardScaler(), LogisticRegression(C=C, max_iter=2000)).fit(Xtr, ytr)
    track({"model": "logreg", "C": C}, {"train_acc": round(m.score(Xtr, ytr), 4), "test_acc": round(m.score(Xte, yte), 4)})
runs = [json.loads(l) for l in open(log)]
print("run  C        train_acc  test_acc")
for i, r in enumerate(runs, 1):
    print("%3d  %-7g  %9.4f  %8.4f" % (i, r["params"]["C"], r["metrics"]["train_acc"], r["metrics"]["test_acc"]))
best = max(runs, key=lambda r: r["metrics"]["test_acc"])
print("best run by test accuracy:", best["params"], best["metrics"]["test_acc"])

Ten seeds, ten different scores (run for real)

  • Set seeds for Python, NumPy and the ML framework; remember that GPUs, multithreading and some libraries are still not bit-for-bit repeatable unless you ask for deterministic mode (usually slower).

  • Reproducibility levels: same code and data gives the same pipeline; same seed gives the same numbers; both together give a trustworthy comparison.

14 Hyperparameter Tuning: Grid, Random and Smarter

Picture: Finding the best oven temperature and baking time. Trying 4 temperatures × 4 times is a grid. Trying 16 random pairs often covers each setting more richly.

Hyperparameters are the knobs you set before training (learning rate, tree depth, regularisation). Same budget of 16 trials, two strategies, on the digits dataset with an SVM:

Grid vs random search with equal budget (run for real)
# Hyper-parameter search: grid vs random with the SAME budget of 16 trials.
import numpy as np, time
from sklearn.datasets import load_digits
from sklearn.svm import SVC
from sklearn.model_selection import cross_val_score, ParameterGrid
X, y = load_digits(return_X_y=True); X = X / 16.0
def score(C, gamma): return cross_val_score(SVC(C=C, gamma=gamma), X, y, cv=3).mean()
grid = list(ParameterGrid({"C": [0.1, 1, 10, 100], "gamma": [1e-4, 1e-3, 1e-2, 1e-1]}))            # 4 x 4 = 16 trials
rng = np.random.default_rng(0)
rand = [{"C": 10 ** rng.uniform(-1, 2), "gamma": 10 ** rng.uniform(-4, -1)} for _ in range(16)]  # 16 random trials
res_g = [(score(**p), p) for p in grid]; res_r = [(score(**p), p) for p in rand]
bg, br = max(res_g, key=lambda t: t[0]), max(res_r, key=lambda t: t[0])
print("grid   best CV accuracy %.4f  with C=%g gamma=%g" % (bg[0], bg[1]["C"], bg[1]["gamma"]))
print("random best CV accuracy %.4f  with C=%.3g gamma=%.3g" % (br[0], br[1]["C"], br[1]["gamma"]))
print("grid tries only 4 distinct values of each setting; random tries 16 distinct values of each.")
print("best-so-far by trial (grid):  ", [round(float(max(s for s, _ in res_g[:k + 1])), 3) for k in range(0, 16, 3)])
print("best-so-far by trial (random):", [round(float(max(s for s, _ in res_r[:k + 1])), 3) for k in range(0, 16, 3)])

16 Train, Validation, Test: Splitting the Right Way

Picture: Practice questions, mock exam, final exam. If you also train on the final exam the grade means nothing.

When the world changes over time, a random split mixes the past and the future and is too optimistic. A time-based split imitates production: train on the past, test on what came after.

Random split vs time split on drifting data (run for real)
# Random split vs time-based split when the world changes over time. Honest estimate = split by time.
import numpy as np
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import train_test_split
rng = np.random.default_rng(5)
n = 6000; t = np.arange(n)
x = rng.normal(size=(n, 2))
w = np.stack([np.cos(t / n * 2.2), np.sin(t / n * 2.2)], axis=1)         # the true rule slowly rotates with time
y = ((x * w).sum(axis=1) + rng.normal(scale=0.3, size=n) > 0).astype(int)
X = np.column_stack([x, t / n])
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.3, random_state=0)
rand_acc = LogisticRegression().fit(Xtr[:, :2], ytr).score(Xte[:, :2], yte)
cut = int(n * 0.7)
time_acc = LogisticRegression().fit(X[:cut, :2], y[:cut]).score(X[cut:, :2], y[cut:])
print("random split : test accuracy %.3f  (test rows come from the same periods as training rows)" % rand_acc)
print("time split   : test accuracy %.3f  (train on the past, test on the future: what production does)" % time_acc)

# ----- Output (real run) -----
# random split : test accuracy 0.787  (test rows come from the same periods as training rows)
# time split   : test accuracy 0.631  (train on the past, test on the future: what production does)

0.787 with a random split, 0.631 with a time split on the same data: the random number would have promised far more than production delivers.

Good to know

  • Rules: group split when one customer has many rows; time split for time-dependent data; stratified split for rare classes; keep the test set locked until the end.
  • Cross-validation is a way to use small data fully; time-series data needs forward cross-validation (TimeSeriesSplit).

17 ML Pipelines and Orchestration

Picture: A factory conveyor belt with stations. If the paint changes only the painting and later stations must re-run, not the cutting before it.

A pipeline is a DAG (directed acyclic graph) of steps: load → clean → features → train → evaluate → register. An orchestrator runs it on a schedule or on events, retries failures, and remembers which steps are up to date. The simulation shows the caching rule: re-run a step only when its code or its inputs changed.

Which steps re-run after each change? (run for real)
# An ML pipeline is a DAG of steps. Re-run only the steps whose inputs changed (what DVC / Dagster / Airflow caching do).
import hashlib
steps = {"load": [], "clean": ["load"], "features": ["clean"], "train": ["features"], "evaluate": ["train", "features"], "register": ["evaluate"]}
code = {s: "v1" for s in steps}
cache = {}
def run(label):
    out = {}
    ran = []
    for s, deps in steps.items():                                  # dict order is already topological here
        key = hashlib.sha256((code[s] + "".join(out[d] for d in deps)).encode()).hexdigest()[:8]
        if cache.get(s) == key: status = "cached"
        else: cache[s] = key; status = "RUN"; ran.append(s)
        out[s] = key
    print("%-34s ran: %s" % (label, ran if ran else "nothing"))
run("first run")
run("run again, nothing changed")
code["features"] = "v2"; run("changed the feature code")
code["train"] = "v2"; run("changed only the training code")
code["load"] = "v2"; run("new raw data arrived")

# ----- Output (real run) -----
# first run                          ran: ['load', 'clean', 'features', 'train', 'evaluate', 'register']
# run again, nothing changed         ran: nothing
# changed the feature code           ran: ['features', 'train', 'evaluate', 'register']
# changed only the training code     ran: ['train', 'evaluate', 'register']
# new raw data arrived               ran: ['load', 'clean', 'features', 'train', 'evaluate', 'register']

19 The Model Registry: One Source of Truth

Picture: A library catalogue that says which edition of a book is on the shelf now, which are in storage, and which was recalled. You can swap the shelf copy in seconds.

A registry stores versions of a model with their metrics, lineage (run, data, code) and a stage or alias (candidate, staging, production/champion). Serving code asks the registry for 'the champion', never for a file path. The simulation adds a gate (quality and speed) and an instant rollback.

Promotion gate and rollback (run for real)
# A model registry: versions of a model, each with metrics and a stage, plus a gate for promotion and an instant rollback.
class Registry:
    def __init__(self): self.v, self.stage = {}, {}
    def register(self, name, metrics): n = len([k for k in self.v if k[0] == name]) + 1; self.v[(name, n)] = metrics; self.stage[(name, n)] = "None"; return n
    def promote(self, name, n, to, gate=None):
        if gate and not gate(self.v[(name, n)]): print("  v%d NOT promoted to %s: gate failed %s" % (n, to, self.v[(name, n)])); return False
        if to == "Production":
            for k, s in self.stage.items():
                if k[0] == name and s == "Production": self.stage[k] = "Archived"
        self.stage[(name, n)] = to; print("  v%d -> %s" % (n, to)); return True

# A REAL model behind a REAL HTTP server (standard library only), measured with 300 requests on this machine's loopback.
import json, threading, time, urllib.request
from http.server import BaseHTTPRequestHandler, HTTPServer
import numpy as np
from sklearn.datasets import load_digits
from sklearn.ensemble import RandomForestClassifier
X, y = load_digits(return_X_y=True)
model = RandomForestClassifier(n_estimators=100, random_state=0).fit(X, y)
class H(BaseHTTPRequestHandler):
    def log_message(self, *a): pass
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        pred = model.predict(np.array(body["rows"]))           # the model call
        out = json.dumps({"predictions": pred.tolist()}).encode()
        self.send_response(200); self.send_header("Content-Length", str(len(out))); self.end_headers(); self.wfile.write(out)
srv = HTTPServer(("127.0.0.1", 0), H); port = srv.server_port
threading.Thread(target=srv.serve_forever, daemon=True).start()

24 Latency, Throughput and Dynamic Batching

Picture: A lift. Taking one person per trip is quick for them but the queue grows. Waiting a few seconds to fill the lift moves many more people per minute, though the first person waits.

Models often take about the same time for 1 row or 32 rows (fixed overhead + small cost per item). Dynamic batching waits a short time to group requests. The simulation uses an assumed cost (8 ms fixed + 0.5 ms per item) and 300 random arrivals per second.

Batch size and wait window vs latency and throughput (run for real)
# Dynamic batching: wait a little to group requests -> higher throughput, but each request waits. A simulation of the trade-off.
import numpy as np
rng = np.random.default_rng(0)
def simulate(max_batch, max_wait_ms, rate_per_s=300, n=20000, fixed_ms=8.0, per_item_ms=0.5):
    t = np.cumsum(rng.exponential(1000.0 / rate_per_s, n))                  # arrival times in ms
    lat, i, free_at, batches = [], 0, 0.0, 0
    while i < n:
        start = max(t[i], free_at)
        deadline = max(start, t[i] + max_wait_ms)
        j = i + 1
        while j < n and j - i < max_batch and t[j] <= deadline: j += 1
        launch = max(start, t[j - 1]) if j - i < max_batch else max(start, t[j - 1])
        done = launch + fixed_ms + per_item_ms * (j - i)
        lat += list(done - t[i:j]); free_at = done; batches += 1; i = j
    lat = np.array(lat); return n / (free_at / 1000.0), np.mean(lat), np.percentile(lat, 95), n / batches
print("assumed cost model: 8 ms fixed + 0.5 ms per item; 300 requests/second arrive at random")
print("max_batch  max_wait   served/s   mean ms   p95 ms   avg batch")
for mb, mw in [(1, 0), (8, 5), (16, 10), (32, 20), (64, 40)]:
    th, mean, p95, ab = simulate(mb, mw)
    print("%9d  %6d ms  %8.0f  %8.1f  %7.1f  %9.1f" % (mb, mw, th, mean, p95, ab))

# ----- Output (real run) -----
# assumed cost model: 8 ms fixed + 0.5 ms per item; 300 requests/second arrive at random
# max_batch  max_wait   served/s   mean ms   p95 ms   avg batch
#         1       0 ms       118   51841.0  98586.4        1.0
#         8       5 ms       298      14.2     19.2        3.0
#        16      10 ms       299      14.7     20.2        4.0
#        32      20 ms       301      20.6     31.0        7.0

Good to know

  • Trade-off: bigger batches = higher throughput and lower cost, but higher latency. Tune with load tests that mimic real traffic.
  • Inference servers (Triton, vLLM, TGI) have built-in dynamic or continuous batching. See the LLM section for the LLM version.
  • Also useful: warm-up requests before taking traffic, model caching, quantisation (smaller numbers), distillation (smaller models), ONNX Runtime / TensorRT, and CPU vs GPU choices.

26 Safe Releases 2: A/B Tests Without Fooling Yourself

Picture: Two medicines, two groups of patients. If 5.6% got better with B and 5.0% with A, is B truly better, or was it luck? Statistics answers that, but only if you ask once, and only with enough patients.
Significance, sample size and the peeking trap (run for real)
# A/B test: is the new model really better, or just lucky? Two-proportion z-test, sample size, and the 'peeking' trap.
import math
import numpy as np
from scipy import stats
def ztest(c1, n1, c2, n2):
    p1, p2, p = c1 / n1, c2 / n2, (c1 + c2) / (n1 + n2)
    z = (p2 - p1) / math.sqrt(p * (1 - p) * (1 / n1 + 1 / n2)); return p1, p2, z, 2 * (1 - stats.norm.cdf(abs(z)))
p1, p2, z, pv = ztest(500, 10000, 560, 10000)
print("old model 5.0%% vs new 5.6%% with 10,000 users each: z=%.2f  p=%.3f  -> %s" % (z, pv, "significant" if pv < 0.05 else "NOT significant (could be luck)"))
p1, p2, z, pv = ztest(5000, 100000, 5600, 100000)
print("same rates with 100,000 users each:               z=%.2f  p=%.5f -> significant" % (z, pv))
def n_needed(p, lift, alpha=0.05, power=0.8):
    za, zb = stats.norm.ppf(1 - alpha / 2), stats.norm.ppf(power); q = p + lift
    return math.ceil(((za + zb) ** 2 * (p * (1 - p) + q * (1 - q))) / lift ** 2)
print("users needed per group to detect 5.0%% -> 5.6%% (80%% power): %d" % n_needed(0.05, 0.006))
# the peeking trap: both models are IDENTICAL; stop as soon as p < 0.05 at any of 20 looks
rng = np.random.default_rng(0); false_pos = 0; trials = 400
for _ in range(trials):
    a = rng.random(20000) < 0.05; b = rng.random(20000) < 0.05; hit = False
    for look in range(1, 21):
        k = look * 1000; _, _, _, pv = ztest(a[:k].sum(), k, b[:k].sum(), k)
        if pv < 0.05: hit = True; break
    false_pos += hit
print("identical models, peeking 20 times: 'significant' in %.0f%% of experiments (should be 5%% if you look once at the end)" % (100 * false_pos / trials))

# ----- Output (real run) -----
# old model 5.0% vs new 5.6% with 10,000 users each: z=1.89  p=0.058  -> NOT significant (could be luck)
# same rates with 100,000 users each:               z=5.99  p=0.00000 -> significant
# users needed per group to detect 5.0% -> 5.6% (80% power): 21882
# identical models, peeking 20 times: 'significant' in 21% of experiments (should be 5% if you look once at the end)

With 10,000 users per group, 5.0% vs 5.6% is not significant (p=0.058); you need about 21,900 users per group (80% power). And if you peek at the results 20 times and stop as soon as p<0.05, two identical models show a 'winner' in about 21% of experiments instead of 5%.

Good to know

  • Decide before you start: the metric, the minimum effect worth detecting, the sample size, the duration. Then look once (or use sequential testing methods designed for peeking).
  • Randomise at the right unit (user, not request) and check that the groups look alike (sample-ratio mismatch checks).
  • Offline metric gains do not always become online business gains: the A/B test is the judge for product impact.
  • Alternatives for continuous learning: multi-armed bandits and interleaving (ranking systems).

29 Data Drift: Detecting It With PSI and KS

Picture: A weather forecaster trained on summer data starts getting winter inputs. The inputs look different even before any forecast is judged wrong. Drift detection compares 'what we trained on' with 'what arrives now'.

PSI (Population Stability Index) splits a feature into bins and measures how the shares moved. KS test (Kolmogorov–Smirnov) asks whether two samples could come from the same distribution. Commonly used rules of thumb for PSI: below 0.1 stable, 0.1 to 0.25 watch, above 0.25 act (conventions, not laws).

Fig S6 — PSI of one feature as its average drifts away from the training data (simulated weeks).
PSI and KS for a slowly shifting feature (run for real)
# Data drift: compare today's feature values with the training values. PSI (Population Stability Index) and the KS test.
import numpy as np
from scipy import stats
rng = np.random.default_rng(0)
train = rng.normal(50, 10, 20000)
def psi(expected, actual, bins=10):
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected); a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, 1e-4, None), np.clip(a, 1e-4, None); return float(np.sum((a - e) * np.log(a / e)))
print("week  mean shift   PSI    KS p-value   verdict (common rule of thumb: PSI<0.1 stable, 0.1-0.25 watch, >0.25 act)")
rows = []
for week, shift in enumerate([0, 0, 1, 2, 3, 5, 8], 1):
    live = rng.normal(50 + shift, 10, 5000); p = psi(train, live); ks = stats.ks_2samp(train, live).pvalue
    verdict = "stable" if p < 0.1 else ("watch" if p < 0.25 else "ACT")
    print("%4d  %10d  %6.3f  %10.4f   %s" % (week, shift, p, ks, verdict)); rows.append(p)
print("PSI series:", [round(x, 3) for x in rows])
print("Note: with huge samples the KS test flags tiny, harmless shifts; look at the size of the shift (PSI) AND at model performance.")

30 Concept Drift and Retraining Strategies

Picture: Fashion changes. A shop that stopped updating its catalogue in 2019 slowly loses customers. The model's rule 'what predicts a purchase' changes with time.

# Concept drift: the world's RULE changes, so an old model slowly gets worse. Retraining on a schedule vs on a trigger.
import numpy as np
from sklearn.linear_model import LogisticRegression
rng = np.random.default_rng(2)
def batch(week, n=1500):
    x = rng.normal(size=(n, 2)); ang = week * 0.14                              # the true decision rule rotates a little every week
    w = np.array([np.cos(ang), np.sin(ang)]); y = (x @ w + rng.normal(scale=0.3, size=n) > 0).astype(int); return x, y
x0, y0 = batch(0); frozen = LogisticRegression().fit(x0, y0)
sched = LogisticRegression().fit(x0, y0); trig = LogisticRegression().fit(x0, y0)
rows, retrains_trig, retrains_sched = [], 0, 0
for week in range(1, 21):
    x, y = batch(week)
    a_f, a_s, a_t = frozen.score(x, y), sched.score(x, y), trig.score(x, y)
    note = ""
    if a_t < 0.85: trig = LogisticRegression().fit(*batch(week)); retrains_trig += 1; note = "<- trigger: retrain (accuracy fell below 0.85)"
    if week % 8 == 0: sched = LogisticRegression().fit(*batch(week)); retrains_sched += 1

32 Fairness and Bias Monitoring

Picture: A ruler that is slightly shorter for one group of children measures them as smaller even if they are not. A model can do the same when its input data is measured differently for different groups.

The simulation gives group B systematically lower values of an observed feature while the true outcome does not depend on the group. The model never sees the group, yet the results differ.

Group metrics: approval rate, true-positive rate, precision (run for real)
# Monitoring fairness: the same model can work very differently for different groups. Compare rates per group (a simulation with a built-in bias).
import numpy as np
from sklearn.linear_model import LogisticRegression
rng = np.random.default_rng(4)
n = 12000; group = rng.choice(["A", "B"], n, p=[0.8, 0.2])
skill = rng.normal(size=n)
proxy = skill + np.where(group == "B", -0.8, 0.0) + rng.normal(scale=0.5, size=n)         # the observed feature is systematically lower for group B
y = (skill + rng.normal(scale=0.5, size=n) > 0.3).astype(int)                             # the true outcome does not depend on the group
m = LogisticRegression().fit(proxy.reshape(-1, 1), y); pred = m.predict(proxy.reshape(-1, 1))
print("group  share  approved  true-positive rate  precision")
for g in ["A", "B"]:
    mk = group == g; tp = ((pred == 1) & (y == 1) & mk).sum()
    print("  %s    %.2f    %.3f        %.3f              %.3f" % (g, mk.mean(), pred[mk].mean(), tp / ((y == 1) & mk).sum(), tp / max(1, ((pred == 1) & mk).sum())))
ra, rb = pred[group == "A"].mean(), pred[group == "B"].mean()
print("demographic parity difference: %.3f   disparate impact ratio: %.2f (a common rule of thumb flags < 0.80)" % (ra - rb, rb / ra))
print("Different fairness definitions can conflict; choose with the people affected, the law and the use case, and monitor them like any other metric.")

# ----- Output (real run) -----
# group  share  approved  true-positive rate  precision
#   A    0.80    0.422        0.775              0.732
#   B    0.20    0.178        0.421              0.918
# demographic parity difference: 0.244   disparate impact ratio: 0.42 (a common rule of thumb flags < 0.80)
# Different fairness definitions can conflict; choose with the people affected, the law and the use case, and monitor them like any other metric.

Group A is approved 42% of the time, group B 18%. Group B's true-positive rate is 0.42 vs 0.78 for A (many qualified B cases are missed) while precision is higher for B: different fairness measures disagree, which is why they must be chosen with the people affected, not by a formula alone.

Good to know

  • Typical measures: selection rate (demographic parity), true-positive rate (equal opportunity), calibration within groups, disparate-impact ratio (the '80% rule' is a rule of thumb from US employment practice, not a universal law).
  • Monitor fairness over time and per slice, like any other metric; data drift can create unfairness later.
  • Tools: Fairlearn, AIF360, What-If Tool, Evidently fairness reports. Removing the sensitive column does not remove bias (other columns act as proxies).
This is a simulation with a built-in bias made to show the monitoring idea. It is not legal or ethical advice.

# Prompts are code: version them, validate their variables, diff them, roll back. (The model call is not needed to manage the prompt.)
import difflib, hashlib, string
class PromptRegistry:
    def __init__(self): self.versions = {}; self.live = {}
    def add(self, name, template, note):
        v = len([k for k in self.versions if k[0] == name]) + 1
        self.versions[(name, v)] = {"template": template, "note": note, "hash": hashlib.sha256(template.encode()).hexdigest()[:8]}; return v
    def render(self, name, v=None, **vars):
        t = self.versions[(name, v or self.live[name])]["template"]
        needed = {f for _, f, _, _ in string.Formatter().parse(t) if f}
        missing = needed - set(vars)
        if missing: raise KeyError("missing variables: %s" % sorted(missing))
        return t.format(**vars)

42 LLM-as-Judge: Useful and Biased

Picture: Asking a clever friend to grade essays. Fast and cheap, but the friend may prefer the first essay, the longer one, or one written like themselves. So you check the friend against a human teacher first.

Known biases: position bias (prefers the first answer), length bias (prefers longer), self-preference (prefers answers from the same model family), and plain noise. Cures: swap positions and count only consistent verdicts, use clear rubrics, compare against a human-labelled sample (Cohen's kappa), and prefer a different judge model.

Simulated judge: position bias and the swap fix (run for real)
# LLM-as-judge: a model grades answers. Judges have biases (e.g. liking the FIRST answer). A SIMULATION of judge behaviour to show how to measure and reduce it.
import numpy as np
rng = np.random.default_rng(0)
N = 400
truth = rng.choice(["A", "B", "tie"], N, p=[0.4, 0.4, 0.2])                # which answer a careful human prefers
def judge(true, first_is, p_correct=0.80, first_bias=0.65):
    # the simulated judge finds the better answer 80% of the time; on genuine ties or confusion it prefers the answer shown FIRST 65% of the time
    if true != "tie" and rng.random() < p_correct: return true
    return first_is if rng.random() < first_bias else ("B" if first_is == "A" else "A")
def kappa(a, b):
    a, b = np.array(a), np.array(b); po = (a == b).mean(); labels = set(a) | set(b)
    pe = sum((a == l).mean() * (b == l).mean() for l in labels); return (po - pe) / (1 - pe)
single = [judge(t, "A") for t in truth]
print("single call (candidate A always shown first):")
print("  agreement with human %.1f%%   kappa %.2f" % (100 * (np.array(single) == truth).mean(), kappa(single, truth)))
print("  on the human 'tie' cases the judge picks A %.0f%% of the time (it should be mixed)" % (100 * np.mean([s == "A" for s, t in zip(single, truth) if t == "tie"])))
fixed = []
for t in truth:
    r1 = judge(t, "A")                                 # A first
    r2 = judge(t, "B")                                 # second call: the answers are shown in the other order (B first); labels stay the original ones
    fixed.append(r1 if r1 == r2 else "tie")
fixed = np.array(fixed)
print("swap positions, count a win only if both orders agree (else tie):")
print("  agreement with human %.1f%%   kappa %.2f" % (100 * (fixed == truth).mean(), kappa(fixed, truth)))
print("  on human 'tie' cases it answers tie %.0f%% of the time" % (100 * np.mean([f == "tie" for f, t in zip(fixed, truth) if t == "tie"])))

43 How Many Test Cases? Noise and Regression Gates

Picture: Tasting one spoon of soup tells little; tasting ten tells more. A small eval set gives wobbly scores, so a 'better' prompt may only be lucky.

The uncertainty of a pass rate shrinks with the square root of the number of cases: 4 times as many cases halves the uncertainty.

A release gate built on this idea compares old and new versions with a bootstrap interval for the difference. Here the new version is truly 3 points worse; watch how many cases it takes before the gate can prove it:

Bootstrap gate: block only when the whole interval is below zero (run for real)
# A release gate for prompts/models: the new version must not be WORSE than the old one, judged with uncertainty (bootstrap), not by one noisy number.
import numpy as np
rng = np.random.default_rng(0)
def gate(n, old_rate=0.80, new_rate=0.77, margin=0.02, B=4000):
    old = rng.random(n) < old_rate; new = rng.random(n) < new_rate                     # per-case pass/fail on the SAME-size eval set
    diffs = []
    for _ in range(B):
        i = rng.integers(0, n, n); j = rng.integers(0, n, n); diffs.append(new[j].mean() - old[i].mean())
    lo, hi = np.percentile(diffs, [2.5, 97.5]); return new.mean() - old.mean(), lo, hi
print("true quality: old 80%, new 77% (the new version is genuinely 3 points WORSE). Gate rule: BLOCK when the whole 95% interval is below zero.")
print("eval cases  observed diff   95% interval for the difference   verdict")
for n in (30, 100, 400, 1500, 6000):
    d, lo, hi = gate(n)
    verdict = "BLOCK (regression shown)" if hi < 0 else ("inconclusive: collect more cases" if lo < 0 else "pass")
    print("%10d  %+12.3f   [%+.3f, %+.3f]                  %s" % (n, d, lo, hi, verdict))
print("Small eval sets cannot tell a real regression from luck. Size the set for the differences you care about (see the next demo).")

45 Fine-Tuning Operations: SFT, LoRA, QLoRA, DPO

Picture: Teaching a trained chef a new cuisine. Retraining from scratch would take years; instead you add a small recipe notebook (an adapter) that changes how the chef cooks.

LoRA freezes the big weight matrix W and learns a small change B × A of low rank. The program below does this with real PyTorch on a toy layer: it recovers a hidden low-rank change with only 256 trainable numbers instead of 4,096.

A real LoRA update on a toy layer (run for real)
# LoRA idea with real PyTorch: freeze the big weight matrix W and learn only a small low-rank change B @ A.
import torch
torch.manual_seed(0)
d, r = 64, 2
W0 = torch.randn(d, d) / d ** 0.5                                      # the 'pretrained' weights (frozen)
delta = (torch.randn(d, r) @ torch.randn(r, d)) * 0.25 / d ** 0.5        # the new skill we want to teach: a low-rank change
X = torch.randn(512, d); Y = X @ (W0 + delta).T                         # data produced by the 'fine-tuned' target function
A = torch.nn.Parameter(torch.randn(r, d) * 0.1); B = torch.nn.Parameter(torch.zeros(d, r))   # B starts at zero: training starts exactly at W0
opt = torch.optim.Adam([A, B], lr=0.02)
def loss_fn(): return ((X @ (W0 + B @ A).T - Y) ** 2).mean()
print("loss before fine-tuning (just the frozen W0): %.5f" % loss_fn().item())
for step in range(1, 401):
    opt.zero_grad(); l = loss_fn(); l.backward(); opt.step()
    if step in (50, 100, 200, 400): print("step %3d  loss %.6f" % (step, l.item()))

docs = ["Please reset my password, my email is anna.k@example.com and phone +91 98765 43210.",
        "Please reset my password. My email is anna.k@example.com, phone +91 98765 43210",

        "Revenue growth in Europe was twelve percent according to the quarterly report.",
        "Completely different note about the office picnic on Friday afternoon."]

    w = re.findall(r"\w+", t.lower()); return {" ".join(w[i:i + k]) for i in range(max(1, len(w) - k + 1))}
def jac(a, b): return len(a & b) / len(a | b)

47 Serving LLMs: Continuous Batching and vLLM

Picture: A bus that lets new passengers board at every stop, instead of waiting at the terminal until the slowest group finishes. That is continuous batching.

LLMs produce one token at a time. Requests have very different lengths. With static batching every request waits for the longest one in its batch; with continuous batching a free slot is refilled at once. The simulation (16 slots, 400 requests with varied lengths) counts decode steps.

Fig S11 — Tokens produced per decode step (higher = better GPU use), simulated.
Static vs continuous batching (simulation) (run for real)
# Serving LLMs: static batching waits for the longest answer; continuous batching refills a slot the moment a request finishes. A simulation.
import numpy as np
rng = np.random.default_rng(0)
lengths = np.clip(rng.lognormal(mean=4.0, sigma=0.8, size=400).astype(int), 5, 800)        # tokens each request will generate (varied!)
SLOTS = 16
def static(lengths):
    steps = 0
    for i in range(0, len(lengths), SLOTS): steps += lengths[i:i + SLOTS].max()               # the whole batch lasts as long as its longest member
    return steps
def continuous(lengths):
    slots = [0] * SLOTS; q = list(lengths); steps = 0
    while q or any(slots):
        for k in range(SLOTS):
            if slots[k] == 0 and q: slots[k] = q.pop(0)
        steps += 1; slots = [max(0, s - 1) for s in slots]                                      # one decode step: every active slot makes one token
    return steps
tokens = lengths.sum()
for name, f in [("static batching", static), ("continuous batching", continuous)]:
    s = f(lengths); print("%-20s %6d decode steps   %5.1f tokens per step (max possible %d)" % (name, s, tokens / s, SLOTS))
print("requests: %d, mean output %d tokens, longest %d, shortest %d" % (len(lengths), lengths.mean(), lengths.max(), lengths.min()))
print("Real servers (vLLM, TGI, SGLang, TensorRT-LLM) use continuous batching plus paged KV-cache memory for exactly this reason.")

# ----- Output (real run) -----

51 Caching LLM Answers (Exact and Semantic)

An exact cache reuses an answer when the whole prompt is identical. A semantic cache reuses it when a new question is similar enough (by embeddings). The demo uses TF-IDF similarity as a stand-in for embeddings.

54 Structured Output and Validation

Picture: A form with boxes, not a free letter. Programs need fields they can read; free text breaks them.

Models sometimes add chatter, break JSON, or put text where a number belongs. The standard recipe: ask for a schema, validate, and on failure retry with the error message, up to a small limit. (The 'model' here is a scripted stand-in.)

Validate, explain the error, retry (run for real)
# Structured output: ask for JSON, VALIDATE it, and retry with the error message. The 'model' is a scripted stand-in that makes typical mistakes.
import json
def scripted_model(prompt, attempt):
    if "Fix this error" not in prompt and attempt == 0:
        return 'Sure! Here is the JSON: {"name": "Anna", "age": "thirty",}'                       # chatter + trailing comma + wrong type
    if attempt == 1: return '{"name": "Anna", "age": "thirty"}'                                  # valid JSON, still the wrong type
    return '{"name": "Anna", "age": 30}'
def validate(text):
    try: d = json.loads(text)
    except json.JSONDecodeError as e: return None, "not valid JSON (%s)" % e.msg
    if not isinstance(d.get("name"), str): return None, "'name' must be a string"
    if not isinstance(d.get("age"), int): return None, "'age' must be an integer, got %r" % (d.get("age"),)
    return d, None
prompt = "Extract name and age as JSON from: 'Anna is thirty years old.'"
for attempt in range(4):
    out = scripted_model(prompt, attempt); d, err = validate(out)
    print("attempt %d: %-70s -> %s" % (attempt + 1, out[:68], "OK " + str(d) if d else "REJECTED: " + err))
    if d: break
    prompt += "\nFix this error: " + err

55 Gateways, Rate Limits and Retries

Picture: A reception desk for all outgoing calls: it holds the keys, limits who can call, tracks the bills and re-routes when one provider is down.

Providers answer HTTP 429 ('too many requests') when you exceed limits. Retrying instantly makes it worse. The simulation sends 60 clients at once against a limit of 20 requests per second.

Instant retry vs fixed pause vs exponential backoff with jitter (run for real)
# Rate limits (HTTP 429): retrying instantly just hammers the server. Exponential backoff with jitter spreads clients out. Simulated clock, no real waiting.
import random
def simulate(policy, clients=60, limit_per_s=20, horizon=60, tick=0.05, seed=3):
    rnd = random.Random(seed)
    due = {c: 0.0 for c in range(clients)}; tries = {c: 0 for c in range(clients)}; done = {}; used = {}; rejected = 0; t = 0.0
    while len(done) < clients and t < horizon:
        sec = int(t)
        for c in range(clients):
            if c in done or due[c] > t + 1e-9: continue
            if used.get(sec, 0) < limit_per_s: used[sec] = used.get(sec, 0) + 1; done[c] = t
            else:
                rejected += 1; tries[c] += 1
                due[c] = t + {"instant retry": tick, "fixed 1s": 1.0, "backoff + jitter": min(30, 2 ** tries[c]) * rnd.uniform(0.5, 1.0) * 0.5}[policy]
        t += tick
    return len(done), rejected, max(done.values())
print("60 clients arrive at the same moment; the API allows 20 requests per second")
print("policy             finished  wasted calls (429s)  seconds until the last one is served")
for p in ("instant retry", "fixed 1s", "backoff + jitter"):
    f, r, last = simulate(p); print("%-18s %8d  %19d  %.1f" % (p, f, r, last))
print("Instant retries flood the server with useless calls (1200 here). A fixed pause is simple; backoff with jitter spreads many clients out over time and keeps load low, but the last client may wait longer.")
print("Always combine: respect the Retry-After header, cap the retries, add jitter, and set a client-side limit so you do not hit the wall at all.")

# LLM observability: one request = a TRACE made of nested SPANS (retrieval, prompt build, model call, tool call), each with a duration and metadata.
import time, contextlib
spans, stack = [], []
@contextlib.contextmanager
def span(name, **meta):
    s = {"name": name, "depth": len(stack), "meta": meta, "start": time.perf_counter()}; stack.append(s); spans.append(s)
    try: yield s
    finally: s["ms"] = (time.perf_counter() - s["start"]) * 1000; stack.pop()
with span("handle_request", user="u42", prompt_version="support@v2"):
    with span("retrieve", k=4):
        time.sleep(0.012)
    with span("build_prompt"):
        time.sleep(0.001)
    with span("llm_call", model="scripted-model", input_tokens=1800, output_tokens=210):
        time.sleep(0.060)
    with span("tool:lookup_order", order_id="123"):
        time.sleep(0.020)
    with span("llm_call", model="scripted-model", input_tokens=2100, output_tokens=95):
        time.sleep(0.035)
for s in spans: print("%s%-22s %6.0f ms  %s" % ("  " * s["depth"], s["name"], s["ms"], s["meta"]))
llm = sum(s["ms"] for s in spans if s["name"] == "llm_call"); tot = spans[0]["ms"]
print("\nmodel calls took %.0f%% of the request; in/out tokens: %d / %d" % (100 * llm / tot, sum(s["meta"]["input_tokens"] for s in spans if s["name"] == "llm_call"), sum(s["meta"]["output_tokens"] for s in spans if s["name"] == "llm_call")))

58 Operating Agents: Budgets, Loops and Approvals

Step limit, token budget and a loop detector (run for real)
# Agents loop (think -> call a tool -> think ...). Without budgets a confused agent can loop forever and spend money. A scripted agent + limits.
def scripted_agent_step(history):
    # a confused 'model': keeps calling the same search tool because it never finds what it wants
    return {"tool": "search", "args": "annual report 2019 page 7"}
def run(max_steps, max_tokens, tokens_per_step=900):
    history, spent = [], 0
    for step in range(1, 1000):
        if step > max_steps: return "STOPPED: step limit (%d) reached after %d tokens" % (max_steps, spent)
        if spent + tokens_per_step > max_tokens: return "STOPPED: token budget (%d) would be exceeded at step %d (spent %d)" % (max_tokens, step, spent)
        act = scripted_agent_step(history); history.append(act); spent += tokens_per_step
        if len(history) >= 2 and history[-1] == history[-2] == act and len(history) >= 3: return "STOPPED: same tool call repeated 3 times (loop detector) at step %d, %d tokens spent" % (step, spent)
    return "never stopped"

print(" step limit 2 :", run(max_steps=2, max_tokens=200000))

# PROJECT: a tiny but complete MLOps loop in one script -- validate data, train, gate, register, serve, detect drift, retrain, promote.
import json, hashlib, numpy as np, pandas as pd
from scipy import stats
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import roc_auc_score
rng = np.random.default_rng(10)
def make_data(n, shift=0.0, rule=0.0):
    X = pd.DataFrame({"age": rng.normal(40 + shift, 10, n), "visits": rng.poisson(5, n).astype(float), "spend": rng.gamma(2, 50, n)})
    z = 0.04 * (X.age - 40) + 0.2 * (X.visits - 5) + 0.006 * (X.spend - 100) - rule * 0.04 * (X.age - 40) * 2
    y = (z + rng.normal(scale=0.8, size=n) > 0).astype(int); return X, y
def validate(X): assert X.notna().all().all() and (X.age.between(0, 120)).all(), "data validation failed"
registry, serving = {}, {"version": None}
def train_register(X, y, tag):
    validate(X); cut = int(len(X) * 0.8)
    m = GradientBoostingClassifier(random_state=0).fit(X[:cut], y[:cut]); auc = roc_auc_score(y[cut:], m.predict_proba(X[cut:])[:, 1])
    v = len(registry) + 1; registry[v] = {"model": m, "auc": round(auc, 3), "data": hashlib.sha256(X.to_csv().encode()).hexdigest()[:8], "tag": tag, "train_age_mean": X.age.mean()}
    print("registered v%d (%s): AUC %.3f, data %s" % (v, tag, auc, registry[v]["data"])); return v
def promote(v, min_auc=0.75):
    if registry[v]["auc"] >= min_auc: serving["version"] = v; print("  gate passed -> serving v%d" % v)
    else: print("  gate FAILED (AUC below %.2f) -> keep serving v%s" % (min_auc, serving["version"]))
X, y = make_data(6000); promote(train_register(X, y, "initial"))
print("\n--- weeks pass; customers get older and behave differently ---")
Xl, yl = make_data(3000, shift=12, rule=1.0)
m = registry[serving["version"]]["model"]
ks = stats.ks_2samp(X.age, Xl.age).pvalue; live_auc = roc_auc_score(yl, m.predict_proba(Xl)[:, 1])
print("drift check on 'age': KS p=%.2g;  live AUC (labels arrived): %.3f (was %.3f)" % (ks, live_auc, registry[serving["version"]]["auc"]))
if ks < 0.01 or live_auc < registry[serving["version"]]["auc"] - 0.05:
    print("ALERT -> retraining on recent data")
    Xn, yn = make_data(6000, shift=12, rule=1.0); promote(train_register(Xn, yn, "retrained"))
    print("new model on the new world: AUC %.3f" % roc_auc_score(yl, registry[serving["version"]]["model"].predict_proba(Xl)[:, 1]))
print("registry:", {v: (r["tag"], r["auc"]) for v, r in registry.items()}, " serving: v%d" % serving["version"])

import hashlib, json, re
prompts = {1: "Answer the question.", 2: "Answer with only the final answer, no extra words."}
def scripted_llm(prompt, question):                       # behaves differently depending on the prompt text (a stand-in for a real model)
    m = re.search(r"What is (\d+) \+ (\d+)", question); ans = str(int(m.group(1)) + int(m.group(2))) if m else "unknown"
    return ans if "only the final answer" in prompt else "Sure! The result is %s. Let me know if you need anything else." % ans
evalset = [("What is %d + %d?" % (a, b), str(a + b)) for a, b in [(1, 2), (10, 5), (7, 8), (20, 22), (3, 3), (9, 9), (40, 2), (6, 7)]]
def score(v, scorer):
    return sum(scorer(scripted_llm(prompts[v], q), exp) for q, exp in evalset) / len(evalset)
exact = lambda out, exp: out.strip() == exp
live = 1; log = []
for cand in (2,):

70 FAQ

Picture: Click a question to reveal the answer.
Q: Do I need MLOps for one small model?

You need the habits: version data and code, track runs, test, and watch the model. You do not need a big platform.

Q: What is the first thing to set up?

Git for code, a way to version data, experiment tracking, and one repeatable training script. Then a registry and a CI check.

Q: How often should I retrain?

As often as the world changes and labels allow. Measure drift and performance over time (see the concept-drift demo); start with a schedule and add triggers.

Q: How do I know my model got worse if labels arrive late?

Watch proxies (input drift, prediction distribution, business metrics) and evaluate on matured cohorts when labels arrive.

Q: Is MLOps different for LLMs?

Same principles, different artifacts: prompts, eval sets, retrieval indexes, token cost, guardrails and tracing replace much of the training pipeline.

Q: Should I fine-tune or use RAG?

Use prompting + RAG for changing facts and citations; fine-tune for style, format and narrow skills after the eval shows a gap prompting cannot close. They can be combined.

Q: Can an LLM evaluate another LLM reliably?

Partly. Judges are biased (position, length, self-preference); calibrate against human labels and use swapped orders. Keep humans for high-stakes decisions.

Q: How do I control LLM costs?

Shorter prompts and answers, prompt caching, batch APIs, routing easy requests to cheaper models, response caching, budgets and per-feature cost tracking.

Q: Are the commands on this page tested?

The Python programs (scikit-learn, NumPy, SciPy, pandas, PyTorch) were run for real and their output is shown; LLMs inside demos are scripted or simulated and labelled. Cloud, server, GPU and API-key commands are templates, not run.

71 Interview Questions: MLOps (With Answers)

Picture: Grouped by theme, easiest first. Click to reveal.

A. Basics

Q1: What is MLOps?

Practices and tools to take ML models from experiments to reliable, monitored production systems: automation, versioning, testing, deployment, monitoring and retraining.

Q2: How is MLOps different from DevOps?

Behaviour depends on data as well as code, so you version data and models, track experiments, test data and model behaviour, and monitor drift.

Q3: Describe the ML lifecycle.

Problem definition, data collection and validation, features, training and tracking, evaluation, registration, deployment, monitoring, feedback and retraining.

Q4: Why do models fail in production?

Data drift, concept drift, training/serving skew, pipeline bugs, leakage that hid a weak model, latency or cost limits, and missing monitoring.

B. Data and experiments

Q5: What is data leakage? Give examples.

Training uses information unavailable at prediction time: a feature computed from the label, duplicates across splits, future data. Our demo went from 0.67 to 1.00 accuracy with one leaking column.

Q6: How do you version data?

Content-addressed storage with pointers in Git (DVC, lakeFS) or table time travel (Delta, Iceberg); record the data version with every run.

Q7: What goes into experiment tracking?

Parameters, metrics, artifacts, code commit, data version, environment and seed; tools like MLflow or Weights & Biases.

Q8: Why report results over several seeds?

Scores vary with randomness (0.930 to 0.979 in our demo); a single run can mislead.

Q9: Random vs time-based split?

With changing data a random split is optimistic (0.787 vs 0.631 in our demo); time splits imitate production.

Q10: What is a feature store and what is point-in-time correctness?

Shared, consistent features for training and serving; point-in-time joins use only values known at each event time, avoiding future leakage.

Q11: What is training/serving skew and how do you prevent it?

Features computed differently at the two stages. Use one shared transformation (pipeline object, feature store) and compare logged serving features with training features.

C. Pipelines and release

Q12: What does an ML pipeline orchestrator do?

Runs a DAG of steps on schedules or events, retries, caches unchanged steps and records lineage (Airflow, Dagster, Kubeflow ...).

Q13: What is a model registry?

A versioned catalogue of models with metrics, lineage and stages/aliases; serving loads 'champion' by alias and rollbacks are alias moves.

Q14: How do you test ML code and models?

Unit tests for features, data validation, minimum-quality and per-slice tests, invariance and directional tests, a pipeline smoke test and API contract tests.

Q15: CI vs CT vs CD in ML?

CI tests code and data checks on each change; CT retrains models on schedule or triggers; CD packages and releases services and models with canary and rollback.

Q16: Shadow, canary, blue/green, A/B?

Shadow: no user impact, compare. Canary: small share of real traffic. Blue/green: instant switch. A/B: randomised comparison of business impact.

Q17: What is the peeking problem in A/B tests?

Checking significance repeatedly and stopping when p<0.05 inflates false positives (about 21% in our demo with identical models).

D. Serving and monitoring

Q18: Batch vs online inference?

Batch scores on a schedule (simple, cheap, stale); online answers per request (low latency, needs uptime and scaling).

Q19: How do you reduce serving latency and cost?

Load the model once, dynamic batching, smaller or quantised models, ONNX/optimised runtimes, caching, right-sized hardware, autoscaling.

Q20: What is the trade-off in dynamic batching?

Throughput and cost improve while each request waits a little; choose the smallest window that keeps up with load.

Q21: What do you monitor for a model in production?

Infrastructure, service (errors, latency percentiles), data (quality, drift), model (prediction distribution, accuracy when labels arrive, slices) and business metrics.

Q22: Data drift vs concept drift?

Data drift: input distribution changes. Concept drift: the input-to-output relationship changes. Both can degrade a model.

Q23: How do you detect drift?

PSI, KS test, Jensen-Shannon distance, comparing prediction distributions, and monitoring performance on labelled data.

Q24: Schedule or trigger for retraining?

Schedule is simple; triggers react faster but need good monitors and labels; combine them and always gate the result.

E. Advanced

Q25: Why is pickle risky?

Loading it can execute arbitrary code; use safe formats (ONNX, safetensors, skops) and verify files.

Q26: How do you handle delayed labels?

Proxy metrics, matured-cohort evaluation, label-join pipelines, and sampling for human labels.

Q27: How would you monitor fairness?

Track selection rate, true-positive rate and calibration per group over time; choose metrics with stakeholders because they can conflict.

Q28: Design an end-to-end MLOps system for churn prediction.

Versioned data and validated features (feature store or SQL), tracked training pipeline, registry with gates, batch scoring (or an API), monitoring for drift and performance, scheduled retraining with champion/challenger, model card and rollback.

Q29: Your model's accuracy dropped last week. What do you check?

Data pipeline and schema changes first, then input drift, label delays or changes, upstream model or feature changes, deployment changes, and finally real concept drift.

Q30: How would you cut GPU cost for a serving workload?

Measure utilisation, batch, quantise or distil, choose smaller instances, autoscale (down to zero if possible), use spot for training, and cache.

72 Interview Questions: LLMOps (With Answers)

Picture: Grouped by theme, easiest first. Click to reveal.

A. Basics

Q1: What is LLMOps?

Operating applications built on large language models: prompt and model versioning, evaluation, serving, cost and latency control, guardrails, tracing and continuous improvement.

Q2: How is LLMOps different from MLOps?

Free-text outputs need eval sets and judges; cost is per token; prompts are code; you often use a hosted model and rarely train; new risks (hallucination, prompt injection) appear.

Q3: What is a token and why does it matter?

A piece of text the model reads and writes. Cost, latency and context limits are all counted in tokens.

Q4: Prompting, RAG or fine-tuning?

Start with prompting; add RAG for changing or private facts; fine-tune for style, format or narrow skills when evaluation shows a stable gap.

B. Evaluation

Q5: How do you evaluate an LLM application?

An eval set with scorers (exact, regex, schema, retrieval metrics, LLM judge, humans), per-category results, and a frozen regression set run on every change.

Q6: What are LLM-as-judge biases and fixes?

Position, length and self-preference bias; fix with swapped orders, clear rubrics, calibration against human labels (kappa) and a different judge model.

Q7: How many eval cases do you need?

Enough for the differences you care about: the interval shrinks with the square root of n (an 80% rate is ±11 points at n=50 and ±3.5 at n=500).

Q8: How do you stop prompt changes from causing regressions?

Version prompts, run the eval suite in CI with a gate that uses paired comparisons and intervals, canary the release and monitor.

Q9: How do you evaluate a RAG system?

Separate retrieval metrics (hit@k, MRR, recall) from generation metrics (faithfulness, answer relevance), with labelled questions.

C. Serving, cost and latency

Q10: What is continuous batching?

Refilling a batch slot as soon as a request finishes instead of waiting for the longest one; about 2.9x fewer steps in our simulation. Used by vLLM, TGI, SGLang.

Q11: What is the KV cache and why is it a bottleneck?

Per-token key/value memory for each layer; grows with context length and number of concurrent requests, so long prompts exhaust GPU memory. Mitigate with paging, prefix sharing, quantisation and context limits.

Q12: How do you reduce LLM cost?

Shorter prompts and outputs, prompt caching, batch APIs, routing to cheaper models, response caching, retrieving less but better context, budgets.

Q13: Time to first token vs total latency?

TTFT is the wait before output starts; total adds tokens ÷ speed. Streaming makes TTFT the felt latency.

Q14: Exact vs semantic caching risks?

Semantic caches can return a similar but wrong answer (e.g. a different order number) or leak personal data across users; restrict to safe, general content and key by prompt/model version.

Q15: How do you handle 429 rate limits?

Respect Retry-After, exponential backoff with jitter, retry caps, client-side limits, queues, fallbacks and a gateway.

D. Safety, reliability, operations

Q16: What guardrails would you add?

Input and output checks (PII, injection patterns, safety classifiers, schema validation), least-privilege tools, approvals for risky actions, red teaming and monitoring; rules alone miss reworded attacks.

Q17: How do you get reliable JSON out of a model?

Structured-output or tool-calling features, a schema, validation, bounded retries with the error message, and logging failures as eval cases.

Q18: What do you trace in an LLM app?

Spans for retrieval, prompt building, model calls and tools, with model, prompt version, token counts, latency, errors and scores; redact personal data.

Q19: How do you keep agents from running wild?

Step, token and time budgets, loop detection, tool allow-lists, idempotent tools, human approval for irreversible actions and full traces.

Q20: What do you do when a provider deprecates your model?

Pin versions, track notices, keep a tested fallback, re-run the eval set on the replacement, re-tune prompts and migrate behind a flag.

Q21: How do you handle privacy in LLM apps?

Minimise and redact inputs, check provider data terms and regions, enforce access control in retrieval, mask and expire logs.

E. Design

Q22: Design the LLMOps stack for a customer-support assistant.

Gateway with keys and budgets; RAG with an index refresh job and retrieval metrics; versioned prompts; eval set + CI gate; guardrails; routing (cheap first); streaming; caching of general FAQs; tracing and feedback; human escalation; canary and rollback; privacy controls.

Q23: Users complain answers got worse after an upgrade. Steps?

Check traces for model/prompt/index version changes, re-run the eval set on old vs new, compare slices and failure types, roll back by flag, then fix and add tests from the failures.

Q24: When would you self-host an open-weights model?

Strict privacy or residency, steady high volume where GPU cost beats per-token pricing, need for custom fine-tunes; accept the burden of GPUs, scaling, updates and safety.

Q25: How would you explain LoRA?

Freeze the base weights and learn a small low-rank update B×A per layer: far fewer trainable numbers (0.39% for rank 8 on a 4096×4096 layer), small adapter files and easy swapping.

74 Quick Quiz 🎯

Picture: Click each question to reveal the answer.
Q1: Name two reasons a model's accuracy can fall after launch even though the code did not change.

Data drift and concept drift (the world changed), or an upstream data pipeline change.

Q2: What do you need to rebuild a model exactly?

Code version, data version, parameters/config, and the environment (plus seed).

Q3: In our demo, which join leaked the future?

The naive 'latest value' join; the as-of (point-in-time) join did not.

Q4: Why did the time split give 0.631 and the random split 0.787?

The rule drifted over time; random splitting mixed past and future, so test rows resembled training rows.

Q5: What does PSI above 0.25 usually suggest (rule of thumb)?

A large shift: investigate and consider action.

Q6: Why did no-batching serving collapse at 300 requests/s in our simulation?

One-at-a-time service capacity (about 118/s) was below the arrival rate, so the queue grew without limit.

Q7: What is the risk of a semantic cache with a low threshold?

Returning a similar-looking but wrong answer, possibly another user's.

Q8: How much does an LLM adapter of rank 8 add to a 4096×4096 layer?

65,536 trainable numbers (0.39% of 16.8 million).

Q9: Why swap answer positions in an LLM judge?

To cancel position bias; count a win only if both orders agree.

Q10: Why can't a 50-case eval prove a 3-point regression?

The interval is about ±11 points at 50 cases; you need thousands of cases (or paired, richer scores).
