Part A — What an Operating System Is

1 What Is an Operating System?

Picture: A school. The hardware is the building: classrooms (memory), a playground (disk), one or a few teachers (CPU cores). The programs are the students. The operating system is the principal's office: it decides who gets a teacher now, which classroom each student uses, keeps students from fighting over the same desk, and stores everybody's homework safely.
Fig S1 — Layers of a computer system: programs ask the OS; only the OS talks to the hardware directly.
Job of the OSPlain meaningCovered in

SynchronizationStop programs that share data from corrupting itPart D
Memory managementGive each program its own memory and keep them apartPart E
File systems and storageKeep files safe on disks with names and foldersPart F
Device and I/O managementTalk to keyboards, disks, networks through driversPart F

In one line: an operating system is the program that is always running, shares the hardware between many programs safely, and offers them easy services (files, memory, network) so they do not have to touch the hardware themselves.

Good to know

  • Two views: the OS as a resource manager (fair, efficient sharing) and as an extended machine (nice abstractions like 'file' instead of 'sector 81,920').
  • Examples: Linux (Android, servers, most of the cloud), Windows, macOS/iOS (Darwin/XNU kernel), FreeBSD, real-time systems like FreeRTOS and Zephyr.
  • Related guides: Linux, Computer Organization & Architecture, Computer Networks, DBMS, Docker & Kubernetes, C++.

5 User Mode, Kernel Mode and System Calls

Picture: A bank: customers stand on the public side of the counter (user mode). Only staff may enter the vault (kernel mode). To get money you fill a form and hand it through the window: that form is a system call.

The CPU has (at least) two modes. In user mode a program cannot touch hardware or other programs' memory. A system call is a controlled jump into the kernel (a special instruction such as syscall on x86-64 or svc on ARM); the kernel checks the request, does the work and returns. The run below makes real Linux system calls.

open, write, read, stat, unlink: real system calls from Python on Linux (run for real)
# Every program talks to the kernel through SYSTEM CALLS. Python's os module is a thin wrapper around them.
import os, platform
print("uname()      ->", os.uname().sysname, os.uname().release.split("-")[0], os.uname().machine)
print("getpid()     ->", "a number like", type(os.getpid()).__name__, "(this process's id)")
fd = os.open("note.txt", os.O_CREAT | os.O_WRONLY | os.O_TRUNC, 0o644)     # open(2)  -> a small integer: a FILE DESCRIPTOR
print("open()       -> file descriptor", fd, "(0, 1, 2 are already taken by stdin, stdout, stderr)")
n = os.write(fd, b"hello kernel\n"); os.close(fd)                           # write(2), close(2)
print("write()      ->", n, "bytes written")
fd = os.open("note.txt", os.O_RDONLY); data = os.read(fd, 100); os.close(fd) # read(2)
print("read()       ->", data)
st = os.stat("note.txt")                                                    # stat(2)
print("stat()       -> size", st.st_size, "bytes, inode", "a number", ", mode", oct(st.st_mode & 0o777))
os.unlink("note.txt")                                                       # unlink(2)
print("unlink()     -> file removed:", not os.path.exists("note.txt"))

# ----- Output (real run) -----
# uname()      -> Linux 6.18.33.2 x86_64
# getpid()     -> a number like int (this process's id)
# open()       -> file descriptor 3 (0, 1, 2 are already taken by stdin, stdout, stderr)
# write()      -> 13 bytes written
# read()       -> b'hello kernel\n'
# stat()       -> size 13 bytes, inode a number , mode 0o644
# unlink()     -> file removed: True

9 Process States and the Context Switch

Picture: A student in class: ready (hand up, waiting for the teacher), running (talking with the teacher), waiting (gone to fetch a book). Only one student per teacher can be running.
Fig S5 — The five-state process model.

A context switch saves the running process's registers into its PCB and loads another's. It is pure overhead (typically microseconds) and also cools down caches and the TLB. The real Linux process states can be seen with ps: R (running/ready), S (sleeping), D (uninterruptible disk wait), T (stopped), Z (zombie).

10 Creating Processes: fork, exec, wait

Picture: fork is a photocopier for a running program; exec replaces the copy's recipe with a completely different recipe; wait is the parent collecting the child's report card.
fork() for real: separate memory, an exit status, and a zombie (run for real)
# fork(): one process becomes TWO almost identical processes. The return value tells them apart.
import os, sys
x = 10
pid = os.fork()
if pid == 0:                                        # child
    x += 5
    print("child : fork() returned 0, my x =", x, ", parent pid matches:", os.getppid() > 0)
    sys.stdout.flush(); os._exit(7)                 # exit status 7
else:                                               # parent
    _, status = os.waitpid(pid, 0)                  # wait for the child (otherwise it becomes a ZOMBIE)
    print("parent: fork() returned the child's pid; my x is still", x, "(memory is copied, not shared)")
    print("parent: child exited with status", os.WEXITSTATUS(status))
# A zombie: the child has finished but the parent has not collected its exit status yet
pid = os.fork()
if pid == 0:
    os._exit(0)
import time; time.sleep(0.3)
state = open("/proc/%d/stat" % pid).read().split(")")[1].split()[0]
print("\nunwaited finished child is in state:", state, "(Z = zombie)")
os.waitpid(pid, 0)
print("after waitpid() the zombie is gone:", not os.path.exists("/proc/%d" % pid))

# ----- Output (real run) -----
# child : fork() returned 0, my x = 15 , parent pid matches: True
# parent: fork() returned the child's pid; my x is still 10 (memory is copied, not shared)
# parent: child exited with status 7
#
# unwaited finished child is in state: Z (Z = zombie)
# after waitpid() the zombie is gone: True

After fork the child changes x to 15 but the parent still sees 10: each has its own memory. A finished child that nobody has waited for shows state Z (zombie) until the parent calls waitpid.

A shell runs printf ... | wc -w exactly like this: two forks, a pipe, and two execs.

fork + exec + pipe: building a shell pipeline by hand — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
# fork + exec + pipe: how a shell runs  "printf ... | wc -w"
import os
r, w = os.pipe()                                   # a pipe: a one-way byte channel inside the kernel (two file descriptors)
p1 = os.fork()
if p1 == 0:                                        # child 1: stdout -> pipe write end, then BECOME printf
    os.dup2(w, 1); os.close(r); os.close(w)
    os.execvp("printf", ["printf", "the quick brown fox jumps"])
p2 = os.fork()
if p2 == 0:                                        # child 2: stdin <- pipe read end, then BECOME wc -w
    os.dup2(r, 0); os.close(r); os.close(w)
    os.execvp("wc", ["wc", "-w"])
os.close(r); os.close(w)                           # the parent must close its copies, or wc never sees end-of-file
for p in (p1, p2): os.waitpid(p, 0)
print("(the number above was printed by 'wc', a different program that replaced the child via exec)")

# ----- Output (real run) -----
# 5
# (the number above was printed by 'wc', a different program that replaced the child via exec)

The output '5' was printed by the real wc program; our child process became wc through exec.

The same in C (template, not run)
/* fork + exec + wait in C (POSIX). Compile on Linux:  gcc -Wall fork.c -o fork && ./fork      (template: not run here) */
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>
int main(void) {
    pid_t pid = fork();                       /* -1 error, 0 in the child, child's pid in the parent */
    if (pid < 0) { perror("fork"); exit(1); }
    if (pid == 0) {
        char *args[] = {"ls", "-l", NULL};
        execvp("ls", args);                   /* replaces this program; returns only on error */
        perror("execvp"); _exit(127);
    }
    int status;
    waitpid(pid, &status, 0);                 /* reap the child: no zombie */
    if (WIFEXITED(status)) printf("child exited with %d\n", WEXITSTATUS(status));
    return 0;
}

Good to know

  • Zombie: finished, but its exit status is not collected yet (wastes a process-table slot). Orphan: its parent died first; PID 1 adopts it and reaps it.
  • Linux makes fork cheap with copy-on-write: pages are shared until one side writes (Part E).
  • Modern alternatives: posix_spawn, vfork, clone (Linux, also used for threads and containers).

Private memory vs a shared mmap after fork (run for real)
# Memory after fork: normal memory is COPIED (copy-on-write); a shared mapping (mmap) is truly shared.
import os, mmap, ctypes
private = bytearray(b"A" * 8)
shared = mmap.mmap(-1, 8, flags=mmap.MAP_SHARED | mmap.MAP_ANONYMOUS)
shared[:] = b"A" * 8
pid = os.fork()
if pid == 0:
    private[0:5] = b"CHILD"; shared[0:5] = b"CHILD"; os._exit(0)
os.waitpid(pid, 0)
print("private bytearray seen by parent :", bytes(private))
print("shared mmap seen by parent       :", shared[:])
print("page size on this machine        :", mmap.PAGESIZE, "bytes")

# ----- Output (real run) -----
# private bytearray seen by parent : b'AAAAAAAA'
# shared mmap seen by parent       : b'CHILDAAA'
# page size on this machine        : 4096 bytes

The child's change to the private bytearray is invisible to the parent (copy-on-write gave it its own copy), but its change to the shared mapping is visible: that is shared-memory IPC.

Good to know

  • Shared memory + a semaphore is the classic fast IPC; message passing is safer and easier to reason about.
  • Across machines see Computer Networks (sockets, TCP).

12 Signals: Tapping a Process on the Shoulder

Picture: A referee's whistle. Some whistles mean 'please stop when you can' (SIGTERM); one means 'off the field, now' (SIGKILL) and cannot be argued with.
Handlers, a polite shutdown, and why SIGKILL always wins (run for real)
# Signals: tiny notifications the kernel delivers to a process (Ctrl+C = SIGINT, kill = SIGTERM, kill -9 = SIGKILL).
import os, signal, sys, time
got = []
signal.signal(signal.SIGUSR1, lambda sig, frame: got.append("SIGUSR1"))
os.kill(os.getpid(), signal.SIGUSR1); time.sleep(0.05)
print("my handler ran for:", got)
try:
    signal.signal(signal.SIGKILL, lambda s, f: None)
except (OSError, ValueError) as e:
    print("trying to catch SIGKILL ->", type(e).__name__, ": SIGKILL and SIGSTOP can never be caught or ignored")
sys.stdout.flush()                                     # flush before fork, or the child inherits unprinted text
pid = os.fork()
if pid == 0:
    signal.signal(signal.SIGTERM, lambda s, f: (print("child : got SIGTERM, cleaning up and exiting politely", flush=True), os._exit(0)))
    while True: time.sleep(0.1)
time.sleep(0.2); os.kill(pid, signal.SIGTERM); _, st = os.waitpid(pid, 0)
print("parent: child exit status", os.WEXITSTATUS(st))
pid = os.fork()
if pid == 0:
    signal.signal(signal.SIGTERM, signal.SIG_IGN)       # a stubborn child that ignores SIGTERM
    while True: time.sleep(0.1)
time.sleep(0.2); os.kill(pid, signal.SIGTERM); time.sleep(0.2)
print("stubborn child still alive after SIGTERM:", os.waitpid(pid, os.WNOHANG) == (0, 0))
os.kill(pid, signal.SIGKILL); _, st = os.waitpid(pid, 0)
print("after SIGKILL: killed by signal", os.WTERMSIG(st), "(9 = SIGKILL)")

# ----- Output (real run) -----
# my handler ran for: ['SIGUSR1']
# trying to catch SIGKILL -> OSError : SIGKILL and SIGSTOP can never be caught or ignored
# child : got SIGTERM, cleaning up and exiting politely
# parent: child exit status 0
# stubborn child still alive after SIGTERM: True
# after SIGKILL: killed by signal 9 (9 = SIGKILL)

# Round Robin: the time slice (quantum) trades response time against context-switch overhead.
import random
random.seed(1)
jobs = [(random.randint(0, 30), random.randint(2, 20)) for _ in range(12)]        # (arrival, burst)
def rr(q, switch_cost=0.5):
    t, rem, queue, i, done, switches, first = 0.0, [b for _, b in jobs], [], 0, {}, 0, {}
    order = sorted(range(len(jobs)), key=lambda k: jobs[k][0])
    while len(done) < len(jobs):
        while i < len(order) and jobs[order[i]][0] <= t: queue.append(order[i]); i += 1
        if not queue: t = jobs[order[i]][0]; continue
        k = queue.pop(0); first.setdefault(k, t)
        run = min(q, rem[k]); t += run; rem[k] -= run
        while i < len(order) and jobs[order[i]][0] <= t: queue.append(order[i]); i += 1
        if rem[k] > 0: queue.append(k)
        else: done[k] = t
        t += switch_cost; switches += 1
    resp = sum(first[k] - jobs[k][0] for k in first) / len(jobs); tat = sum(done[k] - jobs[k][0] for k in done) / len(jobs)
    return resp, tat, switches
print("quantum  avg response  avg turnaround  context switches   (each switch costs 0.5 units: ASSUMED)")

22 Race Conditions: When Sharing Goes Wrong

Picture: Two people update the same shared bank balance of ₹100 at the same moment. Both read 100, one adds 50, the other adds 20, and each writes its answer. The balance ends at 150 or 120, not 170. One update is lost.

counter += 1 looks like one step but is three: read, add, write. If two workers interleave those steps, updates disappear. Real run on Linux: 4 processes × 200,000 increments on shared memory.

# A RACE CONDITION, for real: 4 processes add 1 to a shared counter 200,000 times each, with and without a lock.
import multiprocessing as mp
def work(counter, n, lock):
    for _ in range(n):
        if lock:
            with lock: counter.value += 1
        else:
            counter.value += 1           # read, add, write: three steps that another process can interleave
def run(use_lock, procs=4, n=200_000):
    c = mp.Value("i", 0, lock=False); lk = mp.Lock() if use_lock else None
    ps = [mp.Process(target=work, args=(c, n, lk)) for _ in range(procs)]
    [p.start() for p in ps]; [p.join() for p in ps]
    return c.value
if __name__ == "__main__":

23 The Critical-Section Problem and Peterson's Solution

Picture: One bathroom, one key. Rules: only one person inside (mutual exclusion); if it is free and someone wants it, someone gets in (progress); nobody waits forever (bounded waiting).

Can two threads get mutual exclusion using only ordinary shared variables? The naive idea 'wait until busy is false, then set it' fails. Peterson's algorithm (1981) works for two threads using a flag per thread and a shared turn. The program below checks every possible interleaving of the two threads.

Exhaustive check of all interleavings (run for real)
# Checking a lock algorithm by trying EVERY possible interleaving of two threads (a tiny model checker).
# Each thread: [entry protocol] -> critical section -> [exit]. We look for any order that puts BOTH in the critical section.
def explore(program, init):
    seen, bad = set(), []
    def step(state, pcs, trace):
        key = (tuple(sorted(state.items())), pcs)
        if key in seen: return
        seen.add(key)
        if all(program[i][pcs[i]][0] == "cs" for i in (0, 1)): bad.append(trace); return
        for i in (0, 1):
            ins = program[i][pcs[i]]
            if ins[0] == "done": continue
            new, pc = dict(state), pcs[i]
            if ins[0] == "set": new[ins[1]] = ins[2]; pc += 1
            elif ins[0] == "wait": pc = pc + 1 if ins[1](new) else pc        # busy-wait: move on only when the condition holds
            elif ins[0] == "cs": pc += 1
            if (new, pc) == (state, pcs[i]) and ins[0] == "wait": continue
            np = list(pcs); np[i] = pc; step(new, tuple(np), trace + ["T%d:%s" % (i, ins[0])])
    step(init, (0, 0), []); return bad, len(seen)
naive = [[("wait", lambda s: not s["busy"]), ("set", "busy", True), ("cs",), ("set", "busy", False), ("done",)]] * 2
peter = [[("set", "flag0", True), ("set", "turn", 1), ("wait", lambda s: not s["flag1"] or s["turn"] == 0), ("cs",), ("set", "flag0", False), ("done",)],
         [("set", "flag1", True), ("set", "turn", 0), ("wait", lambda s: not s["flag0"] or s["turn"] == 1), ("cs",), ("set", "flag1", False), ("done",)]]
bad, n = explore(naive, {"busy": False})
print("naive 'check busy, then set busy': %d states explored, %d interleavings put BOTH threads inside. Example: %s" % (n, len(bad), bad[0] if bad else None))
bad, n = explore(peter, {"flag0": False, "flag1": False, "turn": 0})
print("Peterson's algorithm:              %d states explored, %d interleavings put both inside" % (n, len(bad)))
print("(This assumes each step is atomic and memory is sequentially consistent; real CPUs reorder memory, so real code uses atomic instructions and fences.)")

27 Monitors and Condition Variables

Picture: A doctor's waiting room with a receptionist: only one patient in the consulting room (the lock), and patients who cannot be seen yet sit in a waiting area until their name is called (condition variable).

A monitor = a lock + condition variables + the shared data, packaged together. wait() releases the lock and sleeps; notify() wakes a waiter, which re-checks its condition. Real threads below, with a bounded buffer of 3 slots:

Producer-consumer with a condition variable (run for real)
# Producer-consumer with a bounded buffer (size 3), using a condition variable. Real threads.
import threading, collections, time
buf, CAP = collections.deque(), 3
cv = threading.Condition(); log = []; max_seen = 0
def producer():
    global max_seen
    for i in range(8):
        with cv:
            while len(buf) == CAP: cv.wait()               # buffer full: sleep (not spin)
            buf.append(i); max_seen = max(max_seen, len(buf)); cv.notify_all()
def consumer(out):

29 Deadlock: The Four Conditions

Picture: Two cars meet on a one-lane bridge. Each waits for the other to reverse. Nobody moves, forever.

A deadlock needs all four (Coffman) conditions: (1) mutual exclusion (resources cannot be shared), (2) hold and wait (holding one while waiting for another), (3) no preemption (cannot be taken away), (4) circular wait (A waits for B waits for A). Real run with two locks taken in opposite order, using a timeout so the demo ends:

Opposite lock order vs same lock order (run for real)
# DEADLOCK, for real (with a timeout so the demo ends): two threads take two locks in OPPOSITE order.

a, b = threading.Lock(), threading.Lock()
log = []
def worker(name, first, second):
    with first:
        time.sleep(0.1)                                   # make the bad interleaving likely
        ok = second.acquire(timeout=1.0)
        log.append("%s: %s" % (name, "got both locks" if ok else "STUCK waiting 1 s for the other lock -> deadlock"))
        if ok: second.release()
t1 = threading.Thread(target=worker, args=("T1", a, b)); t2 = threading.Thread(target=worker, args=("T2", b, a))
t1.start(); t2.start(); t1.join(); t2.join(); print("opposite order :", log)
log.clear()
t1 = threading.Thread(target=worker, args=("T1", a, b)); t2 = threading.Thread(target=worker, args=("T2", a, b))   # same global order
t1.start(); t2.start(); t1.join(); t2.join(); print("same order     :", log)

30 Deadlock Avoidance: The Banker's Algorithm

Picture: A bank lends money only if, after the loan, it can still satisfy every customer's maximum need in some order. Otherwise the customer waits.

Data: Available, Max, Allocation, Need = Max − Allocation. A state is safe if there is an order in which every process can get its remaining need and finish. The classic textbook example (5 processes, resources A, B, C):

Safety check and three requests (run for real)
# Banker's algorithm: grant a request only if the system stays in a SAFE state (some order lets everyone finish).
avail = [3, 3, 2]
maxneed = {"P0": [7, 5, 3], "P1": [3, 2, 2], "P2": [9, 0, 2], "P3": [2, 2, 2], "P4": [4, 3, 3]}
alloc = {"P0": [0, 1, 0], "P1": [2, 0, 0], "P2": [3, 0, 2], "P3": [2, 1, 1], "P4": [0, 0, 2]}
def need(p): return [m - a for m, a in zip(maxneed[p], alloc[p])]
def safe(avail, alloc):
    work, fin, seq = avail[:], set(), []
    while len(fin) < len(alloc):
        for p in alloc:
            if p not in fin and all(n <= w for n, w in zip([m - a for m, a in zip(maxneed[p], alloc[p])], work)):
                work = [w + a for w, a in zip(work, alloc[p])]; fin.add(p); seq.append(p); break
        else: return None
    return seq
print("need matrix:", {p: need(p) for p in alloc})
print("safe sequence now:", safe(avail, alloc))
def request(p, req):
    if any(r > n for r, n in zip(req, need(p))): return "error: asks for more than its declared maximum"
    if any(r > a for r, a in zip(req, avail)): return "must wait: not enough free resources"
    new_av = [a - r for a, r in zip(avail, req)]; new_al = dict(alloc); new_al[p] = [a + r for a, r in zip(alloc[p], req)]
    s = safe(new_av, new_al); return ("GRANT, still safe: %s" % s) if s else "DENY: would leave the system unsafe"
print("P1 requests [1,0,2] ->", request("P1", [1, 0, 2]))
print("P4 requests [3,3,0] ->", request("P4", [3, 3, 0]))
print("P0 requests [0,2,0] ->", request("P0", [0, 2, 0]))

# ----- Output (real run) -----
# need matrix: {'P0': [7, 4, 3], 'P1': [1, 2, 2], 'P2': [6, 0, 0], 'P3': [0, 1, 1], 'P4': [4, 3, 1]}
# safe sequence now: ['P1', 'P3', 'P0', 'P2', 'P4']
# P1 requests [1,0,2] -> GRANT, still safe: ['P1', 'P3', 'P0', 'P2', 'P4']
# P4 requests [3,3,0] -> DENY: would leave the system unsafe
# P0 requests [0,2,0] -> GRANT, still safe: ['P3', 'P1', 'P0', 'P2', 'P4']

P1's request keeps the system safe, so it is granted. P4's request [3,3,0] would leave only [0,0,2] free, from which no process can finish: denied, even though the resources are physically available. (Each request is checked against the original state.)

Good to know

  • Needs every process to declare its maximum in advance and costs O(m·n²) per check, so general-purpose OSes rarely use it; the idea of a safe state is what matters.

# Deadlock detection: build a WAIT-FOR graph (who waits for whom) and look for a cycle.
def find_cycle(g):
    color, stack = {}, []
    def dfs(u):
        color[u] = "grey"; stack.append(u)
        for v in g.get(u, []):
            if color.get(v) == "grey": return stack[stack.index(v):] + [v]
            if v not in color:
                c = dfs(v)
                if c: return c
        color[u] = "black"; stack.pop(); return None
    for u in g:
        if u not in color:
            c = dfs(u)
            if c: return c
    return None
print("graph A:", {"T1": ["T2"], "T2": ["T3"], "T3": []}, "-> cycle:", find_cycle({"T1": ["T2"], "T2": ["T3"], "T3": []}))
g = {"T1": ["T2"], "T2": ["T3"], "T3": ["T1"], "T4": ["T1"]}
print("graph B:", g, "-> cycle:", find_cycle(g))
print("Recovery choices: abort one process in the cycle (the 'cheapest' victim), or pre-empt a resource and roll it back.")

38 Virtual Memory and Demand Paging

Picture: A library lends you a book only when you open it at that chapter. You can 'own' a 1,000-page book while carrying only the 3 pages you are reading.

Demand paging: a page is brought into RAM only when first touched. The first touch causes a (minor or major) page fault; the OS finds a frame, fills it (zeros or data from disk) and restarts the instruction. Real measurement on Linux:

Reserving 200 MiB costs nothing; touching it costs one fault per page (run for real)
# Demand paging: memory pages are given to a process only when it TOUCHES them (each first touch = a minor page fault).

print("after reserving 200 MiB  : %6d new minor faults (nothing touched yet)" % (faults() - f0))
for off in range(0, size // 2, mmap.PAGESIZE): m[off] = 1  # touch the first half, one byte per page
f1 = faults()
print("after touching 100 MiB   : %6d new minor faults (about one per 4 KiB page = %d pages)" % (f1 - f0, size // 2 // mmap.PAGESIZE))
for off in range(0, size // 2, mmap.PAGESIZE): m[off] = 2  # touch the SAME pages again
print("touching them a 2nd time : %6d new minor faults (pages are already mapped)" % (faults() - f1))

Good to know

  • Minor fault: the page is in RAM or just needs a zeroed frame. Major fault: data must be read from disk: thousands of times slower.
  • Benefits: programs larger than RAM, faster start-up, more programs in memory, cheap fork, memory-mapped files.
  • Linux overcommits: it may promise more memory than exists; if everyone uses it, the OOM killer ends a process (often seen in containers).

39 Page Replacement Algorithms

# Page replacement: which page leaves memory when a new one must come in? Count page FAULTS.
def fifo(refs, n):
    mem, f, order = set(), 0, []
    for p in refs:
        if p not in mem:
            f += 1
            if len(mem) == n: mem.discard(order.pop(0))
            mem.add(p); order.append(p)
    return f
def lru(refs, n):
    mem, f = [], 0
    for p in refs:
        if p in mem: mem.remove(p)
        else:
            f += 1
            if len(mem) == n: mem.pop(0)
        mem.append(p)
    return f
def opt(refs, n):
    mem, f = set(), 0
    for i, p in enumerate(refs):
        if p in mem: continue
        f += 1
        if len(mem) == n:
            nxt = {q: (refs.index(q, i + 1) if q in refs[i + 1:] else 10 ** 9) for q in mem}
            mem.discard(max(nxt, key=nxt.get))
        mem.add(p)
    return f
def clock(refs, n):
    frames, bits, hand, f = [None] * n, [0] * n, 0, 0
    for p in refs:
        if p in frames: bits[frames.index(p)] = 1; continue
        f += 1
        while bits[hand]: bits[hand] = 0; hand = (hand + 1) % n
        frames[hand], bits[hand] = p, 1; hand = (hand + 1) % n
    return f

#
# Belady's anomaly with FIFO on [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
#   3 frames: 9 faults   4 frames: 10 faults   <- MORE memory, MORE faults!
#   LRU on the same string: 3 frames 10, 4 frames 8 (LRU never shows the anomaly)

OPT is always lowest (it is the yardstick). LRU is close to OPT at 3+ frames on this string. With FIFO on the string 1,2,3,4,1,2,5,1,2,3,4,5, 4 frames give 10 faults but 3 frames give 9: Belady's anomaly. LRU and OPT are 'stack algorithms' and never show it. Honest detail: on this short string FIFO beat LRU at 2 frames; no practical policy wins on every input.

Good to know

  • Exact LRU is too expensive in hardware, so real systems approximate it: the Clock (second-chance) algorithm uses the accessed bit; Linux uses active/inactive lists (and newer multi-generational LRU).
  • A dirty page must be written back before reuse: replacing clean pages is cheaper.

40 Thrashing and the Working Set

Picture: Too many students sharing too few desks: everyone spends the day carrying books back and forth and nobody studies.
Fig S11 — CPU busy vs number of programs in memory (simple model with ASSUMED numbers).
The thrashing cliff (model) (run for real)
# Thrashing (a simple model): more programs in memory -> more CPU use, until their working sets no longer fit.
FRAMES, WS = 1000, 120                                       # ASSUMED: 1000 frames in RAM, each program needs ~120 pages to run smoothly
print("programs  frames each  CPU busy (model)")
rows = []
for n in (1, 2, 4, 6, 8, 9, 10, 12, 16, 20):
    each = FRAMES / n
    miss = max(0.0, (WS - each) / WS)                         # share of the working set that does not fit
    fault_rate = 0.0005 + 0.2 * miss                          # ASSUMED: faults per memory access grow fast when the working set does not fit
    io_wait = fault_rate * 10_000 / (1 + fault_rate * 10_000) # each fault costs ~10,000 access-times of waiting
    single_busy = 1 - io_wait
    busy = 1 - (1 - single_busy) ** n                         # CPU is busy if ANY program is runnable
    rows.append(busy); print("%8d  %11.0f  %6.0f%%" % (n, each, 100 * busy))
print("Fixes: give each process enough frames for its working set (working-set model, page-fault frequency control), or run fewer programs at once.")

46 Disk Scheduling (Hard Disks)

Picture: A lift in a tall building. Going to floors in the order buttons were pressed wastes time zig-zagging; sweeping up then down (the elevator algorithm) is smoother.
Fig S12 — Total head movement for the same 8 requests (cylinders, simulated).
FCFS, SSTF, SCAN, C-SCAN, LOOK (run for real)
# Disk scheduling for a hard disk: how far must the head travel? (cylinders 0..199, head starts at 53)
reqs, start, hi = [98, 183, 37, 122, 14, 124, 65, 67], 53, 199
def total(path): return sum(abs(a - b) for a, b in zip(path, path[1:]))
def fcfs(): return [start] + reqs
def sstf():
    left, cur, path = reqs[:], start, [start]
    while left:
        n = min(left, key=lambda r: abs(r - cur)); left.remove(n); path.append(n); cur = n
    return path
def scan():
    up = sorted(r for r in reqs if r >= start); down = sorted((r for r in reqs if r < start), reverse=True)
    return [start] + up + [hi] + down
def cscan():
    up = sorted(r for r in reqs if r >= start); low = sorted(r for r in reqs if r < start)
    return [start] + up + [hi, 0] + low
def look():
    up = sorted(r for r in reqs if r >= start); down = sorted((r for r in reqs if r < start), reverse=True)
    return [start] + up + down
print("requests:", reqs, " head at", start)
for name, f in [("FCFS", fcfs), ("SSTF", sstf), ("SCAN (elevator)", scan), ("C-SCAN", cscan), ("LOOK", look)]:
    p = f(); print("%-16s %4d cylinders   path %s" % (name, total(p), p))
print("(C-SCAN counts the jump back from 199 to 0 as movement; some books do not.)")

# ----- Output (real run) -----

56 Interview Questions (With Answers)

Picture: Grouped by theme, easiest first. Click to reveal.

A. Basics

Q1: What is an operating system?

Software that manages hardware resources and provides services and abstractions (processes, memory, files, devices) to programs, safely and fairly.

Q2: What is a kernel? Monolithic vs microkernel?

The core running in privileged mode. Monolithic: all services inside (fast, less isolated; Linux). Microkernel: minimal kernel, services in user space via messages (isolated, slower; QNX, seL4).

Q3: What is a system call?

A controlled entry from user mode into the kernel to request a service such as open, read, fork.

Q4: Process vs program vs thread?

Program: passive file. Process: program in execution with its own address space. Thread: unit of execution inside a process sharing its memory.

B. Processes

Q5: Explain the process states.

New, ready, running, waiting (blocked), terminated, with transitions on dispatch, preemption, I/O wait/completion and exit.

Q6: What does fork return?

0 in the child, the child's PID in the parent, −1 on error.

Q7: Zombie vs orphan?

Zombie: finished but not yet reaped by its parent (state Z). Orphan: parent died; adopted by PID 1.

Q8: What is a context switch and why is it costly?

Saving one task's CPU state and loading another's; costs time directly and indirectly through cold caches and TLB.

Q9: IPC methods?

Pipes, FIFOs, shared memory, message queues, sockets, signals, files.

C. Scheduling

Q10: Compare FCFS, SJF, SRTF, RR and priority.

FCFS simple but convoy effect; SJF/SRTF minimise average waiting but need burst estimates and can starve long jobs; RR fair and responsive, quantum matters; priority needs aging to avoid starvation.

Q11: What happens if the RR quantum is very small or very large?

Very small: too many context switches. Very large: becomes FCFS with poor response.

Q12: What scheduler does Linux use?

For normal tasks EEVDF since kernel 6.6 (replacing CFS); real-time classes SCHED_FIFO/RR/DEADLINE.

D. Synchronization and deadlock

Q13: What is a race condition?

Result depends on the timing of concurrent operations on shared data (our demo lost roughly 60 to 70 percent of the increments).

Q14: Mutex vs semaphore?

Mutex: ownership-based lock for mutual exclusion. Semaphore: counter for N resources or for signalling; no owner.

Q15: Spinlock vs mutex?

Spinlock busy-waits (good for very short holds on multi-core); mutex sleeps.

Q16: Four conditions for deadlock?

Mutual exclusion, hold and wait, no preemption, circular wait.

Q17: How do you prevent deadlock in practice?

Global lock ordering, timeouts with retry, acquiring all resources at once, avoiding nested locks.

Q18: Explain the Banker's algorithm.

Grant a request only if the resulting state is safe, i.e. some order lets every process obtain its maximum need and finish.

Q19: What is priority inversion?

High-priority task waits on a lock held by a low-priority task that a medium task preempts; fix with priority inheritance (Mars Pathfinder, 1997).

E. Memory

Q20: Paging vs segmentation?

Paging: fixed-size pages, no external fragmentation, invisible to programmers. Segmentation: variable logical segments, external fragmentation.

Q21: What is a TLB?

A small hardware cache of virtual-to-physical translations that avoids walking the page table on most accesses.

Q22: What is a page fault?

An exception when a page is not mapped; the OS loads or allocates it and restarts the instruction (or kills the process on an invalid access).

Q23: Explain Belady's anomaly.

With FIFO, more frames can cause more faults (9 with 3 frames vs 10 with 4 on 1,2,3,4,1,2,5,1,2,3,4,5).

Q24: What is thrashing and how do you fix it?

Processes spend most time paging because working sets do not fit; reduce multiprogramming or allocate by working set/PFF.

Q25: Internal vs external fragmentation?

Internal: unused space inside an allocated block. External: free space split into small holes.

F. Storage and others

Q26: Hard link vs soft link?

Hard link: another name for the same inode. Soft link: a file containing a path.

Q27: What is journaling?

Logging intended changes before applying them so the file system can recover consistently after a crash.

Q28: What is DMA?

Direct Memory Access: a controller moves data between device and memory without the CPU copying each byte.

Q29: VM vs container?

VM virtualises hardware and runs its own kernel; a container is an isolated process group sharing the host kernel.

Q30: What happens when you type a command in a shell and press Enter?

The shell parses it, forks, the child execs the program (loader maps the ELF, demand paging brings pages in), the parent waits; output goes through file descriptors to the terminal.

58 FAQ

Picture: Click a question to reveal the answer.
Q: Which OS should I learn on?

Linux: it is open, used on servers and in the cloud, and every concept can be observed with real tools (/proc, strace).

Q: Why does my computer show little 'free' memory?

The OS uses free RAM as a file cache and gives it back when programs need it; look at 'available', not 'free'.

Q: Are threads always faster than processes?

Cheaper to create and to share data, but sharing needs locks, and one crash takes down all threads. In CPython, CPU-heavy work usually needs processes.

Q: Do I need to memorise every scheduling algorithm?

Understand the trade-offs (waiting time, response, starvation, overhead) and be able to draw a Gantt chart; exams love it.

Q: Were the code samples really run?

Yes for the Python demos (Linux system calls inside WSL and simulations on Windows) and the C++ threads program; the C POSIX programs and admin commands are templates, labelled so.

Q: Which books are classic?

Silberschatz, Galvin and Gagne 'Operating System Concepts'; Tanenbaum 'Modern Operating Systems'; the free online 'Operating Systems: Three Easy Pieces' (OSTEP).

59 Common Mistakes and Checklist

Picture: Traps students and engineers fall into.

🔀 Forgetting to wait()

Zombies pile up; always reap children.

🧵 Unlocked shared data

Races lose updates silently.

🔒 Locks in different orders

Deadlock; use one global order.

❓ 'if' instead of 'while' around wait()

Spurious wake-ups break the condition.

🚪 Ignoring SIGTERM

Services get killed hard; handle shutdown.

📏 Confusing internal and external fragmentation

Inside a block vs between blocks.

🧮 Gantt chart off-by-one

Waiting = turnaround − burst; check with a table.

💾 Trusting write() means on disk

Use fsync for durability.

SRTF (3.4).

Mutual exclusion, hold and wait, no preemption, circular wait.

Demand paging: pages get frames only when touched.

Recent virtual-to-physical page translations.

SSTF (236 cylinders).

Nothing: the data stays while any link exists.
