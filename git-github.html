Part A — Foundations

1 What is Git? (the 10-second answer)

Git is a free tool that remembers every version of your project's files — who changed what, when and why — so you can go back in time, try ideas safely on the side, and combine many people's work without overwriting each other.
Imagine writing a story with friends. Without Git you'd email around files named story_final.docx, story_final_v2.docx, story_REALLY_final.docx — and someone always edits the wrong one. Git is like a magical notebook that keeps every page-version automatically, lets each friend work on a private copy, and then helps you merge the copies into one story.

Git does three big jobs:

JobWhat it meansEveryday picture
⏪ Time machineEvery saved snapshot (commit) can be viewed or restoredVideo-game save points
🌿 Parallel universesBranches let you try something without touching the main versionDrafting a risky paragraph on a spare sheet
🤝 TeamworkMany people contribute and Git merges their changesA shared recipe book where everyone adds pages

Git is distributed: every person has the whole project history on their own computer, not just a view of a central server. So you can work offline, and if a server disappears, any copy can rebuild it. Git works with any kind of file but shines with text such as code; it is the standard tool in DevOps and almost all software teams.

4 How Git Thinks — Snapshots, Not Edits

Git doesn't store "change lists". Each time you commit, Git takes a snapshot of what all your files look like right now (reusing identical files from before to save space) and links it to the previous snapshot. The result is a chain of snapshots — the project's history.

Fig 2 — A repository is a chain of commits. Each commit has a unique fingerprint (hash) and points to its parent. A branch is just a label pointing at one commit.

The words you need

CommitA saved snapshot + message + author + time + pointer to parentA save point in a game

BranchA movable label pointing at a commit; new commits advance itA bookmark that moves forward as you read

RemoteA copy of the repo somewhere else (e.g., on GitHub), usually named originThe shared cloud album
The hash is a content fingerprint: if even one letter in any file (or the message, or the parent) changes, the id changes. That's why Git history is very hard to tamper with silently. (More in Section 18.)

6 A Short History & Timeline

WhenWhat happened
1970s–2000sEarly version-control systems (SCCS, RCS, CVS, then Subversion) keep history on a central server; branching and merging are painful.
2005The Linux kernel loses access to its proprietary tool (BitKeeper). Linus Torvalds writes Git in a few weeks, aiming for speed, safe history and easy branching. The first version is released in April 2005; Mercurial appears around the same time.
2008GitHub launches, making hosting, forking and pull requests easy; Git spreads across open source.
2010sGit becomes the default everywhere; pull-request workflows, CI services and "social coding" become normal. GitLab and Bitbucket grow.
2018Microsoft completes its acquisition of GitHub. GitHub Actions (CI/CD built into GitHub) arrives in 2018–2019.
2020The industry moves new repos' default branch name from master to main; Git adds switch/restore (2019) to make everyday commands clearer.
2021–2024Copilot (AI pair-programmer) launches; SSH commit signing, rulesets and merge queues arrive; supply-chain security becomes a major theme; Git gains better large-repo tooling (partial clone, sparse checkout, scalar, maintenance).
2025–2026AI coding agents open pull requests directly; Copilot CLI reaches general availability (Feb 2026); GitHub Actions gets workflow lockfiles (generally available 28 Oct 2026); Git reaches 2.56 (Sept 2026). Git 3.0 is planned (new defaults: SHA-256 hashes, reftable ref storage, main, Rust required) but has no release date yet.
Git's core ideas haven't changed since 2005 — snapshots, hashes, branches. What changes is the world around it: bigger repos, stronger security, and now AI helpers that propose changes you still have to review.

10 Branches — Parallel Universes

A branch is an independent line of development. Because a branch is just a label on a commit (Fig 2), creating one is instant and free. The usual rule: main always works; do new work on a branch.

Fig 4 — Branching and merging. Work on the feature never disturbs main until you choose to merge.
CommandDoes
git branchList branches (the current one has a *)
git switch -c feature/loginCreate a branch and move onto it
git switch mainMove to another branch
git merge feature/loginBring that branch's work into the current one
git branch -d feature/loginDelete a merged branch (-D to force)

(Older tutorials use git checkout for both switching and restoring; switch and restore were added to split those jobs. checkout still works and is not being removed.)

Two kinds of merge

TypeWhenResult
Fast-forwardmain hasn't moved since you branchedGit just slides the main label forward — no merge commit, straight line
Three-way (merge commit)Both branches have new commitsGit creates a new commit with two parents that joins them (--no-ff forces this even when a fast-forward is possible, keeping the "feature happened here" bubble)
You photocopy a chapter (branch), scribble improvements, and later staple your improved pages back into the book. If the book changed meanwhile, Git helps blend both sets of edits.

12 Remotes — Clone, Fetch, Pull, Push

A remote is another copy of the repository, usually on GitHub. By convention the main one is called origin. Your computer has the whole history locally; these commands synchronise it with the remote.

Fig 5 — fetch downloads new commits into origin/main without touching your work; pull = fetch + integrate; push uploads your commits.
CommandWhat it doesSafe?
git clone URLCopy a whole repo (with history) to your computer; sets up origin✔ Always
git remote -vShow remote names and addresses✔
git fetchDownload new commits; update origin/*; don't change your files✔ Always safe — look before you leap
git pullfetch + merge (or rebase) into your branchUsually fine; may cause a merge/conflict
git pushUpload your commits to the remote branchRejected if the remote has work you lack
git push -u origin my-branchFirst push of a new branch; -u remembers the pairing✔

When git push says "rejected … fetch first", it isn't an error to fear: it's Git protecting your teammate's work. git pull --rebase (or merge), then push again. You'll see this happen for real in Level 4. Avoid plain --force; if you must, use --force-with-lease and never on shared branches like main.

13 Undoing Things Safely

The best thing about Git is that nearly any mistake can be undone — if you pick the right tool. Ask: "What do I want to undo, and has it been shared?"

Fig 6 — Pick the undo by situation: unsaved changes → restore; local commits → reset/amend; shared commits → revert; lost work → reflog.
CommandEffectDanger
git restore FILEThrow away unsaved edits to FILE (back to last commit)⚠ The edits are gone (they were never saved)
git restore --staged FILETake FILE out of the basket; keep your editsNone
git commit --amendReplace the last commit (fix message, add forgotten file)Rewrites that commit — don't amend after pushing
git reset --soft HEAD~1Un-commit; keep changes stagedSafe
git reset HEAD~1 (mixed)Un-commit; keep changes in your files, unstagedSafe
git reset --hard HEAD~1Un-commit and delete the changes⚠ Destroys uncommitted work (commits can still be rescued via reflog)
git revert COMMITMake a new commit that reverses an old oneSafe for shared history
git reflogGit's private diary of where HEAD has been (kept for a while, about 90 days by default)It's the rescue tool
restore = erase a pencil mark on your page. reset = tear out the last pages of your own notebook. revert = add a new page saying "ignore page 12". reflog = the CCTV footage that shows where you put things.
Golden rule: rewrite only what you haven't shared. Once teammates have pulled a commit, undo it with revert, not reset. Real runs of all of these are in Levels 0 and 2.

git bisect — find the culprit fast

Say it worked 100 commits ago and is broken now. Instead of checking all 100, bisect checks the middle, you say good or bad, it halves the range again… finding the bad commit in about 7 steps (log₂ 100). With a test script it does it automatically (Level 3).

15 Stash, Cherry-Pick & Worktrees

Stash — "hold this for a minute"

You're mid-edit and an urgent bug arrives. You're not ready to commit. git stash tucks your unfinished changes into a drawer and gives you a clean desk.

CommandDoes
git stash (or git stash push -m "wip search")Save uncommitted changes and clean the working directory
git stash -uAlso stash new (untracked) files
git stash listSee the drawer
git stash popBring back the latest stash and remove it from the drawer

Sweeping your half-finished homework into a drawer so you can answer the door, then pulling it out exactly as it was.

Cherry-pick — "copy just that one commit"

git cherry-pick COMMIT copies a single commit from anywhere onto your current branch. Typical use: a bug fix made on main must also go to the release-1.2 branch.

Photocopying one useful page out of another notebook and pasting it into yours, without copying the whole notebook.
Cherry-picked commits get new ids (they are copies), so overusing it can create duplicate-looking history and confusing conflicts later.

Worktrees — two branches open at once

git worktree add ../my-hotfix hotfix-branch checks out another branch into a second folder sharing the same history. You can fix the hotfix in one window while your feature stays untouched in another — no stashing, no switching. Remove it with git worktree remove ../my-hotfix. Worktrees are also handy for letting AI coding agents work on separate branches in parallel without stepping on each other.

Squash merge on GitHub

GitHub can combine all of a PR's commits into one when merging ("Squash and merge"). Many teams love it: main gets one clean commit per PR. (More in Section 24.)

The hash function is changing (slowly)

Git has used SHA-1 (40 hex characters) since 2005. SHA-1 is now considered weak against deliberate attacks, so Git supports SHA-256 (64 characters). You can try it today: git init --object-format=sha256 — in a quick test the commit id was 64 characters long instead of 40. The planned Git 3.0 would make SHA-256 (and "reftable" ref storage, and main) the defaults for new repos; Git's own notes say there's no release date yet and that readiness of the wider ecosystem (hosting sites, other tools) is a prerequisite. Existing repos keep working.

The hash is a fingerprint, not a name: change one comma in a file and the fingerprint (and every commit after it) becomes completely different — that's why you can trust history hasn't been secretly edited.

Line endings — the Windows vs Mac/Linux gotcha

Windows ends lines with two invisible characters (CRLF); macOS/Linux use one (LF). Without care, Git sees "every line changed" or shows warnings like "LF will be replaced by CRLF". (This bit the example repos used to write this page!) The clean fix is a committed .gitattributes file: 

# .gitattributes
* text=auto          # let Git normalise text files to LF in the repo
*.sh text eol=lf     # shell scripts must always be LF
*.png binary         # never touch images

falseDo nothing
A .gitattributes in the repo beats everyone's personal settings, so the whole team behaves the same.

21 Git Security

Who really made this commit? Signing

Anyone can type any name and email into git config, so commits can be faked. Signing proves the commit came from someone holding a specific key; GitHub shows a green Verified badge.

# sign with the SSH key you already use (no GPG needed)
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true     # sign every commit
# add the same public key on GitHub as a "Signing key" in Settings → SSH and GPG keys

"I committed a password!"

StepDo
1. Rotate the secret NOWRevoke the key/token and issue a new one. Assume it's already copied — bots scan public repos within minutes
2. Remove from history (optional, after step 1)Use git filter-repo (the tool Git recommends instead of the old filter-branch) or BFG Repo-Cleaner, then force-push and ask collaborators to re-clone
3. Prevent next timeAdd to .gitignore; use a secrets manager; turn on GitHub secret scanning and push protection (Section 29)
Deleting the file in a new commit does not remove it from history. Anyone who cloned earlier (or any fork) still has it. Rotation is the real fix.

40 Level 2 — "I Lost My Commits!" Rescue With the Reflog

Commands and real output 
$ git log --oneline
0ba9b90 version 3
999a8a5 version 2
3604544 version 1

$ git reset --hard HEAD~2          # ouch: throws away 2 commits (and their changes)
$ git log --oneline
3604544 version 1                  # "version 2" and "version 3" seem gone!

$ git reflog                       # Git's diary of where HEAD has been
3604544 HEAD@{0}: reset: moving to HEAD~2
0ba9b90 HEAD@{1}: commit: version 3        # <- there it is
999a8a5 HEAD@{2}: commit: version 2
3604544 HEAD@{3}: commit (initial): version 1

$ git reset --hard 0ba9b90         # jump back to the lost commit
$ git log --oneline
0ba9b90 version 3
999a8a5 version 2
3604544 version 1                  # everything is back

# --- the SAFE way to undo something that was already shared:
$ git revert --no-edit HEAD        # adds a NEW commit that reverses version 3
$ git log --oneline
88ef8bc Revert "version 3"
0ba9b90 version 3
999a8a5 version 2
3604544 version 1

Commits you "lose" aren't deleted immediately — they stay in Git's database and in the reflog for a while until Git's cleanup removes them (by default reflog entries expire after 90 days, or 30 days for commits no branch can reach). Uncommitted changes destroyed by --hard are the only thing truly unrecoverable — one more reason to commit early.

45 FAQ

Q: Is Git the same as GitHub?

No. Git is the open-source version-control tool that runs on your computer. GitHub is a hosting and collaboration service for Git repositories (owned by Microsoft). Alternatives such as GitLab, Bitbucket and Forgejo host Git repos too.

Q: What's the difference between git add and git commit?

add places changes in the staging area (choosing what goes in the next snapshot); commit saves everything staged as a permanent snapshot in the history.

Q: git pull vs git fetch?

fetch only downloads new commits and updates your view of the remote (origin/main) without touching your files. pull is fetch plus merging (or rebasing) into your current branch.

Q: I made a mistake — can I undo it?

Almost always. Unsaved edits: git restore. Last local commit: --amend or reset. Already-shared commit: revert. "Lost" commits: find them in git reflog and reset to them. The only truly unrecoverable thing is uncommitted work destroyed by --hard or restore.

Q: Merge or rebase?

Merge preserves the real branching history and is always safe on shared branches. Rebase makes a straight line by rewriting your commits — great for tidying your own branch before a PR, but never rebase commits others have pulled.

Q: I committed a password. Deleting the file is enough, right?

No — it remains in history and in anyone's clone or fork. Revoke and rotate the secret immediately; optionally rewrite history with git filter-repo and force-push; then add prevention (secret scanning, push protection, a secrets manager).

Q: What's origin, and why is it called that?

It's simply the default nickname for the remote you cloned from. You can have more remotes (like upstream for the original project of a fork) with any names.

Q: Why do people say "main" instead of "master" now?

The industry shifted new repositories' default branch to main around 2020; GitHub and Git both support it, and Git 3.0 is planned to make main the built-in default. Existing repos can rename their default branch.

Q: Will AI make Git/GitHub obsolete?

No — AI agents work through Git and GitHub: they branch, commit and open pull requests, and your reviews, checks and rulesets are how you control them. Knowing Git matters more when much of the code is machine-written and must be reviewed and traced.

46 Interview Questions (With Answers) — The Complete Set

Grouped by category, easy → hard.

46.1 — Fundamentals

Q: What is Git and why is it called distributed?

A version-control system that records snapshots of a project. Distributed means every clone contains the full history, so most operations work offline and any clone can restore the project if a server is lost.

Q: Git vs GitHub?

Git is the tool; GitHub is a hosting platform adding collaboration (pull requests, issues, Actions, security, Copilot).

Q: Explain the three areas of Git.

Working directory (files you edit), staging area/index (changes selected for the next commit), and the repository (committed history). add moves changes to staging; commit moves them to history.

Q: How does Git store data — snapshots or diffs?

Conceptually snapshots: each commit references a tree of the entire project state, with unchanged files reused by hash. (Packfiles may delta-compress storage, but that's an implementation detail.)

Q: What is a commit hash and why does it matter?

A fingerprint computed from the commit's contents (tree, parents, author, message). Any change produces a different hash, which makes history tamper-evident and lets Git deduplicate identical content.

Q: What is HEAD?

A pointer to the currently checked-out commit, usually via a branch. "Detached HEAD" means it points directly at a commit instead of a branch.

46.2 — Everyday Commands & Branching

Q: What does git status show?

Which files are untracked, modified, or staged, which branch you're on, and how it compares to its remote counterpart.

Q: What is a branch, and why is creating one cheap?

A branch is just a small file holding a commit id (a movable pointer). Creating one doesn't copy any files, so it's instant.

Q: Fast-forward vs three-way merge?

Fast-forward: the target hasn't diverged, so Git just moves the pointer. Three-way: both sides have new commits, so Git creates a merge commit with two parents using the common ancestor.

Q: How do you resolve a merge conflict?

Open the conflicted files, choose/combine the correct content and remove the conflict markers (<<<<<<<, =======, >>>>>>>), git add the files, then commit (or git merge --continue); git merge --abort cancels.

Q: git switch / restore vs checkout?

checkout did two jobs (change branches, restore files). switch (branches) and restore (files) split them for clarity (since Git 2.23). checkout still works and isn't being removed.

Q: What is .gitignore and what doesn't it do?

It lists patterns of untracked files Git should ignore. It doesn't affect files already tracked or remove anything already committed.

46.3 — Undoing & Rewriting History

Q: Reset (soft/mixed/hard) vs revert?

Reset moves the branch pointer back: soft keeps changes staged, mixed keeps them unstaged, hard discards them. Revert creates a new commit that inverts an earlier one without rewriting history — the right tool for shared branches.

Q: How do you recover commits after a bad reset --hard?

Run git reflog, find the commit id from before the reset, then git reset --hard <id> (or create a branch there). Reflog entries expire (default 90 days; 30 for unreachable commits).

Q: How would you change the last commit's message or add a forgotten file?

git add file then git commit --amend (optionally -m). It creates a new commit id, so don't amend commits that have already been pushed and shared.

Q: What does interactive rebase let you do?

Reorder, reword, squash/fixup, edit or drop commits in a range (git rebase -i HEAD~N) to tidy local history before sharing.

Q: Why is force-pushing dangerous and what's safer?

It overwrites remote history and can destroy teammates' commits. Use --force-with-lease, which fails if the remote moved unexpectedly; never force-push shared protected branches (ruleset them).

Q: How do you remove a secret that was committed?

Rotate/revoke it first. Then optionally purge history with git filter-repo or BFG, force-push, and have everyone re-clone; enable secret scanning and push protection to prevent repeats. Deleting it in a new commit isn't enough.

46.4 — Collaboration & Remotes

Q: fetch vs pull?

Fetch downloads remote commits and updates remote-tracking branches without altering your working files; pull = fetch + merge (or rebase).

Q: Why was your push rejected and what do you do?

The remote branch has commits you lack (non-fast-forward). Fetch, integrate with merge or pull --rebase, resolve conflicts, then push.

Q: Fork vs clone vs branch?

Clone copies a repo to your machine. Branch is a parallel line within a repo you can write to. Fork is your own server-side copy of someone else's repo, used when you lack write access; you PR back from the fork.

Q: How do you keep a fork up to date?

Add the original as upstream, git fetch upstream, merge or rebase upstream/main into your main, and push to your fork (or use GitHub's "Sync fork").

Q: What is rebase's "golden rule"?

Never rebase commits that others may have based work on (shared/public history); rebase only your own local or personal-branch commits.

Q: How do you work on two branches at once without stashing?

Use git worktree add to check out the second branch in another folder sharing the same repository.

46.5 — GitHub Workflow

Q: What makes a good pull request?

Small and focused, clear description (what/why/how tested), linked issue, passing checks, screenshots for UI, and responsive handling of review comments; use draft PRs for early feedback.

Q: Merge commit vs squash vs rebase-and-merge on GitHub?

Merge commit keeps all commits plus a merge commit; squash collapses the PR into one commit (clean main, popular); rebase-and-merge replays commits linearly without a merge commit. Teams choose one default.

Q: What is a merge queue?

A GitHub feature that serialises approved PRs, testing each combined with the latest main (and earlier queued PRs) so that individually passing PRs can't break main together.

Q: Branch protection rules vs rulesets?

Both enforce policies (PRs required, approvals, status checks, no force-push). Rulesets are newer: layered, can target tags and many repos at the organization level, have bypass lists and an evaluate mode.

Q: What is CODEOWNERS?

A file mapping path patterns to users/teams; with the right rule enabled, PRs touching those paths need their review.

Q: How do issues and PRs link?

Closing keywords in a PR description or commit (Fixes #123) auto-close the issue when the PR merges into the default branch; references (#123) create cross-links.

46.6 — Branching Strategy & Release

Q: Compare GitHub Flow, trunk-based development and GitFlow.

GitHub Flow: main + short feature branches + PRs. Trunk-based: even shorter integration (daily) with feature flags. GitFlow: develop/release/hotfix long-lived branches for scheduled versioned releases — more ceremony and bigger merges. Research favours short-lived branches for delivery performance.

Q: How do you ship a hotfix to an older release?

Fix on main (or a hotfix branch), then cherry-pick the commit onto the release branch, tag a patch version, and release; ensure the fix exists on both lines.

Q: Lightweight vs annotated tags, and SemVer?

Lightweight is a bare pointer; annotated stores tagger, date and message (and can be signed) — preferred for releases. SemVer: MAJOR for breaking changes, MINOR for compatible features, PATCH for fixes. Tags must be pushed explicitly.

Q: Monorepo vs polyrepo trade-offs?

Monorepo: easy cross-project changes and consistency, but needs tooling for scale, partial builds and permissions. Polyrepo: clear boundaries and simple pipelines, but dependency versioning and cross-repo changes are harder.

46.7 — Internals & Performance

Q: Name Git's object types and how they relate.

Blob (file contents), tree (directory listing of blobs/trees), commit (points to a tree and parent commits, with metadata), tag (annotated pointer). Refs (branches/tags) are names pointing to commits; HEAD points to a ref.

Q: Why do identical files share storage?

Objects are stored by the hash of their content (content-addressable), so identical content has the identical id and is stored once.

Q: What's changing with SHA-256 and Git 3.0?

Git supports SHA-256 repositories now (git init --object-format=sha256). Git 3.0 is planned to make SHA-256, reftable ref storage and main the defaults for new repos and to require Rust to build — but there's no release date, and ecosystem support is a prerequisite. Existing SHA-1 repos continue to work.

Q: How do you work with a huge repository?

Shallow clone (--depth), partial clone (--filter=blob:none), sparse checkout, Git LFS for big binaries, background maintenance, and tools like Scalar; in CI fetch only what's needed.

Q: How do you find which commit introduced a bug?

git bisect: mark a known good and bad commit; Git binary-searches, and with git bisect run <test> automates it, finding the culprit in about log₂(N) steps.

46.8 — Security, Actions & AI

Q: How do you prove a commit's author?

Sign commits with GPG or an SSH key (gpg.format ssh, commit.gpgsign true) and register the public key on GitHub as a signing key to get the Verified badge; rulesets can require signed commits.

Q: How would you secure GitHub Actions workflows?

Read-only GITHUB_TOKEN by default; pin third-party actions to commit SHAs or use workflow lockfiles (.github/workflows/actions.lock, GA Oct 2026); OIDC for cloud access; avoid script injection and risky triggers like pull_request_target with untrusted code; require CODEOWNERS review for workflow changes; use environments with approvals; ephemeral runners.

Q: What do secret scanning and push protection do?

Secret scanning detects known credential formats in repos; push protection blocks a push that contains a detected secret before it lands. Both are on by default for supported patterns, including free public repos; GitHub keeps adding detectors.

Q: What does Dependabot do?

Alerts about vulnerable dependencies and opens PRs to update them (security and version updates), including GitHub Actions versions; configured via .github/dependabot.yml.

Q: How should you integrate AI coding agents with GitHub safely?

Treat the agent as another contributor: it works on a branch and opens a PR; enforce required checks, CODEOWNERS and rulesets; review every line; give it minimal permissions; keep secrets out of prompts; and beware prompt injection through issue text or web pages it reads.

Q: GitHub App vs personal access token?

A GitHub App acts as its own identity with fine-grained, installable permissions and short-lived tokens — best for automation. A fine-grained PAT is scoped to repos/permissions for personal scripts; classic PATs are broad and long-lived and best avoided.

47 Common Problems & Checklist

🔓 Secrets in history

Committing keys or .env files. Ignore them, scan, and rotate immediately if leaked.

💥 Force-pushing shared branches

Overwrites teammates' work. Use --force-with-lease on your own branches only; protect main.

🐘 Giant commits & PRs

Impossible to review. Commit and open PRs in small, focused pieces.

📦 Committing big binaries or dependencies

Bloats history forever. Use .gitignore, LFS or an artifact store.

🌳 Long-lived branches

Painful merges. Integrate often; hide unfinished work with feature flags.

🔀 Rebasing shared history

Makes teammates' clones diverge. Rebase only your own unpushed commits.

↩️ reset --hard with unsaved work

Uncommitted changes can't be recovered. Commit or stash first.

⚙️ Unpinned CI actions

A moved tag can run malicious code. Pin to SHAs or use a workflow lockfile; read-only tokens.

Repo health checklist:
  • ☐ README, LICENSE, CONTRIBUTING, CODE_OF_CONDUCT and SECURITY.md exist
  • ☐ .gitignore and .gitattributes committed; no secrets or big binaries in history
  • ☐ main protected by a ruleset: PR + review + passing checks + no force-push/delete
  • ☐ CODEOWNERS for sensitive paths (especially .github/workflows)
  • ☐ CI runs on every PR; workflows use read-only token permissions and pinned/locked actions
  • ☐ Dependabot, secret scanning + push protection, and code scanning enabled
  • ☐ 2FA/passkeys on all accounts; signed commits where required; fine-grained tokens with expiry
  • ☐ Conventions written down: branch names, commit style, merge method, release/tag process
