Part A — Cloud Foundations

1 What Is the Cloud?

Picture: Electricity. Long ago every factory had its own generator. Today you plug into the grid and pay for what you use. Cloud computing is the same idea for computers: instead of buying and running your own machines, you rent computing, storage and software over the internet from a big provider, by the hour or the second.

Cloud computing means using someone else's data centres — servers, storage, networks, databases, and now AI chips — through the internet, on demand, and paying only for what you use.

Own your computers (on-premises)Use the cloud
Buy hardware first (big upfront cost)Rent it when you need it (pay as you go)
Weeks to order, install and set upMinutes to start a server
You guess how much capacity you will needGrow and shrink automatically
You repair the hardware, power and coolingThe provider runs the buildings and machines
Hard to be in many countriesMany regions around the world, a few clicks away
In one line: the cloud turns computers from something you buy and maintain into something you rent and call from code.

Good to know

  • Everything in the cloud is reached through APIs: a web console, a command line (CLI), SDKs in languages like Python, or Infrastructure-as-Code files all call the same APIs.
  • 'The cloud' is not one thing. It is hundreds of services from providers such as AWS, Microsoft Azure, Google Cloud, Oracle Cloud, Alibaba Cloud and software platforms such as Salesforce.
  • This guide teaches the shared ideas first (Parts A–B), then each provider's own names and workflows (Parts C–F), then advanced topics (Part G).
Rule to remember: the cloud is not magic and not automatically cheaper or safer. It gives you speed and elasticity; you still must design for cost, security and failure.

3 The Five Essential Characteristics (NIST)

Picture: A water tap in the kitchen. You turn it on yourself, any time (self-service); it reaches you through pipes everyone can use (broad access); the water company serves many houses from one big system (pooling); the flow grows or shrinks as you need (elasticity); and a meter counts what you use (measured service).

The US standards body NIST defined cloud computing (SP 800-145) by five characteristics, plus three service models and four deployment models:

CharacteristicMeaningExample
On-demand self-serviceYou provision resources yourself, no human neededClick 'create server' or run one command
Broad network accessAvailable over the network from many device typesPhone, laptop, CI server all use the same API
Resource pooling (multi-tenancy)The provider's resources are shared among many customers, securely separatedYour VM and a stranger's VM run on the same physical host
Rapid elasticityCapacity can grow and shrink quickly, even automaticallyAdd 20 servers for a sale, remove them after
Measured serviceUsage is metered and billedPay per second of compute, per GB stored

Good to know

  • If a service lacks these (for example you must phone someone and wait a week), it is hosting or outsourcing, not cloud in the NIST sense.
  • Multi-tenancy is the secret of cloud economics and also the reason security isolation matters (see the Salesforce multi-tenancy simulation later).

6 The Shared Responsibility Model

Picture: Renting a flat. The landlord looks after the building, the roof, the lifts and the main gate. You look after your own door lock, who you give keys to, and what you keep inside. If a burglar walks in because you left the door open, it is not the landlord's fault.
LayerOn-premIaaSPaaSSaaS
Data and who can access itYouYouYouYou
Identity, users, permissionsYouYouYouYou (and the provider's tools)
Application codeYouYouYouProvider
Runtime and middlewareYouYouProviderProvider
Operating system and patchesYouYouProviderProvider
Virtualisation and hostsYouProviderProviderProvider
Network hardware, data centre, power, cooling, physical securityYouProviderProviderProvider

Good to know

  • Cloud providers secure the cloud (hardware, facilities, core services). You secure what you put in the cloud (configuration, identities, data).
  • Most real cloud breaches are customer misconfigurations (public storage buckets, leaked keys, over-broad permissions), not the provider's data centres being hacked. See the AI Security guide for how this applies to AI services.
  • Read each service's own shared-responsibility page; the line moves with the service type.

Why regions matter: latency has a physical floor (simulation of round-trip times) (run for real)

import random, statistics

# Where should a user be served from? Latency-based routing picks the region with the lowest measured round-trip time.
regions = {"mumbai": (19.1, 72.9), "frankfurt": (50.1, 8.7), "virginia": (38.9, -77.4), "singapore": (1.35, 103.8), "sao-paulo": (-23.5, -46.6)}
users = {"Pune": (18.5, 73.9), "Berlin": (52.5, 13.4), "Boston": (42.4, -71.1), "Jakarta": (-6.2, 106.8), "Lagos": (6.5, 3.4)}
import math
def km(a, b):
    la1, lo1, la2, lo2 = map(math.radians, (*a, *b))
    h = math.sin((la2 - la1) / 2) ** 2 + math.cos(la1) * math.cos(la2) * math.sin((lo2 - lo1) / 2) ** 2
    return 6371 * 2 * math.asin(math.sqrt(h))
def rtt_ms(a, b, rng): return 8 + km(a, b) / 100 * 1.0 + rng.uniform(0, 6)          # rough rule: light in fibre ~ 1 ms per 100 km round trip, plus overheads

rng = random.Random(1)
print(f"{'user':8} {'best region':12} {'RTT ms':>7}   {'if everyone used virginia':>26}")
for u, loc in users.items():
    best = min(regions, key=lambda r: rtt_ms(loc, regions[r], rng))
    print(f"{u:8} {best:12} {rtt_ms(loc, regions[best], rng):7.0f}   {rtt_ms(loc, regions['virginia'], rng):20.0f} ms")
print("\nPhysics sets a floor: light in fibre travels about 200 km per millisecond, so a round trip of 10,000 km costs at least about 100 ms.")
print("Put regions near users (and use a CDN), keep data residency laws in mind, and keep chatty parts of your system in the same region.")

# ----- Output (real run) -----
# user     best region   RTT ms    if everyone used virginia
# Pune     mumbai            12                    142 ms
# Berlin   frankfurt         17                     75 ms
# Boston   virginia          15                     15 ms
# Jakarta  singapore         17                    173 ms
# Lagos    frankfurt         59                     97 ms
#
# Physics sets a floor: light in fibre travels about 200 km per millisecond, so a round trip of 10,000 km costs at least about 100 ms.
# Put regions near users (and use a CDN), keep data residency laws in mind, and keep chatty parts of your system in the same region.

Each user was routed to the closest of five example regions: Pune → Mumbai (about 12 ms), Berlin → Frankfurt, Boston → Virginia, Jakarta → Singapore. Sending everyone to Virginia would have cost Jakarta about 173 ms. Light in fibre moves about 200 km per millisecond, so distance sets a minimum delay no software can beat.

Good to know

  • Choosing a region: (1) where are the users? (2) where must data legally stay? (3) which services and GPUs exist there? (4) price (differs by region) (5) carbon intensity of the local grid.
  • Rule of AZs: run at least two, ideally three, AZs for anything important. A region-wide failure still needs a multi-region plan (HA and DR).
  • Naming differs: AWS ap-south-1a, Azure 'Central India' zones 1–3, Google asia-south1-a, Oracle 'ap-mumbai-1' with ADs/FDs. Zone letters/numbers are mapped per customer account on some clouds, so 'zone a' for you may not be 'zone a' for someone else.

Reserved vs on-demand vs spot, and the break-even point (illustrative prices) (run for real)

# ILLUSTRATIVE prices (not any provider's real price list): $ per instance-hour
ON_DEMAND = 0.10
RESERVED_EFFECTIVE = 0.062       # about 38% cheaper in exchange for a 1-year commitment (paid whether used or not)
SPOT = 0.03                      # about 70% cheaper but can be interrupted at short notice
HOURS_YEAR = 24 * 365

print("1) Steady workload: runs all year")
print(f"   on-demand : ${ON_DEMAND * HOURS_YEAR:8,.0f}")
print(f"   reserved  : ${RESERVED_EFFECTIVE * HOURS_YEAR:8,.0f}   (commitment pays off)")
print(f"   spot      : ${SPOT * HOURS_YEAR:8,.0f}   (only if the work tolerates interruptions)")

print("\n2) Break-even: at what share of the year must a server run before a commitment beats on-demand?")
be = RESERVED_EFFECTIVE / ON_DEMAND
print(f"   reserved costs the full year no matter what: break-even utilisation = {be:.0%} of hours")
print("\n   run-time share   on-demand   reserved   cheaper")
for share in (0.2, 0.4, 0.62, 0.8, 1.0):
    od = ON_DEMAND * HOURS_YEAR * share; rs = RESERVED_EFFECTIVE * HOURS_YEAR
    print(f"   {share:13.0%}   ${od:8,.0f}   ${rs:7,.0f}   {'on-demand' if od < rs else 'reserved' if rs < od else 'tie'}")

print("\n3) Mixed fleet for a web shop: baseline 10 servers all year + 20 extra servers for 200 hours of sales")
base = 10 * HOURS_YEAR; burst = 20 * 200
all_od = (base + burst) * ON_DEMAND
mixed = base * RESERVED_EFFECTIVE + burst * ON_DEMAND
print(f"   everything on-demand       : ${all_od:9,.0f}")
print(f"   baseline reserved + burst OD: ${mixed:9,.0f}   (saves {1 - mixed / all_od:.0%})")
print("\nPattern: commit for the steady floor, rent on demand for the peaks, use spot for the interruptible.")

With example prices, a server that runs all year costs $876 on-demand, $543 reserved and $263 on spot. A one-year commitment only wins if the server runs more than about 62% of the time; below that on-demand is cheaper. A shop with a steady base plus short sales saved about 36% by reserving the base and renting peaks on demand.

Good to know

  • The prices in the demo are made up to show the method; real prices differ by provider, region, instance family and date. Always use the provider's pricing calculator.
  • Hidden costs: data transfer out (egress), cross-AZ traffic, NAT gateways, load balancer hours, IP addresses, logging volume, support plans, idle disks and forgotten test resources.

10 When the Cloud Is Not the Best Choice (and Cloud Repatriation)

Picture: Renting a taxi every day for a 100-km commute may cost more than owning a car. Renting is great for trips, owning can win for daily use.
  • Very steady, high-utilisation workloads (a database busy 24/7 at 90%) can be cheaper on owned or leased hardware.
  • Huge data egress (moving petabytes out regularly) gets expensive.
  • Strict latency to a local machine (factory robots) may need on-site or edge compute.
  • Legal limits on where data may live or who may operate it.
  • Specialised hardware that you can buy more cheaply in bulk.
  • Skills and tooling: a team without cloud skills can build an expensive, insecure setup.

Some companies have moved certain workloads back from cloud to their own hardware ('repatriation'). Usually they keep other workloads in the cloud: it is a per-workload decision.

A five-year cost comparison model (all numbers made up) (run for real)

# A simple 5-year comparison. ALL NUMBERS ARE MADE UP to show the method, not to predict your real costs.
years = 5
onprem_capex = 400_000                # servers, network, storage bought up front
onprem_opex_year = 90_000             # power, space, support contracts, 1.5 admins
cloud_year_for_same_peak = 260_000    # if you ran peak capacity 24x7 in the cloud on demand

print("Utilisation of the peak capacity over time decides everything.")
print("avg utilisation of peak   on-prem 5y total   cloud 5y (pay for what you use)   cheaper")
for util in (0.15, 0.30, 0.50, 0.62, 0.70, 0.90):
    onprem = onprem_capex + onprem_opex_year * years                      # you pay for the whole box whether used or not
    cloud = cloud_year_for_same_peak * util * years + 40_000              # + fixed cost for tooling, migration and training
    print(f"{util:23.0%}   ${onprem:15,.0f}   ${cloud:30,.0f}   {'cloud' if cloud < onprem else 'on-prem'}")
print("\nWhat the simple model leaves out: staff time saved or needed, speed of experiments, discounts for commitments, egress, licences,")
print("compliance, the cost of getting capacity wrong, and the option value of scaling to zero. Always model YOUR workload.")

How object stores survive disk failures: copies vs erasure coding, and what '11 nines' means (run for real)

# 1) Replication vs erasure coding: storage overhead for the same fault tolerance
print("Storing 1 TB of data:")
print("  3 full copies             : 3.00 TB used, survives loss of any 2 copies")
k, m = 6, 3

print("  (same-ish safety, half the space; the price is more CPU and slower repairs)")

# 2) A tiny erasure code: split data into k pieces + 1 XOR parity piece; rebuild any single lost piece
def split(data, k):
    size = -(-len(data) // k); data = data.ljust(size * k, b"\0")
    return [data[i * size:(i + 1) * size] for i in range(k)]
def xor(a, b): return bytes(x ^ y for x, y in zip(a, b))
data = b"Hello object storage! This file is stored as pieces plus parity."
pieces = split(data, 4)
parity = pieces[0]
for p in pieces[1:]: parity = xor(parity, p)
print("\n4 data pieces + 1 parity piece, on 5 different disks/racks. Disk 2 dies...")
lost = 2
rebuilt = parity
for i, p in enumerate(pieces):
    if i != lost: rebuilt = xor(rebuilt, p)
print("rebuilt piece == lost piece:", rebuilt == pieces[lost])
print("recovered file:", b"".join(pieces[:lost] + [rebuilt] + pieces[lost + 1:]).rstrip(b"\0").decode())

# 3) What does "11 nines of durability" mean? Chance a given object is lost in a year.
print("\nDurability maths: probability an object is lost in a year (simple model)")
def p_loss(copies, annual_disk_failure=0.02, repair_days=1):
    # object is lost if all remaining copies fail before repair finishes after the first failure (rough, illustrative)
    window = repair_days / 365
    p_first = 1 - (1 - annual_disk_failure) ** copies
    p_others = (annual_disk_failure * window) ** (copies - 1)
    return p_first * p_others
for c in (1, 2, 3, 4):
    print(f"  {c} copy/copies on independent disks: ~{p_loss(c):.2e} per year  ({-math.log10(p_loss(c)) if p_loss(c) > 0 else 99:.1f} nines)" if c > 1 else f"  1 copy: ~{0.02:.2e} per year  (1.7 nines)")
print("Providers advertise 11 nines (99.999999999%) for object stores by spreading data over several facilities and repairing quickly.")
print("Durability (not losing data) is different from availability (being reachable right now).")

Health checks: with and without (real simulation) (run for real)

import itertools, random

class Server:
    def __init__(self, name, healthy=True): self.name, self.healthy, self.handled = name, healthy, 0
servers = [Server("s1"), Server("s2"), Server("s3")]
rng = random.Random(5)

def balance(strategy, requests=300, fail_at=102, recover_at=202, use_health_checks=True):
    for s in servers: s.handled = 0; s.healthy = True
    rr = itertools.cycle(servers); failed = 0
    marked_down = set()
    for r in range(requests):
        servers[1].healthy = not (fail_at <= r < recover_at)               # s2 crashes for a while
        if use_health_checks and r % 5 == 0:                               # a health check every 5 requests
            marked_down = {s.name for s in servers if not s.healthy}
        candidates = [s for s in servers if s.name not in marked_down]
        if not candidates: failed += 1; continue
        if strategy == "round robin":
            s = next(rr)
            while s.name in marked_down: s = next(rr)                      # skip servers the load balancer believes are down
        else:
            s = min(candidates, key=lambda x: x.handled)                   # least loaded among the servers believed healthy
        if s.healthy: s.handled += 1
        else: failed += 1                                                  # sent to a crashed server: the user sees an error
    return failed, [s.handled for s in servers]

for use in (False, True):
    for strat in ("round robin", "least loaded"):
        f, h = balance(strat, use_health_checks=use)
        print(f"health checks {'ON ' if use else 'OFF'} {strat:12}: failed requests = {f:3d}, handled per server = {h}")
print("\nWithout health checks, round robin keeps sending a third of the traffic to the crashed server for its whole outage.")
print("Worse, 'least loaded' sends EVERYTHING to it: a crashed server looks idle, so it always has the lowest load (a classic black hole).")

class Queue:
    """SQS-style queue: a received message is hidden for a visibility timeout; if not deleted in time it reappears. After N receives it goes to the dead-letter queue."""
    def __init__(self, visibility=30, max_receives=3): self.msgs, self.vis, self.max, self.dlq, self.now = [], visibility, max_receives, [], 0
    def send(self, body): self.msgs.append({"body": body, "visible_at": 0, "receives": 0})
    def receive(self):
        for m in self.msgs:
            if m["visible_at"] <= self.now:
                m["receives"] += 1
                if m["receives"] > self.max: self.msgs.remove(m); self.dlq.append(m["body"]); return self.receive()
                m["visible_at"] = self.now + self.vis; return m
        return None
    def delete(self, m): self.msgs.remove(m)

q = Queue(visibility=30, max_receives=3)
for body in ("resize photo 1", "resize photo 2", "poison message (always crashes)"): q.send(body)
log = []

    m = q.receive()
    if not m: continue

print(*log, sep="\n")
print("\ndead-letter queue:", q.dlq, "| still in queue:", [m["body"] for m in q.msgs])

How an IAM decision is made (a small policy engine) (run for real)

import fnmatch

# A tiny model of how cloud IAM (AWS-style) decides: 1) any explicit DENY wins, 2) otherwise an ALLOW is needed, 3) else implicit deny.
def matches(patterns, value): return any(fnmatch.fnmatch(value, p) for p in patterns)

def evaluate(policies, action, resource, context=None):
    context = context or {}
    allowed = False
    for pol in policies:
        for st in pol["Statement"]:
            if not (matches(st["Action"], action) and matches(st["Resource"], resource)): continue
            cond = st.get("Condition")
            if cond and context.get("source_ip", "").split(".")[0] != cond.get("ip_prefix", context.get("source_ip", "").split(".")[0]): continue
            if st["Effect"] == "Deny": return "DENY (explicit deny always wins)"
            allowed = True
    return "ALLOW" if allowed else "DENY (implicit: nothing allowed it)"

18 Encryption, Keys and Secrets

Picture: A bank's safe-deposit system. Each customer's box has its own key (data key), and all those keys are kept in a master vault (key service) that never lets the master key out.
  • In transit: TLS between users, services and databases.
  • At rest: disks, buckets and databases encrypted, usually by default; you may choose provider-managed keys or customer-managed keys (CMK) in a KMS (AWS KMS, Azure Key Vault/Managed HSM, Google Cloud KMS, OCI Vault, Alibaba KMS).

  • Secrets managers: store passwords, tokens and certificates (AWS Secrets Manager, Azure Key Vault, Google Secret Manager). Apps fetch them at runtime with their identity.
  • HSMs and confidential computing: hardware-protected keys and encrypted memory for very sensitive workloads.
Envelope encryption with AES-GCM (real cryptography library) (run for real)

import os, base64
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# Envelope encryption, the pattern behind cloud KMS: a master key (KEK) never leaves the key service.
# Each file gets its own random data key (DEK). The DEK encrypts the data; the master key encrypts (wraps) the DEK.
class MiniKMS:
    def __init__(self): self._master = AESGCM.generate_key(256)             # in a real KMS this lives in hardware and is never exported
    def wrap(self, dek):
        nonce = os.urandom(12); return nonce + AESGCM(self._master).encrypt(nonce, dek, b"dek")
    def unwrap(self, blob): return AESGCM(self._master).decrypt(blob[:12], blob[12:], b"dek")

kms = MiniKMS()
def encrypt_file(plaintext):
    dek = AESGCM.generate_key(256); nonce = os.urandom(12)
    ct = AESGCM(dek).encrypt(nonce, plaintext, None)
    return {"ciphertext": nonce + ct, "wrapped_dek": kms.wrap(dek)}          # store both; the plain DEK is discarded
def decrypt_file(obj):
    dek = kms.unwrap(obj["wrapped_dek"])                                      # asks the KMS (which checks permissions and logs the call)
    return AESGCM(dek).decrypt(obj["ciphertext"][:12], obj["ciphertext"][12:], None)

def schedule(order, strategy):
    nodes = []                                              # each node: [cpu_used, mem_used]
    for c, m in order:
        fits = [n for n in nodes if n[0] + c <= NODE_CPU and n[1] + m <= NODE_MEM]
        if not fits: nodes.append([c, m]); continue
        n = fits[0] if strategy == "first-fit" else max(fits, key=lambda x: x[0] / NODE_CPU + x[1] / NODE_MEM)     # best-fit: fullest node that still fits
        n[0] += c; n[1] += m
    return nodes

# Function-as-a-Service model: each request needs a warm "execution environment". If none is free, a new one starts (cold start).
def simulate(rps, minutes=60, warm_ttl=60, cold_ms=800, warm_ms=40, seed=1, provisioned=0):
    rng = random.Random(seed); t = 0.0; end = minutes * 60
    envs = [{"free_at": 0.0, "last": -1e9} for _ in range(provisioned)]       # pre-warmed environments
    for e in envs: e["last"] = 0.0

        env = next((e for e in envs if e["free_at"] <= t and t - e["last"] <= warm_ttl), None)

        lat.append(dur); gb_seconds += 0.5 * dur / 1000                       # a 512 MB function
    lat.sort()
    return total, cold, lat[int(len(lat) * 0.5)], lat[int(len(lat) * 0.99)], len(envs), gb_seconds

One day of traffic: fixed fleets vs target tracking (simulation) (run for real)

import math

# A day of web traffic (requests per second) at 15-minute steps: quiet night, morning ramp, lunch peak, evening bump
def traffic(step):
    h = step / 4
    base = 120 + 1150 * math.exp(-((h - 13) ** 2) / 8) + 700 * math.exp(-((h - 20) ** 2) / 4)
    return base

CAP_PER_SERVER = 100          # requests per second one server can handle
SERVER_HOUR = 0.10            # illustrative price
STEPS = 96

def run(policy):
    servers, cost, dropped, total, pending = policy["start"], 0.0, 0.0, 0.0, []
    cooldown = 0
    series = []
    for step in range(STEPS):
        rps = traffic(step)
        # servers requested earlier become ready after a 2-step warm-up
        pending = [(t - 1, n) for t, n in pending]
        ready = sum(n for t, n in pending if t <= 0); pending = [(t, n) for t, n in pending if t > 0]
        servers += ready
        capacity = servers * CAP_PER_SERVER
        served = min(rps, capacity); dropped += max(0, rps - capacity); total += rps
        cost += servers * SERVER_HOUR * 0.25
        series.append((step, rps, servers))
        if policy["auto"]:
            util = rps / capacity
            want = math.ceil(rps / (CAP_PER_SERVER * policy["target"]))      # target tracking: keep utilisation near 60%
            incoming = sum(n for _, n in pending)
            if want > servers + incoming and cooldown == 0:
                pending.append((2, want - servers - incoming)); cooldown = 1
            elif want < servers - 1 and cooldown == 0:
                servers = max(policy["min"], servers - 1); cooldown = 1       # scale in slowly, one at a time
            cooldown = max(0, cooldown - 1)
    return cost, dropped / total, max(s for _, _, s in series), series

Cross-region replication lag decides how much data you lose (run for real)

import random

# Two regions. Region A takes writes and copies them to region B asynchronously with some lag.
def simulate(lag_seconds, write_rate=50, fail_at=1000, detect_and_switch=90, seed=3):
    rng = random.Random(seed)
    writes = [(t, i) for i, t in enumerate(sorted(rng.uniform(0, fail_at) for _ in range(write_rate * fail_at // 10)))]
    replicated = [w for w in writes if w[0] + lag_seconds <= fail_at]          # copies that reached B before A died
    lost = len(writes) - len(replicated)

    for name, spec in desired.items():

        elif actual[name] != spec:

            steps.append(("UPDATE", name, diff))
    for name in actual:
        if name not in desired: steps.append(("DELETE", name, actual[name]))
    return steps

26 API Limits, Quotas and Retries

Picture: A busy kitchen pass. The cook can only accept so many orders a minute; if a hundred waiters shout at once, the cook says 'wait', and good waiters wait a little and try again, not all at the same second.

Every cloud API has rate limits and every account has quotas (for example, number of vCPUs, GPUs or IP addresses per region). When you exceed them you get errors such as 429 Too Many Requests, ThrottlingException or QuotaExceeded. Official SDKs retry automatically with exponential backoff and jitter.

Retry strategies against a rate-limited API (simulation) (run for real)

import random

# Cloud APIs throttle you ("429 Too Many Requests" / "ThrottlingException"). SDKs retry with exponential backoff + jitter.
class API:
    def __init__(self, limit_per_sec): self.limit, self.window, self.count = limit_per_sec, -1, 0
    def call(self, t):
        sec = int(t)
        if sec != self.window: self.window, self.count = sec, 0
        self.count += 1
        return self.count <= self.limit

def simulate(clients, mode, seed=2):
    rng = random.Random(seed); api = API(limit_per_sec=20)
    events = [(rng.random() * 0.2, i, 0) for i in range(clients)]       # all clients start within 0.2 s
    done, calls, last = 0, 0, 0.0
    events.sort()
    while events:
        t, c, attempt = events.pop(0)
        calls += 1
        if api.call(t): done += 1; last = max(last, t); continue
        if attempt >= 8: continue
        if mode == "immediate retry": delay = 0.01
        elif mode == "backoff": delay = 0.1 * 2 ** attempt
        else: delay = rng.uniform(0, 0.1 * 2 ** attempt)              # full jitter
        events.append((t + delay, c, attempt + 1)); events.sort()
    return done, calls, last

print("100 clients start together against an API that allows 20 calls per second")
print(f"{'strategy':18} {'completed':>10} {'API calls made':>15} {'time to finish (s)':>19}")
for mode in ("immediate retry", "backoff", "backoff + jitter"):
    d, c, last = simulate(100, mode)
    print(f"{mode:18} {d:10d} {c:15d} {last:19.2f}")
print("\nImmediate retries pile onto the limit and most clients give up. Backoff spaces them out; jitter stops them retrying in lock-step.")

# ----- Output (real run) -----

Spot capacity needs checkpoints (run for real)

import random

# A 10-hour batch job on spot (cheap, interruptible) vs on-demand. Spot is interrupted on average once every 4 hours.
def run(checkpoint_every, seed, work_hours=10.0, mtbi=4.0, spot_price=0.03, od_price=0.10):
    rng = random.Random(seed); done = 0.0; wall = 0.0; paid_hours = 0.0
    while done < work_hours:
        time_to_interrupt = rng.expovariate(1 / mtbi)
        step = min(work_hours - done, time_to_interrupt)
        wall += step; paid_hours += step
        if step < work_hours - done:                        # interrupted: progress is kept only up to the last checkpoint
            saved = (step // checkpoint_every) * checkpoint_every if checkpoint_every else 0
            done += saved; wall += 0.05                     # 3 minutes to get a replacement
        else: done = work_hours
    return paid_hours * spot_price, wall

print("on-demand: 10.0 h wall-clock, cost $1.00 (no interruptions)")

34 AWS Workflow 1: Deploy a Three-Tier Web App, Step by Step

Picture: Building a shop: first the land and roads, then the building, then the staff, then the front door, then the cameras.
Fig S7 — Workflow 1 — a classic three-tier web app on AWS.
  1. Create the foundation. Set up a multi-account structure (or at least separate dev and prod accounts), enable MFA, create an admin role through IAM Identity Center, turn on CloudTrail and a budget alarm.
  2. Design the network. Choose a region near users. Create a VPC (for example 10.0.0.0/16) with public, app and data subnets in three AZs; an Internet Gateway; NAT gateways; route tables.
  3. Create security groups. ALB group (443 from the internet) → app group (app port from the ALB group only) → database group (database port from the app group only).
  4. Build the database. RDS or Aurora, Multi-AZ, private subnets, encryption with KMS, automated backups, credentials in Secrets Manager.
  5. Bake the app image. Create a launch template from an AMI (or use containers on ECS); the app reads secrets with its instance role, not keys.
  6. Create the Auto Scaling group. Min 2, max N across AZs, target tracking on CPU or request count per target, health checks from the ALB.
  7. Add the load balancer. ALB in public subnets, HTTPS listener with an ACM certificate, target group to the Auto Scaling group.
  8. Add CDN, WAF and DNS. CloudFront in front of the ALB and S3 for static files; AWS WAF managed rules; Route 53 alias record to CloudFront.
  9. Observe. CloudWatch dashboards and alarms (5xx rate, latency, CPU, database connections), centralised logs, alarms to a chat/pager.
  10. Automate. Put everything in Terraform or CloudFormation/CDK; deploy with a pipeline using blue/green or rolling updates.
  11. Test failure. Terminate an instance, fail an AZ in a game day, restore the database from backup, and watch the alarms.
  12. Control cost. Tag resources, review Cost Explorer weekly, add Savings Plans for the steady base, clean unused resources.

The same flow on other clouds appears in the Azure and Google sections.

35 AWS Workflow 2: A Serverless API, Step by Step

39 AWS Case Study: The October 2025 us-east-1 DynamoDB DNS Event

Picture: A phone book that suddenly lists one very important number as 'empty'. Everything that looks up that number fails, and then the services that rely on those services fail too.

AWS published a post-event summary (aws.amazon.com/message/101925). As summarised by that page and write-ups of it:

  • When: from 11:48 PM PDT on 19 Oct to about 2:20 PM PDT on 20 Oct 2025 in the US-EAST-1 region, in three phases of impact.
  • Trigger: a latent race condition in the automation that manages DynamoDB's DNS records left the regional endpoint's DNS record empty, and the automation could not repair it by itself.
  • Cascade: services that depend on DynamoDB (and the control machinery for launching EC2 instances and for network load balancer health) were impaired as it recovered; AWS throttled some operations to help recovery.
  • Follow-up: AWS disabled the DNS automation worldwide until safeguards were added.

Lessons for your design

A region can fail in ways AZs do not protect againstFor critical systems, plan multi-region failover and test it
Hidden dependencies (DNS, control planes, a database used by many services)Map dependencies; keep the data plane independent of control-plane actions during an incident
Recovery stormsAdd backoff and jitter to retries, and rate-limit your own recovery work (see the retry simulation)
Status pages lagMonitor your own users' experience, not only provider dashboards

# SIMULATION of Salesforce-style multi-tenancy: many customers (tenants) share one platform, so each transaction gets hard LIMITS.
# Classic published synchronous Apex limits include: 100 SOQL queries, 150 DML statements, 50,000 query rows per transaction (check current Salesforce docs).
class LimitException(Exception): pass

class Transaction:
    LIMITS = {"soql": 100, "dml": 150, "rows": 50_000}
    def __init__(self): self.used = {"soql": 0, "dml": 0, "rows": 0}
    def _use(self, what, n=1):
        self.used[what] += n
        if self.used[what] > self.LIMITS[what]: raise LimitException(f"Too many {what}: {self.used[what]} (limit {self.LIMITS[what]})")
    def query(self, sql, rows=1): self._use("soql"); self._use("rows", rows)
    def update(self, n_records): self._use("dml")                     # one DML statement can update MANY records

accounts = 200                                                        # a trigger fires for 200 records at once (data load)

def naive_trigger(tx):                                                # query and update INSIDE a loop
    for _ in range(accounts):
        tx.query("SELECT ... WHERE AccountId = :id", rows=3)
        tx.update(1)

def bulkified_trigger(tx):                                            # one query for all, one update for all
    tx.query("SELECT ... WHERE AccountId IN :ids", rows=accounts * 3)
    tx.update(accounts)

for fn in (naive_trigger, bulkified_trigger):
    tx = Transaction()
    try:
        fn(tx); print(f"{fn.__name__:18}: OK, used {tx.used}")
    except LimitException as e:
        print(f"{fn.__name__:18}: FAILED -> {e}   (used so far: {tx.used})")
print("\nWhy limits? One tenant's runaway code must not slow down thousands of others sharing the same servers. Design for it: bulkify, avoid queries in loops,")
print("use asynchronous processing (batch/queueable) for big jobs, and test with 200+ records. Other clouds use quotas and throttles for the same reason.")

HDFS in miniature: blocks, 3 replicas across racks, and re-replication after failures (simulation) (run for real)

import random

BLOCK_MB = 128
class Cluster:
    def __init__(self, racks=3, nodes_per_rack=3):
        self.nodes = {f"r{r}n{n}": {"rack": r, "blocks": set(), "alive": True} for r in range(racks) for n in range(nodes_per_rack)}
        self.block_map = {}                                      # block id -> set of nodes holding it (the NameNode's metadata)
        self.rng = random.Random(4)
    def place(self, block, writer_node):
        # HDFS default idea: 1st copy on the writer's node, 2nd on a different rack, 3rd on another node of that second rack
        first = writer_node
        other_racks = [n for n, v in self.nodes.items() if v["rack"] != self.nodes[first]["rack"] and v["alive"]]
        second = self.rng.choice(other_racks)
        same_rack = [n for n, v in self.nodes.items() if v["rack"] == self.nodes[second]["rack"] and n != second and v["alive"]]
        third = self.rng.choice(same_rack)
        for n in (first, second, third): self.nodes[n]["blocks"].add(block)
        self.block_map[block] = {first, second, third}
    def write_file(self, name, size_mb, writer):
        n = -(-size_mb // BLOCK_MB)
        for i in range(n): self.place(f"{name}#{i}", writer)
        return n
    def kill(self, node):
        self.nodes[node]["alive"] = False
        for b in self.nodes[node]["blocks"]: self.block_map[b].discard(node)
        self.nodes[node]["blocks"] = set()
    def under_replicated(self): return sorted(b for b, holders in self.block_map.items() if len(holders) < 3)
    def heal(self):
        fixed = 0
        for b in self.under_replicated():
            holders = self.block_map[b]
            candidates = [n for n, v in self.nodes.items() if v["alive"] and n not in holders]
            while len(holders) < 3 and candidates:
                n = self.rng.choice(candidates); candidates.remove(n); holders.add(n); self.nodes[n]["blocks"].add(b); fixed += 1
        return fixed

MapReduce word count with mappers, combiner, shuffle and reducers (real run) (run for real)

from collections import defaultdict
import re, time

docs = ["the cloud is just someone else's computer", "the cloud scales and the cloud is elastic",
        "hadoop splits big data into blocks and the blocks into tasks", "map then shuffle then reduce",
        "the big data is big and the cluster is bigger"]

# MAP: each mapper turns its own chunk of data into (key, value) pairs, in parallel on different machines
def mapper(text):
    return [(w, 1) for w in re.findall(r"[a-z']+", text.lower())]

# COMBINER (optional): partially add up on the mapper's machine to shrink network traffic
def combiner(pairs):
    acc = defaultdict(int)
    for k, v in pairs: acc[k] += v
    return list(acc.items())

# SHUFFLE: send every pair with the same key to the same reducer
def shuffle(all_pairs, reducers=2):
    parts = [defaultdict(list) for _ in range(reducers)]
    for k, v in all_pairs: parts[hash(k) % reducers][k].append(v)
    return parts

# REDUCE: each reducer adds up the values for its keys
def reducer(part): return {k: sum(vs) for k, vs in part.items()}

mapped = [mapper(d) for d in docs]

Why clusters need a fair scheduler (simulation) (run for real)

# SIMULATION: a cluster with 100 "containers" (slots). Jobs arrive in this order: (name, queue, containers wanted, duration at full size)
JOBS = [("etl-big", "data", 100, 10), ("report-a", "bi", 10, 2), ("report-b", "bi", 10, 2), ("ml-train", "ml", 40, 6), ("etl-small", "data", 10, 1)]
CAPACITY = 100

def fifo():
    """One line: a job starts only when the one in front of it has started and enough slots are free (head-of-line blocking)."""
    now, free, running, pending, start, end = 0.0, CAPACITY, [], list(JOBS), {}, {}
    while pending or running:
        while pending and pending[0][2] <= free:
            n, q, c, d = pending.pop(0); start[n] = now; end[n] = now + d; running.append((now + d, c)); free -= c
        if running:
            running.sort(); t, c = running.pop(0); now = max(now, t); free += c
    return start, end

QUEUE_MAX = {"data": 70, "bi": 20, "ml": 40}          # capacity scheduler: each team's queue may use at most this many slots
def capacity_scheduler():
    """Several queues. A job bigger than its queue's maximum runs smaller (and so longer); small jobs do not wait behind big ones."""
    now, free, used, running, pending, start, end = 0.0, CAPACITY, {q: 0 for q in QUEUE_MAX}, [], list(JOBS), {}, {}
    while pending or running:
        for job in list(pending):
            n, q, c, d = job
            alloc = min(c, QUEUE_MAX[q] - used[q], free)
            if alloc >= min(c, 10):                                # start as soon as it can get a useful slice (at least 10 slots)
                pending.remove(job); dur = c * d / alloc
                start[n] = now; end[n] = now + dur; running.append((now + dur, alloc, q)); free -= alloc; used[q] += alloc
        if running:
            running.sort(); t, a, q = running.pop(0); now = max(now, t); free += a; used[q] -= a
        elif not pending: break
    return start, end

for name, f in (("FIFO (one line)", fifo), ("capacity scheduler (queue limits)", capacity_scheduler)):
    s, e = f()
    print(name)
    for n, q, c, d in JOBS: print(f"   {n:9} ({q:4}) wants {c:3d} slots: starts t={s[n]:5.1f}, finishes t={e[n]:5.1f}")

The migration workflow, step by step

  1. Assess: inventory applications, dependencies, data size, licences, performance; classify with the 6 Rs.
  2. Plan: business case and TCO, landing zone (accounts, network, identity, security baseline), wave plan (group apps that depend on each other).
  3. Build the landing zone: accounts/subscriptions/projects, networking and connectivity, IAM, logging, guardrail policies, cost tags.
  4. Pilot: migrate one low-risk application end to end to learn and fix the process.
  5. Migrate in waves: use tools (AWS Application Migration Service/DMS, Azure Migrate, Google Migrate to Virtual Machines, database replication); replicate data, test, cut over with a rollback plan.
  6. Validate: performance, security, backups and cost against the plan.
  7. Optimise: rightsizing, managed services, commitments, automation.
  8. Operate and improve: new run-books, monitoring, training; decommission the old environment (and stop paying for it).

69 Reliability Engineering: SLOs, Error Budgets and Chaos

Picture: Pilots practise emergencies in a simulator so the real thing is calm.
  • SLI (a measurement, e.g. 99% of requests under 300 ms), SLO (the target), SLA (a contract with penalties).
  • Error budget: if the SLO is 99.9% the allowed failure is 0.1%; when the budget is spent, slow down feature releases and fix reliability.
  • Chaos engineering / game days: deliberately stop servers, block an AZ or break a dependency in a safe way to see how the system copes (AWS Fault Injection Service, Azure Chaos Studio).
  • Blameless post-incident reviews and runbooks.
  • Reliable design basics: timeouts, retries with backoff, circuit breakers, bulkheads, graceful degradation (see the HLD guide).

81 FAQ

Picture: Questions beginners ask most.
Q: Which cloud should I learn first?

Learn the shared concepts (Parts A–B), then pick the cloud your target employers or projects use. AWS has the broadest job market, Azure dominates in Microsoft shops, Google Cloud is strong in data and AI. Skills transfer well (Rosetta Stone).

Q: Is the cloud cheaper than owning servers?

Not always. It wins for variable, new and experimental workloads and loses for very steady, heavy ones (model). Cost discipline decides the outcome.

Q: Is the cloud safe?

Providers secure their side very well; most incidents are customer misconfigurations. Follow the shared-responsibility model and the security checklist.

Q: What is the difference between a region and an availability zone?

A region is a geographic area; availability zones are separate data-centre locations inside it. Use several AZs for high availability and several regions for disaster recovery.

Q: Do I need Kubernetes?

Not always. Start with a simple platform (Cloud Run, App Service, Container Apps, ECS/Fargate). Move to Kubernetes when you need its ecosystem or control.

Q: Is Google App Engine dead?

No: second-generation standard runtimes are supported, but Google recommends Cloud Run for new apps and has deprecated first-generation runtimes (Jan 2026) (details).

Q: Is Hadoop obsolete?

Hadoop is still released (3.5.0 in April 2026) and its ideas power today's data lakes, but many teams run Spark and SQL engines over cloud object storage instead of operating HDFS clusters themselves (section).

Q: Is Salesforce a cloud like AWS?

No. Salesforce is SaaS plus a business-application platform. It runs on public-cloud infrastructure (Hyperforce) and is not a place to rent general servers.

Q: How do I avoid a surprise bill?

Budget alerts on day one, tags, IaC with destroy, clean-up routines, caps on autoscaling, and review costs weekly (checklist).

Q: Are the outputs on this page real?

Yes for all Python demos (run with Python 3.12 on my machine). They are simulations of cloud ideas with illustrative prices and numbers. The AWS/Azure/Google/Oracle/Alibaba/Salesforce/Hadoop commands and files are templates that were not run, because they need accounts and cost money.

82 Interview Questions (With Answers)

Picture: Grouped by theme, easiest first. Click a question to reveal the answer.

A. Fundamentals

Q1: What is cloud computing?

On-demand delivery of computing resources over the internet with pay-per-use pricing, self-service and elasticity.

Q2: IaaS vs PaaS vs SaaS with examples?

IaaS: VMs (EC2). PaaS: App Engine/App Service. SaaS: Salesforce. FaaS/serverless: Lambda.

Q3: Public, private, hybrid and multi-cloud?

Shared provider cloud; one organisation's own cloud; the two connected; more than one public cloud.

Q4: Shared responsibility model?

Provider secures the cloud; customer secures what they put in it (identities, data, configuration).

Q5: Region vs AZ vs edge location?

Geographic area; independent facilities inside it; small caches near users.

B. Core services and design

Q6: Block vs file vs object storage?

Raw disk for one server; shared filesystem; key-based HTTP storage with huge scale.

Q7: How do you make a web app highly available?

Stateless servers in multiple AZs behind a load balancer with health checks, autoscaling, a multi-AZ managed database, and tested failover (section).

Q8: Public vs private subnet?

Public subnets have a route to an internet gateway; private subnets do not (outbound only via NAT).

Q9: How does autoscaling work?

A policy compares a metric (CPU, requests per target, queue depth) with a target and adds or removes instances within min/max, with warm-up and cooldown.

Q10: Serverless benefits and drawbacks?

No servers to manage, scale to zero, pay per use; but cold starts, limits and provider-specific triggers.

Q11: What is Infrastructure as Code and why use it?

Declaring infrastructure in files: repeatable, reviewable, drift-detectable, quick to tear down.

Q12: Explain RTO and RPO and DR strategies.

RTO: downtime tolerated; RPO: data loss tolerated. Strategies: backup/restore, pilot light, warm standby, active-active.

C. Providers

Q13: How is AWS organised?

Organizations → accounts → regions → AZs → services; IAM roles and SCPs govern access; services are global or regional (section).

Q14: Azure's hierarchy?

Entra tenant → management groups → subscriptions → resource groups → resources; ARM is the control plane.

Q15: Google Cloud's hierarchy?

Organisation → folders → projects → resources; APIs are enabled per project; the VPC is global.

Q16: App Engine standard vs flexible?

Standard: sandboxed runtimes, fast scaling to zero. Flexible: Docker containers on VMs, any runtime, slower, no scale to zero. For new apps Google recommends Cloud Run.

Q17: What is special about OCI?

Compartments, strong database offerings (Autonomous, Exadata), flexible shapes, dedicated and sovereign regions, and Database@ partner-cloud offerings.

Q18: Alibaba Cloud considerations?

Strong in China/APAC; ICP filing and Chinese data rules; services such as ECS, OSS, PolarDB, MaxCompute.

Q19: Why does Salesforce have governor limits?

Multi-tenancy: limits stop one tenant's code from consuming shared resources; developers must bulkify and use async processing.

Q20: Explain Hadoop's architecture.

HDFS (NameNode metadata, DataNodes with replicated blocks), YARN (ResourceManager and NodeManagers), MapReduce/Spark processing near the data (section).

Q21: How does HDFS survive node and rack failures?

Blocks have multiple replicas on different racks; the NameNode detects missing replicas and re-replicates; HA NameNodes avoid a single point of failure.

Q22: Map a service across clouds, for example queues.

SQS (AWS), Service Bus/Queue Storage (Azure), Cloud Tasks/Pub/Sub (Google), MNS/RocketMQ (Alibaba).

D. Security, cost, operations

Q23: How do you secure a cloud account?

MFA, SSO, least privilege, no root use, audit logs, encryption, private networking, secrets management, guardrail policies, monitoring.

Q24: What is envelope encryption?

Data encrypted with a data key; data key encrypted by a master key in a KMS (demo).

Q25: How do you reduce cloud costs?

Tag and allocate, rightsize, delete idle, autoscale, commitments for the baseline, spot for batch, cheaper storage tiers, CDN and locality to reduce egress.

Q26: Reserved vs on-demand vs spot?

Commitment discount for steady use; flexible baseline price; deep discount for interruptible work. Our break-even example: about 62% utilisation.

Q27: What caused the Oct 2025 AWS us-east-1 outage?

A race condition in DynamoDB's DNS automation left an empty DNS record; dependent services were impaired and recovery cascaded (case study).

Q28: How do you prevent retry storms?

Exponential backoff with jitter, retry budgets, circuit breakers and rate limits.

Q29: How would you migrate a legacy app?

Assess with the 6 Rs, build a landing zone, pilot, migrate in waves with replication and rollback, validate, optimise, decommission.

Q30: What is the EU Data Act's effect on cloud?

Customers have switching rights; switching charges including egress for moving are banned from 12 Jan 2027 (as reported).

Q31: How would you design multi-region active-active?

Global traffic routing, data replication strategy (conflict handling), regional independence, tested failover, higher cost; weigh against warm standby.

Q32: How do you handle secrets in CI/CD?

Federated short-lived credentials (OIDC), a secrets manager, no secrets in repos or logs.

84 Quick Quiz 🎯

Q1: Who is responsible for patching the operating system on an IaaS VM?

You (the customer). On PaaS and serverless the provider does it.

Q2: Why use at least 3 AZs for important workloads?

With 3 AZs you need only 50% extra capacity to survive losing one (our demo: 9 servers for a load needing 6), versus 100% with 2.

About 62% of hours.

A crashed server handles nothing, so it looks idle and always has the lowest load.

Q5: What does explicit deny do in IAM?

It overrides any allow.

Q6: In HDFS what happens when a DataNode dies?

The NameNode sees under-replicated blocks and re-replicates them from surviving copies.

Q7: Why bulkify Salesforce code?

Governor limits (for example queries per transaction) are quickly exceeded by per-record queries in loops.

Cloud Run.

Q9: What is the difference between durability and availability?

Durability is not losing data; availability is being reachable right now.

Serve through a CDN, and keep chatty services in the same AZ/region.
