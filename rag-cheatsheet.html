⚡ 30-second RAG

  • What: LLM + search. Look facts up first, then answer from them (open-book exam).
  • Why: cures hallucination, stale knowledge, no private data, context limits.
  • Core loop: Retrieve → Augment → Generate.
  • Quality lever #1: data cleaning + chunking. #2: hybrid search + re-rank.
  • Math: cosine similarity = closeness of meaning; RRF merges ranked lists.
  • Prove it works: golden set + faithfulness / context precision / recall.
  • Ship it safely: RBAC at retrieval, treat docs as data, redact PII, monitor.

Part A — Foundations

§1What is RAG

LLM + retrieval: fetch relevant facts at question time, answer grounded in them. Like an open-book exam instead of a closed-book one.

§2Why RAG

  • Hallucination → answers cite real text
  • Stale knowledge (training cutoff) → fresh docs
  • Private data (HR policy, notes) → your KB
  • Context limit → send only the relevant bits

§3Prerequisites (4 words)

  • LLM — predicts the next token
  • Token — piece of text (~¾ word)
  • Prompt — instructions + context
  • Embedding — meaning as a list of numbers

§4RAG vs Fine-tuning vs Long-context

What it doesBest forDownside
RAGmodel unchanged; fetch facts per questionchanging data, big KBs, citations, cheap updatesretrieval can miss; more moving parts
Fine-tuneretrains weightsstyle / tone / format / skills (e.g. valid JSON)costly, slow to update, bad for facts
Long-contextpaste everything in the promptone small static doc set (e.g. a 200-page contract)per-query cost, slow, lost-in-the-middle, doesn’t scale

§5History

§6Big picture

Retrieve → Augment → Generate. Two phases: index once (ingest→clean→chunk→embed→store) and per question (search→prompt→answer).

§8Chunking strategies

Too big = noise; too small = lost context. Start 300–800 tokens, ~10% overlap, tune on real questions.

StrategyIdeaUse when
Fixed-sizecut every N tokens (+overlap)quick baseline
Recursiveparagraph → sentence → wordgeneral text (default)
Semanticcut where topic changes (embeddings)mixed-topic docs
Structure-awareheadings / sections / rowsmanuals, legal, reports
Sentence-windowmatch 1 sentence, return neighboursprecision + context
Parent-documentsearch small child, return big parentprecise search, rich context

§9Embeddings

Text → vector (384–3072 numbers); close vectors = similar meaning.

  • 9.1 trained by contrastive learning (pull similar, push different)
  • 9.2 bi-encoder: query & docs embedded separately → docs pre-computed
  • 9.3 bigger dims = more nuance, more cost; Matryoshka = truncatable vectors
  • 9.4 pick via MTEB leaderboard; fine-tune for niche jargon

§10Vector databases

§11Metadata filtering & self-query

Tag chunks: source · date · author · dept · access level · page.

  • Filter first, then vector search (precise + faster)
  • Self-query: LLM turns “finance, March 2025, budget cuts?” into filter + semantic query

TechniqueTrick

§14Re-ranking

Bi-encoder (fast) pulls ~top-20/50 → cross-encoder reads question+chunk together (slow, precise; e.g. Cohere Rerank) → keep best 3–5. Two-round talent show.

§15Augmentation (prompt build)

Template = instructions + context chunks + question. Say: answer only from the context; otherwise say “I don’t know.” Order and count of chunks matter.

§16Generation & citations

  • LLM writes the grounded answer
  • Cite source numbers per claim
  • Stream tokens for speed
  • Guardrails: check for claims not in context

Part C — The Math

§17Math behind RAG

ConceptFormula / meaning
17.1 Vectorlist of numbers = a point (embeddings have 100s–1000s of dims)
17.2 Dot productA·B = Σ AᵢBᵢ (e.g. (1,2)·(3,4) = 11)
17.3 Cosinecos θ = A·B / (‖A‖·‖B‖) → −1 opposite … 0 unrelated … 1 identical
17.4 Compare metricscosine = angle (text default) · Euclidean = distance · dot = cosine if vectors normalised
17.5 ANNapproximate nearest neighbours (HNSW / IVF) instead of brute force
17.6 TF-IDF / BM25keyword scoring — the lexical half of hybrid search

Formulas to remember

  • MMR = λ·sim(chunk, query) − (1−λ)·max sim(chunk, picked)
  • RRF = Σ 1 / (k + rank) over lists, k ≈ 60
  • Cosine = A·B / (‖A‖‖B‖)

Part D — Advanced Architectures

§19Hybrid search + RRF

BM25 (exact names, SKUs, error codes) + vectors (meaning) → merge with RRF. Catches what either misses.

§20Self-RAG & CRAG

  • 20.1 Self-RAG: model self-critiques — retrieve? relevant? supported? retrieve again?
  • 20.2 CRAG: evaluator grades chunks Correct / Ambiguous / Incorrect → bad ⇒ fallback (web search)

§21RAPTOR

Cluster chunks → summarise → repeat = tree. Query any level: leaf detail or big-picture summary.

§22Adaptive RAG & routing

Classify the question: no retrieval (chit-chat) / one-shot (simple fact) / iterative (multi-hop). Router picks which KB or tool.

§23GraphRAG

LLM extracts entities + relations → knowledge graph → communities → summaries.

  • Local search = graph walk (specific)
  • Global search = community summaries (themes)
  • Best for multi-hop & “whole-corpus” questions

§24Agentic RAG

  • 24.1 ReAct: reason → act → observe → loop
  • 24.2 Multi-hop: chain retrievals (A → B → C)
  • 24.3 Three ways: in-app tool · MCP server · platform built-in search

§25Multimodal RAG

  • CLIP-style shared text+image embeddings
  • Caption-then-embed (simple, common)
  • Tables → SQL, not similarity
  • Page-as-image (ColPali family)

§26Long-context vs RAG

RAG still wins on cost · speed · lost-in-the-middle · freshness · scale. Best: RAG narrows, long context reads.

§27Conversational memory

  • Recent turns in the prompt
  • Summarise older turns
  • Past turns as retrievable long-term memory

  • ☑ RBAC at retrieval
  • ☑ monitoring + logging
  • ☑ “nothing found” fallback

Bad answer? debug in this order

1 were the right chunks retrieved? (log them) → 2 chunking size/overlap → 3 query rewrite / hybrid / metadata filter → 4 re-rank & lower top-k → 5 prompt says “only from context” → 6 index fresh? → 7 model choice.
