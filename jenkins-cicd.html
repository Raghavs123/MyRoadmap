Part A — CI/CD Foundations

1 What Are CI and CD?

Picture: A bakery with a conveyor belt. Many bakers add their dough all day. A machine checks every loaf as it arrives (is it baked? does it taste right?), boxes the good ones and puts them on the van. Nobody carries trays by hand at the end of the week and hopes nothing is burnt. CI/CD is that conveyor belt for software.
TermMeaningWhat happens
Continuous Integration (CI)Developers merge their changes into the shared code often (at least daily), and every merge is automatically built and testedCompile, run unit tests, static checks; bad changes are caught within minutes
Continuous Delivery (CD)Every good change is automatically packaged and made ready to release; a human presses the buttonBuild artefact, test in a production-like environment, keep it deployable at all times
Continuous Deployment (CD)Every good change goes to production automatically, with no buttonAutomated tests and monitoring act as the safety net
PipelineThe automated path from a commit to production, made of stagesSource → build → test → package → deploy → verify
In one line: CI/CD = merge small changes often, let machines check them on every change, and make releasing boring and safe.

Good to know

  • The word 'CD' means two different things (delivery vs deployment). Ask which one a team means.
  • CI is a practice first (small, frequent merges and a team habit of fixing a broken build at once); the tool (Jenkins, GitHub Actions…) only supports it.
  • Related guides: DevOps, Git & GitHub, Cloud, Linux.
The three rules of a healthy CI: (1) everyone merges to the main line often, (2) the build and tests run automatically and fast, (3) a broken main branch is fixed immediately, before anything else.

2 Why Do We Need CI/CD? (Life Without It)

Picture: Cooking for a wedding. If everyone cooks alone for a month and you taste all the food on the wedding day, you will find surprises. If you taste every dish as it is made, you fix problems while they are small.
Without CI/CDWith CI/CD
'Integration week': everyone merges at the end and the code does not fit togetherSmall merges daily; problems appear within minutes
'Works on my machine' builds that nobody else can reproduceA clean, scripted build on a neutral machine for every change
Manual, scary releases at midnight with a 30-step checklistA repeatable button (or no button) that does the same steps every time
Bugs found weeks later by customersBugs found by tests in the pipeline, before release
Fear of deploying, so releases are big and riskyFrequent small releases that are easier to understand and roll back
Knowledge locked in one person's headThe pipeline file documents how to build and release

Good to know

  • Research summarised in the DORA reports links frequent, small, automated delivery with both higher speed and higher stability.
  • CI/CD does not remove testing or review; it makes them run every time without anyone forgetting.

  • A pipeline is a graph, not a straight line: independent steps run in parallel (see the speed section).

How the chance of a merge conflict grows with branch age and team size (random-model simulation) (run for real)

import random

# Why long-lived branches hurt: the longer a branch lives, the more other people's changes pile up, and the more likely a merge conflict.
def conflict_probability(team_size, branch_days, files=500, edits_per_dev_per_day=1, trials=3000, seed=2):
    rng = random.Random(seed); conflicts = 0
    for _ in range(trials):
        mine = {rng.randrange(files) for _ in range(edits_per_dev_per_day * branch_days)}
        theirs = set()
        for _ in range(team_size - 1):
            theirs |= {rng.randrange(files) for _ in range(edits_per_dev_per_day * branch_days)}
        conflicts += bool(mine & theirs)
    return conflicts / trials

print("chance that merging your branch touches a file someone else changed (500-file repo, 1 file edited per developer per day):")
print(f"{'branch lifetime':>16} " + " ".join(f"{n:>3} devs" for n in (3, 8, 20)))
for days in (1, 2, 5, 10, 20):
    print(f"{days:>10} day(s) " + " ".join(f"{conflict_probability(n, days):7.0%}" for n in (3, 8, 20)))
print("\nTrunk-based development: merge small changes to the main branch at least daily (hide unfinished work behind feature flags) so conflicts and surprises stay tiny.")
print("This is a simplified random model, but the trend is real: conflict risk grows with team size AND branch age.")

# ----- Output (real run) -----

#          1 day(s)      0%      2%      4%
#          2 day(s)      2%      5%     13%
#          5 day(s)      8%     29%     61%
#         10 day(s)     34%     76%     98%
#         20 day(s)     78%    100%    100%

In a 500-file repository where each developer edits one file a day, a one-day branch in a 3-person team had almost no conflict risk (0%), but a 10-day branch had 34% and a 20-day branch 78%; with 20 developers a 10-day branch reached 98%. The real world is not random, but the trend is the reason CI asks for small, frequent merges.

Good to know

  • Feature flags let you merge unfinished code safely: the code is in production but switched off until ready; they also enable gradual rollouts (use flag tools and remove old flags).
  • Protect main with required status checks and pull-request reviews (branch protection).

7 Measuring Delivery: The DORA Metrics

Picture: A car's dashboard for the delivery process: how often you drive, how long a trip takes, how often the car breaks, and how fast you get going again.

The DevOps Research and Assessment programme (dora.dev) found five measures that describe software delivery performance. They are system measures, not individual scorecards.

MetricGroupMeaning
Deployment frequencyThroughputHow often you release to production
Change lead timeThroughputTime from a commit to it running in production
Failed deployment recovery timeThroughputHow long it takes to recover from a failed production change (formerly 'time to restore service')
Change fail rateInstabilityShare of deployments that cause a failure needing fix or rollback
Deployment rework rateInstabilityShare of deployments that were unplanned, made to fix a production problem (added around 2024)

DORA's 2025 report is described (secondary summaries) as moving away from fixed performance tiers to team 'archetypes' that also include human factors such as burnout and friction.

Fig S3 — Median lead time in hours: before vs after pipeline automation (synthetic data).
Computing the five metrics from a deployment log (two synthetic teams, made-up data) (run for real)

import random, statistics
from datetime import datetime, timedelta

# Compute the five DORA metrics from a deployment log. Two synthetic teams over 90 days (made-up data).
def make_team(seed, deploys, fail_rate, recovery_hours, lead_hours, rework_rate):
    rng = random.Random(seed); t0 = datetime(2026, 8, 1); log = []
    for i in range(deploys):
        when = t0 + timedelta(hours=rng.uniform(0, 90 * 24))
        lead = rng.lognormvariate(0, 0.6) * lead_hours
        failed = rng.random() < fail_rate
        rec = rng.lognormvariate(0, 0.5) * recovery_hours if failed else 0
        rework = rng.random() < rework_rate
        log.append({"when": when, "lead_h": lead, "failed": failed, "recovery_h": rec, "rework": rework})
    return log

def dora(log, days=90):
    fails = [d for d in log if d["failed"]]
    return {"deploys/week": len(log) / (days / 7), "median lead time (h)": statistics.median(d["lead_h"] for d in log),
            "change fail rate": len(fails) / len(log), "median recovery (h)": statistics.median(d["recovery_h"] for d in fails) if fails else 0,
            "rework rate": sum(d["rework"] for d in log) / len(log)}

before = dora(make_team(1, deploys=12, fail_rate=0.25, recovery_hours=18, lead_hours=120, rework_rate=0.20))
after = dora(make_team(2, deploys=140, fail_rate=0.08, recovery_hours=1.5, lead_hours=6, rework_rate=0.06))
print(f"{'metric':24} {'before CI/CD automation':>24} {'after':>10}")
for k in before:
    b, a = before[k], after[k]
    fmt = (lambda v: f"{v:.0%}") if "rate" in k else (lambda v: f"{v:.1f}")
    print(f"{k:24} {fmt(b):>24} {fmt(a):>10}")
print("\nThree speed measures (deploy frequency, lead time, recovery time) and two stability measures (change fail rate, rework rate).")
print("Teams that deploy small changes often tend to fail less per deploy and recover faster. Use the numbers to improve the system, never to rank people.")

# ----- Output (real run) -----
# metric                    before CI/CD automation      after
# deploys/week                                  0.9       10.9
# median lead time (h)                        172.1        6.4
# change fail rate                              17%         6%
# median recovery (h)                          14.2        1.6
# rework rate                                   17%         6%
#
# Three speed measures (deploy frequency, lead time, recovery time) and two stability measures (change fail rate, rework rate).
# Teams that deploy small changes often tend to fail less per deploy and recover faster. Use the numbers to improve the system, never to rank people.

A team deploying about once a week with 7-day lead times and a 17% change-fail rate improved (after automation) to about 11 deploys a week, 6-hour lead times, a 6% fail rate and 1.6-hour recovery. This is invented data to show the calculations; real numbers come from your own pipeline and incident records.

Good to know

  • Do not use the numbers to rank people (Goodhart's law: a measure that becomes a target stops being a good measure). Use them to find bottlenecks.
  • The pipeline itself can emit the data: deployment events, commit timestamps, incident links.

Part B — Jenkins Fundamentals

9 What Is Jenkins?

Picture: A very flexible butler. Jenkins does not know how to bake or test anything by itself; it follows your instructions, calls the right tools in the right order, and tells you what happened. Thousands of plugins teach the butler new tricks.
  • Jenkins is a free, open-source automation server written in Java, used mostly for CI/CD but able to run any scripted job (backups, reports, infrastructure tasks).
  • Self-hosted: you run it on your own servers, VMs or Kubernetes; you control data, network and cost, and you are responsible for updates and security.
  • Pipeline as code with a Jenkinsfile (Groovy-based DSL), plus older UI-configured 'Freestyle' jobs.
  • Plugin ecosystem: source control, build tools, notifications, cloud agents, credentials and more (see plugins.jenkins.io).
  • Governance: a Continuous Delivery Foundation project; two release lines: weekly and Long-Term Support (LTS).
StrengthsWeaknesses
Extremely flexible; works with any language, tool or OS; on-premises friendly; huge community; no per-minute feesYou must operate it (upgrades, backups, scaling, security); plugin quality varies; Groovy pipelines can get complex; the UI feels dated to some

Good to know

  • Official documentation: jenkins.io/doc.
  • Jenkins versus hosted CI services is a trade-off between control and convenience (see the comparison).

10 Jenkins Architecture: Controller, Agents, Executors, Workspaces

Picture: A restaurant. The head waiter (controller) takes orders, keeps the list and decides who cooks what. The kitchens (agents) have several stoves (executors). Each dish gets its own counter space (workspace).
Fig S4 — Jenkins architecture: a controller coordinates, agents do the work.
PartMeaning
ControllerThe Jenkins server: web UI, REST API, job scheduling, build queue, plugin host, credentials store, configuration (JENKINS_HOME). Best practice: set executors to 0 so no builds run on the controller (a build on the controller can read secrets and damage Jenkins)
Agent (node)A machine or container that runs builds. Connects to the controller by SSH (outbound from controller) or as an inbound agent using a secret/WebSocket
ExecutorOne slot on an agent that can run one build at a time
LabelsTags like linux, docker, gpu used to choose where a job runs (agent { label 'linux && docker' })
WorkspaceA directory on the agent where the job checks out and builds. Clean it after builds
Build queueWhere triggered builds wait until an executor with the right label is free
JENKINS_HOMEThe folder with jobs, build history, plugins, credentials and secrets: back it up and protect it
Static vs ephemeral agentsStatic agents are long-lived servers; ephemeral agents (Docker, Kubernetes pods, cloud VMs) are created for one build and thrown away: cleaner and scalable

Good to know

  • Controller sizing: the controller needs memory and fast disk; do not run heavy builds on it.
  • Since the Jenkins project describes the Java requirement for both controller and agents, plan Java 21 or 25 everywhere (see the versions section).

First-run steps (any method)

  1. Install Java 21 or 25 (or use the Docker image, which bundles Java).
  2. Start Jenkins; open http://localhost:8080.
  3. Paste the initial admin password (printed in the log and stored in secrets/initialAdminPassword).
  4. Choose 'Install suggested plugins' (or select your own) and create your admin user.
  5. Set the Jenkins URL, set controller executors to 0, add an agent, and put the whole thing behind HTTPS (reverse proxy).
  6. Take a first backup of JENKINS_HOME.

Good to know

  • I could not run Jenkins on this machine (no Java installed), so every Jenkins file and command in this guide is a template that was not run; the Python simulations did run.
  • Never expose a Jenkins controller to the internet without authentication, HTTPS and a patching routine.

Why webhooks should be verified: signature check (real HMAC code) (run for real)

import hmac, hashlib, json, time

SECRET = b"shared-secret-stored-in-jenkins-and-the-git-server"       # in real life: a long random value from a secrets manager

def sign(body):                     # what GitHub does: header X-Hub-Signature-256: sha256=<hex digest of the raw body>
    return "sha256=" + hmac.new(SECRET, body, hashlib.sha256).hexdigest()

def verify(body, header, timestamp=None, max_age=300, seen=set()):
    if not hmac.compare_digest(sign(body), header): return "REJECT: bad signature"
    if timestamp is not None and abs(time.time() - timestamp) > max_age: return "REJECT: too old"
    delivery = hashlib.sha256(body).hexdigest()
    if delivery in seen: return "REJECT: replay (already processed)"
    seen.add(delivery); return "ACCEPT: trigger the build"

payload = json.dumps({"ref": "refs/heads/main", "after": "9f2c1ab", "repository": "shop/api"}).encode()
good = sign(payload)
print("legitimate push event      :", verify(payload, good, time.time()))
print("same event delivered again :", verify(payload, good, time.time()))
forged = json.dumps({"ref": "refs/heads/main", "after": "evil123", "repository": "shop/api"}).encode()
print("forged body, old signature :", verify(forged, good, time.time()))
print("attacker without the secret:", verify(forged, "sha256=" + "0" * 64, time.time()))
print("\nWithout signature checking, anyone who finds your Jenkins webhook URL can start builds (and burn money or run code paths). Use HTTPS, secrets, IP allow-lists where possible.")

# ----- Output (real run) -----
# legitimate push event      : ACCEPT: trigger the build
# same event delivered again : REJECT: replay (already processed)
# forged body, old signature : REJECT: bad signature
# attacker without the secret: REJECT: bad signature

How many executors do we need? (queue simulation) (run for real)

import random, statistics

# How many build agents (executors) do we need? Builds arrive randomly and each takes a while. Simulated queue.
def simulate(executors, builds_per_hour, mean_build_min, hours=200, seed=5):
    rng = random.Random(seed); t = 0.0; free_at = [0.0] * executors; waits = []
    end = hours * 60
    while True:
        t += rng.expovariate(builds_per_hour / 60)
        if t > end: break
        free_at.sort(); start = max(t, free_at[0]); waits.append(start - t)
        free_at[0] = start + rng.expovariate(1 / mean_build_min)
    return statistics.mean(waits), sorted(waits)[int(len(waits) * 0.95)], len(waits)

res = []

Why 'H' in cron matters (simulation) (run for real)

import hashlib
from collections import Counter

# Jenkins cron supports "H" = a hash of the job name, so jobs scheduled "hourly" do not all start in the same minute.
# (This uses a different hash than Jenkins, but the effect is the same.)
jobs = [f"project-{i:02d}-nightly" for i in range(60)]
def h_minute(name, lo=0, hi=59): return lo + int(hashlib.md5(name.encode()).hexdigest(), 16) % (hi - lo + 1)

fixed = Counter(0 for _ in jobs)                       # '0 * * * *'  -> every job at minute 0
spread = Counter(h_minute(j) for j in jobs)            # 'H * * * *'
print("60 jobs all scheduled 'hourly':")
print(f"  '0 * * * *' : {max(fixed.values())} jobs start in the same minute (a stampede)")
print(f"  'H * * * *' : at most {max(spread.values())} jobs start in the same minute; busiest minute count = {max(spread.values())}, idle minutes = {60 - len(spread)}")
print("  first five jobs get minutes:", [h_minute(j) for j in jobs[:5]], "(stable: the same job always gets the same minute)")

print("\nWith 10 executors and 8-minute builds, what happens at the stampede?")
executors, build_min = 10, 8
wait_fixed = sum(max(0, (i // executors)) * build_min for i in range(60)) / 60
print(f"  all 60 at once: average wait before starting = {wait_fixed:.0f} minutes (the queue drains over {-(-60 // executors) * build_min} minutes)")
peak = max(spread.values())
print(f"  spread out    : at most {peak} builds start together -> {'no waiting' if peak <= executors else 'little waiting'}")
print("\nPrefer webhooks (the Git server tells Jenkins about a push) over polling; use cron with H for scheduled work.")

#   '0 * * * *' : 60 jobs start in the same minute (a stampede)
#   'H * * * *' : at most 4 jobs start in the same minute; busiest minute count = 4, idle minutes = 26
#   first five jobs get minutes: [5, 27, 52, 57, 41] (stable: the same job always gets the same minute)
#

A complete declarative Jenkinsfile (template — not run)


// ---- TEMPLATE: NOT RUN (needs a Jenkins controller). A realistic declarative Jenkinsfile for a Python web service ----
pipeline {
  agent { label 'linux && docker' }                       // run on an agent that has these labels, never on the controller

  options {
    timeout(time: 30, unit: 'MINUTES')                   // a stuck build cannot hold an agent forever
    disableConcurrentBuilds()                            // one deployment pipeline at a time per branch
    buildDiscarder(logRotator(numToKeepStr: '30'))       // keep only the last 30 builds
    timestamps()
  }

  environment {
    REGISTRY = 'registry.example.com'
    IMAGE    = "${REGISTRY}/shop/api"
  }

  parameters {
    choice(name: 'DEPLOY_TARGET', choices: ['none', 'staging', 'production'], description: 'Where to deploy after tests')
  }

  triggers { cron('H 2 * * 1-5') }                       // nightly full run; normal runs start from a Git webhook

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('Install & unit tests') {
      steps {
        sh '''
          python -m venv .venv
          . .venv/bin/activate
          pip install -r requirements.txt
          pytest --junitxml=reports/junit.xml --cov=app --cov-report=xml
        '''
      }
      post { always { junit 'reports/junit.xml' } }      // test results appear in the build page
    }

    stage('Quality & security') {
      parallel {                                         // these two run at the same time
        stage('Lint')       { steps { sh '. .venv/bin/activate && ruff check .' } }
        stage('Dependency audit') { steps { sh '. .venv/bin/activate && pip-audit -r requirements.txt' } }
      }
    }

    stage('Build image') {
      steps { sh 'docker build -t $IMAGE:$GIT_COMMIT .' }  // single quotes: the SHELL expands variables (safer than Groovy interpolation)
    }

    stage('Push image') {
      when { branch 'main' }                              // only the main branch publishes images
      steps {
        withCredentials([usernamePassword(credentialsId: 'registry-creds', usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS')]) {
          sh 'echo "$REG_PASS" | docker login $REGISTRY -u "$REG_USER" --password-stdin'
          sh 'docker push $IMAGE:$GIT_COMMIT'
        }
      }
    }

    stage('Deploy to staging') {
      when { allOf { branch 'main'; expression { params.DEPLOY_TARGET != 'none' } } }
      steps { sh './deploy.sh staging $IMAGE:$GIT_COMMIT' }
    }

    stage('Approval for production') {
      when { allOf { branch 'main'; expression { params.DEPLOY_TARGET == 'production' } } }
      steps {
        timeout(time: 1, unit: 'HOURS') { input message: 'Deploy this build to production?', ok: 'Deploy' }
      }
    }

    stage('Deploy to production') {
      when { allOf { branch 'main'; expression { params.DEPLOY_TARGET == 'production' } } }
      steps { sh './deploy.sh production $IMAGE:$GIT_COMMIT' }
    }
  }

  post {
    always  { archiveArtifacts artifacts: 'reports/**', allowEmptyArchive: true; cleanWs() }
    failure { echo 'Build failed: notify the team (Slack/email step goes here)' }
  }
}

24 Multibranch Pipelines and Pull Requests

Picture: A recipe book that automatically makes a copy of the recipe for every new dish on the menu and throws away copies of dishes that left the menu.

  2. Jenkins scans the repository and creates a child job for every branch (and PR) with a Jenkinsfile.
  3. A webhook triggers a rescan on each push; builds start for the changed branch.
  4. Use when { branch 'main' } or when { changeRequest() } to behave differently on main vs pull requests (for example deploy only from main).

  6. Status checks report back to the pull request, which can block merging until the build is green.

25 Shared Libraries: Reusable Pipeline Code

Picture: A company recipe binder. Instead of every team writing the 'standard cake' method, they call the shared one and only change the flavour.
  • A shared library is a Git repository of Groovy code with vars/ (steps callable from any Jenkinsfile), src/ (classes) and resources/.
  • Configure it once in Jenkins (name, repository, default version) and use @Library('name@version') _ in the Jenkinsfile.
  • Pin versions (tags) and release them like software; test them (Jenkins Pipeline Unit testing frameworks exist).

Good to know

  • The payoff: 200 repositories get the same secure, fast pipeline and one change updates them all; the risk is that one bad change breaks them all, so version and test.

26 Docker and Kubernetes Agents

Picture: Instead of keeping a kitchen with every tool installed forever, you bring a clean, labelled lunchbox for each meal and throw it away afterwards.
  • Docker agent: agent { docker { image 'python:3.12' } } runs the stage inside that image; the toolchain is defined by the image, so builds are reproducible.
  • Kubernetes agents (Kubernetes plugin): each build gets a pod with one or more containers (for example a language container plus a kaniko container to build images without a Docker daemon); pods are deleted after the build; resource requests and limits protect the cluster.
  • Building images safely: avoid mounting the host Docker socket into builds (it gives root-level control of the host); prefer rootless/daemonless builders (kaniko, buildah, BuildKit in rootless mode) or dedicated build agents.
  • Caching: use persistent volumes, a registry-based layer cache, or remote caches for dependency downloads.

Good to know

  • Ephemeral agents turn build machines from pets into cattle: no leftover files, no 'it works on agent 3'.

A tiny CI engine: stages, fail-fast, retries and post actions (real Python) (run for real)

# A tiny CI engine in Python: stages run in order, a failure stops the pipeline (fail-fast), steps can retry, and "post" actions always run.
# It models what Jenkins, GitHub Actions and GitLab CI do, without running any real build.
import time

class StepFailed(Exception): pass

class Pipeline:
    def __init__(self, name): self.name, self.stages, self.post_always, self.post_failure, self.log = name, [], [], [], []
    def stage(self, name, steps, retries=0): self.stages.append((name, steps, retries)); return self
    def run(self):
        status = "SUCCESS"
        for name, steps, retries in self.stages:
            if status != "SUCCESS":
                self.log.append(f"stage {name:14} SKIPPED (an earlier stage failed)"); continue
            for attempt in range(1, retries + 2):
                try:
                    for step in steps: step()
                    self.log.append(f"stage {name:14} OK" + (f" (after {attempt} attempts)" if attempt > 1 else "")); break
                except StepFailed as e:
                    self.log.append(f"stage {name:14} attempt {attempt} failed: {e}")
                    if attempt == retries + 1: status = "FAILURE"
        for fn in self.post_always: fn(status, self.log)
        if status == "FAILURE":
            for fn in self.post_failure: fn(status, self.log)
        return status

Pipelines are graphs: critical path and speed-up (real calculation) (run for real)

# Pipelines are graphs (DAGs), not lines. How fast can they finish with more parallel agents? (minutes)
tasks = {  # name: (duration, dependencies)
    "checkout": (1, []), "deps": (3, ["checkout"]), "lint": (2, ["deps"]), "unit-a": (6, ["deps"]), "unit-b": (6, ["deps"]),
    "unit-c": (5, ["deps"]), "build-image": (4, ["deps"]), "integration": (9, ["build-image", "unit-a"]), "sast": (5, ["deps"]),
    "e2e": (12, ["integration"]), "package": (2, ["unit-b", "unit-c", "lint", "sast", "e2e"]),
}
def makespan(executors):
    done, running, t = {}, [], 0.0           # running: (finish_time, name)
    pending = dict(tasks)
    def depth(n): return tasks[n][0] + max([depth(d) for d in tasks[n][1]] or [0])   # longest path below this task = priority
    while pending or running:
        ready = [n for n, (d, deps) in pending.items() if all(x in done for x in deps)]
        ready.sort(key=lambda n: -depth(n))
        while ready and len(running) < executors:
            n = ready.pop(0); running.append((t + pending[n][0], n)); pending.pop(n)
        running.sort(); t, n = running.pop(0); done[n] = t
    return t

total_work = sum(d for d, _ in tasks.values())
def critical_path():
    def finish(n): return tasks[n][0] + max([finish(d) for d in tasks[n][1]] or [0])
    end = max(tasks, key=finish); path = [end]
    while tasks[path[-1]][1]:
        path.append(max(tasks[path[-1]][1], key=finish))
    return finish(end), path[::-1]
cp, path = critical_path()
print(f"total work = {total_work} min of effort in {len(tasks)} tasks")
print(f"{'executors':>9} {'pipeline time (min)':>20} {'speed-up':>9}")
for e in (1, 2, 3, 4, 8):
    m = makespan(e); print(f"{e:9d} {m:20.0f} {total_work / m:8.1f}x")
print(f"\ncritical path = {cp} min: {' -> '.join(path)}")
print("No amount of parallelism can beat the critical path. To go faster, shorten the longest chain (split the e2e suite, cache dependencies, test only what changed).")

32 Scaling, Backups and High Availability

Picture: Planning for a restaurant that gets famous: more kitchens, a spare head waiter, and a copy of the recipe book in another building.
  • Scale agents, not the controller: elastic Kubernetes/cloud agents; the controller only schedules.
  • Several controllers: large organisations run many smaller controllers per team or product ('controller sprawl' managed with JCasC) rather than one giant one; a single controller is a single point of failure and a plugin-conflict magnet.
  • Backup: JENKINS_HOME (jobs, config, credentials, secrets) on a persistent disk with snapshots; test restores; with JCasC and Jenkinsfiles in Git, most of the state is already reproducible.
  • High availability: open-source Jenkins controllers are not active-active; practical HA is fast recovery (infrastructure as code + persistent volume + health checks) or commercial offerings.
  • Performance: fast disks, enough heap (monitor GC), limit build history, avoid heavy plugins, keep pipelines light, move work to agents.
  • Observability: expose metrics (Prometheus or OpenTelemetry plugins) for queue length, executor use, build durations and failure rates.

Good to know

  • Capacity planning uses the queue simulation in the agents section: measure arrival rate × build time, then size for 60–80% utilisation.

34 Jenkins Workflow: From Push to Production, Step by Step

Picture: Following one cake from the mixing bowl to the customer's table.
Fig S9 — Jenkins end-to-end workflow, from a developer's push to a running release.
  1. Prepare once: controller with Java 21/25, JCasC, SSO, Kubernetes or Docker agents, credentials for the Git server and registry, a Multibranch (or Organization Folder) job pointing at the repository, a webhook with a secret.

  8. Approval: for delivery, a person (or required reviewers) approves; for deployment, automated checks do.
  9. Deploy to production gradually (canary or rolling) while monitoring error rate and latency; automatic rollback if checks fail.
  10. Notify and record: release notes, change log, deployment event for DORA metrics, Slack message.
  11. Clean up: agent pod removed, workspace deleted, old builds discarded.

def simulate(n_tests=1000, flaky_tests=20, p_flaky_fail=0.1, builds=20000, retry_failed_tests=0, quarantine=False):

        green += ok

commits = [
    "fix: handle empty cart in checkout",
    "feat(search): add fuzzy matching",
    "docs: update README",
    "feat!: drop support for API v1",
    "chore(deps): bump flask to 3.0.3",
    "fix(auth): refresh tokens expire correctly",
    "perf: cache product lookups",

def parse(c):
    m = re.match(r"^(\w+)(\([\w\-]+\))?(!)?: (.+)$", c)
    return m.group(1), m.group(3) == "!", m.group(4)
def bump(version, commits):
    major, minor, patch = map(int, version.split("."))
    level = "none"
    for c in commits:
        kind, breaking, _ = parse(c)
        if breaking: level = "major"
        elif kind == "feat" and level != "major": level = "minor"
        elif kind in ("fix", "perf") and level == "none": level = "patch"
    if level == "major": return f"{major + 1}.0.0", level
    if level == "minor": return f"{major}.{minor + 1}.0", level
    if level == "patch": return f"{major}.{minor}.{patch + 1}", level
    return version, level

# In a monorepo, build and test only what a change can affect: the changed package plus everything that depends on it.
deps = {"core": [], "utils": ["core"], "auth": ["core", "utils"], "payments": ["auth", "utils"], "web": ["auth", "payments"], "admin": ["auth"], "docs": []}

        cur = stack.pop()
        for pkg, ds in deps.items():
            if cur in ds and pkg not in affected: affected.add(pkg); stack.append(pkg)
    return affected

Can a canary tell a bad version from noise? (statistical simulation) (run for real)

import math, random

# Canary analysis: is the new version really worse, or is it just noise? A two-proportion z-test on error rates decides.
def z_test(err_a, n_a, err_b, n_b):
    p = (err_a + err_b) / (n_a + n_b); se = math.sqrt(p * (1 - p) * (1 / n_a + 1 / n_b))
    return 0 if se == 0 else (err_b / n_b - err_a / n_a) / se

def detect(true_new_rate, canary_requests, trials=2000, base_rate=0.005, seed=4):
    rng = random.Random(seed); rollbacks = 0
    for _ in range(trials):
        n_old = canary_requests * 9                                         # canary gets 10% of traffic
        e_old = sum(rng.random() < base_rate for _ in range(n_old // 10)) * 10 if n_old > 1000 else sum(rng.random() < base_rate for _ in range(n_old))
        n_old_eff = n_old
        e_new = sum(rng.random() < true_new_rate for _ in range(canary_requests))
        if z_test(e_old, n_old_eff, e_new, canary_requests) > 2.33: rollbacks += 1      # ~1% one-sided significance
    return rollbacks / trials

print("old version error rate = 0.5%. What share of canary runs correctly roll back, by how bad the new version is and how much canary traffic we watched?")
print(f"{'new version error rate':>24} " + " ".join(f"{n:>8}" for n in (200, 1000, 5000)) + "   <- requests the canary served")

44 Database Changes Without Downtime

Picture: Renovating a shop while it stays open: build the new shelf next to the old one, move goods across, then remove the old shelf.
  1. Expand: add the new column/table in a backward-compatible way (nullable, with defaults). Old code still works.
  2. Migrate: deploy code that writes to both (or reads new, falls back to old); backfill existing data in small batches.
  3. Contract: after everything uses the new structure and enough time has passed, remove the old column.
  • Run migrations through a tool (Flyway, Liquibase, Alembic, Prisma, Rails/Django migrations), version-controlled, executed by the pipeline, not by hand.
  • Make migrations idempotent and reversible where possible; test them on a copy of production-like data.
  • Avoid long locks (adding an index concurrently, batching updates).
  • Never deploy code that needs a column before the migration has run, and never drop a column that still-running old instances need.

Good to know

  • Rollback of code is easy; rollback of data is not. That is why the 'expand/contract' pattern exists.

46 Progressive Delivery, Rollbacks and Release Management

Picture: Opening a new restaurant gradually: first friends, then the neighbourhood, then everyone, and keeping the old restaurant ready to reopen if the kitchen fails.
  • Progressive delivery automates canary and blue/green with metric checks (Argo Rollouts, Flagger, service-mesh traffic splitting, cloud load balancer weights).
  • Automatic rollback triggers: error rate above a limit, latency above a limit, failed health checks, failing smoke tests.
  • Manual overrides: a clearly documented 'stop the rollout' button and on-call ownership.
  • Release management: change records, approvals for high-risk systems, release notes, communication, freeze windows (use sparingly), post-release verification.
  • Rollback vs roll forward: rollback when the previous version is known good and data is compatible; roll forward with a quick fix when rollback is unsafe.
  • Post-incident learning: blameless reviews; add a test or check for every incident.
Fail-fast behaviour in the toy CI engine (same run as the pipelines section) (run for real)

# A tiny CI engine in Python: stages run in order, a failure stops the pipeline (fail-fast), steps can retry, and "post" actions always run.
# It models what Jenkins, GitHub Actions and GitLab CI do, without running any real build.
import time

class StepFailed(Exception): pass

class Pipeline:
    def __init__(self, name): self.name, self.stages, self.post_always, self.post_failure, self.log = name, [], [], [], []
    def stage(self, name, steps, retries=0): self.stages.append((name, steps, retries)); return self
    def run(self):
        status = "SUCCESS"
        for name, steps, retries in self.stages:
            if status != "SUCCESS":
                self.log.append(f"stage {name:14} SKIPPED (an earlier stage failed)"); continue
            for attempt in range(1, retries + 2):
                try:
                    for step in steps: step()
                    self.log.append(f"stage {name:14} OK" + (f" (after {attempt} attempts)" if attempt > 1 else "")); break
                except StepFailed as e:
                    self.log.append(f"stage {name:14} attempt {attempt} failed: {e}")
                    if attempt == retries + 1: status = "FAILURE"
        for fn in self.post_always: fn(status, self.log)
        if status == "FAILURE":
            for fn in self.post_failure: fn(status, self.log)
        return status

state = {"flaky_calls": 0}
def checkout(): pass
def compile_code(): pass
def unit_tests_ok(): pass
def unit_tests_bad(): raise StepFailed("2 tests failed (test_total, test_tax)")
def flaky_network_step():
    state["flaky_calls"] += 1
    if state["flaky_calls"] < 3: raise StepFailed("registry timeout")
def push_image(): pass
def deploy(): pass

def build(tests):
    p = Pipeline("shop-api")
    p.stage("Checkout", [checkout]).stage("Build", [compile_code]).stage("Test", [tests])
    p.stage("Push image", [flaky_network_step], retries=3).stage("Deploy", [deploy])
    p.post_always.append(lambda status, log: log.append(f"post always : workspace cleaned (final status {status})"))
    p.post_failure.append(lambda status, log: log.append("post failure: notification sent to #ci-alerts"))
    return p

for label, tests in (("good commit", unit_tests_ok), ("bad commit ", unit_tests_bad)):
    state["flaky_calls"] = 0
    p = build(tests); result = p.run()
    print(f"--- {label}: {result}"); print(*[("   " + l) for l in p.log], sep="\n")
print("\nFail-fast: a broken test stops later stages, so you never push or deploy a broken build. Retries hide short network glitches but never hide real test failures.")

56 Secrets in Pipelines: Keep Them Out, Keep Them Short-Lived

Picture: A hotel key card that works for one night, for one room, instead of a master key you hand to every guest.
  1. Prefer identity federation (OIDC): the CI job proves who it is (repository, branch, environment) to the cloud and receives a token valid for minutes. No stored cloud keys. Supported by GitHub Actions, GitLab CI, Azure and others; Jenkins can do similar with plugins or workload identity on Kubernetes.
  2. Use a secrets manager (Vault, cloud secret services) and fetch secrets at run time with the job's identity.
  3. Scope narrowly: per environment, per pipeline, per folder; production secrets only on protected branches.
  4. Mask and avoid printing; remember that base64 or transformed values may bypass masking.
  5. Do not give secrets to untrusted code (fork PRs, third-party steps you have not pinned).
  6. Rotate and revoke: automate rotation; revoke immediately on suspicion; deleting a leaked value from a repository does not revoke it.
  7. Scan commits, logs and artefacts for secrets (gitleaks, trufflehog, GitHub secret scanning).

Signing build provenance and enforcing a policy at deploy time (real Ed25519 signatures) (run for real)

import json, hashlib
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey

# Build provenance: the trusted CI system signs a statement "this artifact was built from this commit by this pipeline".
# Deployers verify the signature and apply policy before running anything. (The idea behind SLSA provenance and Sigstore/cosign.)
ci_key = Ed25519PrivateKey.generate(); ci_pub = ci_key.public_key()
def attest(artifact_bytes, commit, branch, builder):
    stmt = {"artifact_sha256": hashlib.sha256(artifact_bytes).hexdigest(), "commit": commit, "branch": branch, "builder": builder}
    raw = json.dumps(stmt, sort_keys=True).encode()
    return stmt, ci_key.sign(raw)

def verify_and_check(artifact_bytes, stmt, sig):
    raw = json.dumps(stmt, sort_keys=True).encode()
    try: ci_pub.verify(sig, raw)
    except Exception: return "REJECT: signature invalid (statement was forged or edited)"
    if hashlib.sha256(artifact_bytes).hexdigest() != stmt["artifact_sha256"]: return "REJECT: artifact differs from what was built"
    if stmt["branch"] != "main": return "REJECT: policy says only main-branch builds may reach production"
    if stmt["builder"] != "jenkins-prod-controller": return "REJECT: not built by the trusted builder"
    return "ALLOW: deploy"

image = b"container image bytes v42"
stmt, sig = attest(image, "9f2c1ab", "main", "jenkins-prod-controller")
print("1) genuine image from main      :", verify_and_check(image, stmt, sig))
print("2) image swapped after the build:", verify_and_check(b"container image bytes v42 + malware", stmt, sig))
stmt_feature, sig_feature = attest(image, "77aa001", "feature/x", "jenkins-prod-controller")
print("3) built from a feature branch   :", verify_and_check(image, stmt_feature, sig_feature))
forged = dict(stmt, branch="main", builder="laptop-of-attacker");
print("4) attacker edits the statement  :", verify_and_check(image, forged, sig))
print("\nSigning proves WHO built it and from WHAT; policies decide whether that is acceptable. Keep the signing key in a hardware-backed service or use keyless signing (OIDC identity) as Sigstore does.")

import random, statistics

# How many build agents (executors) do we need? Builds arrive randomly and each takes a while. Simulated queue.
def simulate(executors, builds_per_hour, mean_build_min, hours=200, seed=5):
    rng = random.Random(seed); t = 0.0; free_at = [0.0] * executors; waits = []
    end = hours * 60
    while True:
        t += rng.expovariate(builds_per_hour / 60)
        if t > end: break
        free_at.sort(); start = max(t, free_at[0]); waits.append(start - t)
        free_at[0] = start + rng.expovariate(1 / mean_build_min)
    return statistics.mean(waits), sorted(waits)[int(len(waits) * 0.95)], len(waits)

Good to know

  • Name the tool but design in concepts so you can swap it.
  • Walk through a failure: a flaky test, a bad deploy, a leaked token, and how the pipeline responds.

72 FAQ

Picture: Questions beginners ask most.
Q: Is Jenkins still worth learning in 2026?

Yes, especially for large or on-premises environments with existing pipelines. The ideas (pipeline as code, agents, stages, artefacts) transfer to every CI tool. Be ready to operate and patch it.

Q: Jenkins or GitHub Actions?

GitHub-centred teams that want zero server work usually choose Actions; teams needing deep customisation, on-premises control or special hardware often keep Jenkins. See the comparison.

Q: What is the difference between continuous delivery and continuous deployment?

Delivery keeps every change releasable and needs a human to release; deployment releases every passing change automatically.

Q: Which Java does Jenkins need now?

Java 21 or 25 from Jenkins 2.555.1 (April 2026); Java 17 was supported only until LTS 2.541.3 (details).

Q: Should builds run on the controller?

No. Set controller executors to 0 and use agents; builds on the controller can access secrets and harm Jenkins.

Q: How many plugins should I install?

As few as possible; each plugin is code in your controller and a possible vulnerability. Pin versions and watch advisories.

Q: How do I stop flaky tests ruining my pipeline?

Find and fix their cause; quarantine them meanwhile; use limited retries only as a stopgap; track flake rates (demo).

Q: Is the pipeline code on this page tested?

Python simulations were run and their output is shown. All Jenkinsfiles, YAML workflows, Docker and Kubernetes files, and commands are templates that were not run, because Jenkins and cloud accounts were not available on this machine.

Q: How do I learn CI/CD without paying?

Run Jenkins in Docker locally, or use the free tiers of GitHub Actions/GitLab (check current limits), with a throwaway repository.

Q: What is the best first improvement for a slow pipeline?

Measure stage times; then add caching, parallelise independent stages and move slow tests out of the PR path (speed section).

73 Interview Questions (With Answers)

Picture: Grouped by theme, easiest first. Click a question to reveal the answer.

A. Fundamentals

Q1: What is CI/CD?

Automating build, test and release so changes are integrated and delivered frequently, safely and repeatably.

Q2: Continuous delivery vs deployment?

Delivery: always ready to release, manual approval; deployment: every passing change goes to production automatically.

Q3: What are the stages of a typical pipeline?

Source, build, test, quality/security checks, package/artefact, deploy to environments, verify/monitor.

Q4: Why trunk-based development?

Small, frequent merges keep conflicts and risk small (our model: a 10-day branch in a 20-person team conflicts about 98% of the time).

Q5: What are the DORA metrics?

Deployment frequency, change lead time, failed deployment recovery time, change fail rate, deployment rework rate.

B. Jenkins

Q6: Describe Jenkins architecture.

A controller (UI, scheduler, plugins, config) coordinating agents with executors and labels; jobs and pipelines defined as code; state in JENKINS_HOME.

Q7: Declarative vs scripted pipeline?

Declarative has a fixed structure (pipeline/agent/stages/post) and validation; scripted is free Groovy (node blocks). Prefer declarative, with script blocks or shared libraries when needed.

Q8: What is a Multibranch Pipeline?

A job that discovers branches and PRs with a Jenkinsfile and creates a pipeline for each.

Q9: How do you manage credentials safely in Jenkins?

Credentials store with folder scope, withCredentials, masking, short-lived tokens or OIDC, never in code or parameters; rotate on exposure.

Q10: What is a shared library?

Reusable pipeline code in a separate Git repository (vars/, src/), loaded with @Library and version-pinned.

Q11: Why set controller executors to 0?

So builds (untrusted code) never run on the controller where secrets and configuration live.

Q12: How would you scale Jenkins?

Elastic ephemeral agents (Kubernetes/cloud), multiple smaller controllers, Configuration as Code, queue monitoring, size for 60–80% utilisation.

Q13: How do you secure Jenkins?

SSO and least privilege, HTTPS, patch LTS and plugins, minimal plugins, sandbox on, no anonymous access, scoped credentials, ephemeral agents, audit and backups.

Q14: Webhook vs polling?

Webhooks push events immediately; polling checks on a schedule and wastes resources. Use signed webhooks.

Q15: What is the H in Jenkins cron?

A hash-based value that spreads scheduled jobs over time to avoid a stampede at the same minute.

C. Pipelines in practice

Q16: How do you make a slow pipeline faster?

Measure; cache dependencies; parallelise; build only affected parts; shard tests; fail fast; cancel old runs; shorten the critical path.

Q17: What is a flaky test and what do you do?

A test failing randomly; isolate, fix the cause, quarantine meanwhile; retries only as a stopgap.

Q18: What is 'build once, deploy many'?

Create one immutable artefact and promote it across environments with only configuration changing.

Q19: How do you handle database migrations in CD?

Expand/contract with backward-compatible steps, versioned migration tools, idempotent migrations and tests.

Q20: Compare deployment strategies.

Rolling (gradual, mixed versions), blue/green (instant switch/rollback, double capacity), canary (small traffic share with metric checks), shadow (mirror traffic), flags (decouple release).

Q21: What is GitOps?

Desired state in Git; an in-cluster agent (Argo CD/Flux) pulls and reconciles; rollback is a revert.

Q22: How do you roll back?

Redeploy the previous immutable artefact or revert the config commit; ensure database compatibility; or roll forward with a fix.

D. Security and supply chain

Q23: What are common CI/CD security risks?

Poisoned pipeline execution, compromised third-party steps, leaked credentials, injection via inputs, vulnerable CI plugins, malicious dependencies, tampered artefacts.

Q24: Why pin actions and dependencies by SHA or hash?

Tags can be moved; hashes cannot. Pinning stops a hijacked tag from changing code you reviewed (our demo).

Q25: What is an SBOM and what is SLSA?

SBOM: list of components; SLSA: framework of build-integrity levels with signed provenance.

Q26: How do you avoid storing cloud keys in CI?

OIDC federation: the job gets short-lived tokens based on its identity.

Q27: How do you prevent script injection in pipelines?

Never interpolate untrusted values (branch names, PR titles, parameters) into shell strings; pass them as environment variables and quote.

E. Tools and judgement

Q28: Jenkins vs GitHub Actions vs GitLab CI?

Self-hosted flexibility and operations burden vs SaaS convenience tied to a platform; choose by where code lives, security needs and skills.

Q29: How would you migrate from Freestyle jobs to pipelines?

Inventory, move logic to scripts, translate one job at a time side by side, move credentials, switch teams, retire old jobs.

Q30: What do you do when the main branch is red?

Stop merging, fix or revert immediately, then find the cause (flaky? real?); alert the team; the broken build is the top priority.

Q31: How many executors do you need?

Arrival rate × average build time gives average load; size for 60–80% utilisation because waiting explodes near 100% (our simulation: 77 min wait at 100%, ~5 min at 80%).

Q32: How do you measure CI/CD success?

DORA metrics, queue and build times, flake rate, change fail rate, developer satisfaction.

75 Quick Quiz 🎯

Picture: Click each question to reveal the answer.
Q1: Name the three rules of a healthy CI.

Merge to main often; build and test automatically and fast; fix a broken main branch immediately.

Q2: What stops a pipeline from being faster than its critical path?

Dependencies: tasks that must wait for others (our demo: 33 minutes even with 8 executors).

Q3: Why must CI webhooks be signed?

Unsigned webhooks let anyone who finds the URL trigger builds; a signature proves the sender knows the shared secret.

Q4: Which Java versions can Jenkins run on from 2.555.1?

Java 21 or 25.

Q5: What is wrong with sh "echo ${params.NAME}"?

Groovy substitutes the value before the shell runs it, so a malicious parameter can inject commands; use single quotes and an environment variable.

Q6: Why pin an action to a commit SHA?

Tags can be moved to malicious code; a SHA cannot.

Q7: What does a canary with only 200 requests risk?

Missing subtle regressions and raising false alarms (statistics are unreliable on tiny samples).

Q8: Why use the expand/contract pattern?

So the old and new code versions both work with the database during rollout and rollback.

Q9: At about what utilisation does queue waiting explode?

As utilisation approaches 100%; aim for 60–80%.

Q10: What is the benefit of GitOps rollbacks?

A rollback is a Git revert; the cluster reconciles to the previous desired state with a full audit trail.
