Part A — Containers From Zero (What They Really Are)

1 The Problem Containers Solve

Picture: You bake a cake at home and it is perfect. You carry the recipe to a friend's kitchen and it fails: a different oven, no baking powder, metric cups. Now imagine you could pack the whole kitchen corner (oven setting, ingredients, tools) into a sealed lunch box that works the same anywhere. A container is that lunch box for a program.
Old problemWhat went wrongHow a container helps
'It works on my machine'The server has a different Python/Java/library version than the laptopThe program ships with its libraries; the same box runs on laptop, test server and cloud
Two apps need different versionsApp A wants Python 3.9, app B wants Python 3.13, on one serverEach app lives in its own box with its own files
Slow, heavy servers for each appOne virtual machine per app wastes memory and takes minutes to bootA container starts in about a second and shares the machine's kernel
Hand-made setupA person follows a 40-step document to install the appThe setup is a short text file (Dockerfile) that a machine follows the same way every time
Messy cleanupOld installs leave files all over the serverDelete the container and everything it made disappears

Good to know

  • Docker is the tool that made containers easy for everybody (2013). Kubernetes is the system that runs many containers on many machines and keeps them healthy (born at Google, open source since 2014).
  • Simple way to remember: Docker packs the box. Kubernetes runs thousands of boxes.
  • Related guides: Linux (the kernel features containers use), Jenkins & CI/CD, Cloud, DevOps, System Design.
You do not need to know Linux internals to use Docker. But a few pages in this part show what is really inside a container, with real runs, so that nothing feels like magic later.

2 Containers vs Virtual Machines

Picture: A virtual machine is a separate small house built on a plot of land, with its own plumbing and wiring. A container is a flat in one big building: every flat has its own door and its own rooms, but all share the building's plumbing and electricity (the kernel).
Fig S1 — Each VM carries a whole operating system; containers share the host's one kernel.

Good to know

  • On Windows and macOS, Docker Desktop quietly runs one small Linux VM and puts your containers inside it. So 'containers on Windows' still use a Linux kernel.
  • They are not rivals: in the cloud, containers usually run inside VMs. Sandboxed runtimes (gVisor, Kata Containers, AWS Firecracker) mix both ideas when you need a stronger wall.
  • A container is not a tiny VM. It is an ordinary Linux process that has been given a private view of the system.

5 Namespaces, For Real: A Private View of the System

Picture: A magic pair of glasses: you put them on and the world shows only your own things. The world did not change; your view did.

Linux's unshare command starts a program in new namespaces. Below, each result was produced by a real run (no Docker). We use a user namespace (-r) so an ordinary user is allowed to do it.

1. Own host name (uts namespace) — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
echo "host name  : $(hostname)"
unshare -r -u bash -c 'hostname my-container; echo "inside box  : $(hostname)"'
echo "host again  : $(hostname)"

# ----- Output (real run) -----
# host name  : ubuntu-box
# inside box  : my-container
# host again  : ubuntu-box

The host's own name did not change; the box has a private name. That is why every container can have a different hostname.

2. Own process list (pid namespace) — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
echo "On the host I can see $(ps -e --no-headers | wc -l) processes."
echo "--- inside a NEW process-id namespace:"
unshare -r -p -f --mount-proc bash -c 'echo "my own PID is $$"; ps -e -o pid,comm'

# ----- Output (real run) -----
# On the host I can see 78 processes.
# --- inside a NEW process-id namespace:
# my own PID is 1
#     PID COMMAND
#       1 ps

Inside, the program believes it is PID 1 and cannot see the host's other processes. This is also why the main program of a container must handle signals like an init process.

3. 'root' that is not really root (user namespace) — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
echo "host   : uid=$(id -u)"
unshare -r bash -c 'echo "inside : uid=$(id -u) ($(id -un))"; echo "uid_map (inside-id host-id count):"; cat /proc/self/uid_map'

# ----- Output (real run) -----
# host   : uid=1000
# inside : uid=0 (root)
# uid_map (inside-id host-id count):
#          0       1000          1

uid_map reads: inside-id 0 equals host-id 1000, count 1. So 'root' in the box is just my ordinary user on the outside.

4. Own network (net namespace) — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
echo "host network interfaces  : $(awk 'NR>2{gsub(":","",$1); printf "%s ", $1}' /proc/net/dev)"
unshare -r -n bash -c 'echo "inside a new net namespace: $(awk "NR>2{gsub(\":\",\"\",\$1); printf \"%s \", \$1}" /proc/net/dev)"'

# ----- Output (real run) -----
# host network interfaces  : lo eth0 
# inside a new net namespace: lo

A fresh network namespace has only the loopback card. A container runtime then plugs a virtual cable (a veth pair) into it, which is how a container gets an IP address.

5. All six namespaces at once — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
for n in mnt pid net uts ipc user; do
  host=$(readlink /proc/self/ns/$n)
  inside=$(unshare -r -m -p -n -u -i -f --mount-proc readlink /proc/self/ns/$n)
  if [ "$host" = "$inside" ]; then echo "$n : same as the host"; else echo "$n : DIFFERENT (own private copy)"; fi
done

# ----- Output (real run) -----
# mnt : DIFFERENT (own private copy)
# pid : DIFFERENT (own private copy)
# net : DIFFERENT (own private copy)
# uts : DIFFERENT (own private copy)
# ipc : DIFFERENT (own private copy)
# user : DIFFERENT (own private copy)

/proc/<pid>/ns/* are the identity cards of the namespaces. A different number means a different namespace.

What this means for Docker

  • docker run does exactly this (plus cgroups and a root file system) and then starts your program inside.
  • Because the kernel is shared, a kernel bug is a way out of any container. This is the main reason containers are less isolated than VMs.
These runs happened in a WSL2 Linux kernel (6.18). Namespace names and the idea are the same on any modern Linux; exact numbers (like the process count) differ per machine.

# file system type of /sys/fs/cgroup : cgroup2fs   (cgroup2fs = cgroup version 2)
# controllers this kernel offers          : cpuset cpu io memory hugetlb pids rdma
# my process lives in cgroup              : /init.scope

Our WSL2 kernel uses cgroup v2 and offers the usual controllers. The refusal to create a child group is expected: the Docker daemon (running as root) is the one that creates and fills these folders for every container.

Limits and restart policies in Docker (template, not run)
docker run -d --name limited --memory 256m --memory-swap 256m --cpus 0.5 --pids-limit 100 nginx:1.27
docker stats --no-stream limited            # live CPU / memory use against the limit
docker inspect -f '{{.HostConfig.Memory}}' limited
# Go over the memory limit and the kernel kills the process ("OOMKilled": true in docker inspect, exit code 137).
docker run -d --restart unless-stopped nginx:1.27      # restart policies: no | on-failure[:N] | always | unless-stopped

Good to know

  • Memory is hard, CPU is soft: too much memory = death; too much CPU = slowness.
  • Modern JDKs and some runtimes read the container's limit; older software may look at the whole host's memory and plan badly. Always test with limits on.
  • Linux 'cgroup v2' is the current design (one unified tree). Check with docker info or stat -fc %T /sys/fs/cgroup.

7 Layered File Systems: Why Images Are Cheap

Picture: Transparent sheets on an overhead projector. The bottom sheet is the printed picture (the image). You write on the top sheet only. Take the top sheet away and the picture is untouched. Ten people can share the same bottom sheet.

overlayfs stacks directories. lowerdir is read-only (the image layers), upperdir is the writable layer (the container's changes) and merged is what the program sees. Real run (user namespace, no Docker):

Copy-on-write and 'whiteout' files — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
cd "$(mktemp -d)"
mkdir lower upper work merged
echo "hello from the image" > lower/readme.txt
echo "old config" > lower/config.ini
unshare -r -m bash -c '
  mount -t overlay overlay -o lowerdir=lower,upperdir=upper,workdir=work merged
  echo "container sees      : $(ls merged | tr "\n" " ")"
  echo "edited inside container" >> merged/readme.txt     # change an image file
  rm merged/config.ini                                    # delete an image file
  echo "brand new" > merged/new.txt                       # create a new file
  echo "container now sees  : $(ls merged | tr "\n" " ")"
  echo "readme.txt (container view): $(cat merged/readme.txt | tr "\n" "|")"
  echo
  echo "writable layer (upper) holds only the changes:"
  stat -c "  %A  %n" upper/*
'
echo
echo "read-only image layer (lower) is untouched:"
echo "  files    : $(ls lower | tr "\n" " ")"
echo "  readme.txt: $(cat lower/readme.txt)"
chmod -R u+rwx . 2>/dev/null; cd / && rm -rf "$OLDPWD" 2>/dev/null

# ----- Output (real run) -----
# container sees      : config.ini readme.txt 
# container now sees  : new.txt readme.txt 
# readme.txt (container view): hello from the image|edited inside container|
#
# writable layer (upper) holds only the changes:
#   c---------  upper/config.ini
#   -rw-r--r--  upper/new.txt
#   -rw-r--r--  upper/readme.txt
#
# read-only image layer (lower) is untouched:
#   files    : config.ini readme.txt 
#   readme.txt: hello from the image

Edit an image file: a full copy lands in the writable layer first (copy-on-write). Delete an image file: a special character-device entry (c---------, a whiteout) hides it. The lower layer never changed.

What this means for you

  • Everything a running container writes lands in its writable layer and disappears with the container. Keep data that must survive in a volume (later section).
  • Writing to many small files in the overlay is slower than on a volume.
  • docker diff <container> lists exactly such changes (A = added, C = changed, D = deleted).
Docker's default storage driver is overlay2 (a tuned overlayfs). Newer Docker versions can also use the containerd image store; the idea of stacked layers is the same.

8 Build a Container With No Docker (30 Lines)

Picture: To understand a car, take the engine out and run it on a bench. Here we take out the container engine and do by hand what docker run does: make a tiny root folder, then start a program inside new namespaces with that folder as its /.

The script copies four programs (bash, ls, cat, ps) and the libraries they need into a folder, then runs a shell with unshare (new namespaces) and chroot (switch the root folder). The container cannot see the host's /home because it does not exist in its world.

A hand-made container — real Linux, run on Ubuntu 26.04 under WSL2 (run for real)
cd "$(mktemp -d)"
# 1) build a tiny "image": a folder holding just a few programs and the libraries they need
mkdir -p rootfs/bin rootfs/proc rootfs/etc rootfs/tmp
for b in bash ls cat ps; do
  src=$(command -v $b)
  cp -L "$src" rootfs/bin/$b
  for lib in $(ldd "$src" | grep -o '/[^ ]*'); do
    mkdir -p "rootfs$(dirname $lib)"; cp -L "$lib" "rootfs$lib"
  done
done
echo "NAME=TinyLinux" > rootfs/etc/os-release
echo "size of this root filesystem: $(du -sh rootfs | cut -f1)"
# 2) start a "container": new namespaces + switch the root directory to that folder
unshare -r -m -u -p -f bash -c '
  mount -t proc proc rootfs/proc
  chroot rootfs /bin/bash -c "echo I am PID \$\$; echo; echo files I can see in /:; ls /; echo; echo my processes:; ps -e -o pid,comm; echo; echo the host home folder:; ls /home 2>&1; echo; cat /etc/os-release"
'
cd / && rm -rf "$OLDPWD" 2>/dev/null

# ----- Output (real run) -----
# size of this root filesystem: 30M
# I am PID 1
#
# files I can see in /:
# bin
# etc
# lib64
# proc
# tmp
# usr
#
# my processes:
#     PID COMMAND
#       1 bash
#       4 ps
#
# the host home folder:
# ls: cannot access '/home': No such file or directory
#
# NAME=TinyLinux

Notice: the shell is PID 1; ps shows only 2 processes; the root has just 6 folders; /home does not exist; /etc/os-release is our own file. This is an 'image' (a folder) plus a 'container' (a process in that folder). Docker adds networking, cgroups, layers, an image format and a friendly CLI.

Good to know

  • An image is basically a packed root folder. A container is a process started with that folder as its root, inside namespaces and a cgroup.
  • Real runtimes use pivot_root rather than chroot (harder to escape), but the idea is the same.
  • runc is the small program that does this from a JSON recipe (the OCI runtime spec). Docker, containerd, CRI-O and Podman all end up calling a runtime like runc or crun.

9 Images, Layers and Digests (OCI Format)

Picture: A lasagna: every layer is a separate sheet. If only the top sauce changes, you do not remake the whole dish. Each sheet gets a fingerprint (a hash), so anyone can check it was not changed.

The next program builds a real miniature OCI image by hand with Python: three layer tar files, a config JSON and a manifest JSON, all identified by sha256 digests. Then it changes one line of code and compares.

Fig S3 — An image = manifest + config + layers, all named by their sha256 digest.
Build a miniature OCI image by hand (run for real)
# An image is just: layers (tar files) + a config (JSON) + a manifest (JSON that lists their sha256 digests).
import gzip, hashlib, io, json, tarfile

def make_layer(files):
    raw = io.BytesIO()
    with tarfile.open(fileobj=raw, mode="w", format=tarfile.PAX_FORMAT) as t:
        for name, text in files.items():
            data = text.encode()
            ti = tarfile.TarInfo(name); ti.size = len(data); ti.mtime = 0; ti.uid = ti.gid = 0; ti.mode = 0o644
            t.addfile(ti, io.BytesIO(data))
    raw = raw.getvalue()
    gz = io.BytesIO()
    with gzip.GzipFile(fileobj=gz, mode="wb", mtime=0) as g:
        g.write(raw)
    gz = gz.getvalue()
    return {"diff_id": "sha256:" + hashlib.sha256(raw).hexdigest(), "digest": "sha256:" + hashlib.sha256(gz).hexdigest(), "size": len(gz)}

def make_image(app_code):
    layers = [
        make_layer({"etc/os-release": "NAME=TinyLinux\n", "bin/hello": "#!/bin/sh\necho hello\n"}),   # base OS layer
        make_layer({"usr/lib/python/flask.py": "# pretend library\n" * 40}),                          # dependencies layer
        make_layer({"app/main.py": app_code}),                                                        # our code layer
    ]
    config = {"architecture": "amd64", "os": "linux",
              "config": {"Cmd": ["python", "/app/main.py"], "ExposedPorts": {"8000/tcp": {}}, "Env": ["PORT=8000"]},
              "rootfs": {"type": "layers", "diff_ids": [l["diff_id"] for l in layers]}}
    cfg = json.dumps(config, sort_keys=True).encode()
    manifest = {"schemaVersion": 2, "mediaType": "application/vnd.oci.image.manifest.v1+json",
                "config": {"mediaType": "application/vnd.oci.image.config.v1+json", "digest": "sha256:" + hashlib.sha256(cfg).hexdigest(), "size": len(cfg)},
                "layers": [{"mediaType": "application/vnd.oci.image.layer.v1.tar+gzip", "digest": l["digest"], "size": l["size"]} for l in layers]}
    m = json.dumps(manifest, sort_keys=True).encode()
    return layers, manifest, "sha256:" + hashlib.sha256(m).hexdigest()

short = lambda d: d[:19]
layers1, man1, id1 = make_image("print('version 1')\n")
print("IMAGE v1  (image id = digest of the manifest) ", short(id1))
for name, l in zip(["base OS", "dependencies", "our code"], layers1):
    print("  layer %-13s digest %s  %4d bytes" % (name, short(l["digest"]), l["size"]))
print("  config digest                  ", short(man1["config"]["digest"]))
layers2, man2, id2 = make_image("print('version 2')\n")
print()
print("IMAGE v2  after changing ONE line of app code", short(id2))
for name, a, b in zip(["base OS", "dependencies", "our code"], layers1, layers2):
    print("  layer %-13s %s" % (name, "reused (same digest, nothing to download)" if a["digest"] == b["digest"] else "NEW digest (only this layer is pushed/pulled)"))
print()
print("manifest v1 (what a registry stores):")
print(json.dumps(man1, indent=1, sort_keys=True)[:700] + " ...")

# ----- Output (real run) -----
# IMAGE v1  (image id = digest of the manifest)  sha256:0cbeb140c554
#   layer base OS       digest sha256:4eca8352005b   170 bytes

15 Your First Dockerfile

Picture: A recipe card: 'Start with a ready dough (base image). Put the flour on the table (copy files). Mix (run commands). Bake when served (CMD).'

Each instruction creates one layer. We build a small web server in Python (standard library only, no extra packages).

# --- app.py ---------------------------------------------------------
from http.server import BaseHTTPRequestHandler, HTTPServer
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        body = b"hello from a container\n" if self.path != "/health" else b"ok\n"
        self.send_response(200); self.send_header("Content-Length", str(len(body))); self.end_headers(); self.wfile.write(body)
HTTPServer(("0.0.0.0", 8000), H).serve_forever()          # 0.0.0.0 = listen on ALL addresses (127.0.0.1 would hide it)

# --- Dockerfile -----------------------------------------------------
FROM python:3.13-slim                  # 1. start from a small ready-made Python image
WORKDIR /app                           # 2. all later commands run in /app
COPY requirements.txt .                # 3. copy ONLY the dependency list first (cache trick)
RUN pip install --no-cache-dir -r requirements.txt     # 4. install libraries (cached until requirements.txt changes)
COPY . .                               # 5. now copy the rest of the code
RUN useradd --uid 10001 --no-create-home appuser       # 6. make a normal user ...
USER 10001                             #    ... and stop running as root
EXPOSE 8000                            # 7. documentation only: "the app listens on 8000"
HEALTHCHECK --interval=30s CMD python -c "import urllib.request as u; u.urlopen('http://localhost:8000/health')"
CMD ["python", "app.py"]               # 8. the command that runs when the container starts

# --- build and run --------------------------------------------------
docker build -t hello:1.0 .
docker run -d --name hello -p 8000:8000 hello:1.0
curl http://localhost:8000

Good to know

  • FROM must be first (except for ARG). Pick a specific version: python:3.13-slim, not python:latest.
  • Order matters: put things that change rarely (dependencies) first and things that change often (your code) last, to reuse the build cache (next section).
  • The app must listen on 0.0.0.0, not 127.0.0.1, otherwise the port mapping cannot reach it.
Write docker build -t name:tag . The final dot is the build context: the folder whose files may be copied into the image.

17 The Build Cache: Why Order Matters

Picture: Making sandwiches in a line: bread, butter, filling, toppings. If only the topping changes, you reuse the first three. But if you change the bread, everything after must be redone. A Docker build works exactly like this: once a step changes, every step after it is rebuilt.

The cache key of a step is its instruction plus the files it copies plus the key of the step before it. The simulation below uses the same rule. Step times are assumed (1 second to copy, 60 s for pip install, 10 s for tests) to make the point visible.

Fig S6 — Seconds to rebuild after editing ONE source file (assumed step costs).
Same project, two Dockerfile orders (run for real)
# How the Docker build cache decides what to re-run. Step costs (seconds) are ASSUMED to make the point.
import hashlib

def build(dockerfile, files, cache):
    parent, total, log = "", 0, []
    for kind, arg, cost in dockerfile:
        content = "".join(files[f] for f in arg) if kind == "COPY" else ""
        key = hashlib.sha256((parent + kind + str(arg) + content).encode()).hexdigest()[:8]
        if key in cache:
            log.append("  CACHED  %s %s" % (kind, arg if kind == "COPY" else arg))
        else:
            cache.add(key); total += cost
            log.append("  RUN     %-4s %s   (%ds)" % (kind, arg, cost))
        parent = key        # once one step misses, every step after it has a new key too
    return total, log

BAD = [("COPY", ["app.py", "requirements.txt"], 1), ("RUN", "pip install -r requirements.txt", 60), ("RUN", "pytest -q", 10)]
GOOD = [("COPY", ["requirements.txt"], 1), ("RUN", "pip install -r requirements.txt", 60), ("COPY", ["app.py"], 1), ("RUN", "pytest -q", 10)]
base = {"app.py": "print(1)", "requirements.txt": "flask==3.1"}
results = {}
for tag, label, df in [("bad", "COPY everything first (bad order)", BAD), ("good", "COPY requirements first (good order)", GOOD)]:
    cache = set(); print(label)
    t0, _ = build(df, base, cache)
    edited = dict(base, **{"app.py": "print(2)"})
    t1, log1 = build(df, edited, cache)
    print(" first build: %ds   | after editing app.py: %ds" % (t0, t1))
    print("\n".join(log1))
    newreq = dict(edited, **{"requirements.txt": "flask==3.1\nrequests"})
    t2, _ = build(df, newreq, cache)
    print(" after adding a dependency: %ds\n" % t2)
    results[tag] = (t0, t1, t2)
for tag, (a, b, c) in results.items():
    print("RESULT %-4s first=%d code_edit=%d new_dep=%d" % (tag, a, b, c))

#  first build: 71s   | after editing app.py: 71s
#   RUN     COPY ['app.py', 'requirements.txt']   (1s)

#   RUN     RUN  pytest -q   (10s)
#  after adding a dependency: 71s
#
# COPY requirements first (good order)

#   CACHED  COPY ['requirements.txt']
#   CACHED  RUN pip install -r requirements.txt

With the bad order, editing a line of code re-installs all libraries every time. With the good order, only the cheap steps run.

Good to know

  • Golden rule: copy the dependency list, install dependencies, then copy the source code.
  • In CI the cache is empty on every fresh runner. Use --cache-from/--cache-to (registry or GitHub Actions cache) to keep it.
  • Changing a file in the build context busts the cache of the COPY that includes it. A .dockerignore keeps unrelated files from doing that.

How Compose orders start-up (same idea: topological sort) (run for real)
# docker compose starts services in dependency order (depends_on). Same idea as a topological sort.
def start_order(services):
    deps = {s: set(d) for s, d in services.items()}
    done, waves = set(), []
    while len(done) < len(deps):
        ready = sorted(s for s in deps if s not in done and deps[s] <= done)
        if not ready:
            left = sorted(set(deps) - done)
            raise ValueError("circular depends_on among: " + ", ".join(left))
        waves.append(ready); done |= set(ready)
    return waves

stack = {"web": ["api"], "api": ["db", "cache"], "worker": ["db", "cache"], "db": [], "cache": []}
for i, wave in enumerate(start_order(stack), 1):
    print("step %d: start together -> %s" % (i, ", ".join(wave)))
print()
print("stopping happens in the reverse order:", " | ".join(", ".join(w) for w in reversed(start_order(stack))))
print()
try:
    start_order({"a": ["b"], "b": ["c"], "c": ["a"]})
except ValueError as e:
    print("error (like compose):", e)

30 Dockerfile Best Practices, Checked by a Linter

Picture: A spell-checker for recipes. It cannot taste the food, but it catches the common slips.

The checker below is a small Python program (not a real tool) that applies a few well-known rules to two Dockerfiles: a messy one and a tidy one. Real linters: hadolint, Docker Build Checks (docker build --check), Trivy config scan.

Lint a messy and a tidy Dockerfile (run for real)
# A tiny Dockerfile checker: flags the habits that make images big, slow, or unsafe.
import re

RULES = [
    ("DL01", "base image uses ':latest' or no tag (builds are not repeatable)", lambda l, s: l.startswith("FROM") and not re.search(r"FROM\s+(--\S+\s+)?\S+:(?!latest)\S+|@sha256:", l) and "scratch" not in l),
    ("DL02", "ADD used where COPY is enough (ADD also unpacks archives and fetches URLs)", lambda l, s: l.startswith("ADD ") and not re.search(r"https?://|\.tar", l)),
    ("DL03", "apt-get install without --no-install-recommends / cache cleanup in the same RUN", lambda l, s: "apt-get install" in l and ("--no-install-recommends" not in l or "rm -rf /var/lib/apt/lists" not in l)),
    ("DL04", "pip install without --no-cache-dir (keeps downloads inside the layer)", lambda l, s: "pip install" in l and "--no-cache-dir" not in l),
    ("DL05", "COPY . before installing dependencies (breaks the build cache)", None),
]

def lint(name, text):
    lines = [l.strip() for l in text.strip().splitlines() if l.strip() and not l.strip().startswith("#")]
    found = []
    for i, l in enumerate(lines, 1):
        for rid, msg, fn in RULES:
            if fn and fn(l, lines):
                found.append((rid, i, msg))
    # whole-file rules
    idx_copy_all = next((i for i, l in enumerate(lines) if re.match(r"COPY\s+\.\s+\S+", l)), None)
    idx_install = next((i for i, l in enumerate(lines) if "install" in l and l.startswith("RUN")), None)
    if idx_copy_all is not None and idx_install is not None and idx_copy_all < idx_install:
        found.append(("DL05", idx_copy_all + 1, RULES[4][1]))
    if not any(l.startswith("USER ") for l in lines):
        found.append(("DL06", len(lines), "no USER instruction: the process runs as root inside the container"))
    if not any(l.startswith("HEALTHCHECK") for l in lines):
        found.append(("DL07", len(lines), "no HEALTHCHECK (fine if the orchestrator probes the container instead)"))
    print("== %s: %d finding(s)" % (name, len(found)))
    for rid, n, msg in found:
        print("  line %2d  %s  %s" % (n, rid, msg))

lint("messy.Dockerfile", """
FROM python:latest
ADD . /app
WORKDIR /app
RUN apt-get update && apt-get install -y curl
RUN pip install -r requirements.txt
CMD ["python", "main.py"]
""")
lint("tidy.Dockerfile", """
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 10001
HEALTHCHECK CMD python -c "import urllib.request as u; u.urlopen('http://localhost:8000/health')"
CMD ["python", "main.py"]
""")

# ----- Output (real run) -----
# == messy.Dockerfile: 6 finding(s)
#   line  1  DL01  base image uses ':latest' or no tag (builds are not repeatable)
#   line  2  DL02  ADD used where COPY is enough (ADD also unpacks archives and fetches URLs)
#   line  4  DL03  apt-get install without --no-install-recommends / cache cleanup in the same RUN
#   line  5  DL04  pip install without --no-cache-dir (keeps downloads inside the layer)
#   line  6  DL06  no USER instruction: the process runs as root inside the container
#   line  6  DL07  no HEALTHCHECK (fine if the orchestrator probes the container instead)
# == tidy.Dockerfile: 0 finding(s)

Good to know

  • Checklist: pinned base tag; small base; .dockerignore; dependency files copied before code; one process per container; exec-form CMD; non-root USER; no secrets; cleanup in the same RUN (rm -rf /var/lib/apt/lists/*); multi-stage; labels; HEALTHCHECK or orchestrator probes; reproducible versions.
  • One concern per container: a web server and a database in one image is almost always wrong. Use two containers and Compose.

37 What Happens When You Run kubectl apply

Control loop = the heartbeat of Kubernetes: observe the actual state, compare with the desired state, act to close the gap, repeat forever. The next program shows this loop healing a set of pods.

A tiny control loop (seeded random failures) (run for real)
# The controller idea: look at the world, compare with what you WANT, fix the difference, repeat forever.
import random
random.seed(11)
desired, pods, next_id = 3, ["p1", "p2", "p3"], 4
print("desired replicas = %d, start: %s" % (desired, pods))
for tick in range(1, 13):
    event = ""
    if random.random() < 0.45 and pods:                       # something goes wrong: a pod/node dies
        dead = random.choice(pods); pods.remove(dead); event = "!! %s died" % dead
    diff = desired - len(pods)                                # the whole reconcile step is this one comparison
    action = ""
    if diff > 0:
        for _ in range(diff):
            pods.append("p%d" % next_id); next_id += 1

43 Rolling Updates: maxSurge and maxUnavailable

Picture: Changing the tyres of a car while it is moving is not possible, but changing the drivers of a bus fleet one at a time is. maxSurge says how many extra buses may exist during the swap; maxUnavailable says how many may be missing.

The simulation below applies the real rounding rule (surge rounds up, unavailable rounds down) to 10 replicas and checks two promises on every step: never too many pods in total, never too few ready ones.

Fig S11 — Rolling update of 10 pods (25% surge, 25% unavailable): old, new and ready pods at each step.
Two rollout settings, step by step (run for real)
# Rolling update with maxSurge / maxUnavailable. Rounding rule: surge rounds UP, unavailable rounds DOWN.
import math

def rollout(replicas, max_surge, max_unavail):
    surge = math.ceil(replicas * max_surge) if isinstance(max_surge, float) else max_surge
    unav = math.floor(replicas * max_unavail) if isinstance(max_unavail, float) else max_unavail
    old, new_total, new_ready, rows = replicas, 0, 0, []
    rows.append((0, old, new_total, new_ready, old + new_total, old + new_ready))
    tick = 0
    while not (new_ready == replicas and old == 0):
        tick += 1
        new_ready = new_total                                   # pods created last tick are ready now
        add = max(0, min(replicas - new_total, replicas + surge - (old + new_total)))
        new_total += add                                        # scale the new ReplicaSet up (within the surge limit)
        available = old + new_ready
        kill = min(old, max(0, available - (replicas - unav)))  # scale the old one down (keep enough available)
        old -= kill
        rows.append((tick, old, new_total, new_ready, old + new_total, old + new_ready))
        assert old + new_total <= replicas + surge                # never more pods than allowed
        assert old + new_ready >= replicas - unav                 # never fewer ready pods than allowed
        assert tick < 100
    return surge, unav, rows

How many DNS queries does one lookup cost? (run for real)
# Inside a pod, /etc/resolv.conf has "search" suffixes and ndots:5. Names with fewer than 5 dots try the suffixes FIRST.
def lookups(name, ns, existing):
    search = ["%s.svc.cluster.local" % ns, "svc.cluster.local", "cluster.local"]
    tried = []
    if name.endswith("."):
        tried.append(name); return tried, name in existing
    candidates = ([name] + [name + "." + s for s in search]) if name.count(".") >= 5 else ([name + "." + s for s in search] + [name])
    for c in candidates:
        tried.append(c)
        if c in existing:
            return tried, True
    return tried, False
existing = {"cart.default.svc.cluster.local", "pay.shop.svc.cluster.local", "api.example.com", "api.example.com."}
for name in ["cart", "pay.shop", "api.example.com", "api.example.com."]:
    tried, ok = lookups(name, "default", existing)
    print("%-17s -> %d DNS queries%s" % (name, len(tried), "" if ok else " (not found)"))
    for t in tried:
        print("      ", t, "<- found" if t in existing else "")

    ("shop.example.com", "Prefix", "/", "frontend-svc"),
    ("shop.example.com", "Prefix", "/api", "api-svc"),
    ("shop.example.com", "Prefix", "/api/v2", "api-v2-svc"),
    ("shop.example.com", "Exact", "/healthz", "health-svc"),
    ("admin.example.com", "Prefix", "/", "admin-svc"),
]
def route(host, path):
    best = None
    for h, kind, p, backend in rules:
        if h != host: continue
        if kind == "Exact" and path == p: score = (2, len(p))
        elif kind == "Prefix" and (path == p or path.startswith(p.rstrip("/") + "/") or p == "/"): score = (1, len(p))
        else: continue
        if best is None or score > best[0]: best = (score, backend, kind + " " + p)
    return best[1:] if best else ("404 default backend", "no rule matched")
for host, path in [("shop.example.com", "/"), ("shop.example.com", "/api/users"), ("shop.example.com", "/api/v2/users"), ("shop.example.com", "/healthz"), ("shop.example.com", "/apix"), ("admin.example.com", "/api"), ("other.example.com", "/")]:
    b, why = route(host, path)
    print("%-18s %-14s -> %-20s (%s)" % (host, path, b, why))

52 Requests, Limits and QoS Classes

Picture: Booking a restaurant table: request = the seats you reserve (always yours). Limit = the most you may take if the room is free. If the restaurant becomes too full, guests who took more than they reserved are asked to leave first.

The scheduler uses requests to place pods. The kubelet and the Linux kernel enforce limits. Quantities: 100m = 0.1 CPU core (millicores), 128Mi = 128 mebibytes.

QoS class and who is killed first (run for real)
# QoS classes decide who is evicted first when a node runs out of memory.
def qty(s):
    if s is None: return None
    if s.endswith("m"): return int(s[:-1])                      # millicores
    if s.endswith("Mi"): return int(s[:-2])
    if s.endswith("Gi"): return int(float(s[:-2]) * 1024)
    return int(float(s) * 1000)                                  # whole cores -> millicores

def qos(containers):
    allset = all(c.get("cpu_req") and c.get("mem_req") and c.get("cpu_lim") and c.get("mem_lim") for c in containers)
    equal = all(c.get("cpu_req") == c.get("cpu_lim") and c.get("mem_req") == c.get("mem_lim") for c in containers)
    anyset = any(c.get(k) for c in containers for k in ("cpu_req", "mem_req", "cpu_lim", "mem_lim"))
    if allset and equal: return "Guaranteed"
    return "Burstable" if anyset else "BestEffort"

NODE_MEM = 8192
def oom_score(cls, mem_req_mi):
    # approximate kubelet rule: Guaranteed -997, BestEffort 1000, Burstable 1000 - 1000*request/capacity (clamped)
    if cls == "Guaranteed": return -997
    if cls == "BestEffort": return 1000
    return int(min(max(2, 1000 - 1000 * mem_req_mi / NODE_MEM), 999))

pods = {

    "batch":   [dict(cpu_req="100m", mem_req="128Mi")],

Good to know

  • CPU limits throttle (slow down, hurting latency); many teams set CPU requests but omit CPU limits. Memory limits kill: always set a memory limit and keep request near limit for predictable behaviour.
  • Right-size from real usage: kubectl top pods, Prometheus graphs, the Vertical Pod Autoscaler in recommendation mode, or tools such as Goldilocks.
  • Java and other runtimes: size heap against the limit (for the JVM, MaxRAMPercentage), leaving room for non-heap memory.
  • Requests that are too high waste money (nodes look full but are idle); too low causes overcommit and evictions.

A slow-starting app with and without a readiness probe (run for real)
# Why the readiness probe matters: traffic should only reach a pod AFTER the app is ready. 1 request per second.
def run(startup_s, probe_period, use_probe, horizon=40):
    failed, joined = 0, None
    for t in range(horizon):                       # t = seconds since the container started
        app_up = t >= startup_s
        if use_probe:
            # the kubelet checks every probe_period seconds; the pod joins the Service after the first check that succeeds
            if joined is None and app_up and t % probe_period == 0:
                joined = t
            receiving = joined is not None
        else:
            joined, receiving = 0, True              # no readiness probe: a running container counts as ready at once
        if receiving and not app_up:
            failed += 1
    return failed, joined

The restart delay ladder (run for real)
# CrashLoopBackOff: the wait between restarts doubles each time (kubelet default 10s start, 300s cap, reset after 10 min healthy).
def delays(start, cap, n):
    d, out = start, []
    for _ in range(n):
        out.append(min(d, cap)); d *= 2
    return out
classic = delays(10, 300, 9)

t = 0

print()

Good to know

  • Shutdown order: preStop hook runs → SIGTERM → the app finishes in-flight work → SIGKILL after terminationGracePeriodSeconds (default 30 s).
  • Handle SIGTERM in your program: stop accepting new work, finish current requests, close connections, exit.

54 Scheduling: Where Does a Pod Land?

Picture: A hotel manager assigning guests to rooms: first rule out rooms that cannot fit (filter), then pick the best of the rest (score). Special rules: 'near the lift', 'not next to a noisy guest', 'this wing is reserved'.

The simulation below is a small model of the scheduler: filter by free CPU/memory, node labels (nodeSelector) and taints; score by free room; place or report Pending with the reason (the same style of message you see in kubectl describe pod).

Filter, score, place (a model, not the real scheduler) (run for real)
# The kube-scheduler idea: FILTER out nodes that cannot run the pod, SCORE the rest, pick the best.
nodes = {
    "node-a": {"cpu": 4000, "mem": 8192, "labels": {"disk": "ssd"}, "taints": []},
    "node-b": {"cpu": 4000, "mem": 8192, "labels": {"disk": "hdd"}, "taints": []},
    "node-gpu": {"cpu": 8000, "mem": 16384, "labels": {"gpu": "true"}, "taints": ["gpu=true:NoSchedule"]},
}
used = {n: {"cpu": 0, "mem": 0} for n in nodes}

def schedule(pod):
    name, cpu, mem = pod["name"], pod["cpu"], pod["mem"]
    reasons, scored = [], []
    for n, d in nodes.items():
        if d["cpu"] - used[n]["cpu"] < cpu:
            reasons.append("%s: not enough CPU" % n); continue
        if d["mem"] - used[n]["mem"] < mem:
            reasons.append("%s: not enough memory" % n); continue
        if any(d["labels"].get(k) != v for k, v in pod.get("selector", {}).items()):
            reasons.append("%s: nodeSelector does not match" % n); continue
        if any(t not in pod.get("tolerates", []) for t in d["taints"]):
            reasons.append("%s: has a taint the pod does not tolerate" % n); continue
        # LeastAllocated style score: more free room after placing = higher score
        free_cpu = (d["cpu"] - used[n]["cpu"] - cpu) / d["cpu"]
        free_mem = (d["mem"] - used[n]["mem"] - mem) / d["mem"]
        scored.append((round(50 * (free_cpu + free_mem), 1), n))
    if not scored:
        print("%-10s PENDING  0/%d nodes are available -> %s" % (name, len(nodes), "; ".join(reasons)))
        return
    scored.sort(key=lambda s: (-s[0], s[1]))
    best = scored[0][1]
    used[best]["cpu"] += cpu; used[best]["mem"] += mem
    print("%-10s -> %-9s scores %s" % (name, best, scored))

pods = [
    {"name": "web-1", "cpu": 500, "mem": 512}, {"name": "web-2", "cpu": 500, "mem": 512}, {"name": "web-3", "cpu": 500, "mem": 512},
    {"name": "db-1", "cpu": 1000, "mem": 2048, "selector": {"disk": "ssd"}},
    {"name": "train-1", "cpu": 4000, "mem": 8192, "selector": {"gpu": "true"}},
    {"name": "train-2", "cpu": 4000, "mem": 8192, "selector": {"gpu": "true"}, "tolerates": ["gpu=true:NoSchedule"]},
    {"name": "huge-1", "cpu": 9000, "mem": 1000},
]
for p in pods:
    schedule(p)
print()
for n, u in used.items():
    print("%-9s CPU %4d/%d m  memory %5d/%d Mi" % (n, u["cpu"], nodes[n]["cpu"], u["mem"], nodes[n]["mem"]))

55 Autoscaling: HPA, VPA, Cluster Autoscaler and KEDA

Picture: A restaurant on match day: add waiters when the queue grows (HPA: more pods), give each waiter a bigger tray (VPA: bigger pods), open another dining room when this one is full (Cluster Autoscaler / Karpenter: more nodes).

The HPA formula: desiredReplicas = ceil( currentReplicas × currentMetric ÷ targetMetric ). It checks about every 15 seconds, ignores changes within a 10% tolerance, and scales down only after a stabilization window (default 5 minutes) so it does not flap. The simulation applies the formula to a load spike (assumed demand curve; 1 step = 1 minute).

Fig S15 — HPA reaction to a traffic spike: pods follow demand up quickly and down slowly.
HPA on a load spike (model) (run for real)
# Horizontal Pod Autoscaler: desired = ceil(current * currentMetric / target), with a 10% tolerance and a scale-down window.
import math
REQ, TARGET, MIN, MAX, WINDOW = 500, 50, 2, 12, 5      # CPU request per pod (m), target util %, replica limits, scale-down window (minutes)
load = [300, 300, 500, 1200, 2400, 3600, 3600, 3600, 3000, 2000, 1000, 600, 400, 300, 300, 300, 300, 300, 300, 300]   # total CPU demand (m) per minute
replicas, recs, rows = 2, [], []
for minute, demand in enumerate(load):
    util = 100.0 * demand / (replicas * REQ)               # average utilisation vs the request
    ratio = util / TARGET
    want = replicas if abs(ratio - 1) <= 0.10 else math.ceil(replicas * ratio)
    want = max(MIN, min(MAX, want))
    recs.append(want)
    stable = max(recs[-WINDOW:])                             # scaling DOWN only follows the highest recommendation of the window
    new = want if want > replicas else min(replicas, stable) if want < replicas else replicas
    rows.append((minute, demand, replicas, round(util), want, new))
    replicas = new
print("minute  demand(m)  pods  util%  wanted  next")
for r in rows:
    print("%6d  %9d  %4d  %5d  %6d  %4d" % r)
print("HPA series:", [r[2] for r in rows])

56 RBAC: Who May Do What

Picture: A building with key cards. A Role is a list of doors ('read pods, edit deployments'). A RoleBinding hands that card to a person or program. If no card opens a door, it stays shut: there is no 'deny' list, only 'allow'.

Authentication (who are you?: certificates, OIDC tokens, service accounts) happens first; authorization (what may you do?: RBAC) second; admission control (is this object acceptable?) third. The simulation answers 'can-i' questions from roles and bindings.

kubectl auth can-i (model) (run for real)
# RBAC: nothing is allowed unless a Role says so (rules only ADD permissions; there is no "deny").
roles = {
    ("dev", "pod-reader"): [{"resources": ["pods", "pods/log"], "verbs": ["get", "list", "watch"]}],
    ("dev", "deployer"): [{"resources": ["deployments"], "verbs": ["get", "list", "create", "update", "patch"]}],
    ("*", "view-all"): [{"resources": ["*"], "verbs": ["get", "list", "watch"]}],
}
bindings = [("alice", "dev", ("dev", "pod-reader")), ("alice", "dev", ("dev", "deployer")), ("bob", "*", ("*", "view-all")), ("ci-bot", "dev", ("dev", "deployer"))]
def can_i(user, verb, resource, ns):
    for who, scope, role in bindings:
        if who != user or scope not in (ns, "*"): continue
        for r in roles[role]:
            if verb in r["verbs"] and (resource in r["resources"] or "*" in r["resources"]):
                return True, "via %s" % role[1]
    return False, "no role grants it"
for user, verb, res, ns in [("alice", "get", "pods", "dev"), ("alice", "delete", "pods", "dev"), ("alice", "get", "pods", "prod"), ("bob", "list", "secrets", "prod"),
                            ("bob", "delete", "deployments", "prod"), ("ci-bot", "patch", "deployments", "dev"), ("ci-bot", "get", "pods", "dev")]:
    ok, why = can_i(user, verb, res, ns)
    print("kubectl auth can-i %-7s %-12s -n %-4s as %-6s -> %-3s (%s)" % (verb, res, ns, user, "yes" if ok else "no", why))

Picture: By default every flat can walk into every other flat. A NetworkPolicy is a guard at selected doors: 'only the API flat may knock on the database flat, only on port 5432'.

Rules: pods are open until some policy selects them; then only what the policies list is allowed. Policies add up (union). The simulation evaluates connection attempts.

Which connections are allowed? (model of the rules) (run for real)
# NetworkPolicy semantics (simplified): once ANY policy selects a pod for ingress, only listed traffic is allowed.
pods = {"web": {"role": "frontend"}, "api": {"role": "backend"}, "db": {"role": "database"}, "debug": {"role": "tools"}}
policies = [
    {"name": "db-only-from-api", "selects": {"role": "database"}, "from": [{"role": "backend"}], "ports": [5432]},
    {"name": "api-from-web",     "selects": {"role": "backend"},  "from": [{"role": "frontend"}], "ports": [8080]},
]
def allowed(src, dst, port):
    chosen = [p for p in policies if all(pods[dst].get(k) == v for k, v in p["selects"].items())]

        if port in p["ports"] and any(all(pods[src].get(k) == v for k, v in f.items()) for f in p["from"]):
            return True, "allowed by %s" % p["name"]
    return False, "blocked: not allowed by any policy that selects %s" % dst

65 Staying Up: Replicas, Disruption Budgets and etcd Quorum

Picture: A hospital rota: even when two nurses go on holiday, at least four must stay on the ward (PodDisruptionBudget). And the hospital board (etcd) can only decide if a majority of its members are present.

1. PodDisruptionBudget (PDB). During voluntary disruptions (node drain, upgrade) the eviction API refuses to remove a pod if too few would remain ready.

Draining nodes with minAvailable=4 (model) (run for real)
# PodDisruptionBudget: while draining nodes, Kubernetes refuses to evict a pod if too few would stay ready.
ready, min_available, log = 5, 4, []
pending_back = []                      # replacement pods that become ready on a later tick
for tick in range(1, 9):
    ready += sum(1 for t in pending_back if t == tick); pending_back = [t for t in pending_back if t != tick]
    if tick <= 6:                      # an operator tries to drain a node every tick, evicting one pod
        if ready - 1 >= min_available:
            ready -= 1; pending_back.append(tick + 2)    # the controller starts a replacement; it is ready 2 ticks later
            log.append("tick %d: eviction ALLOWED  (ready now %d, replacement ready at tick %d)" % (tick, ready, tick + 2))
        else:
            log.append("tick %d: eviction REFUSED  (only %d ready, budget minAvailable=%d)" % (tick, ready, min_available))
    else:
        log.append("tick %d: no more drains; ready = %d" % (tick, ready))
print("\n".join(log))

# ----- Output (real run) -----
# tick 1: eviction ALLOWED  (ready now 4, replacement ready at tick 3)
# tick 2: eviction REFUSED  (only 4 ready, budget minAvailable=4)
# tick 3: eviction ALLOWED  (ready now 4, replacement ready at tick 5)
# tick 4: eviction REFUSED  (only 4 ready, budget minAvailable=4)
# tick 5: eviction ALLOWED  (ready now 4, replacement ready at tick 7)

Evictions alternate between allowed and refused until a replacement is ready. A PDB with minAvailable equal to the replica count would block drains completely: leave room.

Good to know

Check a bad and a good Deployment (run for real)
# Kubernetes accepts JSON as well as YAML, so we can check a Deployment with the standard library only.
import json
def check(d):
    spec, f = d["spec"], []
    tpl = spec["template"]; labels = tpl["metadata"]["labels"]
    sel = spec["selector"]["matchLabels"]
    if any(labels.get(k) != v for k, v in sel.items()): f.append("selector does not match the pod template labels (the API server rejects this)")
    if spec.get("replicas", 1) < 2: f.append("only 1 replica: a restart means downtime")
    for c in tpl["spec"]["containers"]:
        n = c["name"]
        img = c["image"]
        if ":" not in img.split("/")[-1] or img.endswith(":latest"): f.append("%s: image '%s' has no fixed tag" % (n, img))
        if "resources" not in c: f.append("%s: no resources.requests/limits (scheduler cannot plan; QoS = BestEffort)" % n)
        if "readinessProbe" not in c: f.append("%s: no readinessProbe (traffic may arrive before the app is ready)" % n)
        sc = c.get("securityContext", {})
        if sc.get("privileged"): f.append("%s: privileged container" % n)
        if not sc.get("runAsNonRoot"): f.append("%s: runAsNonRoot is not set" % n)
        if not sc.get("readOnlyRootFilesystem"): f.append("%s: root filesystem is writable" % n)
    if tpl["spec"].get("hostNetwork"): f.append("hostNetwork: true bypasses pod networking")
    return f
bad = json.loads("""{"kind":"Deployment","metadata":{"name":"shop"},"spec":{"replicas":1,"selector":{"matchLabels":{"app":"shop"}},
 "template":{"metadata":{"labels":{"app":"shopp"}},"spec":{"hostNetwork":true,"containers":[{"name":"web","image":"shop:latest","securityContext":{"privileged":true}}]}}}}""")
good = json.loads("""{"kind":"Deployment","metadata":{"name":"shop"},"spec":{"replicas":3,"selector":{"matchLabels":{"app":"shop"}},

76 FAQ

Picture: Click a question to reveal the answer.
Q: Do I have to learn Docker before Kubernetes?

Yes, learn Docker (or any OCI image workflow) first: Kubernetes runs images and you must know how to build and debug them.

Q: Is Kubernetes replacing Docker?

No. Kubernetes stopped using Docker Engine as its runtime (dockershim removed in 1.24) and uses containerd or CRI-O, but images built with Docker still run, and Docker is still the most common developer tool for building them.

Q: Do I need Kubernetes for my small project?

Probably not. Compose on one VM, a PaaS, or a serverless container service is cheaper to run and learn. Choose Kubernetes for many services, team autonomy, portability or advanced scaling needs.

Q: Why did my container exit immediately?

Its main process ended. Check docker logs and the exit code. A shell with no terminal (-it) or a program that runs in the background (forked daemon) exits at once.

Q: Where is my data after I removed the container?

Gone, unless it was in a volume or bind mount. The writable layer is deleted with the container.

Q: Why can't I reach my app on localhost?

Check that the app listens on 0.0.0.0, that the port is published (-p / Service), and that the container port is the right one.

Q: Pod or container: what is the difference?

A pod wraps one or more containers that share network and storage; Kubernetes schedules pods, not bare containers.

Q: Why does my pod keep restarting?

Look at kubectl describe pod and kubectl logs --previous: crash, failed liveness probe, or OOMKilled.

Q: Which is better, Helm or Kustomize?

Different jobs: Helm packages and shares configurable software; Kustomize patches your own YAML per environment. Many teams use both.

Q: Are the commands on this page tested?

The Linux kernel demos (namespaces, overlayfs, hand-made container) and all Python simulations were really run and their output is shown. Docker, kubectl, Helm, Kustomize and YAML files are templates, not run, because this machine has no Docker engine and no cluster.

Q: How do I practise for free?

Install Docker Desktop or Podman and kind or minikube on a laptop; use the free browser labs of Kubernetes tutorials; destroy and rebuild clusters often.

Q: How current is this page?

Reviewed 17 November 2026. Kubernetes versions and support dates come from kubernetes.io/releases on that day; product facts marked 'as reported' come from secondary sources and should be re-checked.

77 Interview Questions: Docker (With Answers)

Picture: Grouped by theme, easiest first. Click to reveal.

A. Basics

Q1: What is a container? How is it different from a VM?

A container is an isolated Linux process (namespaces for isolation, cgroups for limits, a layered file system for its files). It shares the host kernel, so it is small and starts in about a second; a VM carries its own OS and kernel.

Q2: Image vs container?

An image is a read-only template (layers + config). A container is a running instance with a thin writable layer on top.

Q3: What happens on docker run nginx?

The client calls the daemon; the image is pulled if missing; a container is created (writable layer, network, namespaces, cgroups) and containerd/runc start the process.

Q4: What is a Dockerfile? Name important instructions.

A text recipe for an image: FROM, WORKDIR, COPY, RUN, ENV, ARG, EXPOSE, USER, CMD, ENTRYPOINT, HEALTHCHECK.

Q5: CMD vs ENTRYPOINT?

ENTRYPOINT is the fixed program; CMD gives default arguments (or a default program) that can be replaced at run time. Use the exec form so the program receives signals.

Q6: COPY vs ADD?

COPY copies files. ADD also unpacks local archives and can fetch URLs; prefer COPY for clarity and safety.

B. Images and builds

Q7: How does the build cache work, and how do you use it well?

Each instruction's cache key depends on the instruction, copied files and the previous step. When a step changes, all later steps rebuild. Copy dependency files first, install, then copy code (see the simulation: 71 s vs 11 s after a code edit).

Q8: How do you make images small?

Small base (slim, distroless, scratch), multi-stage builds, .dockerignore, combine and clean up in one RUN, no build tools in the final stage.

Q9: What is a multi-stage build?

Several FROM stages in one Dockerfile; a heavy build stage produces files and a small runtime stage copies only those (COPY --from).

Q10: Tag vs digest?

A tag is a movable label; a digest is the immutable sha256 of the content. Pin digests for reproducibility.

Q11: What is in an OCI image?

A manifest listing a config JSON and layer tarballs, each identified by a sha256 digest; an index can point to one manifest per platform.

C. Running

Q12: How do you persist data?

Named volumes (managed by Docker), bind mounts (host folders) or tmpfs (memory). The container's writable layer is deleted with it.

Q13: How do containers talk to each other?

Put them on a user-defined bridge network; Docker's DNS resolves container or Compose service names. Publish ports only for outside access.

Q14: How do you limit resources?

--memory, --cpus, --pids-limit (cgroups). Exceeding memory triggers an OOM kill (exit 137).

Q15: Why must a container listen on 0.0.0.0?

127.0.0.1 inside the container is its own loopback, unreachable through port mapping.

Q16: What does docker stop do?

Sends SIGTERM, waits (10 s by default), then SIGKILL. Programs should handle SIGTERM; PID 1 must forward signals.

D. Security and operations

Q17: How do you secure containers?

Non-root user, read-only root filesystem, drop capabilities, no-new-privileges, no privileged mode or docker.sock mounts, minimal pinned images, scanning, signing, secrets out of images, resource limits, rootless mode.

Q18: Why is mounting the Docker socket dangerous?

Whoever can talk to the daemon can start a privileged container that mounts the host's root, so the socket is effectively root on the host.

Q19: Docker vs Podman?

Podman is daemonless and rootless by default with a nearly identical CLI; both build and run OCI images.

Q20: Compose vs Kubernetes?

Compose describes multi-container apps on one machine (development, small deployments); Kubernetes runs and heals workloads across many machines.

E. Deep dive

Q21: Explain how a container is built from Linux features, with a demo you could do without Docker.

Namespaces (pid, mnt, net, uts, ipc, user) give a private view; cgroups limit resources; a root file system (layers via overlayfs) gives the files. With unshare plus chroot into a folder holding a shell and its libraries you get a minimal container (shown on this page).

Q22: Why does a deleted secret in a later layer still leak?

Layers are additive. A RUN rm adds a whiteout in a new layer, but the earlier layer's tarball still contains the file and can be extracted.

Q23: How do you build multi-architecture images?

buildx with --platform linux/amd64,linux/arm64 (QEMU emulation or native builders), pushed as an image index.

Q24: A container is OOMKilled. How do you investigate?

Check docker inspect (OOMKilled true, exit 137), docker stats, application metrics and the limit versus the working set (including non-heap memory); raise the limit or fix the leak.

Q25: Why can't two containers share the same host port?

The host port is bound once by the first container; a second -p to the same port fails. Use different host ports or a reverse proxy.

78 Interview Questions: Kubernetes (With Answers)

Picture: Grouped by theme, easiest first. Click to reveal.

A. Basics

Q1: What is Kubernetes?

An open-source system that automates deploying, scaling and managing containers across many machines, using a declarative API and control loops.

Q2: Name the control plane components.

kube-apiserver, etcd, kube-scheduler, kube-controller-manager and (in clouds) cloud-controller-manager. Nodes run kubelet, kube-proxy and a container runtime.

Q3: What is a pod?

The smallest deployable unit: one or more containers sharing a network namespace (one IP) and volumes, scheduled together.

Q4: Pod vs Deployment vs ReplicaSet?

A Deployment manages ReplicaSets (one per version) which keep N identical pods. Bare pods are not recreated if they die.

Q5: What is a Service? Types?

A stable virtual IP and DNS name in front of pods chosen by label. ClusterIP, NodePort, LoadBalancer, headless, ExternalName.

Q6: What are labels and selectors for?

Labels tag objects; selectors choose them. Services, ReplicaSets, NetworkPolicies and kubectl all use them.

B. Workloads and config

Q7: How does a rolling update work?

The Deployment creates a new ReplicaSet and scales it up while scaling the old one down, bounded by maxSurge and maxUnavailable, and uses readiness to decide when new pods count (our simulation: 10 replicas finish in 5 steps with 25%/25%).

Q8: How do you roll back?

kubectl rollout undo deployment/web, or revert the Git commit in a GitOps setup.

Q9: Deployment vs StatefulSet vs DaemonSet vs Job?

Stateless replicas; stable identity and per-pod storage; one pod per node; run-to-completion tasks (CronJob adds a schedule).

Q10: ConfigMap vs Secret?

Both inject configuration. Secrets are for sensitive data but are only base64-encoded unless encryption at rest is enabled; restrict them with RBAC.

Q11: Requests vs limits?

Requests are reserved capacity used for scheduling; limits are ceilings enforced at run time (CPU throttled, memory OOM-killed). They define QoS classes: Guaranteed, Burstable, BestEffort.

Q12: Liveness vs readiness vs startup probes?

Liveness restarts a stuck container; readiness removes it from Service endpoints; startup holds off the others for slow starters.

C. Networking and storage

Q13: How does a Service route traffic?

EndpointSlices list ready pod IPs; kube-proxy (iptables/IPVS/nftables) or the CNI (e.g. Cilium eBPF) rewrites Service IP traffic to one of them.

Q14: Ingress vs Gateway API vs LoadBalancer?

LoadBalancer exposes one Service. Ingress routes HTTP by host/path to many Services (needs a controller). Gateway API is the newer, role-based, more expressive successor.

Q15: What is a NetworkPolicy and what must be true for it to work?

A pod-level firewall. The CNI plugin must enforce it; once a pod is selected, only listed traffic is allowed.

Q16: PV, PVC, StorageClass?

PV is storage, PVC a request for it, StorageClass the recipe for dynamic provisioning through a CSI driver.

Q17: Why can a DNS lookup of an external name be slow in a pod?

ndots:5 with the search list makes short names try several cluster suffixes first (4 queries for api.example.com in our simulation). Use a trailing dot, lower ndots, or a node-local DNS cache.

D. Scheduling, scaling, reliability

Q18: How does the scheduler pick a node?

Filter (resources, selectors, affinity, taints, volumes), then score the remaining nodes and bind the pod to the best.

Q19: Taints and tolerations vs affinity?

Taints repel pods from nodes unless tolerated; affinity attracts pods to nodes or to/away from other pods.

Q20: How does HPA decide the replica count?

desired = ceil(current × currentMetric ÷ target), with a 10% tolerance and a scale-down stabilization window (default 5 min).

Q21: What is a PodDisruptionBudget?

A limit on voluntary evictions (drains, upgrades) so a minimum number of pods stays available.

Q22: Why 3 or 5 etcd members?

Raft needs a majority: 3 tolerate 1 failure, 5 tolerate 2. 4 tolerates the same as 3, so even sizes waste a node.

Q23: Pod stuck in Pending; what do you do?

kubectl describe pod and read the FailedScheduling event: insufficient CPU/memory, taints, selectors, or an unbound PVC.

Q24: CrashLoopBackOff: cause and steps?

The container exits repeatedly and the kubelet backs off (10 s doubling to 300 s by default). Read kubectl logs --previous, check config, env, probes and limits.

E. Security and operations

Q25: Explain RBAC.

Roles list permitted verbs on resources; RoleBindings attach roles to users, groups or service accounts. There is no deny; permissions only add up; least privilege applies.

Q26: How do you harden a cluster?

RBAC and OIDC, encrypted Secrets, default-deny network policies, Pod Security 'restricted', admission policies, image scanning/signing, minimal nodes, audit logs, regular upgrades and CIS benchmark checks.

Q27: Helm vs Kustomize?

Helm templates and packages with values and release management; Kustomize patches plain YAML with overlays. Both can be used together.

Q28: What is GitOps?

Desired state lives in Git; an in-cluster agent (Argo CD, Flux) pulls and applies it and corrects drift, giving auditability and easy rollback.

Q29: What is an operator?

A custom controller plus CRDs that encode operational knowledge (install, backup, upgrade, failover) for an application.

Q30: How do you achieve zero-downtime deploys?

Multiple replicas, readiness probes, maxUnavailable 0 (and some surge), preStop sleep plus graceful shutdown, PDBs, and compatible database migrations (expand/contract).

F. System design style

Q31: Design the deployment of a web app with a database on Kubernetes.

Deployment (3+ replicas, probes, requests/limits, topology spread) behind a Service and Gateway/Ingress with TLS; config via ConfigMap/Secret (external secrets manager); HPA; PDB; NetworkPolicies; database as a managed service or an operator-managed StatefulSet with backups; Prometheus/Grafana/Loki; GitOps with Argo CD; image scanning and signing in CI.

Q32: Your cluster is 90% full of reserved CPU but nodes are idle. Why, and what do you do?

Requests are too high compared with real usage. Measure usage, right-size requests (VPA recommendations), then let the cluster autoscaler consolidate nodes.

79 Pitfalls and Checklist

Picture: Common mistakes, kindly listed.

🏷️ :latest everywhere

Pin versions and digests; one tag should mean one build.

👑 Running as root

USER non-root, runAsNonRoot, drop capabilities.

🔑 Secrets in images, ENV or Git

Use secret mounts, secret managers, sealed/external secrets.

🐘 Huge images

Slim base, multi-stage, .dockerignore.

🧊 Bad layer order

Dependencies first, code last; the cache saves minutes.

💾 Data in the container layer

Use volumes / PVCs and test restores.

🚫 No resource requests/limits

Unpredictable scheduling, noisy neighbours, OOM surprises.

❤️‍🩹 Missing or wrong probes

Readiness for traffic; keep liveness cheap and local.

🛑 Ignoring SIGTERM

Exec form, handle signals, preStop pause, graceful period.

🔓 Open networks and cluster-admin

Default-deny policies, least-privilege RBAC.

🏗️ Bare pods

Always use a controller.

🧩 Tool sprawl

Master pods, Services, Deployments first; add meshes, operators later.

⏫ Skipping upgrades

Stay within support; upgrade one minor at a time; read deprecations.

🕳️ No backups

Back up etcd (self-managed), volumes and manifests; rehearse a restore.

Pre-launch checklist

  • ☐ Image is pinned, scanned, small, non-root, signed.
  • ☐ Config and secrets come from outside the image.
  • ☐ Requests and limits set from measurements; memory limit present.
  • ☐ Readiness, liveness (and startup) probes tested; graceful shutdown tested.
  • ☐ 2+ replicas spread across zones; PDB; HPA with sane min/max.
  • ☐ NetworkPolicy, RBAC, Pod Security level applied.
  • ☐ Logs to stdout, metrics scraped, alerts and a runbook exist.
  • ☐ Deployment is declarative, in Git, with a tested rollback.
  • ☐ Backups and a restore drill; cost labels set.

80 Quick Quiz 🎯

Picture: Click each question to reveal the answer.
Q1: Which three Linux features make a container?

Namespaces (what it sees), cgroups (how much it can use), and a layered root file system (what files it starts with).

Q2: Why does editing one line of code make a badly ordered build re-install all libraries?

Because the COPY of the whole folder comes before the install step; once a step's inputs change, all later steps rebuild (71 s vs 11 s in our simulation).

Q3: What is PID 1 inside the hand-made container?

Its first process (the shell); the pid namespace restarts numbering at 1.

Q4: Which lasts longer: a container's writable layer or a named volume?

The named volume. The writable layer disappears with the container.

Q5: A Service has no endpoints. Name two causes.

The selector does not match the pods' labels, or the matching pods are not ready.

Q6: 10 replicas, maxSurge 25%, maxUnavailable 25%: how many extra pods and how many missing ones are allowed?

Surge rounds up to 3 extra pods; unavailable rounds down to 2 missing.

Q7: How many etcd failures can 5 members tolerate?

2 (the quorum is 3).

Q8: What does the readiness probe do when it fails?

The pod is removed from Service endpoints; it is not restarted.

Q9: Which QoS class is killed first under memory pressure?

BestEffort (no requests or limits), then Burstable; Guaranteed is protected.

Q10: Why add a preStop sleep?

Endpoint removal takes a moment to reach every proxy; pausing keeps the pod serving until traffic stops (30 requests lost vs 0 in our assumed-numbers simulation).
