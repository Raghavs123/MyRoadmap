Part A — Foundations

1 What is an AI Agent? (The 10-second answer)

Imagine asking a very capable assistant "book me the cheapest flight to Mumbai next Friday." A plain chatbot would just reply with words — maybe tips on how to search for flights yourself. An AI agent, instead, actually goes and does it: it searches flight sites, compares prices, picks one, maybe asks you to confirm, and then completes the booking — taking multiple steps and using real tools, on its own, to reach a goal.

An AI agent is an LLM-powered system that can perceive its situation (read a goal, some data, tool results), decide what to do next, take an action (usually by calling a tool/function), observe the result, and repeat — looping on its own until the goal is done, instead of just answering once.
Think of the difference between a GPS app that just shows you the route (information) and an actual self-driving car that steers, brakes, and reacts to traffic to actually get you there (action). A chatbot is the GPS. An agent is the self-driving car.

We'll build this up from an LLM (covered fully in LLMs — Large Language Models) by adding: the ability to call tools, a way to remember things across steps, and a loop that keeps going until the job is finished.

2 Why Do We Even Need Agents?

A plain LLM call is like asking a brilliant person a question through a letter — they write back one thoughtful reply, but can't go check anything, can't act on your behalf, and can't come back to you with "actually, that didn't work, let me try something else."

🔄 Multi-step tasks need loops

"Plan my trip" isn't one question — it's search, compare, book, confirm. A single LLM reply can't do all of that; an agent loop can.

🛠️ Real-world actions need tools

LLMs only generate text. To actually search the web, query a database, or send an email, something needs to translate the model's intent into a real action — that's what tools give an agent.

🧠 Hard problems need adaptation

If the first approach fails (a search returns nothing useful, an API errors out), an agent can notice that and try a different approach — a single LLM call just gives you one fixed answer.

🤝 Big problems need teamwork

Some tasks are naturally split into specialist roles (researcher, writer, reviewer) — multiple cooperating agents (Agentic AI, Part D) can divide and conquer better than one generalist.

In short: agents exist because real goals are messy, multi-step, and require actually touching the outside world — not just producing one block of text.

Part B — Core Concepts & Anatomy

6 The Big Picture — Anatomy of an Agent

Strip away the fancy branding of every agent framework, and they're all built from the same four pieces:

Fig 1 — An agent is just an LLM wired up to tools, memory, a goal, and a planner — looping until the goal is reached.
It's like a new employee (the LLM) who's handed a task (goal), given access to the office tools (search engine, calculator, email), a notebook to jot things down (memory), and told to figure out the steps themselves (planning) — checking in on progress as they go.
  • LLM (the brain) — reads the current situation and decides the single next action.
  • Tools — the agent's hands: functions it can call to search, compute, read files, hit APIs.
  • Memory — what the agent remembers, both within one task and across multiple sessions (Section 9).
  • Planner / Loop — the logic that keeps calling the LLM repeatedly, feeding back results, until the goal is done (Section 7).

7 The Agent Loop — Perceive, Plan, Act, Observe

Every agent, no matter the framework, runs the same underlying loop. This exact "reason-then-act" pattern was formalized in the influential ReAct paper (2022) — short for "Reasoning + Acting."

Fig 2 — The agent loop: perceive, plan, act, observe, repeat — until a stop condition (goal reached, max steps, or failure) is hit.
  1. Perceive — the LLM reads the current goal, conversation history, and any results from previous steps.
  2. Plan / Think — it reasons about what to do next (often writing out its reasoning as text — the "Thought:" in ReAct).
  3. Act — it calls a tool/function (the "Action:" in ReAct) — e.g., search the web, run code, query a database.
  4. Observe — the tool's real result ("Observation:") is fed back into the next round of the loop.
Without a stop condition, this loop can run forever (or until it burns through your budget). Real agents always cap the maximum number of steps and define clear "I'm done" conditions — see Section 36 for safety practices around this.

8 Tools & Function Calling for Agents

Tools are what separate an agent from a chatbot that just talks. The underlying mechanism is exactly the function/tool calling covered in LLM §22: you describe available functions (name, description, parameters) to the model, and it can request one be called instead of replying in plain text.

Giving an LLM a tool is like giving someone a phone with specific apps installed — a calculator app, a maps app, an email app. The person (LLM) still decides WHEN to use which app and WHAT to type into it; the app itself just does the one job reliably.

A step beyond this is models that can learn to use tools even without being explicitly shown examples for every tool — explored in the Toolformer paper, which trains a model to decide for itself when calling an API would help.

9 Memory in Agents

LLMs themselves are stateless — they only know what's in the current context window (LLM §19). "Memory" in an agent is really just engineering around that limitation: deciding what information to carry forward, and how.

Memory typeWhat it holdsHow it's implemented
Short-term / working memoryThe current task's conversation and tool resultsJust the LLM's context window — the running list of messages in this session
Long-term memoryFacts, preferences, or past interactions that should persist across sessionsAn external store (often a vector database, as in RAG — Vector Databases) that's searched and relevant bits are injected back into context
Episodic memoryA record of specific past episodes/tasks ("last time I tried X, it failed because Y")Logged transcripts or summaries, retrieved when a similar situation comes up again
Procedural memoryLearned skills/routines (not facts) — "how to do X"Often baked into the system prompt, fine-tuning, or reusable sub-routines/tools
Short-term memory is like what you're actively holding in your head during one conversation. Long-term memory is like a notebook you wrote in last month that you flip back to when it becomes relevant again — you don't re-read the whole notebook every time, just the relevant page.
Context windows are limited and expensive (LLM §19) — naively dumping all history into every prompt doesn't scale. Real systems summarize, retrieve selectively, or expire old memory rather than keeping everything forever.

10 Planning & Reasoning Strategies

How does an agent decide the right sequence of steps? A few well-known strategies, each with trade-offs:

StrategyIdeaBest for
Chain-of-ThoughtJust think step by step in a straight line before acting (LLM §21)Simple, mostly-linear tasks
ReActInterleave short reasoning with real actions, one step at a time (Section 11)Tasks needing real-world info mid-reasoning
Plan-and-ExecuteWrite out the FULL multi-step plan up front, then execute each step (Section 12)Complex tasks where the overall structure is knowable in advance
Tree of ThoughtsExplore MULTIPLE possible reasoning paths like branches of a tree, and backtrack from dead ends — see Tree of Thoughts paperPuzzles/search problems with many possible approaches
ReflexionAfter failing, generate a self-critique in plain language and try again informed by it — see Reflexion paperTasks where trial-and-error with self-correction helps (coding, games)
None of these are mutually exclusive — production agents often combine them (e.g., Plan first, then ReAct through each planned step, with Reflexion kicking in only on failure).

Part C — Single-Agent Design Patterns

11 ReAct Pattern Deep Dive

ReAct (from the 2022 paper) is the most widely used single-agent pattern because it's simple and surprisingly robust: at each step, the model writes a short "Thought" (reasoning about the situation), then an "Action" (a tool call), then receives an "Observation" (the tool's real result) — and uses that observation to decide the next Thought.

A typical ReAct transcript looks like:
Thought: I need today's weather for Mumbai.
Action: get_weather(city="Mumbai")
Observation: 31°C, humid, light rain expected.
Thought: It'll rain, so I should recommend an umbrella.
Final Answer: It's 31°C and rainy in Mumbai — bring an umbrella!

Writing the "Thought" out loud (rather than silently deciding) noticeably improves reliability — the same reason Chain-of-Thought prompting helps (LLM §21): putting reasoning into generated tokens gives the model more "working space" to get it right.

It's how a careful cook works: "This sauce tastes bland (thought) → let me add salt (action) → taste it again (observation) → hm, still needs acid (thought) → add lemon (action) → taste again (observation) → perfect, done." Each step is informed by checking reality, not just planning blindly from the start.

12 Plan-and-Execute Pattern

Instead of deciding one step at a time (like ReAct), Plan-and-Execute first asks the LLM to write out the ENTIRE multi-step plan up front, and then executes each step — often with a separate, lighter-weight call per step, only replanning if something goes wrong.

ReActPlan-and-Execute
When is the plan decided?One step at a time, adaptivelyAll upfront, then followed
Cost patternOne (often large) LLM call per stepOne big planning call, then smaller execution calls
Good forUnpredictable tasks needing real-time adaptationTasks whose overall shape is predictable in advance
RiskCan wander/loop without a clear end in sightPlan can become stale if early steps reveal new information
ReAct is like hiking a trail you've never seen, deciding your next move at each fork as you reach it. Plan-and-Execute is like studying the whole trail map first, writing down your route, and then walking it — only pulling the map back out if you hit something unexpected.

13 Reflection / Self-Critique Pattern

After an attempt fails (or produces a mediocre result), a Reflection-style agent generates a short, honest self-critique in plain language — "what went wrong and why" — and feeds that critique back in before trying again. This is the core idea behind the Reflexion paper.

It's the difference between retrying a failed exam question by guessing randomly again, versus first asking "why did I get that wrong?", writing down the actual mistake, and THEN trying again informed by that insight.

This pattern is especially effective for coding agents: write code → run tests → if tests fail, read the error message, reflect on the likely cause, and rewrite the code informed by that specific failure — rather than blindly regenerating from scratch.

14 Tool Use Design

Most agent failures trace back to poor tool design, not a weak model. A few practical rules:

📝 Clear names & descriptions

"search_flights(origin, destination, date)" with a precise description beats a vague "do_travel_stuff(input)" — the model picks the right tool based on exactly this text.

🧩 Narrow, single-purpose tools

One tool that does one thing well is easier for the model to use correctly than one giant tool that does five different things based on a flag.

🛟 Helpful error messages

When a tool fails, return a clear, actionable error ("city not found — did you mean 'Mumbai'?") rather than a raw stack trace — the model has to read and react to this just like a human would.

🔁 Idempotent retries where possible

If a tool call might be retried after a timeout, design it so calling it twice doesn't cause double side-effects (e.g., don't double-charge a payment).

Never let a tool's raw, untrusted output be treated as instructions the agent should blindly obey — that's exactly how prompt injection through tool results happens. See Section 36.

15 Retrieval-Augmented Agents

RAG (covered fully in the RAG guide) and agents are complementary, not competing, ideas. A retrieval step can itself just be ONE tool inside an agent's toolbox — the agent decides WHEN it needs to search, not just always retrieving blindly before every answer.

The RAG guide's own Agentic RAG section covers this exact overlap in detail: letting an LLM decide whether to retrieve, re-formulate the query, retrieve again if the first results were poor, and only answer once it's confident — that IS an agent, just one whose main tool happens to be a retriever.

Rule of thumb: if your system only ever does one fixed retrieve-then-answer pass, call it RAG. If it can decide to search again, try a different query, or skip retrieval entirely when unnecessary, you've built an agent.

Part D — Multi-Agent Systems (Agentic AI)

16 What is Agentic AI / Multi-Agent Systems?

"Agentic AI" describes systems built from MULTIPLE cooperating agents, each often playing a specialized role, working together toward a shared goal — rather than one single generalist agent trying to do everything itself.

A multi-agent system splits a complex goal across several specialized agents (e.g., a Researcher, a Writer, a Reviewer), each with its own instructions, tools, and sometimes its own underlying model — coordinated by a shared process or a dedicated "orchestrator" agent.
It's the difference between one person trying to write an entire newspaper alone (one generalist agent) versus a real newsroom: a reporter researches, a writer drafts, an editor reviews and sends it back for revisions if needed, and a publisher ships the final piece — each specialist focused on what they do best.

Why split work across agents instead of one bigger, smarter single agent? A few real reasons: specialized, shorter, more focused instructions per agent tend to perform more reliably than one giant do-everything prompt; different agents can genuinely run different underlying models (a cheap model for simple sub-tasks, an expensive one only for hard reasoning); and natural checks-and-balances emerge when one agent reviews another's work.

However agents are arranged, they need a way to actually share information. Common patterns:

19 Model Context Protocol (MCP) & Agent2Agent (A2A)

As agents and tools multiplied, the industry needed standard ways to plug them together — instead of every framework inventing its own incompatible format.

The Model Context Protocol (MCP), introduced by Anthropic in November 2024, standardizes how an LLM application connects to external tools and data sources — think of it as a universal adapter: any MCP-compatible tool/data server can plug into any MCP-compatible agent/app, without custom integration code for each pairing. Since December 2025 it has been run as a neutral, open project inside the Linux Foundation's Agentic AI Foundation, and its latest spec (2026-07-28) is "stateless" — see the MCP guide.
Before a standard like MCP, connecting an agent to a new tool was like every phone charger having a different plug shape — you needed a custom adapter for every single combination. MCP is like USB-C: one standard connector that just works across many devices.

Separately, Agent2Agent (A2A) is an open protocol (created at Google in April 2025, then donated to the Linux Foundation) aimed at letting independently-built agents from different vendors discover each other's capabilities and collaborate directly — complementary to MCP, which focuses on agent-to-tool connections rather than agent-to-agent ones. It has reached version 1.0 and, in August 2026, joined the same Agentic AI Foundation as MCP (a2a-protocol.org).

Two more open standards you'll see next to them

  • Agent Skills — folders of instructions, scripts and resources an agent loads only when relevant (a "recipe binder" for agents). Anthropic launched Skills in October 2025, published them as an open standard in December 2025, and donated the standard to the Agentic AI Foundation on 22 October 2026; Anthropic reports 70+ platforms support it. MCP gives agents connections; Skills give them know-how.
  • AGENTS.md — a simple project file, donated by OpenAI, that tells coding agents how a codebase works ("a README for robots"). It was one of the Foundation's three founding projects, along with MCP and Block's goose agent.

20 Debate, Voting & Consensus Patterns

Sometimes the goal isn't delegation but quality improvement — having multiple agents independently attempt or critique the same problem, then combining their outputs.

🗳️ Majority voting

Run the same task through several agents (or the same agent multiple times), and take the most common answer — reduces the impact of any one random mistake.

⚖️ Debate

Two agents argue opposing positions, pointing out flaws in each other's reasoning, often converging on a better-supported final answer than either alone.

🧑‍⚖️ Judge/critic agent

A separate agent (sometimes a stronger model) scores or picks the best output among several candidate agent outputs.

These patterns multiply cost — running the same task 3-5 times is 3-5x the tokens. Reserve them for genuinely high-stakes or hard tasks, not routine ones (see Section 37 on cost management).

Part E — The Math & Theory

21 The Math/Theory Behind Agent Decision-Making

Agents don't need new math on top of LLMs — every individual decision an agent makes is still just an LLM predicting the next token (softmax over a vocabulary, exactly as in LLM §17). What agents add is a THEORETICAL FRAMING for decision-making borrowed from classical AI: the Markov Decision Process (MDP).

A Markov Decision Process formalizes sequential decision-making as: a state (the current situation), a set of possible actions, a transition (what state you end up in after an action), and a reward (how good that outcome was). An agent's "policy" is simply its rule for picking an action given a state — for an LLM agent, the policy IS the LLM itself.
Think of a board game: your state is the board right now, your actions are the legal moves, and the reward is whether that move helps you win. An LLM agent treats "what's the situation + what tools are available" as the state, and uses next-token prediction to pick the best "move" (tool call) — the same underlying idea, just with language instead of game pieces.

Unlike classical reinforcement learning (which explicitly optimizes a reward function through trial-and-error training), most LLM agents today don't retrain on their own experience in real time — they rely on the LLM's existing reasoning ability, shaped only by the prompt and any tool results, to pick good actions in the moment. (RLHF, covered in LLM §15, is where reward-based training DOES happen — but during the model's training, not live during an agent's run.)

Part F — Frameworks & Tooling

22 LangChain & LangGraph

LangChain was one of the earliest and most widely adopted frameworks for building LLM applications — offering reusable building blocks for prompts, tools, memory, and chaining calls together.

LangGraph (from the same team) is purpose-built for agents: it models an agent's logic as an explicit graph of nodes (steps) and edges (transitions, including conditional branches and loops) — making complex, stateful, possibly cyclical agent behavior much easier to reason about and debug than a plain linear chain.

A plain chain is like a recipe you follow top to bottom once. A graph (LangGraph) is like a flowchart with decision diamonds and loop-backs — "if the test fails, go back to step 2" — which is exactly what real agent logic needs.

What's new (as of Oct 2026): version 1.0 for both

On 22 October 2025 the team released LangChain 1.0 and LangGraph 1.0 together, promising no breaking changes until 2.0 (official announcement). Both are still on the 1.x line today. What changed:

MiddlewareLittle "checkpoints" you can plug into each step of the loop — built-ins cover asking a human to approve a tool call, summarizing a long history, and hiding personal data (PII).
Standard content blocksOne consistent shape for model output (text, reasoning traces, citations, tool calls) across different model providers.

Rule of thumb from the team: LangChain to ship a standard agent fast; LangGraph for long-running, high-oversight, mix-of-fixed-and-flexible workflows with durable state (it saves progress at every step, so a run can pause and resume).

23 CrewAI

CrewAI is a framework built specifically around the "newsroom" multi-agent metaphor from Section 16: you define a Crew of Agents, each with a role, a goal, and a backstory (which shapes its behavior via the system prompt), assign them Tasks, and CrewAI handles passing work between them (sequentially or hierarchically with a manager agent).

CrewAI's role/goal/backstory structure is a deliberately human-readable way to design multi-agent teams — it reads almost like a job description, which makes the resulting agent behavior easier to predict than a raw, unstructured prompt.

What's new (as of Oct 2026)

  • Crews vs Flows. A Crew is a team that decides how to cooperate; a Flow is a controlled, event-driven pipeline where you decide the order and call Crews (or single steps) inside it. Real products usually mix both.
  • Active 1.x releases. The project ships frequent releases (the 1.15 series in late October 2026 per its PyPI page). Recent ones added pluggable backends for memory, knowledge and RAG, checkpoints you can fork and edit, and a crewai eval command (see the changelog).
  • Open core + paid enterprise. The open-source framework is free; the company also sells enterprise tooling for security, observability and administration.

24 Microsoft Agent Framework (the successor to AutoGen)

AutoGen (from Microsoft Research) centered on conversable agents — agents that "talk" to each other in structured conversations, including a built-in UserProxyAgent that can represent a human (or execute code on their behalf) inside the conversation. It was particularly strong for code-generation and code-execution workflows where agents iterate by running code and reading the results.

MAF 1.0 became generally available on 3 April 2026 for .NET and Python (report). Part G — Workflow Automation

30 What is AI Workflow Automation?

AI workflow automation tools let you build multi-step automated processes (trigger → step → step → step) using a visual, drag-and-drop interface instead of writing code — and increasingly, let you drop an "AI step" (an LLM call, or even a full agent) into any point of that pipeline.

It's like building with a flowchart made of LEGO blocks: "when a new email arrives" → "ask an AI to summarize it" → "if it's urgent, send a Slack message" → "otherwise add it to a spreadsheet." Each block is pre-built; you just connect them.

This sits right next to agent frameworks (Part F) on the spectrum — workflow automation tools are generally more visual, more accessible to non-programmers, and better suited to well-defined, mostly-fixed pipelines, while code-first agent frameworks give more control for complex, dynamic reasoning.

33 Hybrid Patterns: Agents Inside Workflow Automation Tools

In practice, the cleanest production systems often combine both: a workflow automation tool handles the reliable, predictable "plumbing" (triggers, data routing, retries, approvals, logging), while a genuine agent is invoked as just ONE step inside that workflow for the parts that truly need dynamic reasoning.

Think of it like a factory assembly line (the fixed workflow) where one station is staffed by a skilled problem-solver (the agent) who handles the part of the job that can't be fully scripted — while the conveyor belt around them still runs on fixed, predictable rules.

Part H — Production Engineering

34 Observability & Tracing for Agents

Agents are harder to debug than single LLM calls because one user request can trigger dozens of nested LLM calls, tool calls, and sub-agent handoffs. Good observability captures the FULL trace: every Thought, every tool call with its arguments and result, every sub-agent handoff, in order.

🔍 LangSmith

Tracing/evaluation platform from the LangChain team, with deep native integration for LangChain/LangGraph agents.

🔭 Arize Phoenix

Open-source LLM/agent observability platform, framework-agnostic, with built-in evaluation templates.

📡 OpenTelemetry (GenAI semantic conventions)

An emerging standard for representing LLM/agent spans in the widely used OpenTelemetry format — lets agent traces plug into existing observability stacks (Grafana, Datadog, etc.).

Without full tracing, a failed multi-step agent run is nearly impossible to debug after the fact — you'll be guessing which of a dozen internal steps actually went wrong.

35 Evaluating Agents

Evaluating an agent is harder than evaluating a single LLM response, because what matters is the whole TRAJECTORY (the sequence of steps taken), not just the final answer — two agents can reach the same correct answer, but one did it efficiently and the other wasted 20 wrong tool calls first.

What to measureWhy it matters
Task success rateDid it actually accomplish the goal? (The most important metric, but binary — doesn't show HOW well.)
Trajectory qualityWere the chosen tools/steps sensible and efficient, or wasteful/looping?
Number of steps / costTwo agents that both succeed aren't equal if one costs 10x more tokens to get there.
Robustness to tool failureDoes it recover gracefully if a tool call fails or returns unexpected data?

Classic public benchmarks for agent capability: AgentBench (diverse multi-environment agent tasks), GAIA (general assistant tasks requiring real reasoning + tool use), SWE-bench (real GitHub issues an agent must actually fix), and WebArena (realistic web-browsing tasks).

36 Safety & Guardrails for Agents

Agents are riskier than chatbots precisely because they can take real actions — a bad output isn't just an embarrassing sentence, it can be a wrong email sent, a bad trade executed, or a file deleted.

🔒 Least-privilege tool access

Only grant the specific permissions an agent genuinely needs for its task — never give blanket admin access "just in case."

🧑‍⚖️ Human-in-the-loop approval gates

Require explicit human confirmation before any high-risk or irreversible action (sending money, deleting data, publishing publicly).

🧱 Sandboxing

Run any agent-executed code in an isolated sandbox/container, not directly on production infrastructure.

🪝 Treat tool output as untrusted data

A web page or document an agent reads can contain hidden text trying to hijack it ("ignore previous instructions...") — this is prompt injection via tool results, and it's the #1 agent-specific security risk.

The OWASP LLM Top 10 (LLM §33) applies directly to agents too — but agents add an extra dimension of risk because the "output" isn't just text anymore, it's real actions.

37 Cost & Latency Management for Multi-Step Agents

A single agent task can trigger many LLM calls — cost and latency compound fast.

  • Cap max steps — a hard ceiling prevents a confused agent from looping expensively forever.
  • Model routing per step — use a cheap/fast model for simple sub-steps (tool selection, formatting) and reserve an expensive model only for genuinely hard reasoning steps.
  • Parallelize independent sub-tasks — if two sub-agents don't depend on each other's output, run them concurrently rather than sequentially.
  • Cache repeated tool calls — if the same search/query is likely to repeat, cache results rather than re-calling the tool (and re-paying for the LLM call that follows it).

39 Level 0 — Tiny Agent Loop From Scratch (Pure Python)

No framework, no tools yet — just the bare perceive-plan-act-observe loop (Section 7) with a fake/hardcoded "brain" so you can see the loop mechanics clearly before an LLM enters the picture.

Show me the bare agent loop (code) 
def fake_brain(goal, history):
    """Pretend 'LLM' that decides the next action based on simple rules."""
    if not history:
        return {"thought": "I should check the weather first.", "action": "check_weather"}
    last_obs = history[-1]["observation"]
    if "rain" in last_obs and "reminded" not in str(history):
        return {"thought": "It's going to rain, remind the user.", "action": "remind_umbrella"}
    return {"thought": "Goal is done.", "action": "finish"}

def check_weather():
    return "31C, humid, light rain expected"

def remind_umbrella():
    return "Reminder sent: bring an umbrella!"

def run_agent(goal, max_steps=5):
    history = []
    for step in range(max_steps):
        decision = fake_brain(goal, history)
        print(f"Thought: {decision['thought']}")
        if decision["action"] == "finish":
            print("Done.")
            break
        if decision["action"] == "check_weather":
            obs = check_weather()
        elif decision["action"] == "remind_umbrella":
            obs = remind_umbrella()
        print(f"Action: {decision['action']} -> Observation: {obs}")
        history.append({"action": decision["action"], "observation": obs})

run_agent("Tell me if I need an umbrella today")

This is the loop from Section 7 with the "brain" replaced by plain if/else rules. Every real agent framework replaces fake_brain with an actual LLM call — the loop shape around it stays conceptually identical.

40 Level 1 — Add Tool Use From Scratch

Now let's make tools a real, named registry the "brain" can pick from by name — the core mechanic behind every tool-calling system (Section 8).

Show me manual tool dispatch (code) 
def get_weather(city):
    return f"{city}: 31C, light rain expected"

def send_reminder(message):
    return f"Reminder sent: {message}"

TOOLS = {
    "get_weather": get_weather,
    "send_reminder": send_reminder,
}

def dispatch(tool_name, **kwargs):
    if tool_name not in TOOLS:
        return f"Error: unknown tool '{tool_name}'"
    try:
        return TOOLS[tool_name](**kwargs)
    except Exception as e:
        return f"Error running {tool_name}: {e}"

# The 'brain' decides which tool + arguments to use
result = dispatch("get_weather", city="Mumbai")
print(result)
result2 = dispatch("send_reminder", message="Bring an umbrella today!")
print(result2)
print(dispatch("delete_everything"))   # unknown tool -> handled gracefully

A real agent's "brain" (the LLM) outputs something like {"tool": "get_weather", "args": {"city": "Mumbai"}}, and this exact dispatch-by-name pattern is what turns that structured request into a real function call — with a graceful error path (Section 14) instead of a crash.

41 Level 2 — ReAct Agent via a Real LLM API

Now let's wire this up to an actual model using the Anthropic API's native tool-use feature (the real-world version of LLM §22's function calling), building a genuine ReAct loop (Section 11).

Show me a real ReAct tool-calling loop (code) 
import anthropic

client = anthropic.Anthropic()

def get_weather(city):
    return f"{city}: 31C, light rain expected"

tools = [{
    "name": "get_weather",
    "description": "Get the current weather for a city",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
}]

messages = [{"role": "user", "content": "Should I bring an umbrella in Mumbai today?"}]

while True:
    response = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=4096,            # generous: built-in thinking and the answer share this budget
        tools=tools,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason != "tool_use":
        final_text = next(b.text for b in response.content if b.type == "text")
        print("Final answer:", final_text)
        break

    # The model may request several tools in one turn: answer every tool_use block,
    # and send all the results back together in a single user message.
    results = []
    for block in response.content:
        if block.type == "tool_use":
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": get_weather(**block.input),
            })
    messages.append({"role": "user", "content": results})

This is a genuine agent loop: the model decides to call get_weather, we execute it for real and feed the result back as a tool_result message, and the model continues reasoning (Thought → Action → Observation → next Thought) until it has enough information to give a final text answer.

42 Level 3 — Minimal LangGraph Graph

LangGraph (Section 22) models the same loop as an explicit graph with named nodes and conditional edges:

Show me a minimal LangGraph agent (code) 
from langgraph.graph import StateGraph, END
from typing import TypedDict

class AgentState(TypedDict):
    question: str
    answer: str

def think_node(state: AgentState) -> AgentState:
    # In reality: call an LLM here to reason/decide
    state["answer"] = f"Thinking about: {state['question']}"
    return state

def should_continue(state: AgentState) -> str:
    return "end" if state["answer"] else "think"

graph = StateGraph(AgentState)
graph.add_node("think", think_node)
graph.set_entry_point("think")
graph.add_conditional_edges("think", should_continue, {"end": END, "think": "think"})

app = graph.compile()
result = app.invoke({"question": "What's the capital of France?", "answer": ""})
print(result["answer"])

The StateGraph is exactly the graph from Section 22's analogy: nodes are steps, add_conditional_edges defines the decision-diamond logic (loop back vs. finish), and AgentState is the shared data passed between every node — the "blackboard" from Section 18.

from crewai import Agent, Task, Crew

The context=[research_task] line is the sequential handoff pattern from Section 18 — the writer's task automatically receives the researcher's output as input, exactly like passing a note from one specialist to the next.

45 Agent Framework Decision Guide

Section 29 compared frameworks feature-by-feature; here's a quick decision path for picking one:

  • Want a quick standard agent now, with room to grow? → LangChain 1.0 (create_agent); need tight control over complex, long-running, branching logic? → LangGraph
  • Modeling a team of specialist roles (researcher/writer/reviewer), or mixing teams with controlled pipelines? → CrewAI (Crews + Flows)
  • Used AutoGen or Semantic Kernel before, or live in the .NET/Azure world? → Microsoft Agent Framework (their successor)
  • All-in on one model provider and want the tightest native integration? → OpenAI Agents SDK or Claude Agent SDK
  • Don't want to run the loop and sandbox yourself? → a hosted harness such as Claude Managed Agents (beta)
  • On Google Cloud / Gemini? → Google ADK. On AWS / Bedrock? → Strands Agents. Want strictly validated outputs? → Pydantic AI
  • Core workload is querying/reasoning over your own documents and data? → LlamaIndex Agents
When unsure, start with the framework that matches your team's EXISTING stack and language — the conceptual patterns (Parts B-D) transfer across all of them, so switching later is more about learning a new API than relearning the ideas. Keep your tools behind MCP and your own thin code, and a framework swap (even a forced one, like AutoGen → MAF or the Assistants API shutdown) stays small.

50 FAQ

Q: Is an "agent" just a chatbot with extra steps?

Not quite — the key difference is a chatbot replies once per message, while an agent loops: it can take an action, see the real result, and decide what to do next on its own, potentially many times, before giving a final answer.

Q: Do I need a framework (LangGraph, CrewAI, etc.) to build an agent?

No — Section 39-41 show you can build a working agent loop in plain Python with a direct API call. Frameworks become valuable once you need more complex state management, many integrations, or multi-agent orchestration out of the box.

Q: What's the real difference between Agentic AI and a single agent?

A single agent is one LLM looping through its own decisions. Agentic AI (multi-agent systems) means multiple specialized agents, each with their own role/instructions, collaborating — like one employee vs. an entire team.

Q: Are MCP and A2A the same thing?

No. MCP standardizes how an agent connects to TOOLS and DATA sources. A2A targets how independent AGENTS discover and collaborate with EACH OTHER. They solve different, complementary problems.

Q: Can I just use Zapier/n8n instead of learning agent frameworks?

For well-defined, mostly-fixed pipelines (if this happens, do that), yes — no-code workflow automation is often faster to build and easier to maintain. Code-first agent frameworks are worth the extra effort when the task genuinely needs dynamic, in-the-moment reasoning.

Q: Why do agents fail so often compared to a single good LLM answer?

Errors compound across steps — if each of 5 steps is 90% reliable, the whole chain succeeds only about 59% of the time (0.9^5). This is why good tool design (Section 14), evaluation (Section 35), and safety gates (Section 36) matter so much more for agents than for single-shot LLM calls.

51 Interview Questions (With Answers) — The Complete Set

Organized by category and roughly ordered easy → hard: conceptual warm-up first, then patterns, then multi-agent design, then frameworks/protocols, then production/system design, then coding, then debugging scenarios, then latest trends.

51.1 — Fundamentals & Conceptual

Q: What is an AI agent, in one or two sentences?

An AI agent is an LLM-powered system that can perceive a goal and situation, decide on an action (usually calling a tool), observe the real result, and repeat this loop — taking multiple autonomous steps to accomplish a task, rather than just replying once.

Q: How is an agent different from a plain chatbot?

A chatbot produces one reply per user message and stops. An agent loops: it can take a real action, see what actually happened, and decide the next step itself — potentially many times — before producing a final answer.

Q: How is an agent different from traditional RPA (Robotic Process Automation)?

RPA follows a fixed, pre-programmed sequence of steps that a human designed in advance and can't adapt beyond that script. An agent's LLM decides, in real time, what to do next based on the current situation — it can handle cases nobody explicitly coded for.

Q: What four components make up a typical agent?

An LLM (the brain that decides), tools (the hands that take real actions), memory (what it remembers within and across sessions), and a planner/loop (the logic that keeps the cycle running until the goal is met).

Q: Why do agents sometimes fail even when the underlying LLM is very capable?

Multi-step tasks compound errors — if each step is independently 90% reliable, a 5-step task only succeeds about 59% of the time. Poor tool design, insufficient error handling, and lack of a stopping condition also commonly cause failures independent of the model's raw capability.

Q: What does "Agentic AI" mean, and how is it different from "an AI agent"?

"An AI agent" typically refers to one autonomous LLM-driven loop. "Agentic AI" usually refers to systems built from MULTIPLE cooperating agents, each often with a specialized role, working together toward a shared goal.

51.2 — Architecture & Patterns

Q: Explain the ReAct pattern and why writing out "Thoughts" helps.

ReAct interleaves reasoning ("Thought"), tool calls ("Action"), and real results ("Observation") in a loop. Writing reasoning out as generated text gives the model more "working space" to reason correctly before committing to an action — similar to why chain-of-thought prompting improves accuracy.

Q: Compare ReAct and Plan-and-Execute.

ReAct decides one step at a time, adapting as it goes — good for unpredictable tasks but can wander. Plan-and-Execute writes the full plan upfront then executes it — more efficient for predictable task shapes, but can become stale if early steps reveal new information requiring a replan.

Q: What is the Reflexion pattern and when is it most useful?

After a failed attempt, the agent generates a plain-language self-critique of what went wrong, then retries informed by that critique. It's especially effective for coding agents: write code, run tests, read the failure, reflect on the likely cause, and rewrite informed by that specific failure.

Q: What's the difference between short-term, long-term, and episodic memory in an agent?

Short-term memory is just the current context window/session. Long-term memory persists facts/preferences across sessions, typically via a vector database retrieved when relevant. Episodic memory specifically records past task attempts ("last time X failed because Y") so similar future situations can be informed by them.

Q: Why can't you just always dump an agent's entire history into every prompt?

Context windows are limited and cost scales with tokens used (see the LLM guide's context-window section) — naively keeping everything doesn't scale as a task grows long. Real systems selectively retrieve, summarize, or expire old information instead.

Q: What is Tree of Thoughts and how does it differ from simple chain-of-thought?

Chain-of-thought reasons in one straight line. Tree of Thoughts explores MULTIPLE possible reasoning branches simultaneously, evaluates them, and can backtrack away from dead ends — useful for puzzle-like problems with many possible approaches rather than one obvious path.

51.3 — Multi-Agent Systems

Q: Why split work across multiple agents instead of using one bigger, smarter agent?

Shorter, specialized instructions per agent tend to be more reliable than one giant do-everything prompt; different agents can genuinely use different models matched to task difficulty/cost; and having one agent review another's work creates natural checks-and-balances.

Q: Compare the supervisor/orchestrator and swarm/decentralized multi-agent architectures.

Supervisor/orchestrator has one manager agent delegate to specialists and assemble results — easy to reason about but the supervisor can bottleneck. Swarm/decentralized has agents communicate directly with no fixed controller — more flexible and resilient to one agent failing, but harder to predict and debug overall.

Q: What is the "blackboard" coordination pattern?

All agents read from and write to one shared data structure (the "blackboard"), rather than sending direct messages to specific other agents — simplest to build and debug since you can always inspect the one shared object.

Q: When would you use a debate pattern between agents?

When a problem benefits from having two agents argue opposing positions and point out flaws in each other's reasoning, often converging on a better-supported answer than either alone — worthwhile for high-stakes decisions despite the extra cost of running multiple passes.

Q: How does a hierarchical multi-agent system differ from a simple one-level supervisor pattern?

A hierarchical system has supervisors of supervisors — teams of teams, with delegation happening across multiple layers — scaling to much more complex tasks than a single supervisor managing a flat set of specialist agents, at the cost of additional coordination overhead and latency.

51.4 — Frameworks & Protocols

Q: What problem does LangGraph solve that a simple linear LangChain chain doesn't?

A linear chain can only go step 1 → step 2 → step 3 in one fixed direction. LangGraph models agent logic as an explicit graph with conditional branches and loops (e.g., "if the test fails, go back to step 2"), which is what real, adaptive agent behavior actually requires.

Q: What makes CrewAI's design philosophy distinct from other frameworks?

CrewAI structures agents around role, goal, and backstory — a deliberately human-readable "job description" format for defining a team of specialist agents, which tends to make the resulting multi-agent behavior easier to predict and reason about than a raw unstructured prompt.

Q: What is the Model Context Protocol (MCP) and what problem does it solve?

MCP standardizes how an agent/application connects to external tools and data sources, so any MCP-compatible tool/server can plug into any MCP-compatible agent without writing custom integration code for every single pairing — much like USB-C standardizing device connections.

Q: How does A2A differ from MCP?

MCP connects an agent/app to TOOLS and DATA sources. A2A targets how independently-built AGENTS from different vendors discover each other's capabilities and collaborate directly — a different, complementary layer of the stack.

Q: When would you choose the Microsoft Agent Framework (AutoGen's successor) over CrewAI?

Microsoft Agent Framework (MAF 1.0, GA April 2026, .NET and Python) combines AutoGen's multi-agent patterns with Semantic Kernel's enterprise features as explicit graph workflows with checkpointing, human-in-the-loop, middleware and OpenTelemetry — a good fit for Microsoft/.NET/Azure shops and anyone who used AutoGen or Semantic Kernel. CrewAI is strongest when the workflow maps cleanly onto fixed specialist roles ("crews") with a clear sequential or hierarchical task structure, and when you want to combine those crews with controlled event-driven "flows". Note that AutoGen itself is in maintenance mode, so new projects shouldn't start there.

51.5 — System Design & Production

Q: How would you design an agent system that needs to safely send real emails on a user's behalf?

Use least-privilege tool access (only email-sending permission, nothing broader), require a human-in-the-loop approval gate before any email actually sends, sandbox any code execution involved, and log the full trace of every decision for auditability.

Q: How would you evaluate whether an agent is actually good, not just "usually gets the right final answer"?

Measure the full trajectory, not just success rate: were the chosen tools/steps efficient or wasteful, how many steps/tokens did it cost to succeed, and does it recover gracefully from tool failures — two agents can reach the same correct answer via very different quality paths.

Q: What's the single biggest security risk specific to agents (beyond standard LLM risks)?

Prompt injection via tool results — hidden instructions embedded in content the agent reads (a webpage, a document, an API response) that attempt to hijack its behavior. This is agent-specific because the agent treats tool output as data to reason about, which attackers can exploit if that output isn't treated as untrusted.

Q: How would you control runaway cost in a multi-step agent system?

Cap the maximum number of steps per task, route simpler sub-steps to cheaper/faster models and reserve expensive models for genuinely hard reasoning, parallelize independent sub-tasks instead of running them sequentially, and cache repeated tool calls.

Q: Your agent needs to pause for hours awaiting a human approval. What deployment pattern do you need?

A long-running worker with checkpointing — the agent's state is persisted after each step so the task can pause and resume later, potentially across restarts. A stateless serverless function can't "wait" that long.

51.6 — Coding / Hands-On

Q: Write the skeleton of a basic agent loop with a maximum step limit.

Loop up to max_steps times: call the "brain" (LLM) with the current goal and history, check if it wants to finish or call a tool, execute the tool if so, append the result to history, and break early once the brain signals it's done — exactly the structure in Section 39's from-scratch loop.

Q: How would you implement safe tool dispatch given a tool name and arguments from the model?

Look up the tool name in a registry/dictionary of allowed functions, return a clear error if it's not found (never silently execute arbitrary code), call it inside a try/except so a runtime error becomes a readable error message fed back to the model rather than a crash.

Q: How does a real tool-use loop against an LLM API differ from the hand-rolled fake_brain example?

Instead of if/else rules, you send the model a list of tool schemas and the conversation history; the model itself decides, via its stop_reason, whether to call a tool or give a final answer — you execute whichever tool it requests and append the real result as a new message before calling the model again.

Q: In LangGraph, what's the role of a conditional edge?

It inspects the current state after a node runs and decides which node to transition to next — e.g., loop back to a "think" node if more work is needed, or route to END if the task is complete — implementing the decision-diamond logic of real agent control flow.

Q: How would you test an agent's behavior given that LLM outputs are non-deterministic?

Test the surrounding code (tool dispatch, error handling, state management) with mocked LLM responses for fast, deterministic unit tests, and separately run a small golden evaluation set against the real model/tools in CI, scoring trajectory quality and success rate rather than exact-matching output text.

51.7 — Debugging & Scenario-Based

Q: Your agent gets stuck calling the same tool repeatedly without making progress. What's likely wrong and how do you fix it?

Likely causes: the tool's error message isn't informative enough for the model to understand what went wrong, or the stopping/progress criteria in the prompt are unclear. Fix by improving tool error messages, adding a hard max-step limit as a safety net, and logging the full trace to diagnose the specific repeated failure.

Q: A multi-agent system produces inconsistent results across runs. How do you debug it?

Add full tracing across every agent's inputs/outputs and every handoff, check whether the orchestration logic (who talks to whom, in what order) is itself non-deterministic, and verify each sub-agent's prompt is specific enough that two runs with similar inputs produce similarly-shaped outputs.

Q: Your agent successfully completed a task but it took 40 tool calls when it should have taken 5. What do you investigate?

Check the trajectory trace for unnecessary repeated searches, unclear tool descriptions causing the model to guess/retry, missing information in the system prompt that would let it plan more directly, and whether a Plan-and-Execute approach would suit this task better than open-ended ReAct.

Q: A user manipulates your customer-support agent into revealing internal system prompts or taking unauthorized actions by pasting crafted text. What happened and how do you prevent it?

This is prompt injection — the agent treated untrusted user/tool content as instructions to obey. Prevention: never let retrieved or user-supplied content override system-level instructions, add input/output filtering, and require human approval gates for any sensitive action regardless of what the conversation claims.

Q: Your agent occasionally calls a tool with malformed arguments that crash your backend. How do you harden this?

Add strict schema validation on tool inputs before execution, return a clear validation error back to the model (so it can self-correct) instead of crashing, and never trust that the model's structured output perfectly matches your expected schema just because you asked it to.

51.8 — Advanced, Research & Latest Trends

Q: How do reasoning models (test-time compute) change the design of agents?

Reasoning models already spend extra inference-time compute deliberating before answering, which can reduce (but not eliminate) the need for explicit external patterns like ReAct or Reflexion for certain hard reasoning sub-steps — though tool use and multi-step real-world interaction still require an actual agent loop around the model.

Q: What's the significance of standardized protocols like MCP and A2A for the agent ecosystem's future?

They shift the ecosystem from every framework/vendor building incompatible, bespoke integrations toward a shared, interoperable layer — similar to how standardized ports and APIs enabled the broader software/hardware ecosystem to combine components from different vendors freely.

Q: Why have coding agents become one of the most successful real-world agent categories so far?

Coding tasks have unusually clear, checkable success criteria (tests pass, code compiles, the build succeeds) that let an agent verify its own progress objectively — a narrower, well-defined domain with built-in feedback loops, unlike many open-ended real-world tasks.

Q: What risks come with giving an agent increasingly broad, autonomous authority (e.g., an "autonomous software engineer" that opens its own PRs)?

Larger blast radius if something goes wrong (bad code merged, unauthorized actions taken), harder-to-audit decision chains across many autonomous steps, and a growing need for robust evaluation, sandboxing, and human review checkpoints that scale with the agent's level of autonomy.

Q: How do agentic AI and traditional workflow automation tools (n8n, Zapier) look likely to converge?

Workflow tools are increasingly embedding genuine agent steps (dynamic LLM-driven decisions) inside otherwise-fixed pipelines, while agent frameworks are adding more visual/structured orchestration — the likely trend is less a hard line between the two and more a spectrum of how much dynamic reasoning sits inside an otherwise reliable, observable pipeline.

52 Common Problems & Production Checklist

Agents fail in their own distinctive ways compared to plain LLM calls — mostly because mistakes can compound across many steps, and because tools give the model a way to actually affect the real world.

🔁 Infinite / repetitive loops

An agent calls the same tool over and over without progress. Always set a hard max-step limit as a safety net, and make tool error messages specific enough to guide a correction.

📉 Compounding error rates

Five steps at 90% reliability each only succeed ~59% of the time end-to-end. Keep critical chains short, add verification steps, and consider a reviewer/critic agent for high-stakes tasks.

💉 Prompt injection via tool results

Content an agent reads (web pages, documents, API responses) can contain hidden instructions. Never let retrieved/tool content override system-level instructions; treat all tool output as untrusted data.

🗝️ Over-privileged tools

Giving an agent broad access "just in case" turns a small mistake into a big one. Apply least-privilege: narrow, specific tools, with human approval gates on anything destructive or irreversible.

💸 Runaway cost & latency

Unbounded loops with no step cap can burn enormous token budgets. Cap max steps, route easy sub-steps to cheaper models, parallelize independent work, and cache repeated calls.

🕵️ No observability

Without tracing every step, decision, and tool call, debugging a misbehaving multi-agent system is nearly impossible. Instrument from day one — don't bolt it on after something breaks in production.

🧩 Vague tool descriptions

If a tool's name/description/schema is ambiguous, the model guesses wrong or retries blindly. Write tool docs as carefully as you'd write documentation for a human teammate.

📏 Wrong pattern for the task

Using open-ended ReAct for a predictable, well-understood task wastes steps; using rigid Plan-and-Execute for a genuinely unpredictable task causes brittle failures. Match the pattern to how predictable the task actually is.

Pre-launch checklist:
  • ☐ Hard maximum step/iteration limit enforced in code, not just in the prompt
  • ☐ Every tool follows least-privilege — no tool can do more than its specific job requires
  • ☐ Irreversible or high-stakes actions require explicit human approval before executing
  • ☐ All tool outputs are treated as untrusted data, never as instructions to follow
  • ☐ Full tracing/observability in place (inputs, outputs, tool calls, timing, cost per step)
  • ☐ Evaluation covers trajectory quality and cost, not just final-answer correctness
  • ☐ Sandboxed execution for any agent-written or agent-run code
  • ☐ Clear fallback/escalation path when the agent gets stuck or exceeds its limits
